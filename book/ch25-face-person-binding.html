机器视觉工程实战：用 Rust 看懂图像与模型

第 25 章 · 脸人绑定与跨模型关联

本章导读：第 20 章我们能认出“这张脸是谁“，第 21 章我们能把“同一个人“跨帧连成一条轨迹（track）。可这两件事来自两个不同的模型、两套不同的框——人脸模型只框脸，人体检测器只框整个人。本章要做的，就是把它们关联到同一个人身上：判定“这张脸属于这个人体“，从而给画面里的每个人同时贴上轨迹 + 身份。我们先用空间关系（脸落在人体框上部、包含比例）在单帧里绑定，再用多帧投票把身份稳住，最后把“脸人绑定“提炼成更一般的跨模型关联套路。作为第七部分的收尾：到这里，我们已经能跨模型、跨帧地把信息关联到同一个实体上了，为第八部分的实战系统备好了最后一块拼图。

25.1 为什么要做脸人绑定

先摆清楚两个模型各自能给什么，你就明白为什么它们非绑不可：

模型回答的问题给出的东西强项短板
人体检测 + 跟踪（第 16、21 章）人在哪？有几个？往哪走？人体框 + track_id + 轨迹整个人都在画面里就能稳定跟，可计数不知道“这是谁“
人脸识别（第 20 章）这是谁？人脸框 + 身份（如“张三“）能给出身份脸一小、一侧、一背对就没了

一个管“在哪、是不是同一个“，一个管“是谁“，各说各话。脸人绑定（face-person binding）就是把两者的输出挂到同一个人身上，让我们能说出这样的话：“画面左边这条一直在走的轨迹（track #7），是张三。”

打个生活比喻：开大会时签到台给每人发一张名牌，你得把名牌别到对应的那个人胸前——别错了，张三就成了李四。人脸模型算出的“身份“就是一张张名牌，人体跟踪给出的“一个个人“就是要别名牌的对象；脸人绑定就是把每张名牌别到正确的人身上。

真实场景里，这一步几乎无处不在：

场景人体给什么人脸给什么绑定后能做什么
门禁 / 考勤有人来了、走到哪这是员工张三记一条“张三 08:59 进门“
重点人员布控画面里几个人、各自轨迹某个人是名单里的只对那条轨迹报警、持续追
人流 + 抓拍（第 28 章）每个人一条轨迹、去重计数抓到清晰脸就识别“第 37 个人，疑似 VIP 王总”

那能不能用一个模型直接输出“人 + 他是谁“？ 工程上极少这么做：人脸库天天变（今天入职一个新人），换库不该牵连人体检测器；人脸识别要的是对齐后的标准脸（第 20 章），人体检测要的是整个人，输入差别太大；两个模型各自迭代、各自复用更灵活。所以主流做法始终是“两个模型 + 一层关联“，这层关联就是本章。

25.2 前提：两个框必须在同一套坐标系

绑定的本质是比两个框的位置——脸框和人体框谁套着谁。既然要比位置，那前提就是：两套框必须落在同一套坐标系里。全书早就把这套坐标系钉死了（见第 3.8、16.5 节）：原图像素坐标，左上-右下 (x1, y1, x2, y2)。

这里藏着新手的头号坑。人体检测器和人脸模型是各跑各的：各自做自己的 letterbox（等比缩放加灰边，第 10 章）、各自的输入尺寸、各自的后处理。人体检测器可能吃 640×640，人脸检测器可能吃别的尺寸，甚至人脸走的是“先把人抠出来放大再检测“的小图。只要每个模型都正确地把框还原回了同一张原图的像素坐标（letterbox 逆变换，第 10 章），两套框就活在同一个坐标系里，可以直接比。

反过来，最常见的翻车是：人脸框还停留在人脸模型 640×640 的输入空间里，就直接拿去和原图像素的人体框比——数值风马牛不相及，绑定全错，而且错得“看起来还挺像那么回事“，极难排查。

  ✗ 错：脸框在模型输入空间(640×640)，人体框在原图(1920×1080) —— 不可比
  ✓ 对：两者都做完 letterbox 逆变换，回到原图 1920×1080 像素 —— 可比

一句话记牢：动手绑定前，先确认脸框和人体框都已还原到同一张原图的像素坐标。这一步不对，后面全白搭。

25.3 空间关联：脸落在谁身上

前提对齐了，核心问题来了：怎么判定“这张脸属于这个人体“？

依据来自一个再朴素不过的事实——人的脸长在身体的上部。所以正确的脸-人配对，脸框几乎总是落在人体框内、且靠上。我们就用这个几何关系来判定。

为什么不能直接用 IoU

第 16、21 章里我们用 IoU（交并比） 衡量两个框重不重叠。这里能直接用吗？不能，用一组数字就看穿了。设：

  • 人体框 body = (100, 50, 200, 400)：宽 100、高 350、面积 100 × 350 = 35000
  • 人脸框 face = (130, 60, 170, 120)：宽 40、高 60、面积 40 × 60 = 2400
   body(100,50)                     (200,50)
     ┌───────────────────────────────┐
     │        face(130,60)  (170,60)  │  ← 脸落在人体框「上部」
     │          ┌──────────┐          │
     │          │   脸     │          │
     │          └──────────┘          │
     │        (130,120)   (170,120)   │
     │              躯干 / 腿          │
     └───────────────────────────────┘
   (100,400)                        (200,400)

这张脸完全在人体框内。先算它俩的交集矩形（和 IoU 里算交集是同一套）：

  • 交集左上：(max(100,130), max(50,60)) = (130, 60)
  • 交集右下：(min(200,170), min(400,120)) = (170, 120)
  • 交集面积：(170−130) × (120−60) = 40 × 60 = 2400

再算 IoU：交集 / 并集 = 2400 / (35000 + 2400 − 2400) = 2400 / 35000 ≈ 0.069。

脸明明 100% 在人体里，IoU 却只有 0.07！ 因为人体框比脸框大太多，并集被人体撑得很大，IoU 天生就低。用 IoU 当判据，阈值根本没法设。

正确判据：包含比例（containment）

我们真正想问的不是“两个框重叠占比多少“，而是“脸框有多少落进了人体框“。这就是包含比例：

$$ \text{containment} = \frac{\text{脸框与人体框的交集面积}}{\text{脸框面积}} $$

分母换成脸框自己的面积，而不是并集。还是上面那组数：containment = 2400 / 2400 = 1.0——脸 100% 在人体框内，一目了然。范围永远是 0 ~ 1，1.0 是完全包住，0 是完全在外，阈值特别好设（比如 ≥ 0.6 才认）。

use crate::BBox; // 全书统一边界框：{ x1, y1, x2, y2 }，坐标为原图像素

/// 包含比例：人脸框「落进」人体框的比例 = 交集面积 / 人脸框面积，范围 0~1
/// 1.0 = 脸完全在人体框内；0 = 完全在外
pub fn containment(face: &BBox, body: &BBox) -> f32 {
    // 交集矩形，和第 16 章 iou() 里算交集是同一套逻辑
    let ix1 = face.x1.max(body.x1);
    let iy1 = face.y1.max(body.y1);
    let ix2 = face.x2.min(body.x2);
    let iy2 = face.y2.min(body.y2);
    let iw = (ix2 - ix1).max(0.0); // 不相交时会算出负数，夹到 0
    let ih = (iy2 - iy1).max(0.0);
    let inter = iw * ih;
    inter / face.area().max(1e-6) // 复用 BBox::area()，加 1e-6 防除 0
}

再加一道位置先验：脸得靠上

光有包含比还不够。想象一个人站在另一个人正前方，后面那个高个子的脸，可能正好落进前面人的人体框里——包含比很高，却绑错了人。真正属于某人的脸，应该在他人体框的上部，而不是腰部、腿部。

于是补一个竖直位置比例：脸的中心点在人体框里“从上往下“的相对位置，0 是头顶、1 是脚底。正常人脸这个值应该很小（脑袋在最上面，通常 < 0.35）。

/// 脸中心落在人体框「从上往下」的相对位置：0=顶部，1=底部
/// 正常脸应该在上部，这个值很小；偏大多半是绑错了
pub fn vertical_ratio(face: &BBox, body: &BBox) -> f32 {
    let (_, fcy) = face.center();          // 复用 BBox::center()，取脸的中心 y
    let h = body.height().max(1e-6);       // 复用 BBox::height()
    ((fcy - body.y1) / h).clamp(0.0, 1.0)  // 相对人体框顶边的位置，夹到 0~1
}

判定一对“脸-人“是否成立，就用这两条：包含比够高（≥ 0.6）且脸够靠上（vertical_ratio ≤ 0.4）。前者保证“脸在这个人身上“，后者保证“是他的脸而不是穿帮进来的别人的脸“。

25.4 一对多消歧：拥挤场景怎么择优

人稀疏时，一张脸只落进一个人体框，绑定毫无悬念。可人一挤，麻烦就来了：人体框互相重叠，一张脸可能同时落进两个人体框，到底算谁的？

举个具体例子。两个挨着站的人：

  • 人体 A = (100, 50, 200, 400)
  • 人体 B = (160, 55, 260, 405)（和 A 右半部分重叠）
  • 一张脸 face = (150, 60, 190, 120)，中心在 (170, 90)

脸中心 x = 170，落在 A 的横向范围 [100, 200] 里，也落在 B 的范围 [160, 260] 里——只看“中心在不在框内“根本分不开。那就比包含比：

脸对 A 的包含比：交集 (max(100,150), max(50,60))=(150,60) 到 (min(200,190), min(400,120))=(190,120)，面积 40 × 60 = 2400，脸面积也是 2400，所以 containment_A = 2400 / 2400 = 1.0。

脸对 B 的包含比：交集 (max(160,150), max(55,60))=(160,60) 到 (min(260,190), min(405,120))=(190,120)，面积 30 × 60 = 1800，containment_B = 1800 / 2400 = 0.75。

脸的左边一小条（x 从 150 到 160）伸出了 B 的左边界，所以只有 75% 落进 B，却 100% 落进 A。结论：这张脸属于 A（1.0 > 0.75）。这正是包含比的价值——它给出了一个可比较的分数，让“择优“有据可依。

工程做法是把它变成一个一对一贪心匹配（思路和第 21 章跟踪里的关联一模一样）：算出所有“脸-人“组合的分数，过滤掉不达标的，然后从高分往低分挑，每张脸、每个 track 都只能用一次。

use crate::Track; // 第 21 章统一跟踪目标：{ id, bbox, class_id, score }

/// 单帧脸人匹配：把每张人脸绑到最合适的人体 track（一对一贪心）
/// 返回若干 (人脸下标, track 下标) 的绑定对
pub fn bind_faces_to_tracks(
    faces: &[BBox],
    tracks: &[Track],
    min_contain: f32,  // 包含比阈值，低于它不认为是同一人（如 0.6）
    max_vertical: f32, // 脸最多能落到人体框多靠下（如 0.4，再靠下多半绑错）
) -> Vec<(usize, usize)> {
    // 1) 枚举所有 (脸, 人体) 组合，用包含比当分数，并用位置先验过滤
    let mut cands: Vec<(f32, usize, usize)> = Vec::new();
    for (fi, face) in faces.iter().enumerate() {
        for (ti, tk) in tracks.iter().enumerate() {
            let c = containment(face, &tk.bbox);
            let v = vertical_ratio(face, &tk.bbox);
            if c >= min_contain && v <= max_vertical {
                cands.push((c, fi, ti)); // 分数越高，绑定越可信
            }
        }
    }
    // 2) 按分数从高到低排序，呼应第 21 章的贪心关联
    cands.sort_by(|a, b| b.0.partial_cmp(&a.0).unwrap());

    // 3) 贪心分配：每张脸、每个 track 只能被用一次
    let mut used_face = vec![false; faces.len()];
    let mut used_track = vec![false; tracks.len()];
    let mut pairs = Vec::new();
    for (_score, fi, ti) in cands {
        if !used_face[fi] && !used_track[ti] {
            used_face[fi] = true;
            used_track[ti] = true;
            pairs.push((fi, ti));
        }
    }
    pairs
}

一对一约束很重要：它天然防住了“一张脸绑到两个人““两张脸绑到同一个人“这类矛盾。剩下没配上的脸（可能是路人、误检），或没配上脸的 track（背对镜头、脸太小），本帧就先不绑，交给下一帧和时序机制处理。

25.5 时序稳定：结合 Track 做多帧身份投票

单帧绑定 + 单帧识别，有个绕不开的毛病：抖。人脸识别本就随光照、角度波动，这一帧认成“张三“（相似度 0.62），下一帧可能因为一个侧头就认成“李四“（0.51），再下一帧又变回“张三“。如果每帧都直接信，屏幕上的名字就会疯狂跳变，没法用。

救星正是第 21 章的 track_id。人体轨迹是连续稳定的：同一个人在画面里走，track_id 从头到尾不变。我们不必每帧都相信识别结果，而是为每个 track_id 开一个投票箱，把它这些帧里被识别成的身份都投进去，票数够多、够集中时才确认。某个 track 连着好多帧都被认成“张三“，我们才敢说它是张三；偶尔一帧的“李四“淹没在多数票里，翻不了盘。

use std::collections::HashMap;

/// 单个 track 的身份投票箱
#[derive(Default, Clone)]
pub struct IdentityVote {
    counts: HashMap<String, u32>, // 身份 -> 累计票数
    total: u32,                   // 累计投过票的帧数
}

impl IdentityVote {
    /// 这一帧这个 track 识别出了身份 name，投一票
    /// （工程上也常按识别相似度加权：越像投得越重）
    fn cast(&mut self, name: &str) {
        *self.counts.entry(name.to_string()).or_default() += 1;
        self.total += 1;
    }

    /// 当前确认身份：票数最多、且票数≥min_votes、占比>ratio 才算数
    fn confirmed(&self, min_votes: u32, ratio: f32) -> Option<(String, f32)> {
        let (name, votes) = self.counts.iter().max_by_key(|(_, c)| **c)?;
        let share = *votes as f32 / self.total.max(1) as f32;
        if *votes >= min_votes && share > ratio {
            Some((name.clone(), share)) // 票够多、占比够高，才敢确认
        } else {
            None // 还在观望，先不给身份
        }
    }
}

/// 全场登记表：track_id -> 投票箱
#[derive(Default)]
pub struct IdentityRegistry {
    table: HashMap<u64, IdentityVote>,
}

impl IdentityRegistry {
    /// 处理一帧：把本帧绑定好的每个 (track_id, 识别身份) 各投一票
    pub fn update(&mut self, votes_this_frame: &[(u64, String)]) {
        for (track_id, name) in votes_this_frame {
            self.table.entry(*track_id).or_default().cast(name);
        }
    }

    /// 查某个 track 目前确认的身份：至少 5 票且占比 >60% 才给
    pub fn identity_of(&self, track_id: u64) -> Option<(String, f32)> {
        self.table.get(&track_id)?.confirmed(5, 0.6)
    }

    /// track 消失后清理，避免表无限增长（配合第 21 章的 track 生命周期）
    pub fn remove(&mut self, track_id: u64) {
        self.table.remove(&track_id);
    }
}

这套机制的好处，用一个例子体会：某 track 走过 10 帧，其中 8 帧识别成“张三“、2 帧误识成“李四“。到第 5 帧攒够 5 票且张三占比超 60% 时，身份确认为张三；那 2 帧“李四“始终是少数，撼不动结论。多帧投票把“偶尔认错“变成了“整体认对“，这就是时序一致性的力量。

工程上通常会再加两条：① 人脸模型不必每帧都跑（识别很贵），可以每隔几帧、或只对“还没确认身份“的 track 跑，省算力；② track 消失后调用 remove 清掉投票箱，否则跑一整天，表会越堆越大。

25.6 完整数据结构：以人体 Track 为主体

绑定和投票都有了，该把它们组织成一个清爽的数据结构。核心设计思想一句话：以人体 Track 为主体，把人脸带来的身份当作“挂在它身上的一个属性“。

为什么主体是人体而不是人脸？因为人体在画面里连续、稳定、可跟踪——人转个身、低个头，脸没了，但人还在、轨迹还在。身份只是这条轨迹上一个“识别到了就填、没识别到就空着“的可选字段。

/// 画面里的一个人：以人体 Track 为主体，挂上人脸带来的身份
#[derive(Clone, Debug)]
pub struct Person {
    pub track: Track,             // 人体跟踪目标（第 21 章）：id / bbox / class_id / score
    pub identity: Option<String>, // 已「确认」的身份；没脸或没确认时为 None
    pub face_bbox: Option<BBox>,  // 本帧绑定到的人脸框；背对镜头时为 None
    pub id_confidence: f32,       // 身份可信度 = 多帧投票占比 0~1
}

Option<String> 这个类型选得很讲究：它诚实地表达了“这个人一定在（track 在），但他是谁未必知道“。把前面几节拼起来，一帧的完整处理就是：

/// 把「人体 tracks」和「已识别人脸」组装成带身份的 Person 列表
pub fn assemble_people(
    tracks: &[Track],        // 本帧人体跟踪结果（第 21 章）
    faces: &[BBox],          // 本帧人脸框（已还原到原图像素）
    face_names: &[String],   // 与 faces 一一对应的识别身份（第 20 章检索所得）
    reg: &mut IdentityRegistry,
) -> Vec<Person> {
    // ① 单帧空间关联：脸 ↔ 人体（25.3 / 25.4）
    let pairs = bind_faces_to_tracks(faces, tracks, 0.6, 0.4);

    // ② 把本帧的 (track_id, 身份) 交给投票表累计（25.5）
    let votes: Vec<(u64, String)> = pairs
        .iter()
        .map(|&(fi, ti)| (tracks[ti].id, face_names[fi].clone()))
        .collect();
    reg.update(&votes);

    // ③ 组装：每个 track 都产出一个 Person，身份取「多帧确认」的结果
    let face_of: HashMap<usize, usize> =
        pairs.iter().map(|&(fi, ti)| (ti, fi)).collect(); // track下标 -> 脸下标
    tracks
        .iter()
        .enumerate()
        .map(|(ti, tk)| {
            let (identity, conf) = match reg.identity_of(tk.id) {
                Some((name, share)) => (Some(name), share),
                None => (None, 0.0),
            };
            Person {
                track: tk.clone(),
                identity,
                face_bbox: face_of.get(&ti).map(|&fi| faces[fi]),
                id_confidence: conf,
            }
        })
        .collect()
}

注意 ③：遍历的是 tracks，每个 track 都变成一个 Person——哪怕这一帧没绑到脸、身份还是 None。这正是“人体为主体“的体现：人始终在列表里，身份只是慢慢往上填。画到屏幕上就是：每个人头上永远有框和 track_id，认出来了再多一行名字。

25.7 推广：跨模型关联的通用套路

脸人绑定不是个孤例，它是一大类问题的代表。把上面的思路抽象一层，你会发现只要是“用一个模型的输出去补充另一个模型的输出“，都是同一套路：

主体（连续可跟踪）挂载模型靠什么空间关系挂挂上去的属性
人体 track人脸识别（第 20 章）脸在人体框上部身份（谁）
人体 track姿态 / 关键点（第 17 章）关键点落在人体框内骨架、动作
人体 track属性分类同一个框性别、年龄、衣着颜色
车辆 track车牌识别车牌框在车辆框下部车牌号
车辆 track车型分类同一个框品牌、颜色

提炼成三步通用关联套路，记住它，遇到任何“多模型协同“都能照搬：

  1. 选主体：挑那个在画面里最连续、最容易跟踪的实体当“骨架“（通常是更大、更持久的目标：人体、车辆），给它一条 track。别的模型的输出都往这条 track 上挂。
  2. 用空间关系挂：靠包含比 / 相对位置 / IoU 判定“谁属于谁“。关键是选对判据——像脸人这种“小框落进大框“，包含比比 IoU 靠谱；再配一条位置先验（脸在上、车牌在下）消歧。
  3. 用时序一致性稳：单帧关联必抖，靠多帧投票 / 置信度累计把结论稳住，绝不让某一帧的抖动直接翻盘。

一句话总结：跨模型关联 = 空间关系（谁属于谁）+ 时序一致性（别被一帧带偏），把多个模型的输出挂到同一个实体上。 脸人绑定只是这套通用思想最典型的一个实例。

25.8 工程坑位清单

把真实项目里最容易栽的坑集中列一遍：

  • 坐标系不统一（头号坑）：脸框和人体框必须都还原到同一张原图的像素坐标再比（25.2）。忘了对哪一边做 letterbox 逆变换，绑定全错，还错得难查。
  • 拿 IoU 当判据：脸框比人体框小得多，IoU 天生就低（我们算过，脸 100% 在人体里 IoU 也才 0.07）。用包含比，别用 IoU。
  • 只看“中心在不在框内“：拥挤时一张脸中心会同时落进多个框，分不开。必须用包含比择优 + 位置先验（25.4）。
  • 脸太小 / 侧脸 / 背对镜头：这些情况根本识别不了，也不该硬绑。正确姿态是——人照跟（track 在），身份先空着（None），等有清晰正脸的那几帧再补上。别为了凑一个身份去绑一张模糊的脸。
  • 拥挤误绑：人贴人时偶有绑错。靠“包含比阈值 + 位置先验 + 多帧投票“三重把关，单帧偶发的错绑会被多数票冲掉。
  • 身份翻转要不要允许：确认成“张三“后，突然几帧被识成“李四“，改不改？两种策略——锁定（一旦确认就钉死，稳但可能纠正不了真的错判）、可翻转（新身份持续、大比例压过旧身份才改，灵活但可能被攻击/误导带偏）。安防偏锁定，一般场景可用“迟滞翻转“折中。没有标准答案，按场景定，但一定要显式决定，别让它默默乱跳。
  • 投票表内存泄漏：track 消失后记得 remove（25.5），否则长时间运行表会无限膨胀。

25.9 小结

  • 脸人绑定把两个不同模型的输出关联到同一个人：人体检测 + 跟踪给“在哪、是不是同一个“（第 21 章），人脸识别给“是谁“（第 20 章），绑定后每个人同时有轨迹 + 身份。
  • 绑定的铁前提：脸框和人体框必须在同一套坐标系——都还原到原图像素坐标，否则一切白搭。
  • 空间关联的核心判据是包含比例（交集 / 人脸框面积），而不是 IoU（脸框太小，IoU 天生偏低）；再配竖直位置先验（脸在人体框上部）消歧。
  • 拥挤场景一张脸可能落进多个框，用包含比择优 + 一对一贪心匹配（思路同第 21 章关联）选出最合适的那个人。
  • 单帧绑定会抖，用 track_id → 身份投票表 做多帧投票：票数够多、够集中才确认身份，把“偶尔认错“稳成“整体认对“。
  • 数据结构以人体 Track 为主体、身份为可选属性（Option<String>）；这套“空间关系 + 时序一致性 + 挂到同一实体“的思路可推广到检测+关键点、人体+属性、车辆+车牌等一切跨模型关联。第 28 章会把它落进“人流统计 + 人脸抓拍“的实战系统。

25.10 练习

  1. 手算包含比 vs IoU：给定人体框 body = (0, 0, 80, 300)、人脸框 face = (20, 10, 60, 70)，先手算它们的包含比和 IoU（提示：脸面积 2400、完全在人体内，包含比该是多少？IoU 又是多少？），体会为什么脸人绑定要用包含比。再把脸挪到 (70, 10, 110, 70)（部分伸出人体右边），重算包含比，用阈值 0.6 判断这次还该不该绑。

  2. 拥挤消歧：用本章 containment 和 vertical_ratio，对 25.4 那两个人体框 A、B 和那张脸各算一遍分数，确认代码结果和手算的 1.0 / 0.75 一致。再想一想：如果只用“脸中心在不在框内“来判，会得到什么错误结论？

  3. 投票稳定性：实现 IdentityVote，模拟某 track 连续 10 帧的识别序列 [张三, 张三, 李四, 张三, 张三, 张三, 李四, 张三, 张三, 张三]，每帧调用 cast 后打印 confirmed(5, 0.6)。观察：到第几帧才确认为“张三“？中间那两帧“李四“能不能把结论翻掉？把 min_votes 调到 2 再跑一次，看看结论会不会因为过早确认而更容易被误导。
