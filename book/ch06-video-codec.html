机器视觉工程实战：用 Rust 看懂图像与模型

第 6 章 · 视频编解码与流：帧、码流与 RTSP

本章导读：第 5 章我们把镜头对准“一张图片怎么压缩“。这一章把镜头沿时间轴拉长——一连串图片就是视频。你会先搞懂帧、帧率、时间戳这套“时间坐标系“，再理解视频压缩的核心秘密：I/P/B 帧与 GOP（为什么随便拖动进度条，播放器会先“卡“一下跳到关键帧）。接着分清 codec（编码）和 container（容器）这对最容易混淆的概念，认识视频的常见来源（本地文件、USB 摄像头、RTSP/RTMP、GB28181），最后用 opencv 写一个能真正跑起来的拉流取帧循环，把每一帧变成第 3 章的图像/张量，交给后续章节做预处理和推理。本章也会点名几个上线必踩的坑：花屏、时间戳跳变、断流重连、延迟越跑越大。读完你就能把“一路摄像头“稳稳地接进你的视觉程序。

6.1 视频是什么：帧、帧率与时间戳

小时候玩过手翻书（在本子每一页画一个小人，快速翻动小人就动起来）吗？视频就是这么回事：

  • 帧（frame）：视频里的一张静态图片，就是我们前几章反复处理的那种 RGB 图像。
  • 帧率（fps，frames per second）：一秒钟放多少张。电影 24 fps，监控常见 25/30 fps，游戏可能 60 fps。
  • 时间戳（timestamp）：每一帧“该在第几毫秒出现“。

“1 秒 30 帧“到底意味着什么？ 意味着每 1000 ms ÷ 30 ≈ 33.3 ms 就要显示一张新图片。你的处理程序如果每帧要花 50 ms，那就跟不上 30 fps 的流——这是后面所有实时性问题的根源。

为什么必须压缩？ 我们用小学算术算笔账。一张 1080p（1920×1080）的 RGB 图，每像素 3 字节：

单帧原始大小 = 1920 × 1080 × 3 ≈ 6,220,800 字节 ≈ 6 MB
1 分钟 30fps = 30 × 60 = 1800 帧
1 分钟原始视频 ≈ 1800 × 6 MB ≈ 10.6 GB

一分钟就 10 GB，一路摄像头存一天要 15 TB——完全没法用。而同样这一分钟，H.264 压出来可能只有 50~100 MB，压缩比高达 100~200 倍。视频编码就是干这个的。

pts 与 dts。 每帧带两个时间戳，新手常搞混：

  • pts（Presentation Time Stamp，显示时间戳）：这帧该在什么时候显示给人看。
  • dts（Decode Time Stamp，解码时间戳）：这帧该在什么时候被送进解码器。

只有 I/P 帧的简单流里，两者顺序一致；一旦有了 B 帧（下一节讲），“解码顺序“就和“显示顺序“不一样了，pts 和 dts 于是分道扬镳。时间戳通常不是以秒为单位，而是以一个**时基（time base）**为单位（比如网络流常用 1/90000 秒），换算成秒要除以时基——先记住有这回事，用到时再细说。

6.2 为什么不能每帧都存 JPEG：帧间冗余

一个自然的念头是：既然第 5 章会把单图压成 JPEG，那视频不就是“一堆 JPEG 摞起来“吗？技术上可行（这叫 MJPEG），但极其浪费。

想象一个盯着停车场的监控摄像头：画面里 98% 是一动不动的地面、围墙、车位线，只有一辆车在缓慢移动。如果每帧都独立存成 JPEG，你就把同一堵墙重复存了成千上万遍。

这里有两种“冗余“：

  • 帧内冗余（intra-frame redundancy）：一张图片内部相邻像素相似。JPEG 干掉的就是它（第 5 章）。
  • 帧间冗余（inter-frame redundancy）：相邻两帧之间高度相似。这是视频独有的、也是最大的一块可压缩空间，JPEG 完全没利用。

用小数字感受一下：如果相邻两帧只有 2% 的像素真正变了，那么“只记录变化的那 2%“，理论上能比“整帧重存“小几十倍。视频编码的核心思路就是：别重复存不变的部分，只存“帧与帧之间的差”。怎么存这个“差“？答案就是下一节的 P 帧和 B 帧。

6.3 I 帧 / P 帧 / B 帧 与 GOP

视频编码器把帧分成三种角色：

帧类型全称通俗理解能否单独解码典型大小
I 帧Intra-coded（帧内编码帧，即关键帧）一张完整的画面，本质像一张 JPEG✅ 能，自给自足最大（几十~几百 KB）
P 帧Predicted（前向预测帧）只存“和前面参考帧的差“❌ 不能，得先有参考帧中（几 KB）
B 帧Bi-directional（双向预测帧）同时参考前后帧的差❌ 不能最小

GOP（Group of Pictures，画面组）：从一个 I 帧开始，到下一个 I 帧之前的所有帧，组成一个 GOP。相邻两个 I 帧的间隔就是关键帧间隔（GOP 长度）。摄像头常见设成 1~2 秒一个 I 帧，也就是 30fps 下 GOP ≈ 30~60 帧。

一个 GOP 的显示顺序大致长这样：

显示顺序(PTS):  I  B  B  P  B  B  P  B  B  P  |  I  B  B  P ...
                └──────────── 一个 GOP ─────────┘  └─ 下一个 GOP
                ↑关键帧                              ↑下一个关键帧

  I 帧：完整画面，可独立解码（GOP 的"锚点"）
  P 帧：只记录相对前面参考帧的变化
  B 帧：同时参考前、后帧，压得最狠

为什么随机跳转视频会先跳到最近的关键帧？ 这是本节最该记住的一句话。P 帧、B 帧都是“差值“，离开参考帧根本没法还原。所以当你把进度条拖到某个位置时，解码器不能凭空从那一帧开始，它必须：

1. 往前找到最近的一个 I 帧（关键帧）
2. 从这个 I 帧开始，一帧帧解码 P/B 帧，一路"追"到你想要的那一帧

这就是拖动进度条时那一瞬间“卡顿感“的来源，也是为什么 GOP 越长（关键帧越稀疏）跳转越慢、但压缩率越高——这是个工程取舍。

B 帧如何让 pts ≠ dts？ B 帧要参考它后面的帧，所以那个“后面的帧“必须先解码出来。于是解码顺序被迫重排：

显示顺序(PTS):  I₀  B₁  B₂  P₃  B₄  B₅  P₆
解码顺序(DTS):  I₀  P₃  B₁  B₂  P₆  B₄  B₅
                    ↑ P₃ 必须抢在 B₁/B₂ 前解码，因为 B₁/B₂ 要参考它

看懂这张图，你就彻底理解 6.1 里 pts/dts 为什么要分开了。（好消息：用 opencv/FFmpeg 拉流时，这些重排解码器都替你处理好了，read() 拿到的帧已经是按显示顺序排好的。）

6.4 编码标准 vs 容器：codec 与 container

这是新手最容易混的一对概念。打个比方：

  • 编码（codec）= 用哪种“压缩语言“把画面写小。
  • 容器（container）= 一个“盒子/包装“，把压好的视频流、音频流、字幕、元数据装在一起。
层面常见例子作用
编码 codecH.264/AVC、H.265/HEVC、AV1、VP9决定画面怎么被压小（算法）
容器 containermp4、mkv、flv、avi、ts决定视频+音频+字幕+元数据怎么打包成一个文件/流

关键点：文件后缀（容器）不能告诉你里面是什么编码。一个 .mp4 里可能装的是 H.264，也可能是 H.265；一个 .mkv 里可能是 AV1。所以拿到一个视频，先用 ffprobe in.mp4 看清楚里面到底是哪种 codec，再决定能不能硬解（见 6.6）。

码流（bitstream）与 NAL 单元（点到为止）。 编码器吐出来的那一长串压缩字节就叫码流。H.264/H.265 会把码流切成一个个 NAL 单元（Network Abstraction Layer unit，网络抽象层单元），每个 NAL 单元是一个自包含的小包：有的装参数（分辨率、编码配置，叫 SPS/PPS），有的装一个 I/P/B 帧的一片数据。为什么要切成小包？因为这样才方便在网络上一包一包地传——这正是下一节 RTSP 网络摄像头的工作方式。你暂时不用会手写 NAL 解析，知道“网络传的是一个个 NAL 单元“即可。

6.5 视频从哪来：文件、USB、RTSP/RTMP、GB28181

工程里视频源无非这么几类：

来源典型形式说明
本地文件test.mp4、clip.mkv离线分析、算法调试最常用，稳定可复现
USB 摄像头Linux /dev/video0；OpenCV 里用索引 0UVC 协议免驱，笔记本自带摄像头也算
RTSP 网络摄像头rtsp://user:pass@192.168.1.64:554/Streaming/Channels/101海康/大华等 IP Cam 的主流方式，程序主动去“拉流“
RTMPrtmp://server/live/stream直播场景常见，通常是把流“推“到流媒体服务器
GB28181SIP 信令 + 媒体流国内安防国标：设备先注册到平台，平台再下发指令取流

几点工程经验：

  • **RTSP（Real Time Streaming Protocol，实时流协议）**是安防项目里 90% 会遇到的形式。URL 里的路径（/Streaming/Channels/101 之类）各家厂商不同，一般去摄像头后台或厂商文档查；101 常表示“通道 1 主码流“，102 是子码流（分辨率低、更省带宽，抽帧分析常用子码流）。
  • RTMP 更多是“推流“方向（往服务器送），拉流分析较少直接对接它。
  • GB28181 是国内公安/安防的联网国标，基于 SIP 做信令（设备注册、点播、云台控制），真正的画面数据往往还是一路媒体流。工程上通常由专门的信令网关处理注册和点播，你的视觉程序最终拿到的，多半还是一路可以用 FFmpeg/OpenCV 打开的流地址。所以本章重点讲通用的“拉流取帧“，它对上面所有来源都适用。

6.6 抽帧策略与硬件解码

拿到一路流，不代表每一帧都要处理。抽帧（取哪些帧来分析）是实时系统的第一个设计决策。

策略一：解码全部帧。 跟踪（第 21 章）、拌线计数（第 23 章）、动作识别这类任务需要连续帧，必须逐帧解码，一帧不落。

策略二：只取关键帧（I 帧）做稀疏分析。 如果只是“每隔一会儿看看画面里有没有人/车“，完全不必解码 P/B 帧——只挑 I 帧（或每秒抽 1 帧）送去检测/分类，计算量骤降。因为 I 帧本来就能独立解码，抽起来最省事。

策略三：实时流按需丢帧保时效。 这是本节的重点。如果你的模型每帧要 80 ms（≈12 fps），而流是 30 fps，那流每秒送 30 帧、你只吃得下 12 帧。多出来的帧不能排队等，否则你处理的永远是“几秒前“的旧画面，延迟越拖越长（详见 6.10）。正确做法：只保留最新帧，旧帧直接丢。宁可漏看几帧，也要保证“现在看到的就是现在“。

硬件解码（hardware decoding）：边缘设备的生命线。 软件解码（CPU 硬算）1080p H.264 30fps，往往要吃掉整整一个 CPU 核心——一路就吃满一核，四路摄像头 CPU 就爆了，哪还有算力留给模型推理？硬件解码用的是芯片里专门的解码电路：

硬解方案平台场景
NVDECNVIDIA 显卡 / Jetson服务器、边缘 GPU 盒子
VAAPIIntel 核显 / AMD（Linux）x86 边缘盒子、工控机
RKMPP瑞芯微 Rockchip（RK3588 等）ARM 边缘设备，国产方案常见
VideoToolboxApple（macOS/iOS）Mac 上开发/推理

为什么边缘设备一定要用硬解？ 两个原因：一是省 CPU——把解码卸载给专用电路，CPU/GPU 腾出来跑模型；二是少一次内存搬运——硬解出来的帧可以直接留在 GPU 显存里，喂给 GPU 上的模型推理，省掉“显存→内存→显存“的来回拷贝（这类零拷贝优化留到第 29 章展开）。边缘芯片（如 RK3588、Jetson）的 CPU 往往很弱，不用硬解基本没法多路并发。

6.7 Rust 实操：用 opencv 拉流取帧

原理讲完，上代码。最省心的方案是 opencv crate 的 VideoCapture——它底层走 FFmpeg，本地文件、USB 摄像头、RTSP 一套 API 全搞定。

依赖较重、可选：opencv crate 需要系统先装好 OpenCV 本体和 clang。

  • macOS：brew install opencv
  • Ubuntu：sudo apt install libopencv-dev clang libclang-dev

然后 cargo add opencv（版本以拉到的最新为准）。如果只是离线批量抽帧，不想背这么重的依赖，可以直接用 6.8 的 ffmpeg 命令行。

先定义一个帧处理器接口，把“取帧“和“处理帧“解耦——后续章节（预处理、检测、跟踪）只要实现这个 trait 就能接进来：

#![allow(unused)]
fn main() {
use opencv::{core, prelude::*, videoio};

/// 帧处理器：每来一帧调用一次 on_frame。
/// 后续章节可以让它做 letterbox→推理→NMS（见第 10、16 章）。
pub trait FrameSink {
    fn on_frame(&mut self, idx: u64, frame: &core::Mat) -> opencv::Result<()>;
}

/// 一个最简处理器：只打印帧序号和尺寸，先把链路跑通。
struct Printer;

impl FrameSink for Printer {
    fn on_frame(&mut self, idx: u64, frame: &core::Mat) -> opencv::Result<()> {
        // OpenCV 的 Mat 默认是 BGR、HxWx3、u8（BGR 顺序见第 4 章）
        println!("帧 #{idx}: {}x{} (宽x高)", frame.cols(), frame.rows());
        Ok(())
    }
}
}

核心是这个拉流取帧循环：

/// 打开视频源（本地文件路径 / rtsp:// 地址 / 摄像头），循环取帧喂给 sink。
fn run_capture(source: &str, sink: &mut dyn FrameSink) -> opencv::Result<()> {
    // CAP_FFMPEG：强制走 FFmpeg 后端，文件和 RTSP 都能开
    let mut cap = videoio::VideoCapture::from_file(source, videoio::CAP_FFMPEG)?;

    // 减小内部缓冲到 1 帧，尽量拿"最新帧"，降低实时延迟（见 6.10）
    cap.set(videoio::CAP_PROP_BUFFERSIZE, 1.0)?;

    if !cap.is_opened()? {
        eprintln!("打不开视频源: {source}");
        return Ok(());
    }

    let mut frame = core::Mat::default();
    let mut idx = 0u64;
    loop {
        // read() = grab() + retrieve()，把下一帧解码进 frame（已按显示顺序排好）
        let ok = cap.read(&mut frame)?;
        if !ok || frame.empty()? {
            // 文件读到结尾，或网络流断开
            eprintln!("流结束或读取失败，退出循环");
            break;
        }
        sink.on_frame(idx, &frame)?; // 把这一帧交给处理函数
        idx += 1;
    }
    Ok(())
}

fn main() -> opencv::Result<()> {
    // 用法：cargo run -- test.mp4    或    cargo run -- rtsp://user:pass@ip:554/...
    let source = std::env::args().nth(1).unwrap_or_else(|| "test.mp4".to_string());
    let mut sink = Printer;
    run_capture(&source, &mut sink)
}

打开 USB 摄像头只需换一行——用索引而不是路径：

#![allow(unused)]
fn main() {
// 打开第 0 个摄像头（Linux 的 /dev/video0）
let mut cap = videoio::VideoCapture::new(0, videoio::CAP_ANY)?;
}

把帧接上前几章的图像/张量。 Mat 是 OpenCV 的图像类型，我们要把它变回第 3 章的 ndarray，才能喂给第 10 章的 letterbox 预处理：

#![allow(unused)]
fn main() {
use ndarray::Array3;

/// 把 BGR 的 Mat 转成第 3 章的 ndarray（形状 HxWx3, u8）。
fn mat_to_ndarray(frame: &core::Mat) -> opencv::Result<Array3<u8>> {
    let h = frame.rows() as usize;
    let w = frame.cols() as usize;
    let data = frame.data_bytes()?; // 连续的 BGR 字节切片
    // 长度对得上就不会失败；注意此处假设内存连续、无行填充
    let arr = Array3::from_shape_vec((h, w, 3), data.to_vec())
        .expect("shape 与数据长度不符");
    Ok(arr)
}
}

坑提示：Mat 的每一行可能有对齐填充（padding），data_bytes() 不一定是紧凑的 H×W×3。生产代码要先判断 frame.is_continuous()?，不连续时用 frame.clone() 拷成连续内存，或按行 step 逐行拷贝。另外记得 OpenCV 是 BGR 顺序，喂给多数模型前要转成 RGB（第 4、10 章会反复处理这件事）。

现在，一路视频就变成了“源源不断的 Array3<u8>“，后面接检测、跟踪都顺理成章。

6.8 用 ffmpeg 命令行抽帧（当外部工具）

不想在程序里链接重依赖时，ffmpeg 命令行是最好用的“外部工具“，尤其适合离线批量抽帧。几条最常用的命令：

# 每秒抽 1 帧，存成 out_001.jpg, out_002.jpg ...（稀疏采样做检测/分类很够用）
ffmpeg -i in.mp4 -vf fps=1 out_%03d.jpg

# 只抽关键帧(I 帧)，最省：I 帧本就能独立解码
ffmpeg -i in.mp4 -vf "select='eq(pict_type,I)'" -vsync vfr key_%03d.jpg

# 从 RTSP 拉 10 秒存成 mp4；-c copy 表示不重新编码、直接搬运码流（最快、不失真）
ffmpeg -rtsp_transport tcp -i "rtsp://user:pass@ip:554/stream" -t 10 -c copy clip.mp4

# 先看清楚里面是什么编码/容器/分辨率（决定能不能硬解）
ffprobe in.mp4

两个要点：-rtsp_transport tcp 强制 RTSP 走 TCP，比默认 UDP 更抗丢包（少花屏，见 6.10）；-c copy 是“只搬运不转码“，省 CPU 也不损画质。

在 Rust 里把它当外部命令调用即可：

#![allow(unused)]
fn main() {
use std::process::Command;

/// 调用系统 ffmpeg，每秒抽 1 帧到 out_dir。适合离线批处理。
fn extract_frames(input: &str, out_dir: &str) -> std::io::Result<()> {
    let pattern = format!("{out_dir}/out_%03d.jpg");
    let status = Command::new("ffmpeg")
        .args(["-i", input, "-vf", "fps=1", &pattern])
        .status()?; // 阻塞等 ffmpeg 跑完
    if !status.success() {
        eprintln!("ffmpeg 退出码非 0");
    }
    Ok(())
}
}

如何取舍：离线、批量、一次性的活儿，ffmpeg 命令行最省事；实时、在进程内、要逐帧接推理的活儿，用 6.7 的 opencv（或下一节的库）更合适——总不能对着一路直播每秒 fork 一个进程。

6.9 纯 Rust 方向：ffmpeg-next / video-rs / retina

如果你希望更“Rust 原生“、少依赖 OpenCV 那一大坨，可以看这三个方向：

crate定位说明
ffmpeg-nextlibav* 的安全绑定功能最全（几乎等于 FFmpeg 本体），但仍需链接系统 FFmpeg 库
video-rsffmpeg-next 之上的易用封装解码后可直接拿到 ndarray，上手快，样板少
retina纯 Rust 的 RTSP 客户端自己实现 RTSP/RTP 信令与拆包，不依赖 FFmpeg

几句实话：

  • ffmpeg-next / video-rs 走的还是 FFmpeg 的老底子，稳定、编码格式支持最全，是“想脱离 OpenCV 但要功能全“的首选。
  • retina 专注把 RTSP 这段网络协议用纯 Rust 处理干净（连接、鉴权、断线重连、TCP/UDP 传输控制都能精细掌控），非常适合“我要牢牢控制拉流行为“的场景。但它只负责把 H.264/H.265 的**负载（NAL 单元）**取出来，真正的解码你还得配一个解码器（交给硬件解码器，或另一个解码 crate）。
  • 现实是：目前纯 Rust 的 H.264/H.265 解码还不成熟，绝大多数生产系统底层仍然是 FFmpeg 或硬件解码器在干活。别为了“纯 Rust“这个执念，牺牲了稳定性和编码兼容性。

选型小结：快速上手/多来源统一 → opencv；离线批处理 → ffmpeg 命令行；要精细控制 RTSP → retina（+ 解码器）；要 FFmpeg 全功能又想 Rust API → ffmpeg-next / video-rs。

6.10 工程坑：花屏、时间戳、断流重连、缓冲堆积

拉流循环写出来只是“能跑“，离“能上线跑一年“还差这几个坑：

1. 丢包花屏。 UDP 传的 RTSP 一旦丢包，P/B 帧就拿不到完整的参考数据，画面会糊成马赛克/拖影，直到下一个 I 帧才恢复。对策：优先用 TCP 传输（命令行 -rtsp_transport tcp）；让摄像头缩短 GOP（关键帧更密，花屏恢复更快）；解码报错时别崩，丢掉坏帧继续读。

2. 时间戳跳变 / 回绕。 别天真地拿 dt = pts₂ - pts₁ 当帧间隔。摄像头对时、重连都可能让 pts 突然跳变；而某些格式的时间戳位宽有限会回绕（wraparound）（比如 MPEG-TS 的 33 位时钟约 26.5 小时绕一圈，绕回去后 pts₂ - pts₁ 会变成一个巨大的负数）。对策：对帧间隔做合理性检查（异常的负值/超大值就丢弃或钳制），必要时退回用本机墙上时钟估算节奏。

3. 断流自动重连。 网络摄像头掉线是常态，read() 会返回 false 或空帧。生产代码要把拉流包在一个带退避的重连循环里，而不是一断就退出：

#![allow(unused)]
fn main() {
/// 断流后自动重连，永不退出。注意退避，别 tight-loop 把 CPU 打满。
fn run_forever(source: &str, sink: &mut dyn FrameSink) {
    loop {
        match run_capture(source, sink) {
            Ok(()) => eprintln!("流正常结束"),
            Err(e) => eprintln!("拉流出错: {e}"),
        }
        eprintln!("2 秒后重连 {source} ...");
        std::thread::sleep(std::time::Duration::from_secs(2)); // 退避
    }
}
}

4. 缓冲堆积导致延迟越跑越大。 这是实时视觉最经典的坑。只要解码速度 > 推理速度，帧就会在队列里越堆越多，你处理的永远是几秒前的旧画面，延迟单调增长、再也回不来。根因就是 6.6 说的“没有丢帧“。对策：用有界队列，满了就丢最旧的帧、只留最新帧。6.7 里那句 cap.set(CAP_PROP_BUFFERSIZE, 1.0) 也是同一思路——从源头就少缓冲。

5. 解码线程与推理线程解耦。 正确的实时架构是生产者-消费者：解码线程按实时速率不停取帧、往一个小容量队列里塞；推理线程从队列取“当前最新的一帧“来算，算得慢没关系，因为旧帧早被丢了。

 [解码线程/生产者]                         [推理线程/消费者]
 拉流→解码 ──push──▶ 有界队列(容量 1~2) ──pop──▶ letterbox→模型→后处理
   (按流的实时速率)      队列满就丢最旧的帧        (慢也只处理最新帧,延迟可控)

这套线程模型、通道选型、多路并发和性能调优，是第 29 章的主题，这里只点到为止——先记住“丢帧保时效、有界队列、生产者消费者“这三板斧，你的实时程序就不会越跑越卡。

6.11 小结

  • 视频 = 帧序列 + 帧率 + 时间戳。1080p 原始视频一分钟就要 10 GB，所以必须编码压缩；压缩的核心是消灭帧间冗余（相邻帧太像了）。
  • I/P/B 帧与 GOP：I 帧完整可独立解码，P/B 帧只存“差值“、离不开参考帧。这解释了“随机跳转必先跳到最近关键帧“，以及 B 帧导致 pts ≠ dts（解码顺序 ≠ 显示顺序）。
  • 分清 codec（H.264/H.265/AV1，怎么压） 和 container（mp4/mkv/flv，怎么装）；文件后缀不代表内部编码，网络上传的是一个个 NAL 单元。
  • 视频来源有本地文件、USB、RTSP/RTMP、GB28181，但最终大多能归一成“一路可被 FFmpeg/OpenCV 打开的流“。边缘设备**必须用硬件解码（NVDEC/VAAPI/RKMPP）**省 CPU、少拷贝。
  • Rust 实操首选 opencv 的 VideoCapture：from_file 打开 → 循环 read() → Mat 转 ndarray 交给预处理；离线批量抽帧用 ffmpeg 命令行；要纯 Rust 看 ffmpeg-next/video-rs/retina。
  • 上线四大坑：花屏（用 TCP）、时间戳跳变/回绕（做合理性检查）、断流重连（带退避）、缓冲堆积（丢帧保时效 + 有界队列 + 生产者消费者）。

6.12 练习

  1. 算一笔账：一路 4K（3840×2160）RGB 摄像头，25 fps，若不压缩，一小时原始数据是多少 GB？再查一下同规格 H.265 大约多少 GB，估算压缩比。（提示：先算单帧字节数，再乘帧数。）

  2. 跑通拉流循环：装好 OpenCV 后，用 6.7 的代码打开一个本地 mp4（没有就用手机录一段），打印每帧序号和尺寸；再把 source 换成你手边摄像头的 RTSP 地址或 USB 索引 0，观察行为差异。进阶：实现一个“每 30 帧才真正处理一次“的 FrameSink（模拟稀疏抽帧）。

  3. 理解关键帧：用 ffprobe -show_frames in.mp4 | grep pict_type 统计视频里 I/P/B 帧各有多少、GOP 大概多长；再分别用“每秒抽 1 帧“和“只抽 I 帧“两条 ffmpeg 命令抽图，对比生成的图片数量，解释差异。

  4. 模拟延迟堆积：在你练习 2 的 on_frame 里 sleep(100ms) 假装推理很慢，喂一路 30fps 的流，观察“处理的帧“是否越来越滞后于“当前画面“。然后加一个容量为 1 的有界队列（解码线程只往里塞最新帧、满了丢旧帧），验证延迟是否被稳住。（这题是第 29 章的预热。）
