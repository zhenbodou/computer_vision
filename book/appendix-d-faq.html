机器视觉工程实战：用 Rust 看懂图像与模型

附录 D · 踩坑与常见问题 FAQ

本附录汇总全书高频坑与常见问题，按主题归类，随时来查。遇到“结果不对、又说不清错在哪“时，先按现象在下面找到对应主题，再顺着每条末尾指路的章节回正文看细节。每条都是：一句症状 + 原因 + 一句解法 + 指路章节。

D.1 图像与内存

Q： 图像的宽高（W×H）到底哪个在前？创建/索引时老是崩或者歪？ A： image 里 ImageBuffer::new(width, height) 是宽在前；但内存按行存、ndarray 张量习惯写 [H, W, C]（高/行在前）。640×480 很容易被记反。记死一句话：“文件名、API 里是宽×高，内存里第一维是行（y/高）、第二维是列（x/宽）”。（第 2、3 章）

Q： HWC 和 CHW 分不清，喂给模型后像素全乱、可视化花屏？ A： image 解码出来是 HWC（一个像素的 RGB 连续排列）；模型要 CHW（先所有 R、再所有 G、再所有 B）。直接把 HWC 字节丢进模型等于把像素揉碎了。用 ndarray 的 permuted_axes([2,0,1]) 重排后 to_owned() 再喂。（第 3、10 章）

Q： 按 width * 3 一行一行读，结果图像逐行错位、右边一条斜边？ A： 很多解码器/GPU 纹理为内存对齐会在每行末尾补填充字节，一行真实长度是 stride（行跨距），不等于 width * channels。要按 stride 逐行拷贝，别假设 stride == width*channels。image 的 buffer 一般无填充，OpenCV、硬件解码、显存纹理常有。（第 2、4 章）

Q： 图片红蓝互换了，人脸发蓝？ A： RGB 与 BGR 通道顺序不同：OpenCV 和不少解码器默认 BGR，image 是 RGB，混用时没转就会红蓝对调。明确每个环节的通道序，需要时交换通道 0 和 2。喂 YOLOv8 必须是 RGB。（第 4 章）

D.2 编解码

Q： 同一张 JPEG 反复打开再保存，越来越糊？ A： JPEG 是有损压缩，每次保存都重新 DCT + 量化，误差逐代累积（“代际损失”），块状伪影越来越明显。处理链路中间一律用无损格式（PNG 或内存里的原始像素），只在最后一步存 JPEG；要归档就存 PNG。（第 5 章）

Q： 手机竖拍的照片读进程序里“躺倒了“？ A： 很多相机不旋转像素，只在 EXIF 里写一个 Orientation 标记；解码库若不读 EXIF 就按原始像素方向给你。读取时解析 EXIF Orientation 并据此旋转/翻转，或走支持自动定向的加载路径。（第 5 章）

Q： 视频抽帧拿到的帧顺序乱、画面来回跳？ A： H.264/H.265 有 B 帧（双向参考），解码顺序（DTS）不等于显示顺序（PTS）。按 PTS（显示时间戳）排序后再用，别拿解码到手的先后当播放顺序。（第 6 章）

D.3 预处理

Q： letterbox 之后检测框位置全偏、比例也不对？ A： letterbox 做了等比缩放 + 灰边填充，但后处理没把缩放比和填充记下来，直接拿 640 坐标当原图坐标用。做 letterbox 时就存下 scale、pad_x、pad_y，还原时按下面逆变换：

// 还原到原图：先减填充，再除以缩放比例
let x_orig = (x - pad_x) / scale;
let y_orig = (y - pad_y) / scale;

（第 10、16 章）

Q： 归一化方式和训练不一致，能检出但分数偏低、框不准？ A： 训练用的是 /255（缩放到 0~1）还是 mean-std（减均值除标准差，如 ImageNet 那套）没对齐。本书主模型 YOLOv8：RGB、只 /255、不做 mean-std。务必查模型来源的预处理并严格照抄。（第 10 章）

Q： 通道喂反了（把 BGR 当 RGB 灌进去）？ A： 能出框但类别、分数明显不对。预处理的通道序必须和模型训练时一致。YOLOv8 是 RGB 训练的，预处理就转成 RGB 再喂。（第 10、4 章）

D.4 模型与推理

Q： 模型输入 shape 里有 -1，我当成尺寸去分配内存就崩了？ A： -1（或字母 N、height 这类名字）是动态维度占位符，意思是“运行时才定“，不是真实数字。按你的实际输入定：batch 一般设 1，H/W 设 640。用 Netron 或模型元数据看清哪几维是动态的。（第 12 章）

Q： 输出维度含义猜错——84 还是 85？8400 是什么？ A： 这是最常见的后处理翻车点，看表：

模型输出形状每个候选的含义objectness
YOLOv5[1, 25200, 85]4 框 + 1 目标分 + 80 类有（第 5 位）
YOLOv8[1, 84, 8400]4 框 + 80 类无

YOLOv8 的 84 = 4 框 + 80 类，没有 objectness，分数直接取 80 类里的最大值；8400 是候选框个数。注意 [1, 84, 8400] 是“84 在前、8400 在后“，取第 j 个候选要跨行读（步长 8400），不是连续读 84 个数。（第 12、16 章）

Q： 升级 ort 之后编译不过、类型对不上？ A： ort 2.x 相对 1.x 的 API 改动较大（Session 构建、输入输出接口重构）。锁定版本号、照该版本文档写；升级时先读官方迁移说明。本书按 2.x 写。（第 14 章）

Q： 推理特别慢，视频流才跑几帧？ A： 十有八九是每帧都重建 Session（Session::builder()...commit_from_file() 里加载权重 + 图优化非常贵），或者忘了 --release。Session 只建一次、循环里复用；发布模式编译；再考虑多线程和 GPU/NPU 的 Execution Provider。（第 14、29 章）

D.5 模型转换

Q： opset 不匹配，转换或加载就报错？ A： 导出的 opset 版本高于推理引擎支持的版本（tract 支持的 opset 尤其有限），会报 unsupported opset 或加载失败。导出时指定引擎支持的 opset（如 12 或 17），或换支持更全的引擎（ort）。（第 13 章）

Q： 某个算子目标平台不支持？ A： 边缘设备的 NPU、TFLite、RKNN 等算子集有限，某些算子（如特定的 Resize/上采样模式）不被支持，加载时报“不支持的算子“。用 Netron 定位到具体算子，替换成等价的受支持算子或改导出参数；个别算子可回退 CPU 执行。（第 13 章）

Q： 想要动态 batch，导出后 batch 却被固定成 1？ A： 导出时没设 dynamic_axes。以 PyTorch 为例，torch.onnx.export 里要为输入/输出的 batch 维显式声明 dynamic_axes，才能在推理时改 batch。（第 13 章）

Q： INT8 量化后精度暴跌？ A： 没做校准的 INT8 直接把权重和激活压到 8 bit，激活分布没标定，误差很大。用一批有代表性的校准集做 PTQ 校准；对精度敏感的层保留 FP16；上线前一定先量化后跑一遍 mAP 对比。（第 13 章）

D.6 后处理

Q： 框画出来又小又挤在左上角？ A： 模型输出的框是 cxcywh（中心点 + 宽高），被当成 xyxy（左上-右下）直接用了。先转成统一的 BBox：

// YOLOv8 输出是 中心点+宽高，先转成 BBox 的左上-右下坐标
let bbox = BBox {
    x1: cx - w / 2.0,
    y1: cy - h / 2.0,
    x2: cx + w / 2.0,
    y2: cy + h / 2.0,
};

（第 16 章）

Q： 同一个物体上叠了好几个框，或不同类别互相压制？ A： NMS 没有按类别分组：要么根本没做，要么跨类别一起做把不同类的框也抑制了。正确做法是按 class_id 分组、各自做 NMS（或用“类别偏移“技巧让不同类互不干扰）。（第 16 章）

Q： 置信度阈值取错，满屏框或啥都检不到？ A： 把置信度阈值和 NMS 的 IoU 阈值搞混，或设得过高/过低。两者是分开的两步：先按 conf 阈值（如 0.25）过滤候选，再按 IoU 阈值（如 0.45）做 NMS，分别调。（第 16 章）

Q： 框没还原到原图，画在缩放图上就偏了？ A： 框坐标是 0~640，直接画到原图（如 1920×1080）当然错位。用 letterbox 记下的 scale/pad 逆变换回原图坐标（见 D.3 的代码），最后再 clamp 到原图边界内。（第 16、10 章）

D.7 视频分析业务过滤器

Q： 跟踪 ID 频繁跳变，导致同一个人被重复计数？ A： 检测漏帧或遮挡时轨迹断了又新建，max_age、匹配阈值设得太严。调大 max_age（容忍连续几帧丢失），用 ByteTrack 的二次匹配把低分框也捞回来，适当放宽 IoU/距离阈值。（第 21 章）

Q： 跑得快的目标一下跨过绊线，却没触发？ A： 只判断“目标中心点在线的哪一侧“，两帧之间目标已经跳过了线，单帧采样漏掉。要用“上一帧中心 → 这一帧中心“连成的线段和绊线做线段相交判断，而不是逐帧看点位置。（第 23 章）

Q： 一个事件报警疯狂刷屏，一秒几十条？ A： 每帧只要满足条件就报，没有去抖。加 Cooldown 冷却（同一目标/同一区域 N 秒内只报一次），或用事件窗口去重。（第 24 章）

Q： 没人的时候，树影、旗帜、广告牌被反复误检？ A： 晃动的背景或固定物被当成目标，缺少空间/静态过滤。用 ROI 只看关心的区域，用静态过滤忽略长期不动的框，用 mask 屏蔽已知干扰区。（第 22 章）

Q： 抓拍到的人脸绑错人（张三的脸绑到李四身上）？ A： 脸人绑定只按“最近距离“匹配，多人靠近时容易错绑。应综合判断：脸框被人体框包含 + 包含度/IoU 达标 + 跟踪 ID 一致，再加时间一致性约束。（第 25 章）

D.8 环境与依赖

Q： ort 编译过了，运行却报找不到 libonnxruntime？ A： ort 依赖 ONNX Runtime 的动态库，系统没装或不在库搜索路径里。开启 ort 的下载特性让它自动拉取匹配的库，或自己装好后设 ORT_DYLIB_PATH（Linux 上也可用 LD_LIBRARY_PATH）。（第 14 章）

Q： opencv crate 编译失败，找不到头文件/库？ A： opencv 绑定需要系统预装 OpenCV 和 clang，且环境变量（OPENCV_LINK_LIBS、pkg-config 路径等）要配好。新手可先用 image + ffmpeg 命令行抽帧绕开它（见第 6 章的轻量方案），有需求再装。（第 6、14 章）

Q： 交叉编译到边缘设备（ARM/aarch64）跑不起来？ A： 常见是链接了 x86 的 onnxruntime 库、目标却是 aarch64，或没加目标 target。先 rustup target add aarch64-...，换成对应架构的 onnxruntime 动态库，用交叉编译工具链或容器构建；尽量静态链接以减少目标机上的依赖。（第 29 章）
