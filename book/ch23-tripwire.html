机器视觉工程实战：用 Rust 看懂图像与模型

第 23 章 · 拌线检测：单拌线、双拌线与方向判断

本章导读：第 21 章我们给每个目标配上了稳定的跟踪 ID，第 22 章又用 ROI 把“画面里哪块区域算数“圈了出来——这两样都是空间层面的过滤。本章在它们之上做一件更“动态“的判断：目标有没有跨过一条线、朝哪个方向跨。这就是拌线检测（tripwire，也叫绊线），是人流计数、越界报警最核心的业务过滤器。读完这一章你能：用叉积（cross product）判断点落在线的哪一侧、用线段相交精准抓住“跨线“那一瞬间、区分“进 / 出“两个方向，并亲手写出单拌线的计数骨架，以及更抗误报的双拌线状态机。它们正是第 27 章周界入侵报警、第 28 章人流统计的地基。

23.1 拌线是什么：画面里的一条虚拟线

拌线就是你在摄像头画面里画的一条虚拟线段（不是真的物理设备，只是软件里的两个端点连成的线）。规则很简单：当一个目标从线的一侧移动到另一侧，就算它“跨线“了，触发一个事件。

打两个生活比喻，一下就懂：

  • 跨过起跑线：裁判盯着地上那条白线，谁的身体越过去，就记一次“通过“。线是画在地上的，运动员是移动的目标。
  • 红外对射报警：走廊两头装一对红外收发器，中间形成一条看不见的“光墙“，有人穿过就报警。拌线就是这堵“光墙“的软件版——只不过它是我们在画面里随便画的一条线，位置、朝向都能自由调。

它能干的事非常“业务“：

场景拌线怎么用
商场客流门口画一条线，进店 +1、出店 −1
周界入侵沿围墙画一条线，有人朝院内方向跨 → 报警
车流统计车道上画一条线，每辆车压过计一次
电梯口滞留配合双拌线，只统计“真正走进去“的人

为什么必须基于跟踪 ID

这是新手最容易忽略的一点：拌线判断的不是“某一帧的画面“，而是“同一个目标在相邻两帧的移动“。

想想“跨线“的本质——它是一个过程：某个目标上一帧还在线的左边，这一帧跑到了线的右边。要判断这件事，你必须能回答“这两帧里的这两个框，是不是同一个人“。这正是第 21 章多目标跟踪给我们的东西：每个目标有一个稳定的 id，跨帧不变。

所以拌线的输入不是零散的检测框，而是带 ID 的 Track（复用全书统一类型）：

#![allow(unused)]
fn main() {
// 复用全书统一类型（写作规范第 6 节），本章不再重复定义
use crate::{BBox, Track};        // Track { id, bbox, class_id, score }
use std::collections::HashMap;

/// 画面里的一个点：(x, y)，单位一律是原图像素（写作规范坐标约定）
type Pt = (f32, f32);
}

有了 ID，我们就能给每个目标维护一份“上一帧它在哪“的记录，拿它和这一帧比。没有 ID（比如只有裸检测框），你根本分不清“这一帧线右边的人“和“上一帧线左边的人“是不是同一个，拌线就无从谈起。

23.2 核心几何：叉积判断点在线的哪一侧

拌线检测的全部数学，就压缩在一个问题里：给一条线和一个点，这个点在线的哪一侧？ 解决它的工具叫叉积。

先打比方：河流的左岸和右岸

把拌线想成一条有方向的河，水从端点 $A$ 流向端点 $B$。河把平面分成两半：左岸和右岸。任意一个点，要么在左岸、要么在右岸、要么正好踩在河中央（线上）。叉积做的事，就是用一个数的正负号告诉你：这个点在左岸还是右岸。

它的算式是（$A$、$B$ 是拌线两端，$P$ 是要判断的点）：

$$\text{side}(A,B,P) = (B_x - A_x)(P_y - A_y) - (B_y - A_y)(P_x - A_x)$$

  • 结果 > 0：在一侧（记为正侧）
  • 结果 < 0：在另一侧（记为负侧）
  • 结果 = 0：恰好落在直线上

正负号具体对应哪个方向，取决于你怎么定 $A$、$B$ 的顺序；不用死记，算一次就知道，重要的是“两侧符号相反“这件事。

用具体数字手算一遍

设拌线是一条竖线：$A=(100, 50)$（上端）、$B=(100, 300)$（下端）。注意图像坐标里 x 向右、y 向下。我们拿两个点来算：

点 P1 = (60, 180)，它在竖线左边（x 更小）：

$$\text{side} = (100-100)(180-50) - (300-50)(60-100) = 0\times130 - 250\times(-40) = 0 - (-10000) = +10000$$

点 P2 = (140, 180)，它在竖线右边（x 更大）：

$$\text{side} = (100-100)(180-50) - (300-50)(140-100) = 0\times130 - 250\times40 = 0 - 10000 = -10000$$

结论一目了然：画面左边的点算出来是正号，右边的点是负号。 一条线把世界分成“正侧 / 负侧“，靠的就是这个符号。配张图：

   叉积 side(A, B, p) 的符号 = 点 p 在有向线 A->B 的哪一侧

               A (100, 50)
                *
    左侧(x 小)  |  右侧(x 大)
   P1(60,180)  |  P2(140,180)
      o         |     o
   side=+10000  |  side=-10000
     (正侧)     |    (负侧)
                *
               B (100, 300)

翻成 Rust，就是一行乘减法：

#![allow(unused)]
fn main() {
/// 叉积符号：点 p 相对"有向线段 a->b"在哪一侧
/// 返回值 > 0 一侧、< 0 另一侧、== 0 恰好落在线上
fn side(a: Pt, b: Pt, p: Pt) -> f32 {
    (b.0 - a.0) * (p.1 - a.1) - (b.1 - a.1) * (p.0 - a.0)
}
}

就这么短。但别小看它——单拌线的方向判断、双拌线的过线检测，全都建立在这个 side 上。

23.3 从“在哪侧“到“跨没跨“：线段相交

知道点在哪一侧，还不等于知道它“跨线“了。跨线是一个变化：目标的代表点上一帧在正侧、这一帧到了负侧（或反过来）。

代表点：拿目标的哪个点去判断

一个目标是一个框，不是一个点。我们得先从框里挑一个代表点（representative point）来代表它的位置。最常用的是底边中点——因为对站立的人、地面上的车来说，这个点就是它“脚踩在地面上的位置“，最贴合“它到底走到了地面上的哪里“。

#![allow(unused)]
fn main() {
/// 目标的代表点：底边中点（站立的人/地面车辆，约等于"脚的位置"）
fn foot_point(b: &BBox) -> Pt {
    ((b.x1 + b.x2) * 0.5, b.y2) // x 取左右中点，y 取框底
}
}

顶视（俯拍）摄像头下，人是“一个头顶“，用框的几何中心 BBox::center() 更合适。代表点选错是常见坑，23.8 会专门说。

方法一（简单）：只看两帧的符号变没变

最朴素的判据：把拌线当成一条无限长的直线，只要目标代表点从正侧变到负侧（或反之），就算跨线：

#![allow(unused)]
fn main() {
let s_prev = side(a, b, p_prev); // 上一帧在哪侧
let s_curr = side(a, b, p_curr); // 这一帧在哪侧
let crossed = s_prev * s_curr < 0.0; // 一正一负 => 换侧了 => 跨线
}

s_prev * s_curr < 0.0 是个小技巧：两个数一正一负，乘积才为负。这行代码在很多简单场景里够用了。但它有个毛病——它把拌线当成了无限长的直线，目标从线段端点外侧掠过时也会误判。

方法二（稳）：线段相交

更严谨的做法：把“目标这一步的移动“也看成一条线段 p_prev -> p_curr，判断它和拌线线段 A—B 是不是真的交叉。这解决了两个方法一处理不好的问题：

  (1) 快速目标一帧跨很远：
      只盯"点在不在线上"会漏，因为它从没"踩"在线上过；
      看"移动线段 与 拌线 是否相交"就能稳稳抓住。

     p_prev o- - - - - -|- - - - - -> o p_curr
                     拌线 |
                       （两线段相交 => 触发）

  (2) 无限直线 vs 有限线段：目标从拌线端点"外侧"经过
      p_prev o───────► o p_curr   (从 A 端上方掠过)
              A========B           <- 拌线真正的范围就这么长
                       :
                       :  (A—B 的延长线)
      => 换侧了(叉积变号)，但根本没穿过线段本身 => 不该触发

线段相交怎么判？还是用 side。两条线段 $ab$、$cd$ 真正交叉，当且仅当：$a$、$b$ 分居直线 $cd$ 的两侧，同时 $c$、$d$ 也分居直线 $ab$ 的两侧。四次叉积搞定：

#![allow(unused)]
fn main() {
/// 线段 (a,b) 与线段 (c,d) 是否交叉（一般位置版，暂不处理三点共线的退化情况）
fn segments_intersect(a: Pt, b: Pt, c: Pt, d: Pt) -> bool {
    let d1 = side(c, d, a);
    let d2 = side(c, d, b);
    let d3 = side(a, b, c);
    let d4 = side(a, b, d);
    // a、b 分居 cd 两侧，且 c、d 分居 ab 两侧 => 两线段真正交叉
    ((d1 > 0.0 && d2 < 0.0) || (d1 < 0.0 && d2 > 0.0))
        && ((d3 > 0.0 && d4 < 0.0) || (d3 < 0.0 && d4 > 0.0))
}
}

这里用的是“一般位置“版本，假设不会出现“点恰好落在线上“（叉积正好 = 0）的巧合。对浮点像素坐标，这种巧合几乎不发生；真要较真，工程上会在 == 0 时再补一个“点是否落在线段范围内“的判断。生产系统里优先用方法二，它更稳、也顺带解决了下面要讲的“快速目标跳过线“的坑。

23.4 方向判断：A→B 还是 B→A

拌线不光要知道“跨了没有“，通常还要知道“往哪个方向跨“——进店还是出店、进院还是出院。方向信息其实免费藏在叉积符号的变化方向里：

  • 符号 正 → 负：从正侧跨到负侧，记作一个方向；
  • 符号 负 → 正：从负侧跨到正侧，记作反方向。

用上一节竖线的数字：目标上一帧在 P1(60,180)（正侧，+10000），这一帧到了 P2(140,180)（负侧，−10000），就是“正 → 负“这个方向。哪个方向叫“进“、哪个叫“出“，是你在项目里配置一次的业务约定，和几何无关。

我们用一个枚举把两个方向和“没跨线“钉死：

#![allow(unused)]
fn main() {
/// 一次跨线事件的方向（两个方向的业务含义由你配置，例如"进 / 出"）
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum CrossDir {
    AtoB, // 正侧 -> 负侧，例如"进"
    BtoA, // 负侧 -> 正侧，例如"出"
    None, // 这一步没有跨线
}

/// 判断相邻两帧的移动是否跨过拌线 (wire_a, wire_b)，并给出方向
fn cross_dir(wire_a: Pt, wire_b: Pt, p_prev: Pt, p_curr: Pt) -> CrossDir {
    // 先用线段相交确认：确实跨过了"这条线段"，而不是它的延长线
    if !segments_intersect(wire_a, wire_b, p_prev, p_curr) {
        return CrossDir::None;
    }
    // 再用叉积符号的变化方向定"向"
    let s_prev = side(wire_a, wire_b, p_prev);
    let s_curr = side(wire_a, wire_b, p_curr);
    if s_prev > 0.0 && s_curr < 0.0 {
        CrossDir::AtoB
    } else if s_prev < 0.0 && s_curr > 0.0 {
        CrossDir::BtoA
    } else {
        CrossDir::None // 理论上相交时不会走到这，留作兜底
    }
}
}

一个函数就把“跨没跨 + 往哪跨“两件事一起答了：先用 segments_intersect 确认是真跨过了这条线段，再用两帧的符号变化定方向。

23.5 单拌线：完整判定骨架

单拌线（single tripwire） 就是一条线：目标每跨一次就计一次数或报一次警，并按方向分别累加。要把它跑起来，只差一件事——给每个 track_id 缓存“上一帧的代表点“，这样下一帧来了才有 p_prev 可比。

#![allow(unused)]
fn main() {
/// 单拌线：一条线段 (p1, p2) + 每个 track 上一帧代表点的缓存
pub struct Tripwire {
    p1: Pt,                    // 拌线端点 1
    p2: Pt,                    // 拌线端点 2
    last_pt: HashMap<u64, Pt>, // track_id -> 上一帧代表点
    pub in_count: u64,         // AtoB 方向累计（例如"进"）
    pub out_count: u64,        // BtoA 方向累计（例如"出"）
}

impl Tripwire {
    pub fn new(p1: Pt, p2: Pt) -> Self {
        Self { p1, p2, last_pt: HashMap::new(), in_count: 0, out_count: 0 }
    }

    /// 喂入这一帧所有跟踪目标，返回本帧发生的跨线事件 (track_id, 方向)
    pub fn update(&mut self, tracks: &[Track]) -> Vec<(u64, CrossDir)> {
        let mut events = Vec::new();
        for t in tracks {
            let p_curr = foot_point(&t.bbox);
            // 只有能拿到"上一帧位置"的 track 才判定；首次出现的只记录、不判定
            if let Some(&p_prev) = self.last_pt.get(&t.id) {
                match cross_dir(self.p1, self.p2, p_prev, p_curr) {
                    CrossDir::AtoB => { self.in_count += 1; events.push((t.id, CrossDir::AtoB)); }
                    CrossDir::BtoA => { self.out_count += 1; events.push((t.id, CrossDir::BtoA)); }
                    CrossDir::None => {}
                }
            }
            self.last_pt.insert(t.id, p_curr); // 更新"上一帧位置"
        }
        events
        // 工程提示：还应定期清理已消失 track 的缓存，否则 last_pt 会无限增长；
        // 具体的"目标何时算消失"由第 21 章的跟踪器生命周期决定。
    }
}
}

走一遍：某个 id=7 的人，上一帧代表点在 (60,180)（正侧），这一帧走到 (140,180)（负侧）。update 里 cross_dir 先确认移动线段和拌线相交（人是横着穿过竖线的，相交），再看符号 + -> -，返回 AtoB，于是 in_count 加一、事件 (7, AtoB) 入列。下一帧它继续往右走、不再碰线，cross_dir 返回 None，计数不动。这就是单拌线的全部逻辑。

单拌线简单、够用，但它有个软肋：只要目标在线附近来回抖一下（跟踪框轻微晃动、或人真的在门口犹豫），代表点就可能反复穿越，触发一串“进出进出“的假事件。要更稳，就上双拌线。

23.6 双拌线：状态机与“依次跨越“

双拌线（double tripwire） 用两条平行线 A 和 B，规则升级为：目标必须依次跨过 A 再跨过 B，才算一次有效通过。 顺序 A→B 记为一个方向（比如“进“），顺序 B→A 记为反方向（“出”）。

注意：这一节的 A、B 指两条线；上一节的 A、B 指同一条线的两侧，别混淆。

为什么这样更好？因为它把“通过“从一个瞬间升级成了一段有先后的过程，天然过滤掉大量误触：

  • 抗徘徊/误触：只在一条线附近晃、没走到第二条线，永远不计数；
  • 方向更准：方向由“先碰哪条线“这个顺序决定，比单看一次叉积符号更可靠——哪怕目标斜着走、框在抖，只要它是“先过 A 后过 B“，方向就是确定的。
   双拌线：必须依次跨过 A 再跨过 B，才算一次有效通过

        line A        line B
          |             |
   进 ->  |   (中间带)   |  ->    先 A 后 B = "进"  (in_count++)
          |             |
   出 <-  |             |  <-    先 B 后 A = "出"  (out_count++)
          |             |

   状态机：
     Idle --跨A--> HitA --跨B--> 计一次"进"，回 Idle
     Idle --跨B--> HitB --跨A--> 计一次"出"，回 Idle
     （只碰一条就走开 / 隔太久没碰第二条 => 超时重置，视为徘徊）

核心是给每个 track_id 维护一个状态机，记录它“先碰到了哪条线、在等哪条线“：

#![allow(unused)]
fn main() {
/// 每个 track 的过线状态；括号里存"进入该状态时的帧号"，用于超时重置
#[derive(Clone, Copy)]
enum PassState {
    Idle,      // 还没碰任何线
    HitA(u64), // 先跨了 A，正在等着跨 B
    HitB(u64), // 先跨了 B，正在等着跨 A
}

pub struct DoubleTripwire {
    line_a: (Pt, Pt),
    line_b: (Pt, Pt),
    last_pt: HashMap<u64, Pt>,        // track_id -> 上一帧代表点
    state: HashMap<u64, PassState>,   // track_id -> 过线状态
    max_gap: u64,                     // 跨完第一条线后，最多等几帧就得跨第二条，否则作废
    pub in_count: u64,                // 依次 A->B（"进"）
    pub out_count: u64,               // 依次 B->A（"出"）
}

impl DoubleTripwire {
    pub fn new(line_a: (Pt, Pt), line_b: (Pt, Pt), max_gap: u64) -> Self {
        Self {
            line_a, line_b,
            last_pt: HashMap::new(),
            state: HashMap::new(),
            max_gap, // 例如 30fps 下填 30，即最多允许两条线间隔 1 秒
            in_count: 0, out_count: 0,
        }
    }

    /// frame 是当前帧号（用于超时判断），tracks 是本帧所有跟踪目标
    pub fn update(&mut self, tracks: &[Track], frame: u64) -> Vec<(u64, CrossDir)> {
        let mut events = Vec::new();
        for t in tracks {
            let p_curr = foot_point(&t.bbox);
            // 首帧出现的目标：只记录位置，下一帧才有 p_prev 可比
            let p_prev = match self.last_pt.get(&t.id) {
                Some(&p) => p,
                None => { self.last_pt.insert(t.id, p_curr); continue; }
            };

            // 这一步是否分别跨过了 A / B（用线段相交，天然防"快速目标跳过线"）
            let hit_a = segments_intersect(self.line_a.0, self.line_a.1, p_prev, p_curr);
            let hit_b = segments_intersect(self.line_b.0, self.line_b.1, p_prev, p_curr);

            let st = *self.state.get(&t.id).unwrap_or(&PassState::Idle);
            let next = match st {
                PassState::Idle => {
                    if hit_a { PassState::HitA(frame) }
                    else if hit_b { PassState::HitB(frame) }
                    else { PassState::Idle }
                }
                PassState::HitA(f0) => {
                    if hit_b {
                        // 先 A 后 B：一次完整的"进"
                        self.in_count += 1;
                        events.push((t.id, CrossDir::AtoB));
                        PassState::Idle
                    } else if hit_a || frame - f0 > self.max_gap {
                        PassState::Idle // 又退回 A，或等太久（徘徊）=> 作废重置
                    } else {
                        PassState::HitA(f0) // 继续等 B
                    }
                }
                PassState::HitB(f0) => {
                    if hit_a {
                        self.out_count += 1;
                        events.push((t.id, CrossDir::BtoA));
                        PassState::Idle
                    } else if hit_b || frame - f0 > self.max_gap {
                        PassState::Idle
                    } else {
                        PassState::HitB(f0)
                    }
                }
            };
            self.state.insert(t.id, next);
            self.last_pt.insert(t.id, p_curr);
        }
        events
    }
}
}

读一遍状态转移就懂了：目标在 Idle 时先跨了 A，进入 HitA，开始“等 B“；如果它接着跨了 B，就是一次干净的“进“，计数后回到 Idle；如果它没等来 B、反而又退回跨了 A，或者磨蹭超过 max_gap 帧还没动静，就当它在徘徊，直接重置作废。B→A 方向完全对称。

一个边界情况：如果两条线挨得太近、目标又太快，可能一帧之内同时 hit_a && hit_b。上面的代码在 Idle 时会先记成 HitA，方向可能判不准。解决办法是把两条线拉开一点（间距大于目标一帧的位移），或提高帧率。max_gap 太小也会漏掉走得慢的人，需要按现场步速和帧率调。

23.7 组合与计数：拌线 + ROI + 方向

拌线很少单独用，真实项目里常和前两章的过滤器叠起来，规则越叠越精准：

  • 拌线 + ROI（第 22 章）：只统计“跨线点落在某个 ROI 内“的事件。比如画面远处背景里也有条路，但你只关心店门口那一小块，就用 ROI 把跨线事件限定在门口区域，远处的行人跨线一律忽略。
  • 拌线 + 方向：周界报警往往只关心一个方向——只在目标朝“院内“方向跨线（比如只对 CrossDir::AtoB）时才报警，从院里出来的不管。判定时对 events 里的方向做个筛选即可。
  • 拌线 + 类别（Track.class_id）：车道拌线只数 class_id == car（COCO 中 car=2），门口客流只数 person（person=0），把不相干的类别过滤掉。

进出计数是拌线最典型的产出，做法就是把两个方向分别累加——这正是前面 in_count / out_count 干的事：

   in_count  : A->B 方向累计（进）
   out_count : B->A 方向累计（出）
   当前区域内人数 ≈ in_count - out_count

“当前区域人数 = 进 − 出“是人流看板最常见的指标。但要提醒一句：这个差值对漏计/重计极其敏感——少数一个进、或多数一个出，误差会一直累积下去，越到后面越离谱。怎么防止重复计数、给事件加冷却，是第 24 章的主题，也是让这套计数真正可用的关键一环。

23.8 工程坑清单

拌线的数学不难，真正的坑都在工程细节里。下面这些几乎每个项目都会踩：

  • 代表点选错：站立的人用底边中点（脚的位置）；俯拍/顶视用几何中心；大货车这种大目标用底边中点也可能因为透视而“提前“或“滞后“跨线。代表点决定了“目标到底算走到哪了“，选之前先想清楚你的相机视角。
  • 跟踪 ID 跳变：如果第 21 章的跟踪器在目标跨线的那一两帧恰好把 ID 换了（遮挡、检测漏帧导致），新 ID 没有 p_prev，这一次跨线就漏计；反过来，一个目标被拆成两个 ID，可能被重计两次。这是拌线计数最大的误差来源，缓解手段（去重、冷却）见第 24 章。
  • 快速目标跨帧“跳过“线：目标走得快、或帧率低时，它可能上一帧还在线左边一大截、这一帧已经窜到线右边一大截，从没“踩“在线上。所以判据一定要用线段相交（23.3 方法二），而不是“点是否落在线上“——这也是本章反复强调用 segments_intersect 的原因。
  • 线画在透视地面上的位置：画面里的一条线对应地面上的一条线，但因为透视，同样长的地面距离在画面远处被压得很窄。线要画在目标代表点真正会经过的地面位置上；画高了（画到人的腰部空中）或画在透视严重变形的远景里，都会让跨线时机不准。
  • 抖动导致反复横跳：目标停在线上附近，跟踪框每帧抖一两个像素，代表点就可能反复穿越，刷出一串假事件。双拌线能挡掉很大一部分（必须走完两条线），剩下的靠第 24 章的冷却时间（cooldown）压制。
  • 缓存不清理：last_pt / state 这些 HashMap 要跟着跟踪器的目标生命周期清理已消失的 ID，否则长时间运行会内存越吃越多。
  • 拌线太靠画面边缘：目标可能“半个身子“就到边界外了，代表点抖出画面，跨线判定不稳。线尽量画在画面中间、目标完整可见的区域。

23.9 小结

  • 拌线（tripwire） 是画面里的一条虚拟线段，判断目标有没有跨过它、朝哪个方向跨；它是人流计数、越界报警的核心业务过滤器，必须建立在第 21 章的跟踪 ID 之上（要比较“同一个目标“相邻两帧的位置）。
  • 全部数学压缩成一个叉积 side(a, b, p)：符号告诉你点在有向线的哪一侧（正侧 / 负侧），我们用竖线的例子手算验证了“左边为正、右边为负“。
  • “跨没跨“要用线段相交 segments_intersect（四次叉积）判断“移动线段“和“拌线线段“是否真交叉——这比“点在线上“稳，还能抓住快速目标的跨帧跳跃。
  • 方向藏在叉积符号的变化里：正→负是一个方向、负→正是反方向，业务上映射成“进 / 出“。
  • 单拌线给每个 track_id 缓存上一帧代表点，跨线即按方向计数，简单够用但怕线上抖动；双拌线用状态机要求目标依次跨过两条线，抗徘徊、方向更准，是更工程化的选择。
  • 拌线常和 ROI（第 22 章）、方向、类别叠加使用；进出计数就是两个方向分别累加，但它对漏计/重计敏感，去重与冷却留给第 24 章。这套能力将在第 27 章周界报警、第 28 章人流统计里挑大梁。

23.10 练习

  1. 手算叉积：拌线端点 $A=(0,0)$、$B=(4,4)$（一条 45° 斜线）。分别计算点 $P=(3,1)$ 和 $Q=(1,3)$ 的 side(A,B,·)，判断它们各在哪一侧（正侧还是负侧）。再用本章的 side 函数跑一遍，核对符号是否一致，并说说这条斜线把平面分成了“哪两半“。

  2. 两种判据的差别：拌线是竖线 $A=(100,50)$、$B=(100,300)$。某目标上一帧代表点在 $(90, 400)$、这一帧在 $(110, 400)$（注意 y=400 已在端点 B 的下方）。用“方法一“（只看叉积符号 s_prev * s_curr < 0）和“方法二“（segments_intersect）各判一次，看结果是否不同，并解释为什么方法二更对。

  3. 补一个方向过滤：给单拌线的 Tripwire::update 返回的 events 写一个筛选函数，只保留 CrossDir::AtoB（“进“方向）的事件，模拟“周界报警只对朝院内跨线的目标报警”。再想想：如果要求同时满足“是 person 类别“，该在哪里加判断（提示：Track.class_id）。

  4. 双拌线状态机走查：不写代码，纸上推演。max_gap = 30。一个 id=5 的目标依次经历：第 10 帧跨过 line A、第 15 帧跨过 line B。它的状态怎么变、最终计到 in 还是 out？再换一种：第 10 帧跨 A、之后一直在两线之间徘徊到第 50 帧才跨 B，结果又如何？说明 max_gap 在这里起了什么作用。
