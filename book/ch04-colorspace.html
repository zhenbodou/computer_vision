机器视觉工程实战：用 Rust 看懂图像与模型

第 4 章 · 色彩空间与内存布局：RGB / BGR / YUV / NV12

本章导读：第 2 章我们给灰度、RGB、RGBA 混了个脸熟（也埋下了 RGB→灰度的加权公式），第 3 章学会了在 image 和 ndarray 之间搬运像素。但真到工程现场——从摄像头拿到的一帧往往不是 RGB 而是 NV12；用 OpenCV 读到的图通道顺序是 BGR；要喂给模型的张量又必须是 CHW 排列。本章把“同一堆颜色为什么有这么多种摆法“彻底讲透：色彩空间解决“颜色怎么表达“，内存布局解决“字节怎么摆放“。学完你能亲手把一帧 NV12 转成 RGB，也能一眼看穿“红蓝反了“这类经典事故。（本章只讲颜色的表示与摆放；JPEG 怎么压缩留到第 5 章，视频码流留到第 6 章，完整的喂模型预处理链留到第 10 章。）

学习目标：

  • 说清 RGB / BGR / Gray / HSV / YUV 各自解决什么问题，选型不再靠猜
  • 理解色度下采样 4:4:4 / 4:2:2 / 4:2:0 的含义，能算出各自省了多少数据
  • 看懂并画出一帧 NV12 / I420 在内存里的字节布局（planar vs semi-planar）
  • 分清 packed(HWC) 与 planar(CHW)，能手算同一张图两种布局下的字节顺序
  • 能独立写出、看懂一段把 NV12 buffer 转成 RGB 的 Rust 代码

4.1 为什么会有这么多“色彩空间“

第 2 章说过，色彩空间就是“颜色 ↔ 数字“的解读规则。可为什么不统一用一种，非要搞出一堆？

打个比方：描述同一个人，身份证用“姓名 + 身份证号“，医院用“血型 + 身高体重“，公司用“工号 + 职位“。同一个人，不同场景选不同的“坐标系“来描述，是因为每个场景关心的东西不一样。颜色也是如此——没有“最好“的色彩空间，只有“最适合当前任务“的。

需求场景常用色彩空间为什么是它
屏幕显示、拍照存图RGB / BGR显示器就是红绿蓝三色灯珠，天生说 RGB
人手动调色、按颜色筛选HSV / HSL把“什么颜色、多鲜艳、多亮“拆成三个独立旋钮
只关心明暗的传统算法灰度 Gray单通道，省 2/3 数据，抗光照干扰
视频存储与传输YUV / YCbCr亮度、色度分家，色度可降采样省带宽
喂给深度学习模型RGB（且 CHW 排列）模型训练时就是这么喂的，输入必须对齐

记住一句话：换色彩空间不改变“这是什么颜色“，只改变“用哪几个数字、怎么算出来“。 就像同一个地点，可以用经纬度描述，也可以用“某地铁站 3 号口向北 200 米“描述——地点没变，描述方式变了。

4.2 RGB vs BGR：内容相同，只是顺序不同

先澄清一个新手最容易误解的点：RGB 和 BGR 不是两种颜色，是同一堆数字的两种排列顺序。

  • RGB：一个像素按 (R, G, B) 存，红在前。
  • BGR：同一个像素按 (B, G, R) 存，蓝在前。
同一个"橙色"像素 (R=255, G=128, B=0)：

  按 RGB 顺序存：  255  128    0
  按 BGR 顺序存：    0  128  255

三个数值 255、128、0 一个没变，只是摆放的位置换了。
但如果把 BGR 的 (0, 128, 255) 当成 RGB 去读 →
就变成 (R=0, G=128, B=255) = 蓝青色！橙色瞬间变蓝。

第 2.3 节讲过，OpenCV 默认用 BGR 是个历史包袱。这件事的杀伤力在工程里是巨大的：你辛辛苦苦搭好的目标检测流水线，用 OpenCV（或它的 Rust 绑定 opencv crate）读进来一帧 BGR，忘了转换就直接喂给 YOLO 模型。模型训练时看的是 RGB，现在收到的每一张都“红蓝互换“，等于给它戴了副滤镜看世界——person 的肤色发蓝、消防车变青，置信度普遍暴跌，却又不报任何错。这是视觉工程新人排第一名的隐形 bug。

怎么判断通道顺序对不对

  1. 看数据来源。这是最靠谱的：image::open() 给你 RGB；OpenCV 的 imread / 视频解码给你 BGR；很多硬件相机给你 YUV/NV12（见 4.7）。先问清楚“这帧从哪来“。
  2. 看画面症状。红蓝反了有典型表现：蓝天变橙黄、人脸/肤色发青、绿色植物基本不变（因为 G 在中间没动）。找画面里颜色已知的东西（天空、皮肤、交通标志）对一下。
  3. 打印一个已知像素。拍一张纯红色卡片，读中心像素：若打印出来是 (255, 0, 0) 就是 RGB，是 (0, 0, 255) 就是 BGR。

怎么纠正

纠正非常简单——把每个像素的第 0 和第 2 个字节交换即可：

/// 把 packed 的 BGR 字节流原地翻转成 RGB（3 通道交错，HWC）。
/// 原理：每 3 个字节是一个像素 [B, G, R]，交换首尾 → [R, G, B]。
fn bgr_to_rgb_inplace(buf: &mut [u8]) {
    for px in buf.chunks_exact_mut(3) {
        px.swap(0, 2); // 交换 B 和 R，中间的 G 不动
    }
}

工程建议：在系统边界统一色彩空间。 数据一进来就转成 RGB，整条流水线中间只认 RGB，要输出给 OpenCV 显示时再转回 BGR。别让“这一帧到底是 RGB 还是 BGR“的疑问散落在代码各处——那是灾难的源头。

4.3 灰度 Gray：丢掉颜色，只留明暗

灰度图每个像素只有一个值（0~255，0 黑 255 白），字节数只有 RGB 的三分之一。

什么时候用它？答案是大量场景：

  • 传统图像算法：边缘检测、阈值二值化、形态学、模板匹配、轮廓查找（第 7、8 章），基本都只吃单通道明暗，颜色反而是干扰。
  • 部分模型只吃灰度：一些 OCR 文字识别、某些人脸特征提取、深度/红外相机的输出，输入就是单通道。
  • 省资源：内存和计算量直接砍到 1/3，实时流水线里很值钱。

灰度常用的转换公式如下（ITU-R BT.601 加权，绿色权重最大是因为人眼对绿光最敏感）：

$$Gray = 0.299R + 0.587G + 0.114B$$

一个容易被忽略的坑：“灰度“不是唯一定义的。 有的库用上面的加权，有的图库用简单平均 (R+G+B)/3，还有的用 BT.709（高清标准，系数是 0.2126 / 0.7152 / 0.0722）。跨库比对结果时，几个灰度值差一两级往往就是它——不是 bug，是标准不同。工程上认准一个标准从头用到尾即可。

4.4 HSV / HSL：按“颜色“思考

RGB 对显示器友好，对人脑不友好。你想“把这个红调淡一点、暗一点“，在 RGB 里得三个数一起动，几乎没法凭直觉调。HSV 把颜色按人的直觉拆成三个独立旋钮：

H (Hue) 色相：       是什么颜色？  红/橙/黄/绿/青/蓝/紫，绕一圈 0°~360°
S (Saturation) 饱和度：颜色浓还是淡？0 = 灰扑扑，100% = 最鲜艳
V (Value) 明度：      颜色亮还是暗？0 = 纯黑，100% = 最亮

H (色相): 0° ─ 60° ─ 120° ─ 180° ─ 240° ─ 300° ─ 360°
          红    黄     绿      青      蓝      品红    红(回到起点)

注意 H 是环形的：红色同时在 0° 和 360°（首尾相接）。这个“接缝“是按颜色筛选时的头号坑，下面就会碰到。

HSV 和 HSL 有什么区别？ 两者都以 H、S 开头，差别在第三个：

第三个分量含义直觉
HSVV 明度V=0 全黑，V=100% 该色最亮像调“台灯亮度“
HSLL 亮度L=0 全黑，L=50% 该色最鲜艳，L=100% 全白像“往颜料里兑黑或兑白“

图像处理里 HSV 更常用（尤其颜色阈值分割），HSL 在设计/前端调色里更常见。会一个，另一个看一眼就懂。

它为什么适合“按颜色筛选“？ 假设要在画面里找出所有红色物体。在 RGB 里，阳光下的亮红 (255,80,80) 和阴影里的暗红 (120,20,20) 数值差了十万八千里，根本没法用一个范围框住。而在 HSV 里，红色的 H 永远在 0° 附近，无论明暗，你只要卡 H 的范围就行，亮度和浓淡交给 S、V 去容忍：

提取红色（以 OpenCV 的 H∈[0,179] 刻度为例）：
  红色跨越 0° 接缝，所以要两段并起来：
    段一： H ∈ [0, 10]    且 S > 100 且 V > 60
    段二： H ∈ [170, 179] 且 S > 100 且 V > 60
  两段的掩码取"或"，就把亮红、暗红一网打尽。

这里藏着一个真实的跨库坑：H 的取值范围各库不一样。 标准 HSV 的 H 是 0~360°，但 OpenCV 为了把 H 塞进一个 u8，把它压成了 0~179（除以 2），S、V 则是 0~255。你在别处查到“红色 H≈0 或 360“的结论，搬到 OpenCV 得记得除以 2。传统颜色分割的完整玩法（形态学清理掩码等）留到第 8 章，这里先建立直觉。

4.5 YUV / YCbCr：亮度与色度分家

从工程角度看，YUV 把一个颜色拆成两部分：

  • Y（luma，亮度）：这个像素有多亮。它基本就是灰度值——Y 的算法和 4.3 的加权灰度几乎一模一样。
  • U、V（chroma，色度）：颜色往哪偏。U 是蓝色差、V 是红色差（“色差”= 颜色减去亮度后剩下的部分）。

术语澄清：严格说 YUV 是模拟电视时代的叫法，YCbCr 是数字时代的叫法（Cb 对应 U、Cr 对应 V）。工程里两者常被混用，本书统一叫 YUV，遇到 Cb/Cr 知道是一回事即可。

RGB 转 YUV 的一组标准系数（BT.601，视频常用的 studio/limited range）：

Y =  0.257·R + 0.504·G + 0.098·B + 16     ← 加权和，就是"亮度"
U = -0.148·R - 0.291·G + 0.439·B + 128    ← 蓝色差，灰色时正好 = 128
V =  0.439·R - 0.368·G - 0.071·B + 128    ← 红色差，灰色时正好 = 128

一个直觉检查：纯灰像素 R=G=B 时，U、V 恰好都等于 128（中心值）——因为灰色“不偏任何颜色“。这也是为什么色度的“零点“是 128 而不是 0。

分家的意义在这句话：人眼对亮度 Y 敏感，对色度 U/V 迟钝。 图像的轮廓、细节、清晰度几乎全在 Y 里；U、V 只负责“往轮廓里涂颜色“，涂糙一点人眼根本看不出来。既然色度可以“糊“，那就没必要给它和亮度一样多的数据——这就直接引出了下一节。

4.6 色度下采样：4:4:4 / 4:2:2 / 4:2:0

色度下采样（chroma subsampling）：亮度 Y 按全分辨率存，色度 U/V 用更低的分辨率存，省下的就是纯赚的带宽。记号写成 J:a:b，含义可以这样通俗理解——在一个 4 像素宽、2 像素高的样本块里：

  • 4 = 一行取 4 个亮度（永远全取）；
  • a = 第一行里取几个色度；
  • b = 第二行相对第一行还变不变（0 = 第二行不再单独取，跟着第一行）。
记号色度分辨率每像素平均比特通俗说法用在哪
4:4:4和亮度一样（全）24 bpp色度一点不省专业采集、图像编辑
4:2:2横向减半16 bpp左右两像素共享色度广播、中高端采集卡
4:2:0横竖都减半12 bpp每 2×2 像素共享一组色度绝大多数消费视频/照片

算笔账（一帧 4×4 = 16 像素，8-bit）：

4:4:4：Y 16 + U 16 + V 16 = 48 字节
4:2:2：Y 16 + U 8  + V 8  = 32 字节  （色度横向减半）
4:2:0：Y 16 + U 4  + V 4  = 24 字节  （色度只剩 1/4，总量砍到一半）

4:2:0 是事实标准：JPEG、H.264、H.265、你手机拍的每段视频、每张照片，默认几乎都是它。它把数据砍掉近一半，人眼却几乎无感——这买卖太划算。（它具体怎么和压缩配合，留给第 5、6 章；本章只关心“色度被砍成 1/4 后，这些字节在内存里怎么摆“。）

4.7 NV12 与 I420：一帧 YUV 在内存里长什么样

同样是 4:2:0，“那些字节摆在内存里的顺序“还能有好几种花样，最常见的是 I420 和 NV12。它们的区别是一个新的、极其重要的概念——平面（plane）结构：

  • planar（平面式）：每个分量各占一整块连续内存。I420 就是 Y 一整块、U 一整块、V 一整块，共 3 个平面。
  • semi-planar（半平面式）：Y 单独一块，U 和 V 挤在一块里交错排列。NV12 就是 Y 一块、UV 交错一块，共 2 个平面。

以一帧 4×4 的画面为例（4:2:0，共 4×4×3/2 = 24 字节），先看 NV12：

① Y 平面（亮度，全分辨率）—— 16 字节，一个像素一个 Y
     行0:  Y0   Y1   Y2   Y3
     行1:  Y4   Y5   Y6   Y7
     行2:  Y8   Y9   Y10  Y11
     行3:  Y12  Y13  Y14  Y15

② UV 平面（色度，1/4 分辨率，U、V 两两交错）—— 8 字节
     行0:  U0 V0   U1 V1
     行1:  U2 V2   U3 V3

   每一对 (U,V) 覆盖一个 2×2 的 Y 方块：
     (U0,V0) ← Y0  Y1  Y4  Y5      (U1,V1) ← Y2  Y3  Y6  Y7
     (U2,V2) ← Y8  Y9  Y12 Y13     (U3,V3) ← Y10 Y11 Y14 Y15

内存里其实是一条直线（先整个 Y 平面，紧接着整个 UV 平面）：
   偏移 0                              16                          24
       [ Y0 Y1 Y2 ... Y14 Y15 ][ U0 V0 U1 V1 U2 V2 U3 V3 ]
         └──── 16 字节亮度 ────┘ └──── 8 字节交错色度 ────┘

再看同一帧的 I420（又叫 YU12）——Y、U、V 三块各自独立，色度不交错：

   偏移 0                    16              20              24
       [ Y0 Y1 ... Y15 ][ U0 U1 U2 U3 ][ V0 V1 V2 V3 ]
         └── Y 平面 16B ┘  └ U 平面 4B ┘  └ V 平面 4B ┘

对比一下几种同为 4:2:0 的常见格式，它们总字节数完全相同（都是 12 bpp），只是摆放不同：

格式平面结构色度排列常见出处
I420Y + U + V（3 平面 planar）先整块 U，再整块 VFFmpeg 的 yuv420p、许多软解码器
YV12Y + V + U（3 平面 planar）先整块 V，再整块 U（和 I420 反）部分播放器
NV12Y + UV（2 平面 semi-planar）U V U V 交错硬件解码器、GPU、Windows 相机
NV21Y + VU（2 平面 semi-planar）V U V U 交错（和 NV12 反）Android 相机默认输出

为什么会有 NV12 这种“半平面“？ 因为硬件（相机 ISP、GPU、视频解码芯片）读写交错的 UV 更高效，一次内存访问就能同时拿到一对色度。所以从摄像头、硬件解码器直接拿到的帧，十有八九是 NV12 或 NV21，而不是你以为的 RGB。这正是下一节要动手转换它的原因。

4.8 packed vs planar：HWC 与 CHW

上一节的 planar / semi-planar 其实是一个通用概念，RGB 也有同样的两种摆法。这是本章连接第 10 章的关键，务必吃透。

  • packed（打包 / 交错，也叫 interleaved）：一个像素的几个通道挨在一起，一个像素一个像素地排。RGB 就是 R G B R G B R G B…。这对应张量形状 HWC（Height, Width, Channel，通道在最后）。图片文件、相机、image crate 给你的，通常都是这种。
  • planar（平面 / 通道分离）：先把所有像素的 R 排完，再排所有 G，再排所有 B，即 R R R… G G G… B B B…。这对应张量形状 CHW（Channel, Height, Width，通道在最前）。许多以 PyTorch 为基础的视觉模型使用 CHW planar——包括我们的主模型 YOLOv8，输入张量就是 1×3×640×640（第 3.7 节用 permuted_axes 做过这个转换）。也有模型和运行时使用 NHWC，最终应以模型实际输入 shape 为准。

用一张 2×2 的 RGB 小图手算一遍，把两种布局的字节顺序摆出来。四个像素取好记的值：

      列0            列1
行0  (10,11,12)   (20,21,22)      ← 每个括号是 (R, G, B)
行1  (30,31,32)   (40,41,42)

packed（HWC，RGBRGB… 交错）——像素为单位：
  [ 10 11 12 | 20 21 22 | 30 31 32 | 40 41 42 ]
     像素00     像素01     像素10     像素11
  索引公式： byte[(y*W + x)*3 + c]

planar（CHW，通道分离）——通道为单位：
  [ 10 20 30 40 | 11 21 31 41 | 12 22 32 42 ]
      R 平面         G 平面         B 平面
  索引公式： byte[c*(H*W) + y*W + x]

盯着看会发现：两行方括号里都是那 12 个数字，一个不多一个不少，只是排列顺序彻底不同。 内容一样、顺序不同——这和 4.2 节的 RGB/BGR、4.7 节的 NV12/I420 是同一个道理，只不过这次换的是“通道 vs 像素谁在外层循环“。

工程含义：从图片/相机拿到的是 packed（HWC），模型要的是 planar（CHW），中间必须转一次布局。这次转换加上归一化、letterbox 等一整套动作，就是第 10 章“模型预处理“的主线。本章先让你彻底看清“字节到底怎么摆“。

4.9 NV12 → RGB：公式、手算与 Rust 实现

现在把前面串起来：拿到一帧硬件给的 NV12，怎么变回 RGB？分两步——取值（按 4.7 的布局找到每个像素的 Y、U、V）+ 换算（用公式把 YUV 算成 RGB）。

换算用 4.5 那组系数的逆运算（BT.601，limited range）：

$$ \begin{aligned} R &= 1.164(Y-16) + 1.596(V-128) \ G &= 1.164(Y-16) - 0.392(U-128) - 0.813(V-128) \ B &= 1.164(Y-16) + 2.017(U-128) \end{aligned} $$

先用一组小数字手算一个像素，取 Y=150, U=100, V=170：

先算三个中间量：
  C = Y - 16  = 134
  D = U - 128 = -28     （U<128 → 偏黄/偏绿）
  E = V - 128 =  42     （V>128 → 偏红）

R = 1.164×134 + 1.596×42
  = 155.98 + 67.03 = 223.01           → 223
G = 1.164×134 - 0.392×(-28) - 0.813×42
  = 155.98 + 10.98 - 34.15 = 132.81   → 132
B = 1.164×134 + 2.017×(-28)
  = 155.98 - 56.48 = 99.50            → 99

得到 RGB = (223, 132, 99)，一个暖橙色的肤色调。
合理：V 偏大(偏红)、U 偏小，算出来果然是暖色。✔
（注意箭头处是 `as u8` 的截断取整：132.81 直接砍成 132，不是四舍五入的 133；
  想四舍五入可在转 u8 前加 `.round()`。这点第 2 章提过。）

注意 R、G、B 算出来可能超过 255 或小于 0（比如某些极端色度），所以最后一定要夹紧到 0~255，否则 as u8 会发生数值回绕（256 变成 0），画面出现诡异的彩色噪点。这是转换代码最容易漏的一步。

下面是完整的 Rust 实现。它不依赖任何外部 crate，输入 Y 平面和交错 UV 平面的字节切片，输出 packed RGB（HWC）：

/// 把一帧 NV12 图像转成 packed RGB（HWC，R G B 交错）。
///
/// NV12 内存布局（4:2:0，半平面）：
///   - y_plane ：亮度平面，全分辨率，长度应为 width*height
///   - uv_plane：色度平面，U、V 交错，长度应为 width*height/2
///   - width、height：图像宽高，都应为偶数（4:2:0 的前提）
///
/// 返回：长度为 width*height*3 的 RGB 字节流（HWC 布局）。
fn nv12_to_rgb(y_plane: &[u8], uv_plane: &[u8], width: usize, height: usize) -> Vec<u8> {
    // 输出缓冲：每像素 3 字节（R, G, B），先填 0
    let mut rgb = vec![0u8; width * height * 3];

    for row in 0..height {
        for col in 0..width {
            // ① 取亮度 Y：Y 平面是全分辨率，直接按 行*宽 + 列 定位
            let y = y_plane[row * width + col] as f32;

            // ② 取色度 U、V：色度是 1/4 分辨率，每 2×2 像素共用一对，
            //    所以坐标整除 2 定位到色度网格
            let c_row = row / 2;
            let c_col = col / 2;
            //    NV12 里 U、V 交错，一对占 2 字节（U 在前 V 在后）；
            //    每行色度共有 width/2 对 = width 个字节，故行跨度是 width
            let uv_idx = c_row * width + c_col * 2;
            let u = uv_plane[uv_idx] as f32;
            let v = uv_plane[uv_idx + 1] as f32;

            // ③ BT.601（limited range）YUV → RGB
            let c = y - 16.0;
            let d = u - 128.0;
            let e = v - 128.0;
            let r = 1.164 * c + 1.596 * e;
            let g = 1.164 * c - 0.392 * d - 0.813 * e;
            let b = 1.164 * c + 2.017 * d;

            // ④ 夹紧到 0~255 再转 u8，避免溢出回绕
            let out = (row * width + col) * 3;
            rgb[out]     = r.clamp(0.0, 255.0) as u8; // R
            rgb[out + 1] = g.clamp(0.0, 255.0) as u8; // G
            rgb[out + 2] = b.clamp(0.0, 255.0) as u8; // B
        }
    }
    rgb
}

几点说明：

  1. uv_idx 是全章最绕的一行，对照 4.7 的图理解：色度平面每行有 width 个字节（width/2 对 U、V），所以第 c_row 行的起点是 c_row * width，第 c_col 对的 U 在 + c_col*2，V 紧跟其后 +1。
  2. 这里用 f32 是为了看得懂；工程上通常改成定点整数运算（把系数乘 256 变成整数，最后右移 8 位）避免浮点开销，量大时还会上 SIMD 或直接丢给 GPU。
  3. 想支持 NV21（Android 相机默认），只需把 u 和 v 的取值对调（先 V 后 U），其余不变——这也再次说明“内容相同、顺序不同“这条贯穿全章的主线。
  4. 得到的 RGB 是 packed(HWC)。要喂模型还得转成 planar(CHW) 并归一化，那是第 10 章的活。

4.10 小结

  • 色彩空间是“颜色 ↔ 数字“的坐标系，没有最好只有最合适：显示用 RGB、调色/按色筛选用 HSV、只看明暗用 Gray、视频传输用 YUV、喂模型用 RGB+CHW。
  • RGB 与 BGR 只是通道顺序不同，内容完全一样；OpenCV 默认 BGR 是新手头号坑，判断靠“看来源 + 看症状 + 打印已知像素“，纠正就是每像素 swap 首尾字节，且应在系统边界统一。
  • YUV 把颜色拆成亮度 Y 与色度 U/V；人眼对 Y 敏感、对 UV 迟钝，于是色度下采样 4:2:0 把 UV 砍到 1/4、总量减半而人眼几乎无感，是视频/照片的事实标准。
  • 同为 4:2:0，I420 是三平面 planar（Y/U/V 分开），NV12 是两平面 semi-planar（Y + 交错 UV）；字节总数相同，只是摆放不同，硬件多输出 NV12/NV21。
  • packed(HWC，RGBRGB 交错) vs planar(CHW，通道分离) 是同一堆数字的两种排列；模型要 CHW planar，这条直通第 10 章预处理。
  • NV12→RGB = 按布局取 Y/U/V + BT.601 公式换算 + 夹紧到 0~255；本章给出了能直接编译的 Rust 函数。
