机器视觉工程实战：用 Rust 看懂图像与模型

第 10 章 · 模型预处理全解：letterbox、归一化与张量布局

本章导读：第 3 到第 9 章，我们学会了读图、认识色彩空间、做滤波和几何变换——我们已经能把一张图像“玩“得很熟。但模型不吃图像，它只吃张量（tensor，多维数字数组）。本章就是从“图像世界“通往“模型世界“的那道闸门：把一张任意尺寸的照片，变成 YOLOv8 张口就认的 1×3×640×640、RGB、归一化到 0~1 的 f32 连续张量。读完这一章，你会写出一个可复用的 preprocess 函数（第 14、16、26 章会反复调用它），并且深刻理解一件事——预处理只要有一步和训练时不一样，模型精度就会悄悄崩掉，而且不报错。这也是新手最难查的坑之一。

10.1 预处理是什么，为什么必须和训练时“分毫不差“

先打个比方。模型就像一台极其挑食、又不会说话的自动贩卖机：它只认一种硬币——直径必须是 640、材质必须是 RGB、面值必须缩到 0~1。你塞一枚差不多大小、差不多材质的硬币进去，它不会“报错弹出来“，而是照收不误，然后给你一瓶过期饮料。这就是预处理最可怕的地方：做错了不会崩，只会让结果悄悄变差。

预处理（preprocessing），就是把你手上的原始图像，一步步改造成模型训练时“见过的那个样子“。模型在训练阶段，喂进去的每一张图都经过了一套固定的加工流水线：缩放到固定尺寸、固定的颜色通道顺序、固定的归一化方式、固定的内存布局。模型学到的所有“知识“，都是建立在这套流水线的输出之上的。推理（inference，用训练好的模型做预测）时，你必须用一模一样的流水线，模型才认得。

哪些地方错了会翻车？我们列个表，感受一下“错一个就完蛋“的严重性：

环节训练时你推理时（错误示范）后果
尺寸letterbox 到 640×640直接拉伸到 640×640物体被压扁，框全偏
颜色顺序RGB喂了 BGR红蓝互换，置信度暴跌、漏检
归一化像素 /255 到 0~1忘了除、还是 0~255数值大 255 倍，输出全是垃圾
归一化只 /255又减了 ImageNet 均值数值整体偏移，精度下降
布局CHW喂了 HWC引擎按错误维度解读，结果乱套

注意最阴险的一点：这些错误全都不会让程序崩溃。张量形状可能还是对的（比如 HWC 和 CHW 元素个数一样多），/255 忘了也只是数值大一点——程序照跑，只是检测框莫名其妙地偏、漏、乱。很多新手对着后处理代码查一整天，其实错在预处理第一步。

工程铁律：拿到一个模型，第一件事不是写推理，而是问清楚它的预处理要求——输入尺寸、是 RGB 还是 BGR、怎么归一化、要不要减均值。这些信息在模型的文档、导出脚本，或元数据里（第 12 章会讲怎么读模型元数据）。宁可多问一句，不要瞎猜一次。

本书的主模型 YOLOv8，预处理要求非常明确，本章后面都围绕它展开：

  • 尺寸：letterbox 到 640×640（等比缩放 + 灰边填充，不拉伸）；
  • 颜色：RGB；
  • 归一化：像素值 /255，缩到 0~1（不减 ImageNet 均值方差）；
  • 布局：CHW，最外面再加一个 batch 维，最终 1×3×640×640，f32。

10.2 完整预处理链概览

先看全景。一张原图要经过下面这条流水线，才能变成模型的输入张量：

┌───────────────────┐
│   原图             │  任意尺寸(如 1920×1080)，HWC 布局，u8，RGB 或 BGR
└─────────┬─────────┘
          │  ① letterbox：等比缩放 + 灰边(114)填充
          ▼
┌───────────────────┐
│  方形图 640×640    │  仍是 HWC / u8
│  记下 (scale,     │  ★ 这三个数一定要存下来，
│   pad_x, pad_y)   │    第 16 章把框还原回原图全靠它
└─────────┬─────────┘
          │  ② 颜色顺序：调成模型要的 RGB(YOLOv8 用 RGB)
          ▼
┌───────────────────┐
│  RGB 640×640 u8   │
└─────────┬─────────┘
          │  ③ 归一化：每个像素值 /255 → 0~1(变成 f32)
          ▼
┌───────────────────┐
│  f32 640×640 HWC  │  值域 0~1
└─────────┬─────────┘
          │  ④ 布局转换：HWC → CHW(把三个通道拆成三张平面)
          ▼
┌───────────────────┐
│  f32 3×640×640    │  CHW / planar
└─────────┬─────────┘
          │  ⑤ 加 batch 维：最前面补一个 N=1
          ▼
┌───────────────────┐
│ f32 1×3×640×640   │  NCHW，行主序连续内存 → 交给推理引擎(第 14 章)
└───────────────────┘

五步：缩放 → 颜色 → 归一化 → 布局 → 加 batch。下面逐个拆解。真正写代码时（10.8 节）这几步会揉在一起、一次遍历完成，但思路上要分得清清楚楚。

10.3 尺寸：直接 resize 会变形，letterbox 不变形

模型的输入尺寸是固定死的（YOLOv8 是 640×640）。可现实里的图什么比例都有：1920×1080 的监控、竖着拍的手机照、正方形的头像。怎么把它们统一塞进 640×640？有两条路。

直接 resize：简单，但会“压扁“

最省事的做法是直接把图拉伸到 640×640。问题是：原图 1920×1080 是 16:9 的宽扁形，硬塞进 1:1 的正方形，等于把它在竖直方向拉高——人会变胖、车会变短。

打个比方：这就像把一张 A4 纸横过来、硬塞进一个正方形相框，图案必然扭曲。模型训练时如果没见过这种扭曲（YOLOv8 训练用的正是 letterbox），推理时喂扭曲图，它对形状的判断就全乱了，框的长宽比也跟着错。所以检测任务几乎从不用直接 resize。

letterbox：等比缩放 + 灰边填充

letterbox（意为“信箱“，等比缩放后用灰边把剩余空间填满到目标尺寸）是检测任务的标准做法。名字来自宽电影在 4:3 电视上播放时，上下加的黑边——形状没变，只是补了边。

它分两步：

  1. 等比缩放：宽、高用同一个缩放系数，保证不变形。系数取“宽方向能缩多少“和“高方向能缩多少“里较小的那个，这样缩放后长边刚好贴到 640，短边还留有空间。
  2. 灰边填充：短边留下的空隙，用灰色 114 填满，凑成 640×640 的正方形。

为什么是 114？这是 YOLO 系列约定俗成的填充值（灰色，(114,114,114)）。训练时用的就是它，推理必须一致。灰色是“中性“的，不像纯黑纯白那样容易被模型误当成物体边缘。

手算一遍：1920×1080 → 640×640

光说不练假把式，我们把这条最常见的监控分辨率算到底。设原图宽 1920、高 1080，目标 640×640。

第一步，算缩放系数 scale：

$$ \text{scale} = \min\left(\frac{640}{1920},; \frac{640}{1080}\right) = \min(0.3333,; 0.5926) = 0.3333 $$

取较小的 0.3333（因为宽是长边，它更“吃紧“，得听它的）。

第二步，算缩放后尺寸：

  • 新宽 = 1920 × 0.3333 ≈ 640
  • 新高 = 1080 × 0.3333 ≈ 360

所以先把图缩成 640×360（还是 16:9，没变形）。

第三步，算填充（pad）：

  • 宽方向：640 − 640 = 0，左右各填 pad_x = 0；
  • 高方向：640 − 360 = 280，上下平分，各填 pad_y = 140。

也就是：640×360 的图居中放进 640×640 的画布，上面 140 行、下面 140 行是灰边。示意：

     0 ────────────── 640 (x)
   0 ┌────────────────┐
     │  灰边 pad_y=140 │   ← 顶部 140 行灰色(114)
 140 ├────────────────┤
     │                │
     │  真实图像       │   ← 640×360 的缩放图放这儿
     │  640×360       │
 500 ├────────────────┤
     │  灰边 pad_y=140 │   ← 底部 140 行灰色(114)
 640 └────────────────┘
     (y)

★ 最关键的一句话：scale = 0.3333、pad_x = 0、pad_y = 140 这三个数，必须存下来。因为模型吐出来的检测框坐标，是在这张 640×640 的画布里的；要还原回原图 1920×1080 的真实坐标，就得反着算一遍：

$$ x_{\text{原图}} = \frac{x_{\text{模型}} - \text{pad_x}}{\text{scale}}, \qquad y_{\text{原图}} = \frac{y_{\text{模型}} - \text{pad_y}}{\text{scale}} $$

比如模型说某个框的左上角在 (100, 240)，还原回原图就是 $((100-0)/0.3333,\ (240-140)/0.3333) = (300,\ 300)$。这套还原逻辑第 16 章会详细展开，本章你只需要记住：letterbox 参数是预处理留给后处理的“回执“，一定要存。我们稍后用 LetterboxInfo 结构体把它打包。

（等比缩放里“新的像素值怎么由旧像素插值算出来“，属于几何变换的插值原理，详见第 9 章；本章只关心缩放到多大、怎么填边。）

10.4 颜色顺序：RGB 还是 BGR，必须对上模型

图像的三个颜色通道，排列顺序有两种主流约定：RGB（红绿蓝）和 BGR（蓝绿红）。这俩的区别、以及各种色彩空间的内存细节，第 4 章讲透了，这里只强调预处理必须对上模型这一点。

坑在哪？两个常见来源：

  • image crate：读进来的 RgbImage 本来就是 RGB 顺序——和 YOLOv8 要的一致，省心。本书 preprocess 的入参就是 &RgbImage，天然对齐。
  • OpenCV：imread 读出来是 BGR 顺序（历史原因）。如果你从 OpenCV 那边拿数据喂 YOLOv8，必须先把 B 和 R 换回来，否则红蓝颠倒——消防车会变成蓝色的怪东西，模型置信度直接崩、大面积漏检。

判断依据很简单：看模型训练时用了什么。YOLOv8 官方用 RGB，所以我们全程 RGB。有的老模型（尤其从 Caffe/OpenCV 生态出来的）要 BGR，就得换。换法无非是把三个通道的第 0 和第 2 调个位置，很便宜，但不能忘。

一句话记忆：image 给你 RGB，OpenCV 给你 BGR；喂模型前先确认它要哪个。本书统一 RGB。

10.5 归一化：把像素缩到模型认识的范围

原始像素值是 0~255 的整数（u8）。但神经网络内部做的是浮点乘加，喜欢小而集中的数。如果直接把 0~255 灌进去，数值太大，容易让网络内部的计算“爆表“。所以训练时都会做归一化（normalization），把像素缩到一个小范围。有两种主流方式。

方式一：/255，缩到 0~1（YOLOv8 用这个）

最简单：每个像素值除以 255。

$$ x’ = \frac{x}{255} $$

一个亮红像素 R=200，归一化后就是 $200/255 \approx 0.784$。全部落在 0~1 之间，干净利落。YOLOv8 用的就是这一种，没有额外的减均值操作。本书的 preprocess 也只做这一步。

方式二：(x/255 − mean)/std，均值方差标准化

很多分类模型（ResNet 等，第 15 章会用到）走得更远：在 /255 之后，再逐通道减去均值、除以标准差，让每个通道的数值大致“以 0 为中心“。

$$ x’ = \frac{x/255 - \text{mean}}{\text{std}} $$

最常见的是 ImageNet（一个百万级图像数据集）统计出来的均值方差，几乎成了行业默认值（顺序为 RGB）：

通道meanstd
R0.4850.229
G0.4560.224
B0.4060.225

手算一遍：一个像素，两种归一化

取一个像素 RGB = (200, 128, 50)，分别用两种方式算。

方式一（/255）：

  • R: 200 / 255 ≈ 0.784
  • G: 128 / 255 ≈ 0.502
  • B: 50 / 255 ≈ 0.196

方式二（ImageNet 标准化，在方式一基础上继续算）：

  • R: (0.784 − 0.485) / 0.229 = 0.299 / 0.229 ≈ 1.306
  • G: (0.502 − 0.456) / 0.224 = 0.046 / 0.224 ≈ 0.205
  • B: (0.196 − 0.406) / 0.225 = −0.210 / 0.225 ≈ −0.933

对比一下就明白差别了：方式一永远落在 0~1；方式二可以大于 1、也可以是负数（因为它是“以 0 为中心“的分布）。

这正是最坑的地方：如果你的模型训练时用的是方式二，你却只做了方式一（忘了减均值除方差），数值整体偏了一大截，模型精度悄悄下滑——它不会报错。反过来同理。所以归一化方式必须逐字对上模型要求：几个数、减不减均值、mean/std 具体是多少、通道顺序对不对。查清楚，别猜。

记住本书的设定：YOLOv8 = 只 /255。下面的代码就这么写。

10.6 布局转换：HWC → CHW，模型要“三张平面“

现在数值对了，还差最后一道形状上的改造：内存布局。

图像在内存里最自然的排法是 HWC（Height×Width×Channel）：一个像素的 R、G、B 三个值挨在一起存，一个像素接一个像素。第 4 章把这个“交错存储“讲得很细。

而模型（以及绝大多数推理引擎）要的是 CHW（Channel×Height×Width），也叫 planar（平面式）：把红色通道所有像素单独存成一张平面，绿色一张，蓝色一张，三张平面叠起来。示意：

HWC（交错，像素为单位）        CHW（平面，通道为单位）
R G B  R G B  R G B ...        R R R R ... (整张红平面)
└像素0┘└像素1┘└像素2┘          G G G G ... (整张绿平面)
                               B B B B ... (整张蓝平面)

为什么模型要 CHW？ 因为卷积（神经网络的核心运算，第 11 章讲）是逐通道在整张平面上滑动计算的，把同一通道的像素连续摆好，内存访问更规整、缓存更友好、也方便 SIMD/GPU 并行。这是深度学习框架的历史约定，我们照做即可（HWC 与 CHW 的内存细节详见第 4 章）。

所以要做一次 HWC → CHW 的重排：把原来交错的 R/G/B，拆开、按通道归拢。代码里可以显式遍历着写（10.8 节就是这么干的，一次循环里顺便完成），也可以用 ndarray 的轴重排 permuted_axes ——但后者有个坑，下一节讲。

10.7 batch 维、数据类型与内存连续

加一个 batch 维：NCHW

CHW 之上，模型输入最外层还要再套一个维度 N（batch，一批几张图），凑成 NCHW。因为模型天生支持“一次推理一批图“，第 0 维就是这一批的张数。

本书全程 N = 1（一次处理一张图/一帧），所以最终形状是 1×3×640×640。加 batch 维在代码里就是把 CHW 的 [3,640,640] 变成 [1,3,640,640]——形状最前面多个 1，数据一个不变。

一次喂多张图（N>1）能显著提高吞吐（GPU 尤其明显），这叫 batch 推理，第 13 章讲模型转换和 batch 适配时会展开。本章知道“有这么个维度、我们取 1“就够了。

数据类型：f32

模型的输入类型基本都是 f32（32 位浮点）。我们归一化时把 u8 除以 255，结果天然就是浮点，用 f32 存正好。（少数量化模型吃 int8，那是另一套流程，本书主线不涉及。）

内存连续：行主序 + as_standard_layout

最后一个容易被忽略、但一旦踩到就很懵的点：内存必须连续。

推理引擎（第 14 章的 tract / ort）拿到张量后，往往直接把它当成一段连续的内存来读。它默认这段内存是行主序（row-major，C 顺序）连续排列的：最后一个维度变化最快，一行接一行铺下去。

如果你用 ndarray 的 permuted_axes 来做 HWC→CHW，会有个陷阱——它只是换了“看数据的角度“，底层内存一个字节都没动，得到的是一个非连续视图：

use ndarray::Array3;

// 假设已有一个 HWC 的 f32 数组，形状 [640, 640, 3]
let hwc: Array3<f32> = /* ... */;

// 轴重排成 CHW —— 注意：这只是逻辑上换轴，内存还是原来的交错排列，非连续！
let chw_view = hwc.permuted_axes([2, 0, 1]); // 形状变成 [3, 640, 640]，但不连续

// 引擎要的是连续内存，所以要真正拷贝、整理成标准行主序布局
let chw = chw_view.as_standard_layout();     // 现在内存是连续的 CHW，可以放心喂了

as_standard_layout() 会在需要时把数据真正拷贝成标准行主序连续布局（已经连续就零成本返回）。如果跳过这一步，直接把非连续视图的内存交给引擎，引擎按“连续“去读，读到的就是乱序的字节——结果全错，还是那句话：不报错。

好在，本书 10.8 节的 preprocess 采用另一种写法：直接 Array4::from_elem 建好 [1,3,640,640] 的连续张量，再按 CHW 的位置逐个写入。这样建出来的数组天生就是标准连续布局，压根不需要 as_standard_layout。两种思路都对，但显式写入更省一次拷贝，也更不容易踩连续性的坑。

10.8 完整代码：一个可复用的 preprocess 函数

把前面所有步骤合起来。下面这个函数就是本书的预处理主力，第 14 章推理、第 16 章后处理、第 26 章实战都会调用它。接口设计得尽量干净：进去一张 RgbImage，出来一个 [1,3,640,640] 的张量，外加一份 LetterboxInfo（后处理还原坐标的“回执“）。

先添加依赖：

cargo add image ndarray

然后是完整实现（可编译）：

use image::{imageops::FilterType, RgbImage};
use ndarray::Array4;

/// letterbox 变换的"回执"：预处理时怎么缩放、怎么填边，都记在这里。
/// 第 16 章后处理靠它把模型输出的框坐标还原回原图，一个字段都不能少。
#[derive(Clone, Copy, Debug)]
pub struct LetterboxInfo {
    pub scale: f32,   // 原图 → 缩放后的等比系数(1920×1080→640 时约 0.333)
    pub pad_x: f32,   // 左侧灰边宽度(像素，在 640×640 坐标系里)
    pub pad_y: f32,   // 顶部灰边高度(像素)
    pub orig_w: u32,  // 原图宽，还原时用来把框裁进图内边界
    pub orig_h: u32,  // 原图高
}

/// 把任意尺寸的 RGB 原图，处理成 YOLOv8 要的 [1,3,640,640] f32 张量。
/// 返回：(输入张量, letterbox 参数)。后者请务必保存到后处理阶段。
///
/// - `img`    : 第 3 章读进来的 RgbImage(已经是 RGB 顺序，无需换通道)
/// - `target` : 目标边长，本书恒为 640
pub fn preprocess(img: &RgbImage, target: u32) -> (Array4<f32>, LetterboxInfo) {
    let (orig_w, orig_h) = img.dimensions(); // (宽, 高)

    // ① 等比缩放系数：宽、高各自能缩多少，取"较小"的那个，
    //    保证缩放后长边刚好贴到 target，短边留空(之后用灰边补)。
    let scale = (target as f32 / orig_w as f32).min(target as f32 / orig_h as f32);

    // ② 缩放后的实际尺寸(四舍五入到整像素)
    let new_w = (orig_w as f32 * scale).round() as u32;
    let new_h = (orig_h as f32 * scale).round() as u32;

    // ③ 居中放置：左/上边距取整；若总边距为奇数，多出的 1 像素放到右/下。
    //    记录的 pad 必须和真正写入画布的整数偏移完全一致，否则反算坐标会偏半个像素。
    let off_x = ((target - new_w) / 2) as usize;
    let off_y = ((target - new_h) / 2) as usize;
    let pad_x = off_x as f32;
    let pad_y = off_y as f32;

    // ④ 等比缩放(插值算法原理见第 9 章；这里用双线性 Triangle，和 YOLO 默认一致)
    let resized = image::imageops::resize(img, new_w, new_h, FilterType::Triangle);

    // ⑤ 先把整块画布填成"灰色 114"归一化后的值：114/255 ≈ 0.447。
    //    这样没被图像覆盖的区域天然就是灰边，省去单独一步填充。
    let mut tensor =
        Array4::<f32>::from_elem((1, 3, target as usize, target as usize), 114.0 / 255.0);

    // ⑥ 把缩放后的像素写入张量：一次遍历同时完成
    //    HWC→CHW 布局转换、u8→f32、/255 归一化、以及居中平移。
    for y in 0..new_h as usize {
        for x in 0..new_w as usize {
            let px = resized.get_pixel(x as u32, y as u32); // &Rgb<u8>
            // 三个通道分别落到第 0/1/2 张平面(planar / CHW)
            tensor[[0, 0, y + off_y, x + off_x]] = px[0] as f32 / 255.0; // R
            tensor[[0, 1, y + off_y, x + off_x]] = px[1] as f32 / 255.0; // G
            tensor[[0, 2, y + off_y, x + off_x]] = px[2] as f32 / 255.0; // B
        }
    }

    let info = LetterboxInfo { scale, pad_x, pad_y, orig_w, orig_h };
    (tensor, info)
}

怎么用它：

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 第 3 章：读图并转成 RGB(RgbImage)
    let img = image::open("street.jpg")?.to_rgb8();

    let (input, lb) = preprocess(&img, 640);

    // 形状正是 YOLOv8 要的 [1, 3, 640, 640]
    assert_eq!(input.shape(), &[1, 3, 640, 640]);

    // input 交给推理引擎(第 14 章)；lb 一定要收好，第 16 章还原坐标要用
    println!("scale={:.4}, pad=({:.1}, {:.1})", lb.scale, lb.pad_x, lb.pad_y);
    Ok(())
}

对 1920×1080 的输入，会打印出 scale=0.3333, pad=(0.0, 140.0)——和我们 10.3 节手算的一模一样。

几点工程说明：

  • 为什么用逐像素写入而不是 permuted_axes？ 因为 from_elem 建出来的张量天生是连续的标准布局，逐个写入后可以直接喂引擎，省掉一次 as_standard_layout 的拷贝，也不会踩非连续的坑（见 10.7 节）。
  • 灰边一步到位：先把整块填成 114/255，再覆盖真实图像区域，省去单独填充边框的代码。
  • 性能：逐像素 tensor[[...]] 索引可读性好，但每次都做边界检查，热点路径上偏慢。工程上通常会改用 fast_image_resize（SIMD 加速缩放）配合按行 ndarray 切片批量写入，或直接操作底层 Vec<f32>，能快好几倍。本书先求“看得懂、跑得对“，性能优化留到第 29 章。
  • 健壮性：真实项目里 preprocess 一般返回 Result，对空图、异常尺寸做校验。这里为聚焦主线省略了错误处理。

10.9 预处理与后处理：一对必须对称的镜像

最后强调贯穿本书的一个核心思想：预处理和后处理是一对镜像。你在预处理里对图像做的每一次几何变换，后处理都要反着做一遍，才能把模型在 640×640 世界里给出的结果，翻译回你原图的真实世界。

预处理(正向：原图 → 模型)后处理(逆向：模型 → 原图，第 16 章)
等比缩放 ×scale坐标 ÷scale
加灰边 +pad_x / +pad_y坐标 −pad_x / −pad_y
HWC → CHW无需逆(后处理直接读输出张量)
/255 归一化无需逆(后处理处理的是坐标和分数)

其中真正需要逆运算的，就是 letterbox 的缩放和填充。所以 LetterboxInfo 是这对镜像之间传递的“密钥“。回顾 10.3 的还原公式：

$$ x_{\text{原图}} = \frac{x_{\text{模型}} - \text{pad_x}}{\text{scale}}, \qquad y_{\text{原图}} = \frac{y_{\text{模型}} - \text{pad_y}}{\text{scale}} $$

模型输出的框坐标，先减去 pad、再除以 scale，就回到了原图像素坐标系——正好还原成本书统一约定的 BBox { x1, y1, x2, y2 }（左上-右下，原图像素）。如果预处理时忘了保存 LetterboxInfo，或者后处理时逆运算写错，框就会整体偏移或缩放错位。这套还原、以及 YOLOv8 [1,84,8400] 输出的解析和 NMS，都在第 16 章。本章你只需牢记：在这里，把 scale / pad_x / pad_y 稳稳存进 LetterboxInfo。

10.10 小结

  • 预处理 = 把原图改造成模型训练时见过的样子，尺寸、颜色顺序、归一化、布局四件事必须和训练时分毫不差；错一个精度就崩，且不报错，是最难查的坑。
  • 完整链条：原图 → letterbox 缩放 → 颜色顺序 → 归一化 → HWC→CHW → 加 batch 维 → f32 连续张量，最终 YOLOv8 得到 1×3×640×640。
  • 尺寸用 letterbox（等比缩放 + 灰边 114 填充）而非直接 resize，避免物体变形；scale / pad_x / pad_y 务必保存，第 16 章还原坐标全靠它。1920×1080→640×640 手算得 scale=0.333, pad_x=0, pad_y=140。
  • 归一化分两派：YOLOv8 只 /255 到 0~1；很多分类模型还要按 ImageNet mean/std 做标准化(值可为负、可大于 1)。用哪派查模型要求，别猜。
  • 布局要 CHW（planar），最外再加 N=1 成 NCHW；数据类型 f32，且内存必须行主序连续——用 permuted_axes 换轴后记得 as_standard_layout，或像本章直接写入连续张量。
  • 预处理与后处理是一对镜像：这里怎么缩放、填充，后处理就怎么逆回去。LetterboxInfo 是两者之间的密钥。

10.11 练习

  1. 手算 letterbox：一张竖拍的手机照 1080×1920（宽 1080、高 1920），letterbox 到 640×640。算出 scale、缩放后尺寸、pad_x、pad_y。（提示：这次是高比宽长，谁当“长边“变了。）然后假设模型输出一个框左上角在 (200, 100)，用还原公式算出它在原图的坐标。

  2. 验证归一化：取像素 RGB = (0, 255, 114)，分别用“仅 /255“和“ImageNet 标准化“算出三个通道的结果，观察哪些值超出了 0~1。再想一想：如果模型要 /255 你却做了标准化，R 通道(原本 0)会从 0 变成多少？这偏差有多大？

  3. 改造 preprocess 支持标准化：给 10.8 的函数加一个可选参数（比如传入 Option<([f32;3],[f32;3])> 表示 mean/std），当提供时在 /255 之后再逐通道做 (x-mean)/std。保证不传时行为和原来完全一致（YOLOv8 路径不变）。

  4. 踩一次坑再爬出来：故意把 preprocess 里的通道写反（把 R 写到第 2 个平面、B 写到第 0 个平面，模拟 RGB/BGR 搞反），跑一遍真实图片的检测（等你学完第 14、16 章后回来做），观察置信度和框会烂成什么样。这能让你亲身体会为什么本章反复强调“分毫不差“。
