机器视觉工程实战：用 Rust 看懂图像与模型

第 21 章 · 多目标跟踪：SORT、卡尔曼与 ByteTrack

本章导读：第 15 到第 20 章，我们把“单帧模型“挨个拆了个遍——分类、检测、关键点、分割、差分、人脸。但它们有个共同的“失忆症“：每一帧都从零开始看，认不出“这个人上一帧也在“。从本章起进入第七部分·视频分析，第一课就是跟踪（tracking）：检测是单帧的，跟踪负责把跨帧的框连成同一个 ID。 读完你会明白多目标跟踪（MOT）到底在解决什么问题，掌握 tracking-by-detection 范式、用 IoU 做数据关联、卡尔曼滤波怎么“预测 + 更新“，并亲手写出一个复用全书统一 Track 类型、能编译的简化 SORT 跟踪器；最后理解 ByteTrack“低分框也别扔“的巧思，以及 MOTA / IDF1 / ID switch 这几个评价指标。一句话先记住：给每个目标一个跨帧稳定的 ID，是后面绊线、计数、脸人绑定所有业务过滤器的前提。

学习目标：

  • 说清“检测有了框，为什么还不够“——帧间没有身份，框会闪、会漏、会重叠
  • 掌握 tracking-by-detection 范式：检测负责“看“，跟踪负责把框“连成 ID“
  • 会用 IoU 构造代价矩阵，理解匈牙利算法的目标，会写它的贪心近似
  • 建立卡尔曼滤波的直觉：为什么要预测、“predict + update“两步在干嘛
  • 读懂并能实现 SORT 的生命周期（tentative → confirmed → lost，max_age / min_hits）
  • 理解 ByteTrack 的两阶段匹配，知道 DeepSORT、MOTA/IDF1/ID switch 各是什么

21.1 从检测到跟踪：视频分析的第一课

先把两件事分清楚。检测（第 16 章）回答的是“这一帧里有哪些物体、在哪“——它对每一帧都从零开始，上一帧发生过什么，它一概不知道。你把检测器接到视频上，逐帧跑，会得到一串互不相识的框：

第 100 帧：person(120,80,160,240)  person(400,90,445,250)
第 101 帧：person(124,82,164,242)  person(402,88,447,248)
第 102 帧：person(128,83,168,245)                          ← 右边这人漏检了！
第 103 帧：person(131,85,171,247)  person(406,86,451,246)

问题来了：第 101 帧左边那个 person，和第 100 帧左边那个，是不是同一个人？检测器不告诉你。它给的每个框都只有“是什么 + 在哪 + 多自信“，唯独没有身份。于是三件事必然发生：

  • 框会闪：同一个人这帧被检到、下帧因为轻微遮挡或模糊漏检，框一亮一灭；
  • 框会跳：分数、坐标每帧都抖动，画面上看着框在“哆嗦“；
  • 没法数、没法判：你想“数一共来了几个人““判断有没有人越过警戒线”，前提都是知道“这还是刚才那个人“——否则同一个人会被数很多次，越线也无从谈起。

跟踪（tracking）就是来补这个身份的。 打个生活比方：老师带一队小朋友出门春游，光“看见几个小朋友“没用，一转身就乱了。聪明的做法是点名发号牌——每个人别一个号牌，1 号、2 号、3 号……以后无论谁跑到哪，只要认出“这是 3 号“，就知道“还是刚才那个小孩“。多目标跟踪要做的，正是给画面里每个目标发一个跨帧稳定的号牌——我们叫它 id。

有了稳定 ID，视频分析才真正开始：绊线判越界（第 23 章）要看“同一个 ID 从线这边走到了那边“；时间去重（第 24 章）要靠“同一个 ID 只算一次“；脸人绑定（第 25 章）要把人脸和人体关联起来；完整的人流计数实战在第 28 章。所以本章是整个第七部分的地基。

术语：给多个目标同时维护身份，叫多目标跟踪（Multi-Object Tracking，MOT）；只跟一个目标的叫单目标跟踪（SOT）。本书讲的、工程里最常用的，都是 MOT。

21.2 tracking-by-detection：检测负责“看“，跟踪负责“连“

怎么发号牌？主流做法出奇地朴素，叫 tracking-by-detection（先检测后跟踪）：

检测器每帧照常吐框，跟踪器不碰图像，只干一件事——把这一帧的新框，和已经存在的“轨迹“关联起来，能对上的就沿用老 ID，对不上的就发新号牌，好久没露面的就注销。

这里出现一个新词，轨迹（track）：它是“同一个目标跨越多帧的历史“，带着一个固定的 id。跟踪器内部维护一批轨迹；每来一帧检测，它就更新这批轨迹。用全书统一的数据类型来说，就是这么一条流水线：

             ┌───────────── 每来一帧 ─────────────┐
             │                                    │
  视频帧 ──► 检测器 ──► Vec<Detection>  ──►  跟踪器 Tracker  ──► Vec<Track>
 (第 6 章)  (第 16 章)  {bbox,score,           update()      {id,bbox,
                        class_id}          (关联 + 维护 ID)   class_id,score}
             │                                    │
             └────── 跟踪器把"上一帧的记忆"留在自己肚子里 ──────┘

注意两点，都是全书一以贯之的约定：

  • 跟踪器的输入是 Detection（第 16 章：bbox + score + class_id），输出是 Track（相较检测结果多了一个 id: u64）。跟踪器不做检测、不看像素，它只在框的层面做“连连看“。所以换检测模型不用动跟踪器，这是这套范式最大的工程好处。
  • 所有坐标自始至终是原图像素（第 10 章逆 letterbox 之后的结果）。跟踪器里算距离、算重叠，都在原图坐标系里进行——千万别把 640 画布坐标和原图坐标混着喂，否则 IoU 全错（这是 21.10 会重点敲的坑）。

先列出本章使用的核心类型，本章通篇就围着它们转：

/// 一个检测结果（第 16 章定义，跟踪器的输入）
#[derive(Clone, Debug)]
pub struct Detection {
    pub bbox: BBox,      // 原图像素坐标的框
    pub score: f32,      // 置信度 0~1
    pub class_id: usize, // COCO 类别号
}

/// 带跟踪 ID 的目标（本章的输出）
#[derive(Clone, Debug)]
pub struct Track {
    pub id: u64,         // ★ 跨帧稳定的"号牌"
    pub bbox: BBox,
    pub class_id: usize,
    pub score: f32,
}

剩下的问题只有一个，却是全部难点所在：这一帧的框，怎么和已有的轨迹对上号？ 这就是数据关联。

21.3 数据关联：IoU、代价矩阵与匈牙利算法

数据关联（data association）要回答的是：“新来的 3 个框，分别是老的哪几条轨迹？“人是怎么下意识判断的？——位置差不多、大小差不多的，多半就是同一个。 一个人一帧只走几个像素，不会瞬移。所以“新框和旧轨迹像不像”，最简单好用的度量就是框重叠得多不多。

这正好复用第 16 章 NMS 里那个 IoU（交并比，Intersection over Union）：两个框交集面积 ÷ 并集面积，0 表示完全不沾边，1 表示完全重合。它已经作为方法定义在 BBox 上了（a.iou(&b)），这里直接拿来用——同一个 IoU，第 16 章用来“去重复框“，本章用来“认老朋友“。

假设上一帧有两条轨迹 T1 / T2，这一帧检到两个框 D1 / D2。把每条轨迹和每个检测两两算 IoU，就得到一张 IoU 矩阵：

IoU 矩阵（行 = 轨迹，列 = 检测）
          D1      D2
   T1    0.82    0.01
   T2    0.00    0.86

一眼就看出来：T1↔D1、T2↔D2。跟踪器要做的，就是把这个“一眼“变成算法。工程上习惯把“越像“变成“代价越小“，于是定义代价矩阵 = 1 − IoU：

代价矩阵 cost = 1 - IoU
          D1      D2
   T1    0.18    0.99
   T2    1.00    0.14

现在问题变成一句数学：从矩阵里挑若干个格子，每行最多挑一个、每列最多挑一个，让挑中格子的代价之和最小。 这是运筹学里的经典指派问题（assignment problem），有个最优解法叫匈牙利算法（Hungarian algorithm，又叫 Kuhn–Munkres）——它保证找到全局代价最小的匹配，复杂度 $O(n^3)$，对跟踪那点框（几十个）快得很。

匈牙利算法的代码不短，本章不展开推导；工程里直接用现成实现即可（Rust 生态有 pathfinding 的 kuhn_munkres、lapjv 等）。但为了让你看懂它在追求什么、也为了后面的 Tracker 能自足编译，我们先写一个贪心近似（greedy matching）：反复挑当前 IoU 最大的一对配上，配过的行、列就划掉，直到没有能配的为止。

/// 贪心匹配：反复挑 IoU 最大的一对 (轨迹 i, 检测 j) 配上，
/// 配过的行/列不再参与；返回一批 (i, j) 配对。
/// iou[i][j] = 第 i 条轨迹与第 j 个检测的 IoU。
fn greedy_match(iou: &[Vec<f32>], thresh: f32) -> Vec<(usize, usize)> {
    // ① 收集所有"够像"（IoU ≥ 阈值）的候选对
    let mut cand: Vec<(usize, usize, f32)> = Vec::new();
    for (i, row) in iou.iter().enumerate() {
        for (j, &v) in row.iter().enumerate() {
            if v >= thresh { cand.push((i, j, v)); }
        }
    }
    // ② 按 IoU 从高到低排：先配最像的一对
    cand.sort_by(|a, b| b.2.total_cmp(&a.2)); // 比较 f32 用 total_cmp，别 unwrap 到 NaN

    let rows = iou.len();
    let cols = iou.first().map_or(0, |r| r.len());
    let (mut used_i, mut used_j) = (vec![false; rows], vec![false; cols]);
    let mut out = Vec::new();
    // ③ 从最像的开始拿，谁的行或列被占了就跳过
    for (i, j, _) in cand {
        if used_i[i] || used_j[j] { continue; }
        used_i[i] = true;
        used_j[j] = true;
        out.push((i, j));
    }
    out
}

贪心和匈牙利差在哪？ 贪心只顾“眼前最像的先配“，可能因小失大。看一个精心构造的例子（阈值 0.3）：

IoU 矩阵            D1      D2
           T1     0.90    0.60
           T2     0.85    0.10    （0.10 < 0.3，T2 配不上 D2）
  • 贪心：全场最大是 T1-D1=0.90，先配掉。轮到 T2，它唯一还够格的 D1 已被占，T2-D2=0.10 又低于阈值——于是 T2 没配上（开始“变老“等着被删）、D2 也没配上（起一条新轨迹、发新号牌）。总重叠 = 0.90。
  • 匈牙利：它会算全局——选 T1-D2(0.60) + T2-D1(0.85) = 1.45，比只配一对的 0.90 更优。于是 T1↔D2、T2↔D1，两条老轨迹都保住，一个新号牌都不用发。

贪心那一步“错配“，轻则丢一条轨迹、白发一个 ID（这就是后面要讲的 ID switch），重则把甲的 ID 安到乙头上。所以：能上匈牙利就上匈牙利；本章为了自足和好懂用贪心，够跑通、也够你理解关联的本质。 目标只有一个——让这一帧的框，尽量正确地接回它原本的那条轨迹。

21.4 卡尔曼滤波：给轨迹装上“惯性“

上面的关联有个软肋：它拿上一帧的框去和这一帧比。可目标一直在动，上一帧的位置已经过时了；而且检测框每帧都在抖、还偶尔漏检——漏检那一帧，轨迹连个能比的框都没有。

怎么办？预测。 生活里你早就会了：看着一个人往右匀速走，就算你眨一下眼（漏检一帧），也能估出他下一刻大概在哪——因为他有速度、有惯性，不会瞬移。守门员扑点球、猎手打飞鸟，靠的都是这个“根据当前位置和速度，预判下一步“的能力。卡尔曼滤波（Kalman filter）就是把这种预判写成公式的工具。

它的精髓是两步循环，每帧转一圈：

   ┌─────────────────────────────────────────────────────┐
   │                                                       │
   ▼                                                       │
 ① 预测 predict：靠"惯性"往前推一帧                          │
     用上一帧的位置 + 速度，估出"这一帧应该在哪"              │
     （即使这帧漏检，也照样给得出一个位置）                   │
                          │                                 │
                          ▼                                 │
 ② 更新 update：拿这一帧真实检测框来"校正"预测                 │
     预测和实测各信一点，加权融合成新的位置估计 ───────────────┘
     （检测越准信实测，运动越稳信预测）
  • 预测让轨迹在漏检时也能“续着走“，不至于一漏检就断。
  • 更新把“我以为在哪（预测）“和“实际看到在哪（检测）“揉在一起——检测噪声大就多信预测，运动规律好就多信检测。**卡尔曼增益（Kalman gain）**就是自动决定“这次该信谁多一点“的那个权重。

状态里存什么？ 位置加速度。跟踪一个框，最朴素的状态就是中心点坐标 + 中心点速度 [cx, cy, vx, vy]（真实 SORT 还会带上框的面积和长宽比及其变化率，一共 7 维，思路一样）。

数学上只需记住两个直觉（不推导，想深究见附录 A）：预测是“当前状态乘一个’往前走一步’的矩阵 $F$“，更新是“用一个自动算出的权重 $K$（卡尔曼增益）把实测和预测拉到一起”。最小的一组式子长这样，看个大概即可：

$$\hat{x}{预测} = F,x, \qquad x{更新} = \hat{x}{预测} + K,(z - H\hat{x}{预测})$$

其中 $z$ 是这一帧实测（检测框中心），$H$ 负责“从状态里取出能和 $z$ 比的部分“，$(z - H\hat{x})$ 就是“实测比预测偏了多少“。下面用 nalgebra 给一个匀速模型骨架——它能编译，帮助你把上面两步“摸得着“（实际项目里可直接用它，也可用现成 crate）：

use nalgebra::{Matrix2, Matrix2x4, Matrix4, Matrix4x2, Vector2, Vector4};

/// 匀速模型卡尔曼滤波：状态 = [中心x, 中心y, 速度vx, 速度vy]
struct Kalman {
    x: Vector4<f32>,   // 状态：位置 + 速度
    p: Matrix4<f32>,   // 状态协方差：当前估计有多不确定
    f: Matrix4<f32>,   // 状态转移矩阵：下一帧 = 当前位置 + 速度
    h: Matrix2x4<f32>, // 观测矩阵：从状态里挑出"位置"来和检测比
    q: Matrix4<f32>,   // 过程噪声：运动模型本身有多不准
    r: Matrix2<f32>,   // 观测噪声：检测框有多不准
}

impl Kalman {
    /// 用第一帧检测到的中心 (cx, cy) 初始化；速度先当 0
    fn new(cx: f32, cy: f32) -> Self {
        Kalman {
            x: Vector4::new(cx, cy, 0.0, 0.0),
            p: Matrix4::identity() * 10.0,     // 初始很不确定，给个大值
            f: Matrix4::new(                   // 假设两帧间隔 dt = 1
                1.0, 0.0, 1.0, 0.0,            // x' = x + vx
                0.0, 1.0, 0.0, 1.0,            // y' = y + vy
                0.0, 0.0, 1.0, 0.0,            // vx' = vx（匀速）
                0.0, 0.0, 0.0, 1.0,            // vy' = vy
            ),
            h: Matrix2x4::new(
                1.0, 0.0, 0.0, 0.0,            // 只观测得到 x
                0.0, 1.0, 0.0, 0.0,            // 只观测得到 y
            ),
            q: Matrix4::identity() * 1.0,      // 这些噪声值需按场景调
            r: Matrix2::identity() * 1.0,
        }
    }

    /// ① 预测：把状态往前推一帧（漏检时也能给出位置）
    fn predict(&mut self) {
        self.x = self.f * self.x;
        self.p = self.f * self.p * self.f.transpose() + self.q;
    }

    /// ② 更新：用一帧实测中心 (zx, zy) 校正预测
    fn update(&mut self, zx: f32, zy: f32) {
        let z = Vector2::new(zx, zy);
        let y = z - self.h * self.x;                         // 残差：实测 - 预测
        let s = self.h * self.p * self.h.transpose() + self.r;
        let k: Matrix4x2<f32> =
            self.p * self.h.transpose() * s.try_inverse().unwrap(); // 卡尔曼增益 K
        self.x += k * y;                                     // 按 K 修正状态
        self.p = (Matrix4::identity() - k * self.h) * self.p;
    }
}

用起来就是“每帧先 predict()，匹配上了再 update(实测中心)“。先建立直觉，再照抄骨架，别一上来啃矩阵公式——这是本书对待数学一贯的态度。

21.5 SORT：预测 + 匹配 + 生命周期

把前两节拼起来，就是 2016 年那篇又快又好使的 SORT（Simple Online and Realtime Tracking）。它的配方简单到一句话：

卡尔曼预测（21.4） + IoU 匈牙利匹配（21.3） + 一套轨迹生命周期管理。

前两块讲完了，只差第三块：生命周期。为什么需要它？因为现实很脏——检测器会偶尔漏检（不能一漏就删轨迹，否则 ID 全断）、也会偶尔虚检（不能一冒出个框就当真发号牌，否则满屏乱蹦的 ID）。SORT 用一个小状态机来扛这两种脏：

   新检测无人认领
        │
        ▼
   ┌───────────┐   连续命中够 min_hits 次    ┌───────────┐
   │ Tentative │ ─────────────────────────► │ Confirmed │  ← 只有它对外输出 ID
   │  (试用期)  │                            │  (转正)   │
   └───────────┘                            └───────────┘
        │                                         │
   还没转正就漏检                             连续漏检，计数
        │                                    time_since_update++
        ▼                                         │
     直接删掉                                      ▼
   （多半是虚检）                       超过 max_age 仍没接上 → 删除(Lost)
  • min_hits（转正门槛）：一条新轨迹要连续命中 min_hits 帧才“转正“、才对外输出。这样偶尔跳一下的虚检框，还没转正就没了，不会污染结果。
  • max_age（容忍漏检的寿命）：一条转正的轨迹若连续 max_age 帧都没匹配上检测，才判定目标真的走了、删除。在此之前，全靠 21.4 的卡尔曼预测硬撑着位置——这正是跟踪能扛住短暂遮挡的原因。

整帧流程串起来是这样（这就是 Tracker::update 每帧要走的路）：

  这一帧检测 dets: Vec<Detection>
        │
        ▼
  ① 预测：每条轨迹卡尔曼 predict()，得到"这帧它应该在哪"
        │
        ▼
  ② 关联：预测框 × 检测框 → IoU 矩阵 → 匈牙利/贪心匹配
        │
   ┌────┼──────────────────────┐
   ▼    ▼                       ▼

21.6 动手实现一个简化 Tracker

现在把 21.3 的贪心匹配、21.5 的生命周期落成一段能编译、能跑的代码。为了聚焦跟踪逻辑，这里做两点简化，都在注释里点明“真实 SORT 会怎样“：预测这步用“沿用上一帧框“代替卡尔曼（要上卡尔曼，把每条轨迹换成 21.4 的 Kalman 即可），匹配用贪心代替匈牙利。数据类型全部复用全书统一定义。

先把自足需要的 BBox 列全（iou / center 第 16 章已定义，这里为让代码独立而附上）：

/// 边界框：左上-右下像素坐标（全书统一类型，第 16 章定义）
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct BBox { pub x1: f32, pub y1: f32, pub x2: f32, pub y2: f32 }

impl BBox {
    pub fn width(&self) -> f32 { (self.x2 - self.x1).max(0.0) }
    pub fn height(&self) -> f32 { (self.y2 - self.y1).max(0.0) }
    pub fn area(&self) -> f32 { self.width() * self.height() }
    pub fn center(&self) -> (f32, f32) {
        ((self.x1 + self.x2) / 2.0, (self.y1 + self.y2) / 2.0)
    }
    /// 交并比：重叠程度，0=不沾边，1=完全重合
    pub fn iou(&self, o: &BBox) -> f32 {
        let ix1 = self.x1.max(o.x1);
        let iy1 = self.y1.max(o.y1);
        let ix2 = self.x2.min(o.x2);
        let iy2 = self.y2.min(o.y2);
        let inter = (ix2 - ix1).max(0.0) * (iy2 - iy1).max(0.0); // 无交集则 0
        let union = self.area() + o.area() - inter;
        if union <= 0.0 { 0.0 } else { inter / union }
    }
}

跟踪器内部每条轨迹，比对外的 Track 多几个“管生命周期“的字段：

/// 跟踪器内部的一条轨迹（比对外 Track 多了状态字段）
struct TrackState {
    id: u64,
    bbox: BBox,
    class_id: usize,
    score: f32,
    hits: u32,              // 累计匹配上的次数（用于转正）
    time_since_update: u32, // 距上次匹配过了几帧（漏检计数）
    confirmed: bool,        // 是否已转正
}

主角登场。注意 update 的七步和 21.5 的 ASCII 流程一一对应：

pub struct Tracker {
    tracks: Vec<TrackState>,
    next_id: u64,
    iou_thresh: f32, // 关联阈值：IoU 低于它不认为是同一目标
    max_age: u32,    // 连续漏检超过这么多帧就删轨迹
    min_hits: u32,   // 连续命中够这么多次才转正、才对外输出
    just_removed: Vec<u64>, // 最近一次 update 里被删除的 track id（供上层订阅"消失"）
}

impl Tracker {
    pub fn new() -> Self {
        Tracker {
            tracks: Vec::new(),
            next_id: 1,        // id 从 1 开始发
            iou_thresh: 0.3,
            max_age: 30,       // 30 帧 ≈ 1 秒(30fps)内没接上才判走
            min_hits: 3,
            just_removed: Vec::new(),
        }
    }

    /// 喂进这一帧的检测框，返回本帧"确认且刚更新"的带 ID 目标
    pub fn update(&mut self, dets: &[Detection]) -> Vec<Track> {
        let (iou_thresh, max_age, min_hits) =
            (self.iou_thresh, self.max_age, self.min_hits); // 先取出，规避借用冲突

        // ① 预测：真实 SORT 在此对每条轨迹卡尔曼 predict()；
        //    简化版直接沿用上一帧的 bbox（相当于"静止预测"），什么都不做。

        // ② 关联：算 IoU 矩阵（不同类别直接记 0，人不会变成车），再贪心匹配
        let iou: Vec<Vec<f32>> = self.tracks.iter().map(|t| {
            dets.iter().map(|d| {
                if t.class_id == d.class_id { t.bbox.iou(&d.bbox) } else { 0.0 }
            }).collect()
        }).collect();
        let matches = greedy_match(&iou, iou_thresh);

        let mut det_matched = vec![false; dets.len()];
        let mut trk_matched = vec![false; self.tracks.len()];

        // ③ 命中的轨迹：换上新框、刷新计数（真实 SORT 是卡尔曼 update）
        for (ti, di) in &matches {
            let t = &mut self.tracks[*ti];
            let d = &dets[*di];
            t.bbox = d.bbox;
            t.score = d.score;
            t.class_id = d.class_id;
            t.hits += 1;
            t.time_since_update = 0;
            if t.hits >= min_hits { t.confirmed = true; } // 连续命中够了就转正
            det_matched[*di] = true;
            trk_matched[*ti] = true;
        }

        // ④ 没匹配上的老轨迹：漏检计数 +1（暂不删，靠预测硬撑）
        for (ti, matched) in trk_matched.iter().enumerate() {
            if !matched { self.tracks[ti].time_since_update += 1; }
        }

        // ⑤ 没匹配上的新检测：起一条 tentative 新轨迹，发新号牌
        for (di, matched) in det_matched.iter().enumerate() {
            if !matched {
                let d = &dets[di];
                self.tracks.push(TrackState {
                    id: self.next_id,
                    bbox: d.bbox, class_id: d.class_id, score: d.score,
                    hits: 1, time_since_update: 0, confirmed: false,
                });
                self.next_id += 1;
            }
        }

        // ⑥ 清理：连续漏检超过 max_age 的轨迹，判定目标已离开，删除。
        //    删除前先把它们的 id 收集到 just_removed，让上层能订阅"目标消失"
        //    事件（第 28 章人脸抓拍就靠它在 track 结束那一刻落盘）。
        self.just_removed = self.tracks.iter()
            .filter(|t| t.time_since_update > max_age)
            .map(|t| t.id)
            .collect();
        self.tracks.retain(|t| t.time_since_update <= max_age);

        // ⑦ 输出：只报"已转正、且本帧刚更新过"的轨迹
        self.tracks.iter()
            .filter(|t| t.confirmed && t.time_since_update == 0)
            .map(|t| Track {
                id: t.id, bbox: t.bbox, class_id: t.class_id, score: t.score,
            })
            .collect()
    }

    /// 最近一次 update 中被删除（连续漏检达 max_age）的 track id。
    /// 返回 owned Vec 而非 &[u64]：调用方通常紧接着还要 &mut 借用自己的
    /// 其他字段（如清理 HashMap、落盘快照），借用一个 owned 值能避开借用冲突。
    pub fn just_removed(&self) -> Vec<u64> {
        self.just_removed.clone()
    }
}

（greedy_match 就是 21.3 那个函数，原样复用。）跑一个两帧的小例子，感受 ID 是怎么稳住的：

fn main() {
    let mut tracker = Tracker::new();
    let mk = |x1, y1, x2, y2| Detection {
        bbox: BBox { x1, y1, x2, y2 }, score: 0.9, class_id: 0, // 0 = person
    };

    // 连喂 3 帧，同一个人每帧往右挪几像素（min_hits=3，第 3 帧才转正输出）
    for frame in 0..3 {
        let dx = frame as f32 * 5.0;
        let out = tracker.update(&[mk(100.0 + dx, 80.0, 140.0 + dx, 200.0)]);
        println!("帧 {frame}：输出 {} 条轨迹 -> {:?}",
                 out.len(), out.iter().map(|t| t.id).collect::<Vec<_>>());
    }
}
帧 0：输出 0 条轨迹 -> []      ← 试用期，还没转正
帧 1：输出 0 条轨迹 -> []      ← 命中 2 次，仍没到 min_hits=3
帧 2：输出 1 条轨迹 -> [1]     ← 转正！从此这个人稳定叫 1 号

前两帧不输出，是 min_hits 在“压惊“——真有目标它一定会连命中而转正，虚检则等不到转正就被删。工程上通常会把卡尔曼补回去（换掉第 ① 步）、把贪心换成匈牙利、按类别分别跟踪或加类别一致性约束、给 iou_thresh/max_age/min_hits 按帧率和场景调参——但骨架就是这七步，不会变。

还留了一个小接口值得单独点出：just_removed()。update 每帧在第 ⑥ 步删轨迹前，把“这一帧被删掉的 id“存了下来，just_removed() 就把它交出去。为什么要暴露它？ 因为下游常常需要在“某个目标彻底离开画面“的那一刻做一件事——第 28 章的人脸抓拍就要在这时把这个人“整段视野里最清晰的一张脸“落盘。跟踪器是唯一知道“谁走了“的人，所以它得把这个生命周期事件报出来。返回的是 owned Vec<u64> 而不是借用，是因为调用方（如 PeopleSystem）拿到这批 id 后，紧接着还要 &mut 借用自己其他字段去清理状态、写文件——返回一个独立的值，就不会和那些可变借用打架。

21.7 ByteTrack：低分框也别扔

SORT 有个朴素到吃亏的习惯：它只拿高分框去跟踪，低分框（比如 score < 0.5）直接扔掉。 想想什么时候框会掉分？——目标被挡了一半、运动模糊、离得远变小的时候。可这些恰恰是目标还在、只是看不太清的时刻。SORT 一扔，这条轨迹这帧就没框可匹配，time_since_update 涨、甚至被删；等目标重新露脸、分数回升，它只能当新目标发一个新 ID——一次 ID switch（ID 跳变）就这么来了。

2022 年的 ByteTrack 的改进就一句话，却极有效：低分框也别扔，给它第二次机会。 做法是两阶段匹配——先用高分框正常匹配，剩下没配上的轨迹，再拿低分框来兜底：

输入：这一帧检测按分数分两拨
  高分框 D_high（score ≥ 0.5）
  低分框 D_low （0.1 ≤ score < 0.5）    ← SORT 会直接扔掉这拨

第一轮：D_high  ×  所有轨迹   → IoU 匹配
        配上的轨迹更新；没配上的轨迹记作 T_remain

第二轮：D_low   ×  T_remain   → IoU 再匹配   ★ ByteTrack 的关键一步
        被遮挡/模糊而掉分的目标，在这里被低分框接住，ID 得以延续

收尾：
  仍没配上的 T_remain → 标记 lost，进入 max_age 倒计时（靠预测撑着）
  没配上的 D_high     → 起新轨迹（发新 ID）
  没配上的 D_low      → 直接丢弃（不为低分框新建轨迹，避免把噪声当目标）

体会这里的不对称：低分框只被允许去“续“已有轨迹，不被允许“开“新轨迹。这很讲究——低分框里确实混着噪声，让它新建轨迹会满屏乱蹦；但让它去接一条已经存在、位置也对得上的轨迹，风险很小、收益很大。“信任已有轨迹的惯性，用低分框把它接住”，就是 ByteTrack 显著降低 ID 丢失的秘诀。它几乎不增加计算量，却常能明显提升指标，因此成了当下工程首选之一。落到代码上，无非是把 21.6 的“一次匹配“拆成“高分先配、低分兜底“两次调用 greedy_match，其余生命周期逻辑照旧。

21.8 DeepSORT：用“长相“来关联

IoU 关联只看“框在不在一块儿“，遇到两个人交叉走过就容易犯迷糊——交叠的一瞬间，谁是谁的框全糊在一起，IoU 分不清，ID 就可能对调。DeepSORT 的补法是：除了看位置，再看“长相“——给每个框抽一段外观特征向量（appearance embedding），关联时把“位置像不像（IoU）“和“长相像不像（特征距离）“一起算进代价矩阵。这样即使框暂时重叠，靠衣服颜色、体态这些外观差异也能把两个人分开，遮挡后重新出现也更容易“认回老朋友”。这段外观特征怎么来、怎么比距离，正是第 20 章人脸/ReID 特征那一套（抽 embedding、算余弦/欧氏距离）——DeepSORT 只是把它借来当关联的第二把尺子。代价是要多跑一个特征模型、慢一些，是否值得看场景。

21.9 评价指标：MOTA、IDF1 与 ID switch

跟踪跟得好不好，不能只凭肉眼。学术界和工程里常看这三个（点到为止，够你读懂论文和验收报告即可）：

指标直觉关注点
ID switch同一个目标中途换了 ID 的次数（比如 3 号走着走着变成了 8 号）身份稳不稳，越少越好
MOTAMulti-Object Tracking Accuracy：把漏检 + 虚检 + ID switch 三种错加权汇总的综合分框准不准、丢没丢，越高越好
IDF1以“身份“为核心的 F1：正确保持身份的检测占比身份连贯性（比 MOTA 更看重 ID），越高越好

三者里，ID switch 是本章一切努力的靶心——SORT 的生命周期、ByteTrack 的低分兜底、DeepSORT 的外观特征，本质都是在压低 ID switch。一个直观理解：MOTA 更像在问“你有没有把该检的都检到、别乱检“，偏重检测质量；IDF1 更像在问“你有没有自始至终认准同一个人“，偏重身份质量。有时 MOTA 很高但 IDF1 拉胯，说明框都对、但 ID 老在跳——这正是跟踪没做好的典型信号。

21.10 工程坑位清单

跟踪是“检测的下游“，检测的毛病会被它放大，还会长出自己的坑。上线前对着这张单子过一遍：

  • ID 频繁跳变：iou_thresh 太高（稍一移动就配不上）、或帧率低导致两帧间目标位移过大、或漏检频繁。对策：适度降低阈值、补上卡尔曼预测、上 ByteTrack。IDF1 突然变低就是它在报警。
  • 遮挡后 ID 丢失：max_age 太小，目标被挡几帧就被删，重现时成了新 ID。对策：调大 max_age 给轨迹“留活口“、靠卡尔曼预测撑过遮挡、必要时用 DeepSORT 的外观特征把人“认回来“。
  • 检测漏检拖垮跟踪：跟踪再聪明也变不出检测器没给的框——检测这帧没框，跟踪最多靠预测硬撑几帧。跟踪效果差，先回头查检测的召回率，别只调跟踪参数。这也是为什么 ByteTrack 要去抢救低分框。
  • 坐标系必须统一为原图像素：这是最隐蔽、最致命的坑。检测输出若还停在 640 letterbox 画布坐标，就直接丢进跟踪器，IoU 会全错（画布和原图的缩放、灰边偏移都没还原）。务必在第 10 章的逆 letterbox 之后、拿到原图像素坐标，再喂给跟踪器，全流程一个坐标系。
  • 类别一致性：不加约束时，一个人的框可能被邻近一辆车的框“抢配“。简单有效的做法就是 21.6 里那句——只在同类别之间做匹配。
  • 参数随帧率变：max_age 是按“帧“数的。30fps 下 max_age=30 约等于 1 秒；换成 10fps 的抽帧流，同样 30 帧就是 3 秒，含义完全变了。换帧率务必重算这些阈值。

21.11 小结

  • 检测是单帧的、没有身份；跟踪给每个目标发一个跨帧稳定的 id，是绊线、计数、脸人绑定等所有视频业务过滤器的地基。
  • 主流范式是 tracking-by-detection：检测器逐帧给 Detection，跟踪器只负责关联——把新框接回老轨迹、维护 Track（比 Detection 多一个 id），不碰像素、不做检测。
  • 数据关联用 IoU 度量“新框和旧轨迹像不像“，构成代价矩阵；匈牙利算法求全局最优匹配，本章用贪心近似替代（够懂、能编译，工程建议上匈牙利）。
  • 卡尔曼滤波给轨迹装上“惯性“：预测让漏检时也能续着走、更新融合预测与实测；状态含位置 + 速度，数学只需记住“预测 + 更新“两步的直觉。
  • SORT = 卡尔曼预测 + IoU 匹配 + 生命周期（tentative→confirmed→lost，用 min_hits 抗虚检、max_age 抗漏检）；本章给出了对应的、能编译的简化 Tracker::update。
  • ByteTrack“低分框也别扔”，用两阶段匹配（高分先配、低分兜底续轨迹）显著降低 ID switch；DeepSORT 则借第 20 章的外观特征当关联的第二把尺子。评价看 MOTA / IDF1 / ID switch，靶心是把 ID switch 压下去。
  • 头号工程坑：坐标必须统一用原图像素、跟踪好坏先看检测召回、参数随帧率重算。

21.12 练习

  1. 手算数据关联：轨迹 T1=(100,100,140,180)、T2=(150,100,190,180)，本帧检测 D1=(104,102,146,184)、D2=(152,98,192,178)。用 BBox::iou 手算 2×2 的 IoU 矩阵（保留两位小数），写出代价矩阵 1−IoU，并分别用贪心和匈牙利给出匹配——这个例子两者结果一样吗？再改几个数字，构造一个贪心会配错、匈牙利才对的 2×2 矩阵。
  2. 给简化 Tracker 补漏检与遮挡测试：用 21.6 的 Tracker，构造一段“目标出现 5 帧 → 消失 3 帧 → 又出现 3 帧“的检测序列。观察 ID 是否在重现后保持不变；把 max_age 从 30 改成 2 再跑一次，看看什么时候 ID 会变——解释这背后 max_age 和 time_since_update 的作用。
  3. 把贪心换成两阶段（ByteTrack 思路）：给 update 增加一个低分阈值，把检测分成高分/低分两拨，实现 21.7 的两轮匹配（高分先配所有轨迹、低分只配剩余轨迹、低分不新建轨迹）。造一个“目标中途掉到低分几帧“的序列，对比改造前后 ID 是否还会跳变。
  4. 接上卡尔曼：把 21.4 的 Kalman 塞进 TrackState，在 update 第 ① 步对每条轨迹 predict()、第 ③ 步用检测中心 update()，关联时改用预测后的框算 IoU。用一段匀速直线运动、且中间漏检 2 帧的序列，对比“有无卡尔曼“时漏检帧的框位置估计差多少。
