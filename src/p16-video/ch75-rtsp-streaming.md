# 第 75 章 RTSP / 流媒体接入与实时处理管线

> **本章导读**
> - 学完你能：理解工业/安防摄像头的 **RTSP** 拉流是怎么回事，并用 `std::thread` + `mpsc` 亲手搭一个带**丢帧策略**的实时处理管线骨架——`cargo run` 就能看到「处理了 N 帧、丢弃了 M 帧」的真实数字。
> - 想透实时管线的核心矛盾：当**处理慢于到帧**，你只有两条路——**堆积**（延迟越来越大）或**丢帧**（牺牲完整性保低延迟），这就是**背压（backpressure）**。
> - 认清一个**诚实**的现状：纯 Rust **能收流**（`retina` 是真货），但**解码 H.264 常常还得借助非纯 Rust 解码器或 ffmpeg**——一易一难。

## 场景引入：墙上的摄像头，怎么把画面「拉」进程序

上一章我们处理的是**文件**里的视频。但工业产线、安防监控里的摄像头，画面是**实时**产生、通过网络**持续推送**的——你不可能等它录完一个文件再处理，得像拧开水龙头一样「接」着实时的流。

绝大多数网络摄像头（IP Camera）走的是一个叫 **RTSP** 的协议。你在摄像头说明书上会看到类似这样的地址：

```text
rtsp://admin:password@192.168.1.64:554/Streaming/Channels/101
```

需求很典型：「把这个 RTSP 流拉进来，实时检测有没有人闯入。」这里冒出两个上一章没有的新问题：**① 怎么用纯 Rust 把这个流拉进来？② 如果我的检测算法每帧要跑 50ms，而摄像头每秒来 25 帧（每 40ms 一帧），处理根本追不上，怎么办？** 这一章就死磕这两件事。

## 原理：拉流、解码、与实时管线

### RTSP 是什么：一个「遥控器 + 快递」组合

**RTSP（Real-Time Streaming Protocol，实时流协议）**，你可以把它想成摄像头的**遥控器**：客户端用它发「描述一下你有啥流（DESCRIBE）」「建立连接（SETUP）」「开始播（PLAY）」「暂停/停（PAUSE/TEARDOWN）」这些控制命令。而真正的**视频数据**并不由 RTSP 本身搬运，是由它协商好的 **RTP（Real-time Transport Protocol）** 一个包一个包地送过来——RTP 是「快递小哥」。

RTP 可以走两种传输：**over TCP**（可靠不丢包，但网络差时卡顿累积延迟）或 **over UDP**（低延迟，但可能丢包）——这个权衡我们放到本章末尾的坑里细说。

### 诚实核心：收流容易，解码难

这是本章最重要的一句实话，请刻在脑子里：

> **纯 Rust 能把 RTSP/RTP 流「收」进来，但把收进来的 H.264 码流「解」成像素，常常还得靠非纯 Rust 的解码器。**

拆开说：

- **收流（纯 Rust ✅ 有真货）**：`retina` 是一个**纯 Rust** 的 RTSP/RTP 客户端库（写作时最新 0.4.20），能完成 DESCRIBE/SETUP/PLAY 全流程，把 RTP 包**重组**成一帧帧 H.264 **编码数据**。这一步纯 Rust 完全搞得定。
- **解码（纯 Rust ❌ 短板）**：`retina` 交给你的 `frame.data()` 是**编码后的 H.264 NAL 单元**，**不是像素**！要变成 `RgbImage`，还得送进一个 H.264 解码器。而纯 Rust 的 H.264 解码器**不成熟**；常用的 `openh264`（Cisco，C 库）、AV1 的 `dav1d`（C 库）**都不是纯 Rust**。

于是纯 Rust 实时视觉的现实是「**半纯**」：收流纯 Rust，解码这一环大概率要借助 C 库或 ffmpeg。这也解释了**为什么很多产线干脆整条都交给 ffmpeg**——用 `ffmpeg` 子进程直接把 RTSP 流解码成裸 RGB 帧，通过管道（pipe）喂给 Rust 处理端：

```bash
# ffmpeg 直接拉 RTSP 并输出裸 RGB24 帧到 stdout，Rust 端从子进程 stdout 按 W*H*3 字节切帧
ffmpeg -rtsp_transport tcp -i rtsp://.../101 -f rawvideo -pix_fmt rgb24 -
```

这套「ffmpeg 拉流解码 + Rust 处理」和上一章「ffmpeg 抽帧 + Rust 算法」是同一分工哲学。那什么时候值得上 `retina` 纯 Rust 收流？——当你要**交叉编译到边缘设备、想要单一静态二进制、或需精细控制 RTP 层**，且解码环节有着落（GPU 硬解或能接受 C 解码库）时。

### 实时管线：采集与处理，必须解耦

实时管线的骨架永远是：**拉流 → 解码 → 逐帧处理 → 出结果**。而它和离线处理最本质的区别是——**帧是「按摄像头的节奏」不断涌来的，不等你**。

如果把「采集」和「处理」写在同一个循环里串行做，一旦某帧处理慢了，就会**阻塞采集**，后面的帧在缓冲区堆积甚至被丢弃。所以第一原则是：**采集和处理分线程，用队列解耦。** 在 Rust 里，这天然就是 `std::thread` + `std::sync::mpsc`（多生产者单消费者通道）的活儿。

```text
  采集线程                  队列                 处理线程
┌──────────┐   push   ┌───────────┐   pop   ┌──────────────┐
│ 拉流/解码 │ ───────▶ │  帧缓冲区  │ ──────▶ │ 逐帧跑算法    │
│（快，稳定）│          │（容量有限？）│         │（慢，忽快忽慢）│
└──────────┘          └───────────┘         └──────────────┘
```

### 核心矛盾：处理慢于到帧时，堆积还是丢帧？

真正的难点在队列这一环。设到帧速率 \(\lambda\)（帧/秒），处理速率 \(\mu\)（帧/秒）。若 \(\mu \ge \lambda\)，皆大欢喜。可现实里跑个检测模型，常常 \(\mu < \lambda\)——**处理追不上到帧**。这时队列会发生什么，取决于你的策略：

- **无界队列、不丢帧**：帧只进不出得够快，队列越堆越长。更要命的是**端到端延迟持续累积**——你处理的「当前帧」其实是几秒前拍的，监控画面「慢半拍」越来越离谱。对实时监控是灾难。
- **有界队列 + 丢帧**：给队列设一个容量上限，满了就丢帧。这样**延迟被钳制在上限内**，代价是丢失部分帧。这才是实时监控该做的——**看最新，比看全部更重要**。

「丢帧」还分两种，方向相反：

| 策略 | 满了丢谁 | 保留的是 | 实现 |
|------|---------|---------|------|
| **丢最旧（drop-oldest）** | 队首（最老的帧） | **最新**的一批帧 | 手搓 `VecDeque`：满则 `pop_front` 再 `push_back` |
| **丢最新（drop-newest）** | 当前这一帧 | **较旧**的连续帧 | `sync_channel` + `try_send`：满则 `Full`，丢当前 |

实时监控几乎总是要**丢最旧、保最新**（谁关心 3 秒前的画面）。这种「让队列产生背压、逼着系统丢弃旧数据」的机制，就是**背压（backpressure）**。

> 📖 **术语**：**背压（backpressure）**。当下游（处理）消费不过上游（采集），系统需要一种「往回顶」的压力来取舍。有界队列就是最朴素的背压：用「满」这个信号，逼生产者要么等待、要么丢弃。选对丢弃策略（丢旧还是丢新），是实时系统的关键设计。

## 动手写代码：用 mpsc 搭一个会「丢帧」的实时管线

我们**不真连摄像头**（那不可复现，还要你有台 IP Camera）。而是用一个**采集线程按固定节奏合成帧**来**模拟拉流**，一个**处理线程慢速消费**，把上面两种策略都跑一遍、打印真实的帧账目和延迟。配套示例 `code/examples/ch75_rtsp_pipeline.rs`，只依赖 `std` + `image`。

关键参数刻意设成「处理追不上」：**采集每 20ms 一帧（≈50 fps），处理每帧 45ms（≈22 fps）**。

**策略 A：无界队列、不丢帧**（`std::sync::mpsc::channel`）。采集线程按节奏 `send`，处理线程 `for s in rx.iter()` 慢慢收，一帧不丢：

```rust
let (tx, rx) = std::sync::mpsc::channel::<Stamped>();
// 采集线程：每 20ms 造一帧、打上采集时间戳、send
thread::spawn(move || {
    for seq in 0..N_FRAMES {
        tx.send(Stamped { seq, captured_at: Instant::now(), img: synth_frame(seq) }).ok();
        thread::sleep(CAPTURE_PERIOD);              // 20ms
    }
});
// 处理线程：延迟 = 现在 - 采集时刻；heavy_process 里 sleep 45ms 模拟模型
for s in rx.iter() {
    let latency = s.captured_at.elapsed();          // 端到端延迟！
    heavy_process(&s);
}
```

**策略 B：有界队列 + 丢最旧帧**。标准库的 `sync_channel` 只能「丢最新」（满则 `try_send` 失败），要「丢最旧」得手搓一个带容量上限的 `VecDeque`，配 `Condvar` 让处理线程在空队列上等待：

```rust
// buf: Arc<(Mutex<(VecDeque<Stamped>, bool)>, Condvar)>，bool 是「采集结束」标志
// —— 采集线程：满了就丢队首（最旧），再放入最新帧 ——
let mut g = lock.lock().unwrap();
if g.0.len() >= BOUND_CAP {                         // 容量上限 = 4
    g.0.pop_front();                                // 丢最旧的一帧
    *dropped.lock().unwrap() += 1;
}
g.0.push_back(frame);
cvar.notify_one();                                  // 唤醒处理线程
```

运行：

```bash
cargo run --example ch75_rtsp_pipeline
```

某次实测输出（实时调度，数字每次略有浮动，但趋势稳定）：

```text
采集 40 帧，采集节奏 20ms/帧(≈50 fps)，单帧处理 45ms(≈22 fps) → 处理追不上到帧

—— 策略 A：无界队列 / 不丢帧 ——
产出 40 帧，处理 40 帧，丢弃 0 帧；末帧端到端延迟 963ms，估算峰值积压 ~21 帧
总耗时 1948ms（≈处理端速度决定，采集被拖着走）

—— 策略 B：有界队列(容量 4) + 丢最旧帧 ——
产出 40 帧，处理 24 帧，丢弃 16 帧；最大端到端延迟 179ms
总耗时 1169ms（≈采集时长，处理端始终追最新帧）

结论：A 一帧不丢但延迟随时间累积（末帧延迟 963ms）；B 丢了 16 帧，换来延迟被压在 179ms 内。
```

这几个数字把「实时性的取舍」摊得明明白白：

- **策略 A 一帧不丢，但延迟是灾难**：末帧端到端延迟高达 **963ms**——你屏幕上「刚处理完」的这帧，其实是近 1 秒前拍的。更糟的是这延迟**随时间单调增长**（估算峰值积压约 21 帧全卡在队列里），跑得越久越离谱。对「实时闯入检测」，慢 1 秒可能就错过了。
- **策略 B 丢了 16 帧，但延迟被摁死**：40 帧丢了 16、只处理 24 帧（正好 \(24 + 16 = 40\)，帧账目守恒，程序里有 `assert` 守着），但**最大延迟仅 179ms**，且不随时间增长。处理线程永远在啃「最新的那批帧」，这正是实时监控要的。
- **总耗时对比更直观**：A 花 1948ms（被慢处理拖着走，约 \(40 \times 45\text{ms}\)），B 只花 1169ms（约采集时长 \(40 \times 20\text{ms}\)）——B 跟上了摄像头的真实节奏。

示例末尾还演示了 `sync_channel(2)` 的**丢最新**变体：产出 12 帧、处理 5 帧、丢弃 7 帧，实现最省事（`try_send` 遇 `Full` 直接丢当前帧），但保留的是较旧的帧。两种丢帧方向，按你的业务选。

**那真实 RTSP 怎么接？** 把「采集线程合成帧」这段换成 `retina` 拉流即可（需 `cargo add retina tokio`；因它是异步、且解码环节要额外解码器，不纳入本可运行示例）。骨架如下：

```rust
// retina 0.4.20：纯 Rust 收流。注意它是 async（配 tokio），且给的是编码后的 H.264！
use retina::client::{Session, SessionOptions, SetupOptions, PlayOptions};
use retina::codec::CodecItem;
use futures::StreamExt;

let url = "rtsp://user:pass@192.168.1.64:554/stream1".parse()?;
let session = Session::describe(url, SessionOptions::default()).await?;
session.setup(0, SetupOptions::default()).await?;                 // 选第 0 路视频
let mut demuxed = session.play(PlayOptions::default()).await?.demuxed()?;
while let Some(item) = demuxed.next().await {
    if let CodecItem::VideoFrame(f) = item? {
        let encoded: &[u8] = f.data();     // ⚠️ 这是 H.264 NAL 单元，不是像素！
        let _ts = f.timestamp();           // 带 RTP 时间戳，用于跨帧对齐
        // decode(encoded) -> RgbImage -> 塞进上面的有界队列 -> 交给处理线程
        // ↑ decode 这一步：纯 Rust 无成熟方案，实践里走 openh264(C) 或 ffmpeg
    }
}
```

看到那句 `f.data()` 是 H.264 码流、`decode(...)` 需要非纯 Rust 解码器了吗？**这就是「收流易、解码难」的落地形态。** 收流部分 `retina` 干得漂亮，但从 `encoded` 到 `RgbImage` 的那一步，正是纯 Rust 的缺口。

> 💡 **提示**：本章聚焦**单路流**的实时性与背压。真实系统常要同时接**几十上百路**摄像头——那时的调度、汇聚、资源共享是另一套学问，见第 [92 章 多路流并发调度](../p18-events/ch92-multistream.md)。这里先把「一路怎么不堆积、怎么丢帧」吃透，多路无非是它的并行放大 + 全局资源管理。

## 常见坑与提示

> 🕳️ **坑：把采集和处理写在一个循环里串行做。** 这是实时管线头号错误。处理一慢就阻塞采集，帧在网络/摄像头缓冲区堆积甚至被丢，延迟雪崩。**铁律：采集、处理分线程，用队列解耦**（`std::thread` + `mpsc`）。本章的骨架就是最小可用范式。

> ⚠️ **注意：处理慢于到帧时，延迟会累积，不是「稳定地慢一点」。** 很多人以为「处理慢 10ms 就永远慢 10ms」——错。只要 \(\mu < \lambda\)，积压和延迟会**随时间无上限增长**（策略 A 实测末帧延迟 963ms 就是明证）。所以实时系统**必须**有丢帧/有界缓冲来钳制延迟，不能寄希望于「处理平均够快」。

> 🕳️ **坑：丢帧方向搞反。** 实时监控要**丢最旧、保最新**（`VecDeque` 满则 `pop_front`）；如果误用了「丢最新」（`sync_channel` 满则丢当前帧），你会一直处理陈旧帧、把最新画面丢掉，延迟照样爆。选错方向，比不丢还糟。

> ⚠️ **注意：RTSP over TCP 还是 UDP，是延迟与完整性的又一次权衡。** TCP 不丢包但网络抖动时会**重传、累积延迟**（画面卡顿后「快进」）；UDP 低延迟但**丢包即花屏**。工业监控多用 TCP 求稳，实时性极敏感的场景才赌 UDP。`retina` 的 `SetupOptions` 里可以指定 `Transport`。

> 🕳️ **坑：时间戳对齐。** 别用「到达本机的时刻」当帧时间——网络抖动会让它乱序、不准。要用**帧自带的 RTP 时间戳**（`retina` 的 `f.timestamp()`）做跨帧时序判断（比如「2 秒内闯入」）。这和上一章 VFR 视频的教训一脉相承：**信源头时间戳，别信本地墙钟**。

> 💡 **提示：断流与重连是实时系统的必修课。** 摄像头会掉线、网络会抖。生产级拉流必须有**自动重连**（退避重试）、**心跳检测**（一段时间没帧就判定断流），以及重连后的**状态重置**（清空队列、重置背景模型/跟踪器，避免陈旧状态污染——参见第 [63 章](../p13-tracking/ch63-background-motion.md) 的鬼影教训）。本章骨架为聚焦背压未含这些，真实项目一个都不能少。

## 本章小结

- **RTSP** 是摄像头的「遥控器」（控制协议 DESCRIBE/SETUP/PLAY），真正搬运数据的是 **RTP**（可走 TCP 求稳或 UDP 求低延迟）。
- **诚实的能力边界**：纯 Rust **能收流**——`retina`（0.4.20）是成熟的纯 Rust RTSP/RTP 客户端；但它交给你的是**编码后的 H.264 码流**，**解码成像素**这一步纯 Rust 无成熟方案，实践里靠 `openh264`(C)/`dav1d`(C) 或干脆整条走 **ffmpeg 子进程**（拉流+解码）喂给 Rust 处理端——「收流易、解码难」。
- **实时管线铁律**：采集与处理**分线程 + 队列解耦**（`std::thread` + `mpsc`）。当处理慢于到帧（\(\mu < \lambda\)），延迟会**随时间累积**，必须靠**有界队列 + 丢帧**钳制。
- **两种丢帧方向**：实时监控用**丢最旧保最新**（`VecDeque` 满则 `pop_front`）；`sync_channel` 的 `try_send` 是**丢最新**。实测：无界不丢帧末帧延迟 963ms 且持续增长；有界(容量4)丢最旧丢了 16/40 帧，延迟摁在 179ms 内——**看最新胜过看全部**。
- 别忘工程细节：TCP/UDP 权衡、用源头 RTP 时间戳对齐、断流自动重连与状态重置。

## 动手练习

1. **改处理速度看拐点**：把 `PROCESS_COST`（单帧处理耗时）从 45ms 依次改成 15ms（比到帧快）和 80ms（慢得多），重跑。处理比到帧快时，策略 A 的延迟还会累积吗？丢帧数会怎么变？
2. **改队列容量**：把策略 B 的 `BOUND_CAP` 从 4 改成 1 和 16。容量越小，丢得越多、延迟越低吗？找出「延迟」和「丢帧率」随容量变化的趋势，体会这个权衡旋钮。
3. **丢最新 vs 丢最旧**：把策略 B 改成「满了丢当前帧（最新）」而非丢队首，对比两者处理到的帧序号 `seq` 序列——哪种保留了更「新鲜」的画面？
4. **（进阶）加一个「跳帧采样」**：真实系统常主动抽帧（如每 3 帧处理 1 帧）来匹配处理能力。在采集或处理端加一个 `seq % 3 == 0` 的抽帧逻辑，看它和「被动丢帧」在延迟、覆盖上的差别（抽帧与多路调度详见第 [92 章](../p18-events/ch92-multistream.md)）。
