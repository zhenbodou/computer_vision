# 第 74 章 视频读写与帧处理

> **本章导读**
> - 学完你能：把「一段视频」当成一串按时间排列的帧来处理，亲手合成帧序列、做逐帧运动检测、再把结果写回成 GIF/PNG 序列——全程纯 Rust、免外部视频文件、`cargo run` 即可复现。
> - 搞清一个**诚实但关键**的事实：纯 Rust 生态**没有**成熟的通用视频解码（H.264/H.265/mp4）能力，本章讲清「能做什么、做不到什么、替代方案是什么」。
> - 掌握视频处理的三条工程红线：**别一次性 load 整段视频**、帧率与时间戳怎么算、逐帧 I/O 为什么慢。

## 场景引入：我有一个 mp4，想逐帧跑我的算法

你在前面章节写好了一堆图像算法——边缘检测、背景减除、模板匹配。现在拿到一个真实需求：「这有个 `parking.mp4`，帮我逐帧检测有没有车经过。」

你满怀信心地想：`image` 库能读 PNG/JPG，那读 mp4 应该也是一行 `image::open("parking.mp4")` 吧？

**很遗憾，不行。** 这行代码会直接报错——`image` 库根本不认识 mp4。这不是 bug，而是纯 Rust 视频生态的**真实短板**。本章第一件事，就是把这层窗户纸捅破：视频到底是什么、为什么纯 Rust 解码这么难、以及在这个约束下，我们**能踏实跑通**的是哪一部分。

## 原理：视频 = 一串带时间戳的帧

### 直觉：视频就是「快速翻页的连环画」

小时候在书角画一排小人、快速翻页就「动」起来了——这就是视频的本质。**视频（video）= 一串按时间顺序排列的静态图像（帧，frame）**，播放器以固定速度（帧率）一张张丢给你的眼睛，视觉暂留让你觉得它在动。

所以对机器视觉来说，处理视频从来不是什么新魔法，而是两件老本行的组合：

- **逐帧处理**：把每一帧当成一张普通图像，套用你已经会的所有算法（第二~五部分那一整套）。
- **跨帧关联**：把相邻帧联系起来——它比单帧多出的唯一新东西就是**时间**。帧差、光流（第 [59 章](../p13-tracking/ch59-optical-flow.md)）、背景建模（第 [63 章](../p13-tracking/ch63-background-motion.md)）、跟踪（第十三部分）全都建立在「跨帧」之上。

一段视频除了像素，还带两个元数据：**帧率（frame rate, fps）** 和**时间戳（timestamp）**。帧率是每秒多少帧（常见 25/30/60），时间戳是每一帧对应的播放时刻。两者的关系简单到可以背下来：

\\[ t_f = f / \text{fps} \\]

第 \(f\) 帧（从 0 数）的时间戳就是「帧号除以帧率」。10 fps 下第 5 帧就是 \(5/10 = 0.5\) 秒。反过来，知道时长和帧数也能反推帧率。**注意真实视频的帧率常常不是恒定的**（可变帧率 VFR），所以工业里更信任每帧自带的时间戳，而不是「帧号 ÷ 标称帧率」——这点后面的坑里细说。

### 诚实核心：纯 Rust 为什么解不了 mp4

这里必须跟你说实话，否则你会在真实项目里撞得头破血流。

一个 mp4 文件不是「一堆 PNG 打包」，而是经过 **H.264 / H.265（HEVC）** 等编解码器（codec）**高度压缩**的码流：它只存「关键帧 + 后续帧相对关键帧的差异」，还用了运动补偿、熵编码等一堆复杂技术。**要把它还原成一帧帧像素，需要一个完整的 H.264/H.265 解码器**——这东西极其复杂，工业级实现（如 FFmpeg 的 libavcodec）是几十万行 C 代码、多年打磨的成果。

纯 Rust 生态目前**没有**能与之匹敌的通用视频解码器。这不是「找找看有没有库」的问题，而是生态现状。你有四条路可走，各有取舍：

| 方案 | 纯 Rust？ | 能力 | 何时用 |
|------|:---:|------|--------|
| **① ffmpeg 命令行子进程** | ✅（你的代码是） | 用 `std::process::Command` 调系统装好的 `ffmpeg`，把视频**抽帧成 PNG 序列**，再用 `image` 逐张读 | **最通用、最推荐**。生产线上大量这么干 |
| **② `ffmpeg-next` / `ffmpeg-sys`** | ❌ FFI 绑定 | Rust 直接调 libav* 的 C 库，在进程内解码 | 要在进程内、高性能解码，且能接受 C 依赖与编译复杂度 |
| **③ `image` 原生多帧** | ✅ 纯 Rust | **GIF / APNG** 多帧读写（本章能跑的部分） | 处理动图、或把帧序列**写回**成视频（GIF） |
| **④ `symphonia`** | ✅ 纯 Rust | ⚠️ 只解**音频**（mp3/aac/flac…），**不解视频** | 别指望它抽帧，列在这里是防你误会 |

> 📖 **术语**：**容器（container）vs 编解码器（codec）**。`.mp4`、`.mkv`、`.avi` 是**容器**格式（装视频流、音频流、字幕、时间戳的「盒子」）；H.264、H.265、AV1、VP9 是**编解码器**（盒子里视频流的压缩方式）。「读不了 mp4」准确说是「解不了里面的 H.264 码流」。`image` 能读的 GIF、PNG 属于图像/动图格式，压缩方式简单（无帧间预测或仅简单预测），所以纯 Rust 搞得定。

**方案①的骨架**长这样（需系统已装 `ffmpeg`，故不纳入本章的可运行示例，但这是最实用的一招）：

```bash
# 把视频每一帧抽成 PNG：frame_0001.png, frame_0002.png ...
ffmpeg -i parking.mp4 -vf fps=10 frames/frame_%04d.png
```

```rust
// 然后在 Rust 里用 std::process::Command 调它，再逐帧读 PNG
use std::process::Command;
let status = Command::new("ffmpeg")
    .args(["-i", "parking.mp4", "-vf", "fps=10", "frames/frame_%04d.png"])
    .status()?;                       // 阻塞直到抽帧完成
assert!(status.success());
// 之后 glob 一下 frames/ 目录，image::open 逐张处理即可（就是你已经会的）
```

这套「ffmpeg 抽帧 → Rust 逐帧处理」的组合，**是本书对真实视频落地的务实建议**：ffmpeg 负责它最擅长的解码，Rust 负责它最擅长的算法与安全，各司其职。下一章 [第 75 章](ch75-rtsp-streaming.md) 讲实时流时，我们会看到同样的分工哲学。

## 动手写代码：合成帧序列 → 帧差运动检测 → 写回 GIF

既然真实解码要靠外部工具，那本章的**可运行**部分就聚焦纯 Rust 铁定能做的：**合成**一段视频、**逐帧处理**、把结果**写回**成视频。这三步不碰任何外部文件，`cargo run` 就能复现。

配套示例 `code/examples/ch74_video_io.rs`。思路三步走：

**第一步：把「视频」抽象成 `Vec<RgbImage>`。** 我们合成 16 帧、160×120、假定帧率 10 fps 的「视频」：一张左→右灰度渐变的背景，加一个 28×28 的红色方块从画面左侧**移入**、每帧右移 8 像素。

```rust
fn make_frame(f: usize) -> RgbImage {
    let mut img: RgbImage = ImageBuffer::from_fn(W, H, |x, _| {
        let g = (40 + x * 60 / (W - 1)) as u8;         // 背景灰度渐变 40→100
        Rgb([g, g, g])
    });
    let x0 = -SQ + STEP * f as i64;                    // 方块从画外进入，每帧右移 STEP=8px
    // ... 在 (x0, 46) 处画一个 28×28 的红色方块（越界像素跳过）
    img
}
let frames: Vec<RgbImage> = (0..N).map(make_frame).collect();
```

**第二步：逐帧处理——帧间差分数出运动像素。** 对第 \(f\) 帧和第 \(f-1\) 帧，逐像素比较灰度，差值超过阈值就算「运动」。这正是第 [63 章](../p13-tracking/ch63-background-motion.md) 帧差法的最简形式：

\\[ D_f(x,y) = \lvert \text{gray}(I_f) - \text{gray}(I_{f-1}) \rvert > \tau \\]

```rust
fn motion_mask(cur: &RgbImage, prev: &RgbImage) -> (GrayImage, u32) {
    let mut mask = ImageBuffer::from_pixel(W, H, Luma([0u8]));
    let mut cnt = 0u32;
    for (m, (pc, pp)) in mask.pixels_mut().zip(cur.pixels().zip(prev.pixels())) {
        if (luma(pc) - luma(pp)).abs() > THRESH {      // 感知加权灰度差 > 阈值
            *m = Luma([255]);
            cnt += 1;                                  // 数运动像素
        }
    }
    (mask, cnt)
}
```

> 💡 **提示：注意这里只需要相邻两帧同时在内存里。** 我们虽然为了教学把 16 帧一次性 `collect` 成 `Vec`，但真实的长视频**绝不能这么干**（几分钟 1080p 就能吃光内存）。正确姿势是**流式处理**：读一帧、处理一帧、丢一帧，最多保留「上一帧」用于帧差。这个内存纪律，是视频处理和单图处理最大的思维差别。

**第三步：把结果写回成视频（GIF，纯 Rust）。** `image` 库自带 GIF 编码。关键 API 有两个坑要记牢：GIF 的 `Frame` 只吃 `RgbaImage`（不是 `RgbImage`），每帧延迟用 `Delay::from_numer_denom_ms`：

```rust
use image::codecs::gif::{GifEncoder, Repeat};
use image::{Delay, DynamicImage, Frame};

let mut enc = GifEncoder::new(File::create("out.gif")?);
enc.set_repeat(Repeat::Infinite)?;                     // 循环播放
for f in &frames {
    let rgba = DynamicImage::ImageRgb8(f.clone()).to_rgba8();   // RgbImage → RgbaImage
    let delay = Delay::from_numer_denom_ms(1000 / FPS, 1);      // 10fps → 100ms/帧
    enc.encode_frame(Frame::from_parts(rgba, 0, 0, delay))?;
}
```

我们存两个 GIF：原始帧序列 `out_ch74_movie.gif`，以及把运动区染绿、底部加一条时间进度条的 `out_ch74_motion.gif`。运行：

```bash
cargo run --example ch74_video_io
```

逐字实测输出（节选）：

```text
合成视频：16 帧，分辨率 160x120，假定帧率 10 fps → 时长 1.6s

帧 |  时间戳 | 运动像素数
 0 |   0.0s |      0
 1 |   0.1s |    224
 5 |   0.5s |    448
 7 |   0.7s |    448
 9 |   0.9s |    224
13 |   1.3s |      0

合计运动像素 3416，运动最剧烈的是第 5 帧（448 像素）
参考：方块每帧移 8px、边长 28px，稳定期两条差分带 ≈ 2*8*28 = 448 像素
```

这几个数字把帧差法的原理钉死了，值得逐个品味：

- **第 0 帧运动数为 0**：它没有「上一帧」可比，天经地义。
- **进入期（第 1~3 帧）= 224**：方块正从左边缘挤进来，帧差只逮住它**新露出的那条竖边**（宽 8px × 高 28px = 224）。另一条边还在画外。
- **稳定期（第 5~7 帧）= 448**：方块完全进入画面后，帧差同时逮住「离开处」和「新到处」**两条竖带**，恰好 \(2 \times 8 \times 28 = 448\)。理论值和实测严丝合缝——这就是自包含合成数据的好处，**每个数字都能对上账**。
- **离开期与消失（第 9 帧后回落，第 13 帧归零）**：方块驶出右边缘，可见边逐渐减少，最终完全离开画面，帧差归零。

程序还存了第 5 帧的两张静帧 PNG（`out_ch74_frame.png` 原图、`out_ch74_motion.png` 绿色运动叠加）——这演示了「PNG 序列」这种最朴素的视频落盘方式（也正是 ffmpeg 抽帧的产物形态）。打开那两个 GIF，你会看到红方块平滑移动，运动版里绿色带子始终「追」在方块的前后沿上，底部黄条随时间增长。**一个完整的「读（合成）→ 逐帧处理 → 写」视频闭环，就这么用纯 Rust 跑通了。**

## 常见坑与提示

> 🕳️ **坑：别指望一行 `image::open` 解 mp4。** 这是新手最常见的幻灭。`image` 只认图像/动图格式（PNG/JPG/GIF/WebP/APNG…），**不解 H.264/H.265 视频流**。真要处理 mp4/mkv，老老实实上 ffmpeg 子进程抽帧（纯 Rust 侧）或 `ffmpeg-next` FFI（非纯 Rust）。这不是你没找对库，是纯 Rust 生态的客观边界。

> ⚠️ **注意：不要一次性把整段视频 load 进内存。** 一段 1 分钟、30fps、1080p 的视频有 1800 帧，每帧 `RgbImage` 约 6MB，全 load 进来就是 **10GB+**，直接 OOM。视频处理必须**流式**：读一帧→处理→释放，最多保留跨帧算法需要的那几帧（帧差保留 1 帧、光流保留 1 帧、某些跟踪保留数帧）。本章为教学把 16 帧 `collect` 成 `Vec` 是因为量小，真实项目切忌照搬。

> 🕳️ **坑：帧率不等于「帧号 ÷ 标称 fps」。** 很多视频是**可变帧率（VFR）**，或录制时丢过帧、时间戳有跳变。用「帧号 ÷ 25」去算时间戳，在 VFR 视频上会**越算越偏**，导致后续「N 秒内发生了什么」的时间判断全错。**工业做法：信任每帧自带的时间戳（presentation timestamp, PTS）**，而不是自己拿帧号乘除。ffmpeg 抽帧时可用 `-vsync` 相关选项控制，或直接读 PTS。

> ⚠️ **注意：彩色还是灰度，先想清楚。** 很多逐帧算法（帧差、背景减除、光流）只需灰度就够，还快 3 倍（少算两个通道）。本章 `luma()` 用感知加权 \(0.299R + 0.587G + 0.114B\)（与第 [9 章](../p02-image-basics/ch09-color-spaces.md) 一致）先转灰度再比较。但涉及颜色的任务（比如「检测红色物体」）就必须留在彩色空间。别无脑转灰度丢了信息。

> 🕳️ **坑：逐帧 PNG I/O 很慢。** 「抽成 PNG 序列再逐张读」虽然通用，但 PNG 编解码 + 磁盘 I/O 是实打实的开销，处理长视频时可能**慢到离谱**（几万张小文件还会拖垮文件系统）。优化方向：用更快的图像格式（如 QOI/BMP 免压缩）、直接走 ffmpeg 管道（pipe）把裸 RGB 喂进来免落盘、或干脆上 FFI 在进程内解码。本章的 PNG/GIF 落盘是为了「看得见结果」，性能敏感时要另作打算（详见第 [108 章 性能优化](../p21-mastery/ch108-performance.md)）。

## 本章小结

- **视频 = 一串按时间排列的帧 + 帧率/时间戳**；机器视觉处理视频 = **逐帧处理**（复用单图算法）+ **跨帧关联**（帧差、光流、跟踪）。时间戳 \(t_f = f/\text{fps}\)，但 VFR 视频要信每帧自带的 PTS。
- **诚实的能力边界**：纯 Rust **没有**成熟的通用视频解码（H.264/H.265/mp4）。四条替代路：① ffmpeg 子进程抽帧（纯 Rust 侧、最推荐）② `ffmpeg-next` FFI（非纯 Rust）③ `image` 原生 GIF/APNG 多帧（纯 Rust 能跑）④ `symphonia` 只解音频不解视频。
- **纯 Rust 能踏实跑通的闭环**：合成帧序列 `Vec<RgbImage>` → 帧差运动检测（实测运动像素峰值 448 = 2×8×28，与理论严丝合缝）→ 写回 GIF（`GifEncoder`，注意 `Frame` 只吃 `RgbaImage`）/ PNG 序列。
- **三条工程红线**：别一次性 load 整段视频（要流式）、帧率/时间戳别想当然、逐帧 I/O 是性能瓶颈。

## 动手练习

1. **改帧率看时间戳**：把 `FPS` 从 10 改成 25，重新运行，观察时间戳列的变化，验证 \(t_f = f/\text{fps}\)。再想想：如果这是段 VFR 视频，你这样算时间戳会错在哪？
2. **换个跨帧算法**：把帧差换成第 [63 章](../p13-tracking/ch63-background-motion.md) 的 running-average 背景减除，对比运动掩码——帧差的「空洞/鬼影」会不会消失、变成实心方块？
3. **验证 GIF 是真的多帧**：用 `image::open("out_ch74_movie.gif")` 试试只能读到第一帧；再查 `image` 的 `GifDecoder` + `into_frames()`，把 GIF **读回** `Vec<Frame>`，数一数帧数是不是 16。这就打通了纯 Rust 的 GIF「读」闭环。
4. **（进阶）真上一次 ffmpeg**：如果你机器装了 ffmpeg，找一段几秒的 mp4，用上文的 `Command` 骨架抽帧成 PNG 序列，再用本章的帧差代码逐帧处理。体会「ffmpeg 解码 + Rust 算法」的务实分工。
