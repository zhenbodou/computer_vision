# 第 77 章 视频目标检测与跟踪落地

> **本章导读**
> - 这是第十六部分的**综合落地章**：把[第九部分](../p09-detection/ch45-detection-principles.md)的**检测**、[第十三部分](../p13-tracking/ch62-mot.md)的**跟踪**、[第十八部分](../p18-events/ch83-filtering-basics.md)的**事件**，在一路视频流上真正串成一条又快又稳的流水线。
> - 想清楚落地的头号权衡：**逐帧全检测太慢，怎么办**——关键帧检测 + 跟踪补帧，用少得多的算力换住基本不掉的精度。
> - 动手用合成的逐帧检测结果（`Vec<Frame>`）跑一个"**检测 + IoU 关联跟踪 + 跨帧 ID**"最小闭环，打印稳定轨迹与 **ID 切换数（理想 0）**，再实测不同检测节奏下的算力 / 精度权衡。
> - 认清工程真坑：实时性预算、ID 漂移、检测阈值与关联阈值耦合、遮挡，以及那句让无数人栽跟头的"**离线 demo 好、上线掉点**"。

## 场景引入：demo 里跑得好好的，一上线就崩

你照着前面的章节，把一个 YOLO 检测器（[第 46 章](../p09-detection/ch46-yolo-inference.md)）接上摄像头，逐帧检测、逐帧画框——在录好的测试视频上，框又准又稳，你信心满满地上线了。结果第一天就翻车：

- **卡成幻灯片**：检测器每帧要 30ms，可摄像头每秒吐 25 帧（每帧只有 40ms 预算），CPU 一上多路视频立刻追不上，画面开始丢帧、延迟越积越多。
- **框在跳、ID 在换**：同一个人，这一帧编号 3、下一帧编号 7，客流计数瞬间从"1 人"变成"5 人"——因为检测器是**健忘**的，每帧独立框，根本不知道"这个人"和"上一帧那个人"是同一个。
- **偶尔凭空一个框、偶尔真人没框**：单帧的误检漏检，让告警忽有忽无。

这些都不是"模型不够准"能解决的——它们是**工程落地**的问题。本章要回答的，正是学术论文很少讲、而真实项目天天在头疼的三件事：**怎么让它跑得够快（实时性）、怎么让目标 ID 稳定（跟踪）、怎么让离线的好精度别在上线时掉光（部署一致性）**。

## 原理：检测 + 跟踪的级联流水线

### tracking-by-detection：检测管"有什么"，跟踪管"谁是谁"

单靠检测器，你每帧得到的是"这一帧有哪些框"，但框与框之间**没有身份**。要把"同一个目标"跨帧连成一条轨迹、给一个**稳定 ID**，就得在检测之后接一个**跟踪器**。这套"检测器发现目标、跟踪器负责关联"的范式叫 **tracking-by-detection**，是 [第 62 章](../p13-tracking/ch62-mot.md) SORT 的核心，也是绝大多数落地系统的骨架：

```text
                  ┌──────────────────── 每一路视频流 ────────────────────┐
 摄像头/RTSP → 解码成帧 → 检测器 → 数据关联(IoU) → 跟踪器(卡尔曼/恒速) → 稳定轨迹 → 事件规则层 → 告警
  (第75章)     (第74章)   (第9部分)    ↑本章重点↑      (第62章)          Track     (第18部分)    Event
                          Detection                                              └ 绊线/停留/计数
```

- **检测器（[第 9 部分](../p09-detection/ch45-detection-principles.md)）**：逐帧或隔帧给出 `Detection`（框 + 类别 + 置信度）。
- **数据关联（本章重点）**：把这一帧的检测框，正确地接到上一帧的某条轨迹上——最朴素的度量就是 **IoU（交并比）**。
- **跟踪器（[第 62 章](../p13-tracking/ch62-mot.md)）**：维护每条轨迹的运动状态（位置 + 速度），匹配上就校正，没匹配上就靠预测**续命**。
- **事件层（[第 18 部分](../p18-events/ch83-filtering-basics.md)）**：拿稳定轨迹去做绊线计数、区域停留、逆行判断。

> 📖 **术语**：本章的数据模型 `BBox` / `Detection` / `Frame` 沿用[第 83 章](../p18-events/ch83-filtering-basics.md)介绍的那套**共享心智**（框用左上角 + 宽高，坐标原点在左上）——检测给 `Frame`，跟踪把它连成 `Track`，事件层消费 `Track`。整本书的视频落地都建立在这条"Detection → Track → Event"的链路上。

### 落地头号权衡：逐帧全检测 vs 关键帧 + 跟踪补帧

**逐帧全检测**（每一帧都跑检测器）精度最高，但也最烧算力——检测器通常是整条流水线里**最贵**的一环（几十毫秒），而跟踪器（IoU + 恒速预测）便宜得几乎不要钱（毫秒级）。

于是有了省算力的关键一招：**关键帧检测 + 跟踪补帧**。**每隔 K 帧才跑一次检测**（关键帧），中间的帧只让跟踪器**靠运动预测把框往前推**（补帧）。检测器调用次数直接降到 \\( 1/K \\)：

\\[ \text{检测器调用次数} \approx \frac{\text{总帧数}}{K}, \qquad \text{省下算力} \approx \left(1 - \frac{1}{K}\right)\times 100\% \\]

这背后是一个朴素的物理事实：**目标的运动是连续的**——它不会在两帧之间瞬移。所以中间几帧的位置，完全可以用"上次检测到的位置 + 速度"外推出来，不必每帧都劳师动众地重跑检测。代价是：外推是**近似**，目标一旦拐弯 / 变速，补帧的框就会**漂移**；K 越大漂移越狠。这就引出了精度与算力的权衡——我们马上用代码把它量出来。

### 实时性预算：一道必须算清的算术题

落地前先算一笔账。设检测器单次耗时 \\( D \\)、每帧跟踪开销 \\( t \\)、目标帧率对应的每帧预算 \\( B \\)（25fps 时 \\( B = 1000/25 = 40 \\) ms）。逐帧检测要求 \\( D + t \le B \\)；关键帧模式把检测摊薄到 K 帧，只要求：

\\[ \frac{D}{K} + t \le B \\]

一个 30ms 的检测器，逐帧跑（\\(K=1\\)）平均 31ms/帧、勉强追上 25fps 且毫无余量；改成每 4 帧检一次（\\(K=4\\)），平均只要 8.5ms/帧，余量充足——同样的硬件，要么多扛几路视频，要么换更弱的边缘设备也跑得动。**这道算术题，决定了你的系统能不能上线。**

## 动手写代码：检测 + 跟踪最小闭环 + 算力权衡

配套示例 `code/examples/ch77_video_detection.rs`，只用标准库，直接：

```bash
cargo run --example ch77_video_detection
```

我们**合成** 40 帧、3 个目标沿"缓弯"（水平匀速 + 垂直缓慢正弦摆）运动的场景，并**故意让目标 2 在第 18、19 帧漏检**（模拟短暂遮挡）。每个检测带一个**隐藏的真值 id**（`gt`，跟踪器看不到），只用于事后统计 ID 切换和轨迹误差——这是评估跟踪器的标准手法（同 [第 62 章](../p13-tracking/ch62-mot.md)）。

跟踪器是 SORT 的落地简化版：**IoU 贪心关联 + 生命周期管理**，运动模型用一个对"检测节奏"更友好的**有限差分测速**——匹配上时，用两次观测的位移除以真实间隔 \\( dt \\) 估速度（这样无论隔几帧检一次，速度估计都不失真），非关键帧就靠这个速度把框往前推：

```rust
fn predict(&mut self) {              // 非关键帧也照走：按速度补帧前进
    self.cx += self.vx; self.cy += self.vy;
    self.time_since_update += 1;     // 距上次被检测校正的帧数（即刚 coast 的间隔）
}
fn update(&mut self, b: &BBox) {     // 关键帧匹配上：校正 + 重估速度
    let (mx, my) = b.center();
    let dt = self.time_since_update.max(1) as f32;    // 刚 coast 了几帧
    let (nvx, nvy) = ((mx - self.last_obs.0) / dt, (my - self.last_obs.1) / dt); // 有限差分测速
    if self.hits == 1 { self.vx = nvx; self.vy = nvy; }          // 第 2 个观测：直接定速
    else { self.vx = 0.7*self.vx + 0.3*nvx; self.vy = 0.7*self.vy + 0.3*nvy; } // 之后轻度平滑
    self.cx = mx; self.cy = my;      // 位置贴到观测
    self.last_obs = (mx, my); self.hits += 1; self.time_since_update = 0;
}
```

主循环严格照"**预测 → （关键帧才）关联+更新+新建 → 老化删除 → 评估**"走。关键的一行开关，就是"这一帧要不要跑检测"：

```rust
if f % keyframe_k == 0 {             // K=1 即逐帧全检测；K>1 即隔 K 帧检一次
    detector_calls += 1;
    let (matched, un_d) = associate(&tracks, &frame.detections);  // IoU 贪心关联
    // ... 匹配上的 update；没匹配上的检测新建轨迹；并统计 id-switch
}
// 非关键帧：跳过检测与关联，轨迹仅靠上面的 predict() 补帧前进
```

### 真实运行结果

**先看逐帧全检测（K=1）的最小闭环**——这正是本章要的"检测 + IoU 关联 + 跨帧 ID"（逐字实测）：

```text
== 模式 A：逐帧全检测（K=1）——检测+IoU关联+跨帧ID 最小闭环 ==
  真值目标 gt1 -> 稳定跟踪 id1
  真值目标 gt2 -> 稳定跟踪 id2
  真值目标 gt3 -> 稳定跟踪 id3
  检测器调用 40 次 | ID 切换 = 0（理想 0）| 覆盖率 98% | 平均轨迹误差 1.03px
```

**ID 切换 = 0**——三个目标各自被稳定跟踪，全程编号纹丝不动（包括目标 2 那两帧遮挡，靠恒速预测无缝续上）；轨迹误差仅 1.03px（就是检测抖动本身）。这就是一条健康的检测-跟踪闭环该有的样子。

**再看关键帧 + 补帧的算力 / 精度权衡**——同一个场景、同一套跟踪器，只改检测节奏 K：

```text
== 模式 B：关键帧检测 + 跟踪补帧——省算力 vs 掉精度 ==
K       检测调用      覆盖率      ID切换     平均轨迹误差      省算力
每1帧     40次       98%      0        1.03px      0      %
每2帧     20次       95%      0        1.60px      50     %
每4帧     10次       90%      0        3.34px      75     %
每6帧     7次        3%       16       3.71px      82     %
每10帧    4次        0%       9        0.00px      90     %
```

这张表把落地权衡钉死了，值得逐行盯：

- **K=1→4：省算力立竿见影，精度优雅退化。** 检测调用从 40 次砍到 10 次（省 75% 算力），**ID 切换始终是 0**，轨迹误差从 1.03px 温和涨到 3.34px——目标运动平缓时，补帧的框够准，跟踪照样稳。**K=4 是这个场景的甜点**：四分之一的检测开销，换来几乎不掉的跟踪质量。
- **K=6 起断崖式崩溃。** 覆盖率从 90% 暴跌到 3%、ID 切换飙到 16。为什么？关键帧间隔一旦大到"目标在两次检测之间移动超过一个框的尺度"，冷启动时的预测框和新检测框**完全不重叠（IoU=0）**，关联直接失败——跟踪器接不上，只能不停**新建轨迹、换新 ID**，轨迹碎成一地。（K=10 那行"误差 0.00px"更要小心：它不是完美，而是**覆盖率 0%、几乎没跟住任何目标**，无从谈误差——这正是"覆盖率"这一列存在的意义，别被漂亮的误差数字骗了。）

**最后是实时性预算**，把 K 换算成能不能喂饱帧率：

```text
== 实时性预算（设检测器单次耗时 D=30ms，跟踪+关联≈1ms/帧）==
帧预算（25fps）= 40ms/帧。检测器 D=30ms/次。
  K=1: 平均 31.0ms/帧（检测摊薄 30.0 + 跟踪 1）-> 理论上限 32fps  ✓ 喂得饱
  K=2: 平均 16.0ms/帧（检测摊薄 15.0 + 跟踪 1）-> 理论上限 62fps  ✓ 喂得饱
  K=4: 平均  8.5ms/帧（检测摊薄  7.5 + 跟踪 1）-> 理论上限 118fps ✓ 喂得饱
```

结论一目了然：逐帧检测（K=1）勉强够 25fps 且没余量，K=4 却能理论上冲到 118fps。**把这张精度表和这张预算表并排看，你就知道 K 该怎么选**——在"跟踪还稳"的 K 里，挑最大的那个（这里是 4），算力和精度双赢。

## 真实检测器怎么接进来

demo 里 `Frame` 的检测是合成的；真实系统里，它来自一个跑在图像上的检测器。接口其实很干净——把"哪来的检测"隔离在一个函数后面：

```rust
// demo：返回合成检测。生产：内部加载 ONNX 模型跑前向，把输出解析成 Detection。
fn detect(frame_rgb: &RgbImage) -> Vec<Detection> { /* ... */ }
```

生产里这个 `detect` 内部，就是[第 46 章](../p09-detection/ch46-yolo-inference.md)的 YOLO 推理：用纯 Rust 的 **tract** 加载 `.onnx` 模型（或性能更强、但依赖 C++ 的 **ort**）跑前向，再做 NMS——完整链路见 [第 94 章 ONNX 跨框架推理](../p19-deploy/ch94-onnx.md)，本章不重复塞模型代码。**跟踪、关联、事件那一整套，完全不用改**——这正是把"哪来的检测"隔离出去的价值：检测器可以随便换（YOLO 换成 RT-DETR），下游纹丝不动。

## 常见坑与提示

> 🕳️ **坑：检测阈值和关联阈值是"耦合"的，别孤立调。** 你把检测置信度阈值**调高**（为了少些误检），结果真目标偶尔达不到阈值、漏检变多，跟踪器频繁断轨；你把它**调低**（为了少漏检），又冒出一堆低质量框污染关联、IoU 阈值稍松就接错。检测阈值、关联 IoU 阈值、跟踪的 `max_age`（容忍几帧漏检）必须**一起调**——这和 [第 62 章](../p13-tracking/ch62-mot.md)说的"卡尔曼增益、IoU 阈值、max_age 要一起调"是同一个道理。

> 🕳️ **坑：ID 漂移与遮挡是跟踪的老大难。** 两个目标交叉、遮挡时，纯 IoU 几何信息不足以区分，ID 容易接反（一次 id-switch）。本章场景让三条轨迹分处不同"车道"来规避，真实拥挤场景要么上匈牙利算法求全局最优关联，要么请出 **DeepSORT** 的外观特征（见 [第 62 章](../p13-tracking/ch62-mot.md)）。评估跟踪器时，**ID 切换数**和 MOTA / IDF1 一样是硬指标——框都框对但 ID 乱跳的跟踪器，对客流计数是灾难。

> ⚠️ **注意：漏检 / 误检要靠时序平滑，别信单帧。** 单帧的偶发漏检，交给跟踪器的 `max_age` 用预测续命（本章目标 2 遮挡两帧照样 0 切换）；单帧的偶发误检，交给[第 85 章](../p18-events/ch85-temporal-window.md)的 **N/M 投票 + 状态机**在时间维度上确认。检测、跟踪、事件三层各司其职地"抹平"抖动，最终告警才稳。

> 🕳️ **坑：离线 demo 好，上线掉点——十有八九是预处理不一致。** 这是最坑、最难查的一类问题，务必刻进脑子（呼应 [第 40 章](../p07-dl-basics/ch40-burn-train.md)的专家告诫）：训练 / 导出模型时用的预处理，和上线推理时**必须逐字节一致**，否则精度断崖式下跌。高频雷区——① **通道顺序**：训练用 RGB，而很多视频解码库默认吐 **BGR**，喂反了颜色全错；② **缩放方式**：训练用带 letterbox（保持长宽比补边）的 640×640，上线随手 `resize_exact` 拉伸变形，目标比例全乱；③ **归一化**：均值方差 / 除 255 / 值域 \\([-1,1]\\) 对不上。这些在离线测试集（同一套预处理）上根本暴露不出来，一上线换了数据源就现原形。**排查落地掉点，先查预处理，别急着怪模型。**

> 💡 **提示：多路视频靠"每路一线程 + 通道汇聚"。** 单路跑通后要上多路（一个 NVR 几十路摄像头），纯 Rust 的稳妥架构是 `std::thread` 每路一线程解码 + 检测跟踪，结果用 `std::sync::mpsc` 通道汇到主线程统一处理，并设**丢帧背压**策略（处理不过来就丢旧帧、保实时）。这套并发调度见 [第 92 章](../p18-events/ch92-multistream.md)，性能压榨见 [第 108 章](../p21-mastery/ch108-performance.md)。

## 本章小结

- 视频落地的骨架是 **tracking-by-detection** 的级联流水线：解码 → 检测（给 `Detection`）→ IoU 数据关联 → 跟踪（连成稳定 `Track`）→ 事件层（产出告警）。
- 头号权衡是**逐帧全检测 vs 关键帧 + 跟踪补帧**：每 K 帧检一次、中间靠运动预测补帧，检测算力降到 \\(1/K\\)；代价是补帧框会随 K 增大而漂移。
- 实测（40 帧、3 目标、含遮挡）：逐帧检测（K=1）跑通最小闭环，**ID 切换 = 0**、轨迹误差 1.03px；提到 K=4 省 75% 算力仍是 **0 切换**、误差 3.34px（甜点）；K≥6 则因关联失败**断崖式崩溃**（覆盖率骤降、ID 切换飙升）。配合实时性预算表，就能选出"最省又还稳"的 K。
- 真实检测器接入只需把 `detect()` 换成 [第 94 章](../p19-deploy/ch94-onnx.md) 的 ONNX 推理（tract / ort），下游跟踪与事件不变。
- 工程真坑：检测阈值与关联阈值耦合、ID 漂移与遮挡、漏检误检要靠时序平滑，以及最坑的"**离线好、上线崩**"——先查 BGR / 缩放 / 归一化的预处理一致性。

## 动手练习

1. **找你的甜点 K**：把 `synth_scene` 里目标的水平速度从 4px/帧调到 8px/帧（动得更快），重跑，观察断崖从 K=6 提前到多少——体会"关键帧间隔不能大于目标移动一个框尺度的时间"这条铁律。
2. **制造一次 ID 切换**：把三条轨迹的 `cy`（车道）都设成同一个值，让它们正面交叉重叠，重跑 K=1，看 ID 切换是否从 0 变正——这就是"纯 IoU 打不过遮挡"的现场，也是 DeepSORT 存在的理由（[第 62 章](../p13-tracking/ch62-mot.md)）。
3. **接上事件层**：把跟踪输出的稳定轨迹，喂给[第 87 章](../p18-events/ch87-tripwire.md)的绊线逻辑，在画面中央画一条竖线，数"从左到右穿过的目标数"——把检测、跟踪、事件三层真正串成一个客流计数器（这正是[第 104 章](../p20-projects/ch104-people-counting.md)项目的雏形）。
4. **（进阶）算你自己的实时预算**：把 `D`（检测耗时）改成你手头模型的实测值（用[第 108 章](../p21-mastery/ch108-performance.md)的 `criterion` 基准测一下），再定你的目标帧率与路数，算出该选的 K 和单机能扛几路。
