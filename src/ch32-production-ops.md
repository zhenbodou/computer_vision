# 第 32 章 · 生产化与运维：热更新、监控闭环与告警投递

> **本章导读**：第 29 章把 demo 变成了能稳定跑的服务，第 30、31 章教你量化模型、守住质量。但真正的资深工程师知道：**交付上线不是终点，而是运维的起点**。系统跑起来之后，还有一连串只有生产环境才会逼你面对的问题——**模型要升级，但服务不能停**（热更新）；**报警产出了，怎么保证一条都不丢地送到上层平台**（可靠投递，这正是第 27、28 章反复挖坑说"留到后面讲"的那件事）；**系统半夜悄悄变慢/变差了，谁来告诉你**（监控闭环与系统告警）；**模型没动，但现场环境变了，效果慢慢下滑**（数据漂移）；**新模型不敢直接全量换，怎么灰度**；**这台机器到底能扛几路**（容量规划）。这一章把这些"上线之后"的功课一次讲全，让你的系统不只是"能交付"，而是"交付后还能被人放心地长期运营"。这也是全书的收官——我们会在最后回望从一个像素到一套可运营产品的完整旅程。

## 32.1 从"上线"到"运维"：交付只是开业第一天

先摆正心态。很多人以为项目的终点是"代码写完、跑通、部署"，其实那只是**开业第一天**。

拿开餐厅打比方：装修好、菜单定好、开门迎客，只是**开始**。真正的经营是之后每一天的事——**客流高峰扛不扛得住**（容量）、**食材坏了怎么及时发现**（监控）、**换了个厨师菜味道变没变**（模型热更新与回归）、**客人投诉能不能第一时间知道**（告警）、**淡旺季菜量怎么调**（数据漂移与容量规划）。一家开了三年还口碑稳定的餐厅，靠的不是开业那天的装修，而是**日复一日的运营能力**。

软件系统一模一样。**运维（Operations）关心的是系统"活着的每一天"**：

- 系统现在健康吗？慢了吗？丢帧了吗？（**监控**，32.4）
- 出问题了谁第一时间知道、怎么知道？（**告警**，32.5）
- 模型/配置要改，怎么在不停服的前提下换？（**热更新**，32.2）
- 产出的业务事件（报警、计数、抓拍）怎么可靠地送出去、不丢不重？（**可靠投递**，32.3）
- 模型效果在悄悄下滑吗？（**数据漂移监控**，32.6）
- 新版本怎么安全地放量？（**灰度发布**，32.7）

这一章就沿着这几个问题走。

## 32.2 模型热更新：不停服也能换模型

**痛点很具体**：你的周界报警服务 7×24 跑着，现在算法团队给了个召回更高的新模型，你想换上去。最笨的办法是"停服务、换文件、重启"——但重启期间**这段时间的画面完全没人看**，对安防是不可接受的空窗；多路服务重启还要重新连所有 RTSP、重新预热，几十秒的盲区。**生产系统要能"热更新"：在不中断处理的前提下，把运行中的模型换掉。**

热更新的核心是**原子替换 + 失败回滚**：新模型在后台悄悄加载、预热好，**确认能用了**再一瞬间切过去；**新模型加载失败就继续用旧的**，绝不能因为换模型把服务搞挂。

**先看简单的一半——配置热更新。** 配置（阈值、ROI、计数线）是只读、可安全共享的数据，用 `arc-swap` 的 `ArcSwap` 就能无锁地原子替换。读的一方（处理线程）几乎零开销，写的一方（重载线程）`store` 一下就完成切换：

```rust,ignore
use arc_swap::ArcSwap;
use std::sync::Arc;

// 全局共享、可热替换的配置
static CONFIG: once_cell::sync::Lazy<ArcSwap<PerimeterConfig>> =
    once_cell::sync::Lazy::new(|| ArcSwap::from_pointee(load_config().unwrap()));

// 处理线程：每帧取当前配置（load 极快，几乎零成本），永远拿到"当下最新"的一份
fn per_frame() {
    let cfg = CONFIG.load();          // Arc 快照，读期间不阻塞写
    let _thr = cfg.score_thresh;      // 用它
}

// 重载线程：收到"配置文件变了"信号时，加载新配置、校验通过后原子换上
fn reload_config() -> anyhow::Result<()> {
    let fresh = load_config()?;       // 解析失败就直接返回 Err，旧配置纹丝不动
    validate(&fresh)?;                // ★ 换上去前先校验，别把坏配置生效
    CONFIG.store(Arc::new(fresh));    // 原子替换：下一帧就用新的了
    tracing::info!("配置已热更新");
    Ok(())
}
```

**再看难的一半——模型热更新。** 第 29 章定死了两条事实：`Session::run` 需要 `&mut self`，且**一个 Session 不能跨线程并发 run**，所以每个推理线程独占一个 `Detector`。这意味着模型不能像配置那样简单 `ArcSwap` 共享替换。**正确姿势是让推理线程自己换**：给它发一条"重载"控制消息，它在两帧之间的空隙，后台构建并预热新 `Detector`，成功了就替换自己手里那个、失败就留着旧的继续跑：

```rust,ignore
use crossbeam::channel::Receiver;

/// 推理线程：正常推理的同时，监听重载指令
fn infer_stage_hot(
    rx_frame: Receiver<Prepped>,
    rx_reload: Receiver<String>,      // 收到新模型路径就热切换
    mut detector: Detector,           // 本线程独占，第29章的铁律
) -> anyhow::Result<()> {
    loop {
        // 优先处理重载指令（非阻塞查一下）
        if let Ok(new_path) = rx_reload.try_recv() {
            match Detector::load(&new_path) {         // load 内部已含 warmup（第26章）
                Ok(fresh) => {
                    detector = fresh;                  // ★ 原子替换：旧的在此刻被 drop
                    tracing::info!(model = %new_path, "模型热更新成功");
                }
                // ★ 关键：新模型加载/预热失败，继续用旧的，服务不中断
                Err(e) => tracing::error!(error = %e, "新模型加载失败，继续用旧模型"),
            }
        }
        // 正常推理
        match rx_frame.recv() {
            Ok(prepped) => { let _ = detector.infer(prepped.input)?; /* 送下游 */ }
            Err(_) => break, // 上游关闭，收尾
        }
    }
    Ok(())
}
```

三个必须守住的原则，记牢：**① 先加载预热、校验通过，再切换**（别让第一个真实请求当小白鼠，呼应第 29 章预热）；**② 切换要原子**（不能出现"半旧半新"的中间态）；**③ 失败必须回滚到旧版本**（热更新的底线是"最坏也就是没更新成功"，绝不能是"服务挂了"）。再配上模型文件的**版本号管理**（第 29 章），热更新才算闭环——你永远知道现在跑的是哪一版，出问题能一键切回。

## 32.3 告警与事件的可靠投递：一条都不能丢

第 27 章的 `raise_alarm`、第 28 章的计数与抓拍，都在结尾留了一句"生产里通常改成推 MQ / webhook / 数据库，属于工程化范畴，后面讲"——**就是现在讲。** 这是运维里最容易出事、又最容易被新手忽视的一环。

**问题的本质**：业务事件（"检测到入侵""进出计数+1""抓拍了一张脸"）产生在你的视觉服务里，但真正要用它的是**上层平台**（弹窗派单的监控中心、存档的数据库、通知的消息队列）。这中间隔着网络，而**网络会抖、下游会宕、进程会重启**。天真地写一句 `http_post(alarm)` 会碰上一堆问题：POST 失败了怎么办？下游平台正好在重启、连不上怎么办？同一条报警重试了两次，上层会不会弹两次窗？

生产级投递要解决三件事，逐个说清楚：

**① 至少投递一次（at-least-once）+ 重试退避。** 一次失败不能就把事件丢了——网络抖动是常态。要**重试**，且**退避**（间隔递增，别把正在恢复的下游又打垮）：

```rust,ignore
/// 把一个事件送出去；失败就退避重试，最终仍失败则落本地兜底（见③）
fn deliver_with_retry(sink: &dyn AlertSink, ev: &AlertEvent, max_retry: u32) -> anyhow::Result<()> {
    let mut delay = std::time::Duration::from_millis(200);
    for attempt in 0..=max_retry {
        match sink.deliver(ev) {
            Ok(()) => return Ok(()),
            Err(e) if attempt < max_retry => {
                tracing::warn!(attempt, error = %e, "投递失败，退避重试");
                std::thread::sleep(delay);
                delay = (delay * 2).min(std::time::Duration::from_secs(10)); // 指数退避封顶
            }
            Err(e) => return Err(e), // 重试耗尽，交给上层落兜底
        }
    }
    Ok(())
}
```

**② 幂等 / 去重（idempotency）。** "至少一次"的代价是**可能重复**（重试成功了，但其实上一次也到了）。所以每个事件带一个**全局唯一 ID**（如 `现场id + track_id + 事件类型 + 时间戳` 哈希），下游用这个 ID 去重，**同一个事件 ID 只处理一次**。这样"至少一次投递"+"下游按 ID 去重"就等价于"恰好一次"的效果——这是分布式系统里的经典组合，比追求"精确一次投递"务实得多。

```rust,ignore
struct AlertEvent {
    event_id: String,   // ★ 幂等键：下游靠它去重，重复投递不会重复告警
    site_id: String,    // 哪一路摄像头/现场
    kind: String,       // "intrusion" / "count" / "face_snapshot"
    track_id: u64,
    ts_ms: i64,         // 事件发生的时间戳
    payload: serde_json::Value, // 抓拍图路径、坐标等
}
```

**③ 下游宕了也不丢——本地兜底（outbox）。** 如果下游平台整个挂了、重试也全失败，事件不能就这么蒸发。正确做法是**先写本地持久队列（磁盘文件/嵌入式 DB），再由一个后台任务慢慢补投**——下游恢复后，积压的事件按顺序补送出去。这就是 "outbox 模式"：**本地落盘是最后一道防线，保证"产生了的事件迟早会送达"**。

```text
视觉服务产生事件
      │
      ▼
 ┌──────────┐  投递成功  ┌────────────┐
 │ 本地 outbox│─────────▶│ 上层平台/MQ │
 │ (落盘持久) │◀─┐失败重试 └────────────┘
 └──────────┘  │
      ▲        └─ 下游宕机时事件堆在 outbox，恢复后后台补投——一条不丢
      │
   进程重启也还在（因为落了盘）
```

把 `AlertSink` 抽象成一个 trait（呼应第 27 章"报警动作写成一个方法就是留好扩展点"），不同下游（HTTP webhook、Kafka、数据库）各实现一份，上层逻辑不变：

```rust,ignore
trait AlertSink: Send + Sync {
    fn deliver(&self, ev: &AlertEvent) -> anyhow::Result<()>;
}
struct WebhookSink { url: String }
struct KafkaSink   { /* producer */ }
// impl AlertSink for 各自实现 deliver：HTTP POST / 生产到 topic / INSERT 一行
```

这样第 27 章的 `raise_alarm` 就从"存本地图 + println"平滑升级成"构造 `AlertEvent` → `deliver_with_retry` → 失败落 outbox"，而判定逻辑一行都不用改。

## 32.4 监控闭环：让系统自己说话

第 29 章讲了用 `tracing` 打**日志**，但日志和**监控指标（metrics）**是两件事，资深工程师分得很清：

- **日志（log）**：记录"发生了什么"的**离散事件**，用于**事后排���**——"3 点 07 分这一帧解码失败了"。你出了问题才去翻它。
- **指标（metrics）**：随时间连续变化的**数值曲线**，用于**实时观测趋势**——"最近 5 分钟平均 FPS 从 25 掉到 12"。它主动告诉你系统正在变差，**不用等出事**。

**运维要的是指标闭环**：系统持续吐出关键数值 → 被采集存进时序库 → 画成仪表盘（dashboard）实时看 → 异常了自动告警（32.5）。视觉服务最该监控的一组指标：

| 指标 | 看什么 | 异常意味着 |
| --- | --- | --- |
| **端到端 FPS / 延迟(p50/p99)** | 处理速度 | 掉了 = 过载或卡顿 |
| **各 stage 队列深度** | 通道积压（第29章） | 某段持续满 = 那就是瓶颈 |
| **丢帧率** | 实时流丢了多少 | 飙升 = 处理不过来 |
| **GPU / CPU 利用率** | 算力用满没 | GPU 低 = 没喂饱（第29章）；CPU 满 = 前后处理卡 |
| **内存 RSS** | 是否单调涨 | 涨不停 = 泄漏（第31章长稳） |
| **RTSP 连接状态 / 重连次数** | 每一路活着没 | 频繁重连 = 某路摄像头/网络有问题 |
| **每路在线时长 / 事件产出率** | 业务是否正常 | 某路 0 事件 = 可能挂了或标定错了 |

工程上把这些做成一个可被采集的快照。生产里常用 Prometheus 这类时序系统——服务暴露一个 `/metrics` 端点，监控系统定时来拉：

```rust,ignore
/// 一个可原子更新、随时可读的运行时指标快照
#[derive(Default)]
struct Metrics {
    frames_processed: std::sync::atomic::AtomicU64,
    frames_dropped:   std::sync::atomic::AtomicU64,
    infer_latency_ms: std::sync::atomic::AtomicU64, // 最近一帧（或滑窗均值）
    queue_depth:      std::sync::atomic::AtomicU64,
}
impl Metrics {
    fn on_frame(&self, latency_ms: u64) {
        use std::sync::atomic::Ordering::Relaxed;
        self.frames_processed.fetch_add(1, Relaxed);
        self.infer_latency_ms.store(latency_ms, Relaxed);
    }
    fn on_drop(&self) {
        self.frames_dropped.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
    }
    // 导出成 Prometheus 文本格式，挂到 HTTP /metrics 端点供采集
    fn export(&self) -> String { /* 拼 "app_fps 23.5\n..." 之类 */ String::new() }
}
```

**核心理念叫"可观测性（observability）"**：系统要能**从外部看清内部状态**，而不是个黑盒。没有指标闭环，你对线上系统的了解全靠用户投诉——那太晚了。

## 32.5 系统告警：什么时候该把你叫醒

注意区分：第 27 章的"报警"是**业务事件**（有人闯入）；这里的"告警（alert）"是**系统自身健康**出了问题（服务要挂了）。监控指标（32.4）画成曲线只是"能看见"，还要在**指标越过危险线时主动通知运维**，才闭环。

该为哪些情况设系统告警？——**那些"再不管系统就要出事"的**：

- **某路 RTSP 断流超过 N 秒**：这一路瞎了，安防出现盲区。
- **整体 FPS 跌破阈值 / p99 延迟飙升**：过载了，事件在延迟或丢失。
- **队列持续打满、丢帧率飙升**：处理能力顶不住当前负载。
- **内存单调上涨逼近上限**：泄漏，快 OOM 了（第 31 章长稳）。
- **模型热更新失败 / 进程重启**：需要人介入确认。

但告警有个致命反模式必须避开——**告警疲劳（alert fatigue）**：设得太敏感，天天误报、半夜狂响，运维麻木了，**真出事的那条也被当噪声忽略**。所以：

- **只为"需要人立刻行动"的事设告警**；"仅供参考"的放仪表盘看趋势，别设成告警。
- **设合理的阈值和持续时间**：不是"FPS 掉一帧就报"，而是"连续 1 分钟低于 15 才报"，滤掉瞬时抖动。
- **分级**：致命（服务已挂，立刻叫醒 on-call）、警告（在劣化，工作时间看）、提示（记录即可）。

这背后是 **SLO（服务等级目标）**的思维：先定义"这个服务健康的标准是什么"（如"99% 的时间 FPS≥20、每路断流<30 秒"），告警就是在**即将违反 SLO 时**触发。**先想清楚"什么叫健康"，才知道"什么时候该报警"**。

## 32.6 数据漂移：模型没变，世界变了

这是最隐蔽、最能体现资深水平的一个运维话题。**模型上线时测得好好的（第 30 章 mAP 很高），跑着跑着效果却慢慢下滑——模型文件一个字节没改，怎么会变差？** 因为**变的是世界，不是模型**。这叫**数据漂移（data drift）**：

- 摄像头位置被人挪了、镜头脏了、起雾了；
- 季节变了：夏天短袖、冬天羽绒服、下雪，画面分布和当初的测试集不一样了；
- 新增了一路摄像头，装在了训练数据完全没覆盖的诡异角度；
- 现场业务变了：原来是空旷院子，现在堆满了货箱。

模型是在"过去的数据分布"上评估合格的，**当现场分布偏离了那个分布，模型的表现就没人保证了**——但它不会报错，只是默默变差。这正是第 30 章"测试集必须和上线场景同分布"那句话的运维续集：**分布是会随时间漂移的。**

**难点在于线上没有标注**——你不知道"真值"，怎么发现模型变差了？几个无需人工标注的**代理信号**：

- **检测置信度分布偏移**：把每天所有检测的置信度分数画成直方图，正常时形状稳定；**如果整体分数明显往下移**，往往是画面变得"陌生"了，模型没把握了。
- **产出量异常**：某路平时每天 ~200 次计数，突然连续几天变成 5 次或 5000 次——多半是标定错了、镜头动了或场景变了。
- **框的尺寸/位置分布突变**：目标框普遍变小（镜头拉远了？）、集中在某个角落（视角变了？）。

发现疑似漂移后的闭环做法：**定期从线上抽样一批真实帧 → 人工标注 → 加进测试集重新评估（第 30 章）→ 掉点严重就触发模型迭代**。这个"**抽样—标注—回灌—评估**"的循环，是让模型跟上现实变化的长期机制，也是"运维一个 AI 系统"和"运维一个普通服务"最不一样的地方——**AI 系统的质量会随时间和环境自然衰减，必须主动监测、定期回炉。**

## 32.7 灰度发布与影子模式：新模型怎么安全地换上

第 30 章的版本回归在**离线测试集**上把好了关，但离线测试集再全，也不等于线上真实流量。**新模型全量直接换，万一在某种线上才有的场景翻车，就是全线事故。** 生产里用两招降低风险：

**① 影子模式（shadow mode）——只看不动。** 让新模型和旧模型**并行**跑同样的输入，但**新模型的结果只记录、不生效**（不真的拿去报警/计数）。跑上几天，离线对比两者的差异：新模型是不是在真实流量上也更好？有没有旧模型不会犯的怪错？**它零风险**——反正新模型说了不算，纯粹拿真实流量给它做"实战模拟考"。

```text
          ┌──────────┐  结果生效  ┌────────┐
   输入 ─┬▶│ 旧模型(主) │────��────▶│ 报警/计数│
        │ └──────────┘            └────────┘
        │ ┌──────────┐  结果仅记录、对比
        └▶│ 新模型(影)│─────────▶ 日志/指标（不生效）
          └──────────┘
```

**② 灰度发布（canary）——小流量试水，逐步放量。** 影子模式验证过后，让新模型**先接管一小部分**（比如 32 路里的 2 路，或 5% 的现场），密切盯着这部分的指标和告警；没问题再逐步扩大到 10%、50%、100%。**一旦这一小撮出问题，影响面被限制住，立刻回滚（回滚靠 32.2 的热更新一键切回旧版）。** 这比"全量梭哈"稳健得多。

**核心思想**：**永远保留快速回滚的能力，永远先让影响面可控地暴露风险。** 32.2 的热更新（原子切换 + 失败回滚）是灰度发布的技术底座——能秒级切模型，才谈得上灰度和回滚。

## 32.8 容量规划与成本：这台机器到底能扛几路

第 31 章的压力测试摸出了"这台机器 8 路稳、16 路降级、32 路过载"的拐点，运维要把它变成**容量规划**——**用多少硬件、扛多少路、花多少钱**：

- **单机容量**：由压测拐点定。留安全余量，别���极限排（比如拐点 16 路，就规划跑 10~12 路，给突发和劣化留空间）。
- **算力选型**：GPU 吞吐高但贵、功耗高；边缘 CPU/NPU 便宜省电但慢（第 29 章那张开发机 vs 边缘设备对比表）。**按场景选**——中心机房大并发上 GPU，前端边缘盒子用 NPU。
- **batch 与延迟的账**：第 13、14、29 章的老权衡——攒 batch 提吞吐（每路成本↓）但单帧延迟↑。安防要低延迟，就别攒太大 batch；离线批处理可以攒满省成本。
- **成本模型**：算清"每路每月成本 = 硬件摊销 + 电费 + 带宽 + 运维"，才能对业务报价、做扩容决策。

一句话：**容量规划是把第 31 章的性能数字翻译成"要买几台什么机器、能服务多少客户、成本多少"的商业语言**——这是资深工程师和纯写代码的人之间的一道分水岭。

## 32.9 运维手册与复盘：把救火变成流程

最后一块拼图是**人的流程**。系统再健壮也会出故障，关键是出故障时**不慌、有章可循、事后能改进**。

- **运维手册（runbook）**：把"出现 X 告警时怎么办"写成明确步骤。比如"某路断流告警 → ① 看该摄像头网络 → ② 手动 ping/拉流验证 → ③ 确认是摄像头挂了还是我们的问题 → ④ 分别怎么处理"。**别让排障靠某个人的记忆**，写下来谁都能上手。
- **On-call 值班**：明确谁在什么时段负责响应告警，致命告警多久内必须响应。
- **故障复盘（postmortem）**：每次线上事故后���复盘"根因是什么、为什么没早发现、怎么防止再次发生"，并且**对事不对人**——追的是流程和系统的漏洞，不是追责个人。每次复盘都应产出具体改进（补一条监控、加一个测试、改一段逻辑）。

这套东西不写代码，却是**系统能被长期、可靠运营**的软性保障。回头看会发现：第 31 章的测试、本章的监控告警和 runbook，本质是同一件事的不同阶段——**把"靠人盯、靠救火"变成"靠系统、靠流程"**。

## 32.10 全书结语：从一个像素到一套可运营的产品

到这里，全书三十二章的链路彻底闭合了。回望这一路——

**第一、二部分**从**一个像素**讲起：理解图像的本质与 Rust 工具，再摸透编解码与 RTSP 流，把"数据怎么进出"打通（第 1~6 章）。**第三部分**练**传统视觉算法**：滤波、边缘、形态学、几何变换——不依赖模型的老功夫，至今仍是预处理和后处理的骨干（第 7~9 章）。**第四、五部分**进入**深度学习推理侧**：letterbox 预处理、模型文件、shape 与元数据、格式转换，最后用 tract/ort 把模型真正跑起来，吐出那串 `[1,84,8400]`（第 10~14 章）。**第六部分**把模型输出**解码成有意义的结果**：分类、检测+NMS、关键点、分割、人脸——各类模型的后处理逐个拿下（第 15~20 章）。**第七部分**从"单帧"迈向"**视频与业务**"：多目标跟踪、ROI/绊线/时间去重等过滤器、跨模型关联，把检测框变成"有人翻越了周界"这样的业务事件（第 21~25 章）。**第八部分**用三个实战把零件拼成整机，并完成并发、性能与部署的工程化（第 26~29 章）。**第九部分**——也就是刚刚——把你从"能交付"推向"**能对模型负责、能长期运营**"：量化评估与 mAP、测试与性能剖析、生产化与运维（第 30~32 章）。

一条完整的链路，现在完整地摆在你面前：

```text
像素 → 张量 → 模型输出 → 检测框 → 跟踪轨迹 → 业务事件
   → 稳定并发的服务 → 可度量的质量 → 可运营的产品
```

你现在手里有的，不再是几段能跑的 demo，而是一套**从底层原理到工程落地、再到长期运营**的完整心智地图。你不但知道怎么让一个模型跑出结果，还知道**怎么证明它够好、怎么让它 7×24 不出事、怎么在它悄悄变差时第一时间发现、怎么在不停服的情况下把它换掉**——这些，正是"会用模型的人"和"资深机器视觉开发工程师"之间的全部距离。

**下一步学什么？** 几个方向供参考：往**训练侧**走，学会标注数据、微调模型（本书专注推理与工程侧，训练是另一片天地）；往**更极致的性能**走，深入 TensorRT、量化、算子级优化；往**更大的系统**走，多机多路调度、云边协同、大规模标注回灌平台；或者干脆挑一个真实场景（你家的猫、小区的车、产线的瑕疵），把本书的链路端到端跑通、评估、上线、运维一遍——**纸上得来终觉浅，绝知此事要躬行**。附录 A~D 是你随时可查的数学、crate、术语和踩坑手册。

祝你在机器视觉的工程路上，看得懂图像，看得懂模型，也扛得住生产。

## 32.11 小结

- **交付上线只是运维的起点**。系统"活着的每一天"要操心：监控、告警、热更新、可靠投递、数据漂移、灰度、容量——这些"上线之后"的功课，才是资深与入门的分水岭。
- **模型/配置热更新**靠"原子替换 + 失败回滚"：配置用 `ArcSwap` 无锁替换；模型受"Session 需 `&mut self`、不能跨线程并发 run"（第 29 章）约束，由推理线程自己后台加载预热、成功才换、失败留旧。
- **业务事件的可靠投递**（第 27、28 章欠的账）要三件套：**至少一次 + 退避重试**、**幂等键去重**（至少一次 + 下游按 ID 去重 ≈ 恰好一次）、**本地 outbox 兜底**（下游宕了先落盘、恢复后补投），一条不丢不重。
- **监控闭环**分清日志（离散事件、事后排查）与指标（连续曲线、实时观测趋势）；监控 FPS/延迟/队列深度/丢帧/GPU/内存/连接状态，暴露给时序系统看仪表盘——**可观测性让系统不再是黑盒**。
- **系统告警**只为"需要人立刻行动"的事设，用阈值+持续时间滤抖动、分级、按 SLO 触发，警惕**告警疲劳**。
- **数据漂移**：模型没变、���界变了（季节/镜头/新机位/场景），效果悄悄下滑却不报错；用置信度分布偏移、产出量异常等无标注代理信号监测，靠"抽样—标注—回灌—评估"闭环跟上现实。
- **灰度发布**用影子模式（新模型只看不动）+ canary（小流量逐步放量）+ 秒级回滚（依赖热更新）安全换版；**容量规划**把压测拐点翻译成硬件与成本；**runbook / on-call / 复盘**把救火变成流程。
- **全书链路闭合**：像素 → 张量 → 模型输出 → 检测框 → 轨迹 → 业务事件 → 稳定服务 → 可度量质量 → 可运营产品。从原理到落地到运营的完整地图，已经在你手上。

## 32.12 练习

1. **实现配置热更新**：给第 27 章的周界报警加一个 `ArcSwap<PerimeterConfig>`，监听配置文件变化（可先用一个手动触发的信号代替文件监听），重载时先 `validate` 再 `store`。故意喂一份坏配置，验证旧配置不受影响、服务不中断。

2. **设计一个可靠投递管道**：定义 `AlertEvent`（含幂等 `event_id`）和 `AlertSink` trait，实现一个 `WebhookSink`（可以先用打印+随机失败模拟网络抖动），加上 `deliver_with_retry` 指数退避和一个基于本地文件的 outbox。模拟"下游宕机 1 分钟后恢复"，验证事件一条不丢地补投、且下游用 `event_id` 去重后不重复。

3. **给系统加一组指标**：为第 29 章的流水线加 `Metrics`，统计 FPS、丢帧率、各通道队列深度，每 10 秒用 `tracing` 打一次快照。跑一段视频，逐步增加输入速率，观察哪个队列先满——用指标印证第 31 章压测找到的瓶颈。

4. **模拟数据漂移检测**：跑两段光照差异很大的视频（如白天 vs 夜晚），分别统计所有检测的置信度分数直方图，对比两者的形状差异。设计一个简单的"漂移告警"规则（如平均置信度较基线下降超过 X 就报警），讨论它的误报和漏报风险。

5. **设计一次灰度发布方案**：假设你有 20 路摄像头、一个待上线的新模型。写出完整的发布计划：影子模式跑多久、对比哪些指标、canary 先放几路、按什么标准逐步放量到全量、什么条件触发回滚。把它写成一份 runbook 式的步骤清单。
