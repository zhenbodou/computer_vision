# 第 2 章 为什么用 Rust 做机器视觉

> **本章导读**
> - 想清楚一件事：这本书为什么不走"Python + OpenCV"这条大路，偏要用 Rust？
> - 认识 Rust 的四大杀手锏：接近 C 的性能、无 GC 的内存安全、无畏并发、单文件跨平台部署（含浏览器）。
> - **诚实**盘点 Rust 机器视觉生态的家底：哪些成熟能打，哪些还在快速长身体。
> - 也讲清楚：什么时候你其实该用回 Python。工具没有优劣，只有合不合适。

## 一个真实的深夜：为什么你的 Python 项目跑不动了

想象你花了两周，用 Python + OpenCV 写了个"数人头"的程序，本地跑得挺欢。老板拍板："上线吧，部署到工厂那台旧服务器上，同时接 8 路摄像头。"于是噩梦开始了：

- 你想用多线程同时处理 8 路视频，却发现 Python 有个叫 **GIL（全局解释器锁，Global Interpreter Lock）** 的东西——同一时刻只允许一个线程执行 Python 字节码。8 核 CPU，你的逻辑却只能用满 1 个核。
- 好不容易在自己机器上装好的 `opencv-python`、`numpy`、`torch`，到了服务器上版本对不上，`ImportError` 一个接一个——这就是传说中的**依赖地狱（dependency hell）**。
- 最后打包成 Docker 镜像，一看 3.8 GB。工厂的边缘盒子存储只有 8 GB，一个镜像就吃掉小一半。

这不是说 Python 不好——它是数据科学与快速原型的王者。但当你要把视觉程序**真正跑起来、部署出去、榨干每一颗 CPU 核**时，上面这三座大山（GIL、部署重、依赖乱）就会横在路上。

> 📖 **术语**：**两语言问题（two-language problem）**。Python 自身跑循环很慢，所以 OpenCV、NumPy、PyTorch 的"快"其实来自底层的 C/C++/CUDA——你写的是 Python，真正干活的是 C。这带来一个尴尬：一旦要写一段库里没有的自定义逐像素逻辑，纯 Python 会慢到没法用，你被迫再学 C/Cython 去"补速度"。用一门语言写原型、另一门语言求性能，就是两语言问题。

## Rust 的四大杀手锏

Rust 恰好把上面这些痛点一次性解决了。它最初是为写浏览器引擎而生的语言——既要极致性能、又绝不能崩——这两个诉求，和机器视觉工程惊人地一致。

### 1. 接近 C 的性能，没有"翻译官"

Rust 是**编译型**语言，源码直接编成机器码，没有解释器、没有虚拟机。你写的那段逐像素循环，跑得和 C 一样快，不必为了速度再退回 NumPy 向量化或改写 C 扩展。前面说的"两语言问题"，在 Rust 里根本不存在：**原型和产品是同一门语言**。

**性能直觉**（先建立感觉，不跑基准）：一张 1080p 图像有 1920×1080 ≈ 200 万个像素；视频 25 帧/秒，意味着每秒要"摸" 5000 万个像素，还只是摸一遍。纯 Python 的 `for` 循环干这事会当场卡死；Rust 的循环是 CPU 原生速度，量级上和 C 持平，通常比纯 Python 快**几十到上百倍**。

### 2. 无 GC 的内存安全

C/C++ 快归快，但一不小心就"野指针""数组越界""重复释放"——这些是程序崩溃和安全漏洞的头号来源。带垃圾回收（GC，Garbage Collector）的语言（Java、Go）安全了，可 GC 会时不时"停顿"（stop-the-world），对实时视频处理是灾难。

Rust 走了第三条路：**所有权（ownership）与借用检查（borrow checker）**，在**编译期**就把内存错误挡在门外，运行时既不需要 GC、也几乎不会因内存问题崩溃。打个比方：编译器像个严格的图书管理员，一本书（一块内存）同一时间只能借给一个人写、或者多个人一起读，绝不允许"你正读着，别人把书撕了"。代价是编译器有时会跟你较劲（新手常见的"和借用检查器搏斗"），换来的却是——**编译过了，基本就不会因为内存问题在半夜崩溃**。

### 3. 无畏并发（fearless concurrency）+ rayon

这是 Rust 最爽、也对机器视觉最实用的一点。因为所有权系统在编译期就能揪出"数据竞争（data race）"，Rust 敢让你放心大胆地写多线程——官方管这叫"无畏并发"。

配上 `rayon` 这个库，把一个串行循环改成**并行**，往往只要改一个词（下面是示意片段，帮你建立印象；真正能跑的程序留到下一章）：

```rust
// 串行：一个一个像素处理
pixels.iter_mut().for_each(|p| process(p));

// 并行：自动切分到所有 CPU 核，只差一个词
use rayon::prelude::*;
pixels.par_iter_mut().for_each(|p| process(p));
```

`iter_mut` 换成 `par_iter_mut`，8 核就真能用满 8 核，没有 GIL 拦路。处理 8 路摄像头？rayon 帮你把每颗核都榨干。（性能优化专题见 [第 108 章](../p21-mastery/ch108-performance.md)。）

### 4. 单文件跨平台部署，还能进浏览器

Rust 的编译产物是**一个自包含的可执行文件**，不依赖解释器、不用在目标机器上装一堆库，拷过去就能跑。前面那个 3.8 GB 的 Docker 镜像，用 Rust 常常能压到几十 MB。

更狠的是，Rust 是对 **WebAssembly（简称 WASM）** 支持最好的语言之一。同一份视觉算法代码，`cargo build` 能编成可执行文件跑在服务器，也能编成 WASM **直接在浏览器里跑**（本书 [第 110 章](../p21-mastery/ch110-wasm.md) 会带你做）——用户什么都不用装，打开网页就能用上你的视觉程序。

## Rust 机器视觉生态：诚实的家底盘点

吹了这么多，得说点实在的：Rust 的 CV 生态**远不如 Python 全面**——这是事实，藏着掖着没意思。但它已经"够用，且在飞速长大"。分层来看：

| 层次 | 代表 crate | 成熟度 | 说明 |
|------|-----------|--------|------|
| 图像处理 | `image`、`imageproc` | ⭐⭐⭐⭐ 成熟 | 读写、滤波、边缘、形态学、轮廓、霍夫、模板匹配……经典算法基本齐全，是本书第二~四部分的主力 |
| 数值计算 | `ndarray`、`nalgebra` | ⭐⭐⭐⭐ 扎实 | 多维数组/张量、线性代数、矩阵几何，稳定可靠 |
| 传统机器学习 | `linfa` | ⭐⭐⭐ 可用 | 分类、回归、聚类，类似 Rust 版 scikit-learn |
| 深度学习框架 | `candle`、`burn` | ⭐⭐⭐ 快速发展 | candle（Hugging Face 出品）主打推理，burn 主打训练，进步神速但仍在演进 |
| ONNX 推理 | `tract`、`ort` | ⭐⭐⭐⭐ 可靠 | 把 PyTorch/TF 训练好的模型导成 ONNX，用 Rust 高效推理 |

看出门道了吗？**Rust 当前最稳的路线是"预训练 + 推理"**：前沿模型（YOLO、SAM、CLIP……）大多在 Python 里训练好，导出成 ONNX 或权重文件，再由 Rust 加载来跑推理与部署。这条路线恰好扬长避短——训练借 Python 的成熟生态，落地用 Rust 的性能与部署优势。本书第七部分以后会反复用到这套打法。

> 💡 **提示**：别被"生态不如 Python 全"吓退。真实工程里，**大量工业项目的工作量是"跑推理 + 一堆业务后处理规则"**（见第十八部分），而这恰恰是 Rust 的主场。需要从零训练大模型的场景，反而是少数。

## Rust vs Python：一张对比表

| 维度 | Python + OpenCV | Rust |
|------|-----------------|------|
| 自定义逐像素逻辑速度 | 慢（需退回 C/NumPy） | 快，接近 C |
| 内存安全 | 运行时可能崩/泄漏 | 编译期保证，无 GC |
| 多核并发 | 受 GIL 限制 | 无畏并发 + rayon，吃满多核 |
| 部署 | 需带解释器 + 一堆依赖 | 单个可执行文件，可小到几十 MB |
| 浏览器 (WASM) | 基本不行 | 一等公民 |
| CV 生态广度 | 极其丰富（王者） | 够用，快速发展中 |
| 快速原型/科研 | 极快，可交互 | 略慢，要编译 |
| 学习曲线 | 平缓 | 前期偏陡（借用检查器） |

## 那什么时候还是该用 Python？

工具是用来解决问题的，不是用来站队的。**下面这些情况，Python 依然是更聪明的选择**：

- **纯科研、快速试想法**：你想一天试 20 个模型结构，在 Jupyter 里边写边看图，Python 的交互性和生态无可替代。
- **训练大模型**：PyTorch 生态、海量预训练权重、铺天盖地的教程，训练环节 Python 目前仍是主场。
- **一次性脚本**：跑完就扔的小分析，犯不着为它跟借用检查器较劲。

本书的立场很明确：**用 Python 训练、探索都没问题；但当你要把视觉能力做成一个又快又稳、能部署到真实产线和边缘设备的系统时，Rust 是更省心的那个。** 这，正是从"会跑 demo"到"能交付产品"的分水岭——也是本书想带你跨过的那道坎。

## 本章小结

- Python + OpenCV 上手快，但在**并发（GIL）、部署（重）、依赖（乱）**三处会卡住工程落地；它的"快"其实来自底层 C，暗藏"两语言问题"。
- Rust 四大优势：**接近 C 的性能、无 GC 的内存安全、无畏并发（rayon 吃满多核）、单文件跨平台部署（含 WASM 进浏览器）**。
- Rust CV 生态诚实评价：`image`/`imageproc` 成熟，`ndarray`/`nalgebra` 扎实，`candle`/`burn` 快速发展，`tract`/`ort` 可靠跑 ONNX；当前最稳的路线是**"Python 训练 + Rust 推理部署"**。
- 工具无高下：**科研快速原型、训练大模型仍可选 Python**；要交付又快又稳的产品系统，Rust 更省心。

## 动手练习

1. **对号入座**：回想你（或身边人）用过的一个 Python 视觉项目，它有没有踩过 GIL、部署或依赖的坑？对照本章，想想 Rust 会怎么解决。
2. **查生态**：打开 [crates.io](https://crates.io)，搜索 `image`、`candle`、`ort` 三个 crate，看看它们的下载量和最近更新时间，感受一下 Rust CV 生态的活跃度。
3. **画决策树**：给自己画一张"该用 Rust 还是 Python"的决策流程图，至少覆盖 3 种典型场景（科研试验、工业部署、浏览器 demo）。
4. **想一想**：为什么说"预训练 + 推理"这条路线特别适合 Rust？如果一个项目 90% 的工作量都是业务后处理规则，语言选择会有什么不同？
