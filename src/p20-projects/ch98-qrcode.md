# 第 98 章 项目：二维码与条形码识别

> **本章导读**
> - 学完你能：用**纯 Rust**（`qrcode` 生成 + `rqrr` 解码，`cargo tree` 查无任何 C/C++ 依赖）搭一个**二维码「生成 → 识别」闭环**，并亲手给它做**鲁棒性压力测试**——旋转、缩放、椒盐噪声，看它在什么条件下依然认得出、什么条件下彻底崩。
> - 你会得到一组**最有说服力的真数字**（本机 `cargo run --release` 实测、确定性可复现）：QR 抗旋转堪称满分（直角与任意角全部读回）、能一路缩到 **≈90px（每模块约 2.7 像素）** 才失败；而在**椒盐噪声**下，哪怕开到最高 30% 纠错的「裸码」也**一碰就碎**——但只要解码前加一步 **3×3 中值滤波**（呼应[第 14 章](../p03-classic/ch14-nonlinear-filter.md)），成功率就从个位数**直接拉满到 100%**。
> - 一条**诚实边界**：`rqrr` 只认 QR 码；**一维条形码**（EAN/Code128 等）与 DataMatrix/Aztec 请用 `rxing`（ZXing 的纯 Rust 移植）。而**复杂实拍**（形变、遮挡、光照不均、密集小码）下，纯 Rust 库仍明显弱于商业 SDK——本章会说清差在哪、怎么补。

## 场景：把一张图里的「方块码」读出来

扫码点餐、扫码付款、扫码进站——二维码早就是生活的一部分。它的工作分两头：**生成**（把一段文本编码成黑白方块图）和**识别**（从一张图里定位、解码、还原出那段文本）。这一章我们用纯 Rust 把这两头**串成一个闭环**，然后做一件比「跑通」更有价值的事：**逼它到极限**——转个角度还认得吗？缩到多小就瞎了？画面上撒把噪声点还扛得住吗？

难点不在「生成」——那是确定性的编码；难点在**识别的鲁棒性**：真实世界里码会歪、会小、会脏。我们要用实测数字把「它到底有多结实、哪里最脆」量出来，并找到**对症的补救手段**。

## 原理：定位图案 + 纠错码，是二维码结实的两大支柱

### QR 码长什么样、凭什么好定位

一张 QR 码不是随便的黑白点阵，它有严格的骨架：

```text
┌─────────────────────────────┐
│ ■■■■■■■ ·········· ■■■■■■■ │   三个角上的「回」字 = 定位图案(finder pattern)
│ ■     ■  数据区+   ■     ■ │
│ ■ ■■■ ■  纠错码区   ■ ■■■ ■ │   中间大片：数据 + Reed-Solomon 纠错码
│ ■ ■■■ ■  (深浅模块) ■ ■■■ ■ │
│ ■     ■             ■     ■ │
│ ■■■■■■■ · ■ · ■ · · ■■■■■■■ │   ← 定时图案(timing)：黑白相间定网格
│ ·········                    │
│ ■■■■■■■  ·········· ······· │
│ ■     ■   ← 第三个定位图案     │
│ ■ ■■■ ■                      │
└─────────────────────────────┘
   ↑ 四周还有一圈全白的「静默区」(quiet zone)，少了它解码器常常找不到码
```

三个角上的「回」字**定位图案**是灵魂：不论从哪个方向扫描穿过它，黑白宽度都呈固定的 **1:1:3:1:1** 比例，这个比例旋转、缩放都不变。解码器先在图里搜这个特征找到三个角，就能算出码的**朝向和网格**——这正是 QR **天生抗旋转**的原因。

> 📖 **术语**：**模块（module）** 指 QR 里最小的黑/白方格；**版本（version）** 决定模块数，版本 1 是 21×21，每加一版 +4，本章 58 字节的载荷在等级 M 下用到版本 4（33×33 模块）。**静默区（quiet zone）**：码四周留白的安全边距（标准要求 ≥4 个模块宽），解码定位离不开它，所以生成时务必保留。

### 纠错等级：Reed-Solomon 给你留的「后悔药」

QR 数据区里不只有你的文本，还掺了一大块 **Reed-Solomon 纠错码**（error correction code，ECC）。它的作用是：**即使一部分模块被污损、遮挡、涂改，也能把原文恢复出来**。纠错强度分四档：

| 等级 | 冗余（可恢复比例） | 代价 |
|------|--------------------|------|
| L | 约 7% | 码最小 |
| M | 约 15% | 默认档 |
| Q | 约 25% | 更大 |
| H | 约 30% | 码最大、模块最多最密 |

请记住这句话，它是本章后半段的关键伏笔：**Reed-Solomon 是为「成片的污损/擦除」设计的**（比如印刷缺角、贴纸挡住一块）。它对「每个模块中心恰好被一个坏像素狙击」这种**散点式**破坏，并不占便宜——这一点我们待会儿用数据狠狠验证。

### 一维条形码 vs 二维码

顺带厘清标题里的「条形码」：**一维条形码**（EAN-13、Code128 等）只在**横向**用条纹宽度编码，容量小、要求整条清晰可见、几乎没有纠错；**二维码**（QR、DataMatrix）在**平面**上编码，容量大、自带定位图案与纠错。本章的运行代码聚焦 QR（纯 Rust 生态里 `rqrr` 最干净好用）；一维码与其它二维码格式的纯 Rust 方案见文末「诚实边界」。

### 核心：生成与解码

`qrcode` 把文本渲染成灰度图（记得开 `quiet_zone`），`rqrr` 反过来定位并解码：

```rust
use image::{GrayImage, Luma};
use qrcode::{EcLevel, QrCode};
use rqrr::PreparedImage;

/// 用 qrcode 把文本编码成 QR 灰度图（含静默区）。
fn make_qr(text: &str, ec: EcLevel, min_side: u32) -> GrayImage {
    QrCode::with_error_correction_level(text.as_bytes(), ec).expect("QR 编码失败")
        .render::<Luma<u8>>()
        .min_dimensions(min_side, min_side)
        .quiet_zone(true)          // 保留四周白边，解码定位需要它
        .build()
}

/// 用 rqrr 解码。成功返回 (读回文本, 模块数, 纠错等级原始位)。
fn decode(img: &GrayImage) -> Option<(String, usize, u16)> {
    let mut prep = PreparedImage::prepare(img.clone());
    for grid in prep.detect_grids() {                // 先定位所有 QR 网格
        if let Ok((meta, content)) = grid.decode() {  // 再逐个解码
            return Some((content, meta.version.to_size(), meta.ecc_level));
        }
    }
    None
}
```

> 🕳️ **坑**：`rqrr` 的 `meta.ecc_level` **不是** L/M/Q/H 的序号，而是 QR「格式信息」里的原始 2 bit。标准里 M=00、L=01、H=10、Q=11，所以要用 `0→M, 1→L, 2→H, 3→Q` 来翻译。一开始我按 `[L,M,Q,H]` 顺序去查，把一个 M 码打印成了「L」，对不上——查半天才发现是这个映射的锅。

### 三项压力测试

`main` 里把闭环和三项测试串起来（完整可运行代码约 160 行，含旋转/缩放/噪声全部逻辑，在仓库 `code/projects/ch98_qrcode/src/main.rs`）：

1. **闭环**：`make_qr` 生成 → 存 PNG → `decode` 读回 → 比对是否**逐字一致**。
2. **旋转**：`image::imageops` 的直角旋转 + `imageproc` 的 `rotate_about_center` 任意角（旋转前先把码贴到更大白底画布，免得四角定位图案被裁掉）。
3. **缩放**：把 360px 原图用 `resize` 缩到一系列更小尺寸，看多小还读得出。
4. **椒盐噪声**：这是最见功夫的一项。对 L/M/H 三档纠错的码分别撒不同比例的椒盐噪声，**每档跑 30 个不同随机种子求成功率**；再单独给 M 档加一列「先做 3×3 中值滤波再解码」的对照：

```rust
use imageproc::filter::median_filter;
use imageproc::noise::salt_and_pepper_noise;

let trials = 30u64;
// 对某档码、某噪声率，med=true 表示解码前先中值滤波；返回成功率(%)
let rate_of = |img: &GrayImage, rate: f64, med: bool| -> f64 {
    let mut ok = 0u64;
    for seed in 0..trials {                             // 固定种子序列 → 可复现
        let noisy = salt_and_pepper_noise(img, rate, seed);
        let cand = if med { median_filter(&noisy, 1, 1) } else { noisy };
        if decode(&cand).map(|(t, ..)| t == TEXT).unwrap_or(false) { ok += 1; }
    }
    ok as f64 / trials as f64 * 100.0
};
```

## 怎么读这组数字（本章最值钱的部分）

- **抗旋转满分、缩放到「每模块约 2.7px」才崩。** 旋转全部读回，印证了定位图案的威力——朝向随便变，那三个「回」字一找到，网格就复原了。缩放则卡在 **≈90px**：33 个模块摊到 90px，每模块只剩约 2.7 像素。这背后是**采样定理**的直觉——每个模块至少要有 2~3 个像素，解码器才能稳稳采到它的黑白；再小，模块糊成一团就没救了。**要印小码，就得留足每模块的像素预算。**

- **椒盐噪声下「裸码」惊人地脆——而且纠错等级越高，可能反而越差！** 看那张表：1% 噪声时 L/M 还有 50%，**H（30% 纠错）却只有 26.7%**，比 L/M 更糟；到 2% 时三档齐齐跌进个位数，5% 以上全军覆没。为什么最高纠错反而垫底？因为 **H 码是 41×41 模块**（比 L/M 的 33×33 更多、更小、更密），而 `rqrr` 是**按每个模块中心点采样**的——模块越小越密，一个孤立的坏像素就越容易正好砸在某个模块中心、把它翻转；模块总数又多，中招的期望更高。**Reed-Solomon 那 30% 冗余是为「成片污损」准备的，面对「散点狙击模块中心」的椒盐噪声，冗余还没发力，采样已经错得七零八落。**

- **对症下药：一步 3×3 中值滤波，把成功率从个位数拉满到 100%。** 椒盐噪声的本质是**孤立的极端像素**（非黑即白的脉冲点），而[第 14 章](../p03-classic/ch14-nonlinear-filter.md)讲过，**中值滤波正是脉冲噪声的天敌**——3×3 邻域取中位数，孤立的一个坏点会被周围 8 个好点「投票」淹没掉。解码前加这一步，模块中心恢复干净，**所有噪声档位全部 100%**。这就是本章最硬的工程结论：**噪声类型认对了，选一个几行代码的预处理，远比盲目堆高纠错等级管用。** 匹配错了手段（拿 ECC 去扛椒盐），再贵也白搭。

配套还会存三张样图直观对照：`qr_clean.png`（干净码）、`qr_noise3.png`（撒了 3% 椒盐、满屏雪花点）、`qr_noise3_median.png`（中值滤波后雪花被抹掉、模块重新清晰）——「脆」与「救」一目了然。

## 常见坑与提示

> 🕳️ **坑**：**生成时别忘了静默区（quiet zone）。** 很多人把 QR 紧贴边缘或贴到深色背景上，解码器找不到那圈留白就定位失败。`qrcode` 的 `.quiet_zone(true)` 默认给你留好；自己拼版时也要保证码四周有 ≥4 个模块宽的白边。

> ⚠️ **注意**：**「纠错等级越高越保险」是想当然。** 本章数据是反例：面对椒盐噪声，H 因模块更密反而比 L/M 更脆。纠错等级要按**预期的破坏类型**选——怕遮挡/污损/logo 覆盖就上 Q/H（成片擦除正是 RS 的主场）；怕的是传感器噪声/压缩噪点，**先做去噪预处理**比堆纠错划算得多。

> 💡 **提示**：**解码前的预处理，往往比解码器本身更决定成败。** 实拍二维码常见的敌人是**光照不均**和**噪声**：光照不均先上[第 16 章](../p03-classic/ch16-threshold.md)的**自适应阈值**做二值化，噪声就按类型选滤波（椒盐→中值，高斯→高斯/双边）。把图「洗干净」再喂给 `rqrr`，成功率天差地别。

> ⚠️ **注意（诚实边界）**：**这是教学级 demo，和商业扫码 SDK 还有明显差距。**（1）`rqrr` **只认 QR**；要读**一维条形码**（EAN/Code128）或 DataMatrix/Aztec，请换 `rxing`——它是 **ZXing 的纯 Rust 移植**，多格式、同样不依赖 C/C++。（2）**复杂实拍**——透视形变严重、码被手指/反光遮挡、光照极不均、一张图里挤满密集小码——纯 Rust 库的检测与纠偏能力仍**弱于**微信/支付宝那类商业引擎（后者有大量工程化的定位、超分、多码分割优化）。纯 Rust 能覆盖绝大多数「码基本正、光线基本够」的场景；要啃硬骨头，可自己补透视矫正（[第 26 章](../p04-features/ch26-homography-stitching.md)的单应变换）与超分，或在关键链路诚实地评估商业 SDK。

## 本章小结

- **二维码识别 = 定位 + 解码**：三个「回」字**定位图案**（1:1:3:1:1 比例，旋转缩放不变）负责找到码、复原网格，所以 QR **天生抗旋转**；数据区的 **Reed-Solomon 纠错码**（L/M/Q/H = 7/15/25/30%）负责在**成片污损**时恢复原文。
- **纯 Rust 闭环**：`qrcode` 生成 + `rqrr` 解码，`cargo tree` 查无任何 C/C++ 依赖，`cargo run` 即跑。本章实测生成 33×33 模块的码、读回**逐字一致**。
- **鲁棒性实测三连**：抗旋转满分；缩放到 **≈90px（每模块约 2.7px）** 才失败（采样定理直觉）；**椒盐噪声下裸码极脆，且 H 因模块更密反而比 L/M 更差**——因为 RS 冗余管不了「散点狙击模块中心」。
- **最硬的结论**：**预处理要对症**。椒盐是脉冲噪声，解码前加一步 **3×3 中值滤波**（[第 14 章](../p03-classic/ch14-nonlinear-filter.md)），成功率**从个位数直接拉满 100%**——选对手段远胜盲目堆纠错等级。
- **诚实边界**：`rqrr` 只认 QR，一维码/多格式用 `rxing`（ZXing 纯 Rust 移植）；复杂实拍纯 Rust 仍弱于商业 SDK，需补透视矫正/超分或评估商用方案。

## 动手练习

1. **量出你的「像素预算」**：改 `make_qr` 的 `min_side`，编码一段**更长**的文本（比如 200 字节，会用到更高版本、更多模块），重跑缩放测试，看「仍能解码的最小尺寸」和「每模块像素数」怎么变——验证「模块越多、要求的总尺寸越大」。
2. **换一种噪声，换一种药**：把 `salt_and_pepper_noise` 换成**高斯噪声**（`imageproc::noise::gaussian_noise`），再分别用**中值**和**高斯模糊**预处理做对照。你会发现「中值治椒盐、高斯治高斯」——手段必须匹配噪声类型。
3. **加透视考验**：用 [第 26 章](../p04-features/ch26-homography-stitching.md)的单应变换把 QR 做**透视倾斜**（模拟斜着拍），测 `rqrr` 能扛多大角度；再试试解码前**先矫正**回正，看能救回多少。
4. **（挑战）读一维码**：引入 `rxing`，生成并识别一个 **Code128** 或 **EAN-13** 条形码，跑通一维码的闭环，对比它和 QR 在抗噪、抗遮挡上的差异——体会「一维无纠错、要求整条清晰」的脆弱。
