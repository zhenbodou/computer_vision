# 第 105 章 项目：健身姿态计数器（关键点应用）

> **本章导读**
> - 这是一个**集成项目**：把 [第 52](../p11-keypoints/ch52-keypoint-basics.md)、[53 章](../p11-keypoints/ch53-human-pose.md) 的**人体姿态关键点**接上一个**动作计数器**，做出"数你做了几个深蹲"的完整功能——**图像 → 姿态 → 关节角 → 状态机计数**。
> - 你会学到三个工程要点：**为什么用"关节角"而非绝对坐标**（对人体尺度/位置不变）、**滞回双阈值状态机**为什么能防临界抖动误计（呼应事件层 [第 85 章](../p18-events/ch85-temporal-window.md)）、以及**"感知 vs 逻辑"的瓶颈定位**（[第 55 章](../p11-keypoints/ch55-hand-gesture.md) 的范式）。
> - 全程纯 CPU、不下载模型；正文每个数字都来自本机 `cargo run --release`。我们不重推姿态估计理论（[第 53 章](../p11-keypoints/ch53-human-pose.md) 已讲透），重点在**如何把关键点变成可靠的业务功能**。

## 场景：健身 App 怎么数深蹲

[第 1 章](../p01-start/ch01-what-is-cv.md) 就提过健身 App 数深蹲的例子。现在你已经会做人体姿态估计了（[第 53 章](../p11-keypoints/ch53-human-pose.md)），这一章我们把它变成一个**真能用的功能**。核心链路很短：

```text
视频帧 → 姿态估计（第53章）→ 取髋/膝/踝三点 → 算膝关节角 θ → 状态机数"蹲下再起来" → 计数
```

难点不在姿态估计本身，而在**最后那一步怎么把连续的角度信号，稳稳地数成整数次**——这正是工业落地里"从感知输出到业务事件"的通用命题（第十八部分的主题），我们在这里用一个小项目先尝到它的味道。

## 设计一：为什么用"关节角"而非绝对坐标

第一个关键决策：拿什么信号来判断"蹲下去了"？直觉可能是"看髋关节的 y 坐标降下去"。但**绝对坐标是个坏信号**——它随人**站得远近（尺度）、站在画面左边还是右边（位置）**全都变。同一个深蹲，人靠近镜头时髋的像素坐标变化几十像素，站远时可能只变几像素，你没法用一个固定的坐标阈值。

**关节角就没这问题。** 膝关节角 = 在膝盖处，大腿（髋→膝）和小腿（踝→膝）两条向量的夹角：

\\[ \theta_{\text{膝}} = \arccos\left(\frac{(H-K)\cdot(A-K)}{\lVert H-K\rVert \cdot \lVert A-K\rVert}\right) \\]

它**对平移、缩放天然不变**——不管人在画面哪里、离多远、个子高矮，站直时膝角都接近 180°，蹲到底都在 80° 上下。**用角度写的计数逻辑，一次调好就能通用**，这是姿态类应用反复用到的套路（俯卧撑看肘角、抬手看肩角、开合跳看腿间角……）。本章实测这个膝角在深蹲中从 **169°（站直）荡到 67°（蹲到底）**。

## 设计二：滞回双阈值——防临界抖动的状态机

有了角度信号，怎么数"一次"？最朴素的想法：设一个阈值（比如 130°），角度每"跌破"一次就 +1。**这是个坑。** 角度信号一定带噪（关键点有定位误差，人也会微微晃），当它在阈值附近**来回抖动**时，单阈值会被反复触发——本该 8 次的，可能数出十几次。人在半蹲处停顿一下，更是灾难。

正确做法是**滞回（hysteresis）双阈值状态机**——工程上叫**施密特触发器（Schmitt trigger）**的思路，也正是事件层 [第 85 章](../p18-events/ch85-temporal-window.md) 去抖状态机的核心：

```text
        角度跌破 下阈值(110°)
   ┌──────────────────────────►┐
[站立态]                     [下蹲态]
   └◄──────────────────────────┘
        角度升过 上阈值(150°) → 计 1 次
```

要数成一次，必须**先真的蹲到位（角度跌破 110°）、再真的站起来（角度升过 150°）**。两个阈值之间那 **40° 的"死区"**，把临界抖动全吸收掉了：角度在 130° 附近怎么抖，只要没同时突破两端，状态就不变、不会误计。

```rust
fn count_hysteresis(angles: &[f32], lo: f32, hi: f32) -> usize {
    let mut down = false;  // false=站立态, true=下蹲态
    let mut n = 0;
    for &a in angles {
        if !down && a < lo { down = true; }              // 蹲到位 → 进下蹲态
        else if down && a > hi { down = false; n += 1; }  // 站起来 → 计 1 次并回站立态
    }
    n
}
```

## 动手：把姿态估计器接成计数器

> ⚠️ **注意**：本章基于 **candle 0.11.0**，纯 CPU。完整独立工程见 `code/projects/ch105_pose_counter/`，**`cd` 进去 `cargo run --release`**。姿态估计器**复用 [第 53 章](../p11-keypoints/ch53-human-pose.md)** 的热图回归网络，只是关节改成侧面深蹲的 5 点（头/肩/髋/膝/踝）。

**合成数据**：造侧面"深蹲火柴人"序列——由一个**深蹲深度 `depth∈[0,1]`** 驱动关节位置（0=站直、1=蹲到底），每次深蹲让 `depth` 平滑地 `0→peak→0`。关节点天然空间分离（[第 55 章](../p11-keypoints/ch55-hand-gesture.md) 的教训），离散随机走 LCG 高位（不用 `%k` 低位，见配套工程）。

**训练姿态估计器**（复用第 53 章，260 张随机深度的深蹲帧，热图回归）后，先报**感知质量**——在一段"做 8 次深蹲、224 帧"的演示序列上：

```text
===== 演示序列：224 帧、真实 8 次深蹲 =====
  姿态估计器关键点定位误差 = 0.475 像素（这就是本项目的'感知质量'）
  膝关节角范围：67° (蹲到底) ~ 169° (站直)；阈值 下=110° 上=150°
  计数结果（真实 8 次）：
    理想关键点 + 滞回双阈值 = 8 次  （逻辑上限：规则本身对不对）
    预测关键点 + 滞回双阈值 = 8 次  （真实端到端）
    预测关键点 + 单阈值     = 8 次  （对照：临界抖动会多计）
```

关键点定位误差仅 **0.475 像素**（侧面 5 点分得很开、好定位），端到端**数得准准的 8 次**。配套工程还会存 `angle_curve.png`（膝角随帧数振荡的曲线，绿=理想角、黄=预测角**几乎重合**，蓝/红线是上下阈值——8 个波谷穿过下阈值、8 个波峰穿过上阈值，一目了然）与 `pose_frame_0..2.png`（站直/半蹲/蹲底三帧的骨架，绿真值、黄预测贴合）。

> 💡 **提示**：**在这段干净演示里，连"单阈值"都数对了 8 次**——因为感知太好（0.47px），角度曲线几乎无抖动。**但这掩盖了单阈值的脆弱**。要暴露真正的差距，得加噪声压力测试。

## 感知 vs 逻辑：谁才是瓶颈？

沿用 [第 55 章](../p11-keypoints/ch55-hand-gesture.md) 的范式——**给理想关键点注入不同强度的高斯噪声（模拟不同精度的估计器），看计数准确率怎么变**。这一招能干净地把"感知质量"和"逻辑鲁棒性"分离开。每档噪声跑 40 段随机次数的序列，统计"计数恰好正确的序列占比"：

```text
===== 感知瓶颈：关键点噪声 σ 对计数准确率的影响（40 段序列/档）=====
  σ(px)   单阈值   滞回双阈值   滞回+平滑
     0    100.0%     100.0%      100.0%
     1      0.0%      97.5%      100.0%
     2      0.0%       2.5%       65.0%
     3      0.0%       0.0%        0.0%
     5      0.0%       0.0%        0.0%
     8      0.0%       0.0%        0.0%
```

这张表信息量极大，读出三条结论：

- **逻辑鲁棒性天差地别**：**单阈值一到 σ=1px 就崩到 0%**（临界抖动疯狂误触发），**滞回双阈值**能扛到 σ=1px 还有 97.5%，**再加一层时间平滑**（滑动平均，[第 85 章](../p18-events/ch85-temporal-window.md) 的时间窗思想）能把 σ=2px 从 2.5% 救回 **65%**。**同样的感知输入，逻辑越稳、能容忍的噪声越大**——这就是"逻辑杠杆"。
- **感知是硬瓶颈**：不管逻辑多花哨，**σ≥3px 时全部归零**。这是因为膝角在**接近伸直（站立）时是"病态"的**——腿几乎笔直，三点近乎共线，关键点的一点点垂直抖动就让角度剧烈跳变。感知一旦太差，再好的计数逻辑也回天乏术。
- **定位瓶颈在哪**：本项目估计器实测 **0.475px**，稳稳落在"100% 那一档"里，所以端到端可靠。**这就是"感知 vs 逻辑"的瓶颈定位**——先量出感知质量（0.47px）和逻辑的容噪区间（滞回+平滑能扛到 ~1-2px），一比就知道当前系统是被谁卡住。真上了噪声大的实拍视频，你会立刻知道该去**提升关键点精度**，还是**加强计数逻辑（平滑+滞回）**。

## 常见坑与提示

> 🕳️ **坑**：**关节角在"接近伸直"处是病态的（本章实测的关键教训）。** 腿快伸直时髋/膝/踝近乎共线，此时关键点的微小垂直误差会让角度大幅跳变（上表 σ=2px 时滞回从 97.5% 崩到 2.5% 就是它作祟）。对策：**信号先做时间平滑**再送状态机（本章的"滞回+平滑"把 σ=2px 救回 65%），或**把上阈值设得离"完全伸直"远一点**（别卡在 175°），给病态区留余量。

> ⚠️ **注意**：**滞回的两个阈值和死区宽度要按信号噪声来调。** 死区太窄（两阈值挨太近）防不住抖动，太宽会漏计浅蹲。工程做法：**先看角度曲线的噪声幅度和动作幅度，再把死区设成"明显大于噪声、又小于动作幅度"**。本章 40° 死区（110°~150°）对 67°~169° 的动作幅度绰绰有余。

> 💡 **提示**：**"理想输入 vs 真实/加噪输入"两条曲线，是应用章定位瓶颈的利器。** 和 [第 55 章](../p11-keypoints/ch55-hand-gesture.md) 一样，用"理想关键点跑逻辑"验证**逻辑对不对**，再用"真实/加噪关键点跑逻辑"衡量**端到端**，两者一减就知道差距来自感知还是逻辑。别一上来就瞎调，先分段甩锅。

> ⚠️ **注意（诚实边界）**：**这是个教学级 demo，真健身 App 还差得远。**（1）**单视角 2D 姿态有深度歧义**——侧身、朝向镜头的深蹲，2D 角度会失真，专业方案上多视角或 3D 姿态、或限定拍摄角度；（2）**遮挡**（手臂挡住躯干、自遮挡）会让关键点乱跳；（3）真 App 还要**判断动作是否标准**（蹲够深没有、有没有塌腰）、支持**多种动作**、给实时反馈。本章只解决了"数数"这一环，但"感知→角度→状态机"这套骨架，是所有这些的共同起点。

## 本章小结

- **健身计数器 = 姿态关键点（[第 53 章](../p11-keypoints/ch53-human-pose.md)）+ 关节角 + 状态机**。姿态估计不用重造，重点是把连续信号稳稳数成整数次。
- **用"关节角"而非绝对坐标**：角度对人体的**位置、尺度天然不变**，计数逻辑一次调好就通用（膝角实测 67°蹲底 ~ 169°站直）。
- **滞回双阈值状态机**（施密特触发器，呼应 [第 85 章](../p18-events/ch85-temporal-window.md)）：必须"先蹲到位、再站起来"才计一次，中间 40° 死区吸收临界抖动——**单阈值一遇噪声就狂误触发**。
- 实测：估计器关键点误差 **0.475px**，演示序列端到端**准确数出 8 次**。噪声扫描揭示**逻辑杠杆**（单阈值 σ=1px→0%，滞回→97.5%，滞回+平滑→100%）与**感知硬瓶颈**（σ≥3px 全崩，因膝角在近伸直处病态）。
- **感知 vs 逻辑的瓶颈定位**：量出感知质量（0.47px）与逻辑容噪区间，一比就知道系统被谁卡住——这是应用类项目最值钱的工程直觉。
- **诚实边界**：单视角 2D 有深度歧义，真 App 还需处理遮挡、动作规范性、多动作与多视角。

## 动手练习

1. **换个动作**：把膝角换成**肘角**（肩-肘-腕）数俯卧撑，或**肩角**数抬手——只需改取哪三个关节点和阈值，验证"关节角"套路的通用性。
2. **调死区**：把滞回的上下阈值间距从 40° 缩到 10°，再扩到 60°，在加噪序列上重跑，观察"太窄防不住抖、太宽漏浅蹲"的两难，找你数据上的甜点。
3. **加平滑**：把滑动平均窗口从 5 帧改成 3、9、15 帧，看噪声扫描表怎么变——窗口越大越抗噪，但太大会不会漏掉快速动作？体会平滑的代价。
4. **想一想**：如果换成实拍视频，关键点误差可能到 5~10px（远超本章 0.47px）。对照噪声扫描表，你的计数器还能用吗？该先提升感知，还是先加强逻辑？为什么？
