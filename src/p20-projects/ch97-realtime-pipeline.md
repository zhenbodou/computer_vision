# 第 97 章 项目：实时摄像头处理管线（采集→检测→跟踪）

> **本章导读**
> - 这是第二十部分的**开篇集成项目**：把前面各部分的能力串成一条**完整的实时管线**——**采集 → 检测 → 跟踪 → 事件**，做出一个**可插拔的项目骨架**。后面的周界报警（[第 103 章](ch103-perimeter-intrusion.md)）、客流计数（[第 104 章](ch104-people-counting.md)）都在这条骨架上长出来。
> - 你会学到三个工程要点：**用 `trait Stage` 把每个环节做成可插拔积木**、**跟踪器为什么是管线的“心脏”**（把一帧帧孤立检测缝成带稳定 `track_id` 的轨迹，[第 62 章](../p13-tracking/ch62-mot.md)）、以及**实时性下的“丢帧不变式”**（处理慢于到帧时怎么办，呼应 [第 75 章](../p16-video/ch75-rtsp-streaming.md)）。
> - 全程纯 Rust、只用 `std`、不碰 OpenCV；数据模型复用 [第 83 章](../p18-events/ch83-filtering-basics.md) 的 `BBox/Detection/Frame/Track/Event`。检测原理、跟踪推导、事件规则前面都讲透了，**本章重点是“怎么把它们组装成一个能跑的系统”**，正文每个数字都来自本机 `cargo run --release`。

## 场景：一路摄像头背后的完整链路

一个门口摄像头，要同时做到“数进出的人、车”“有人闯进布防区就报警”。这些业务功能背后，是同一条被反复复用的链路：

```text
摄像头出帧 → 检测器框出目标 → 跟踪器缝成带 id 的轨迹 → 事件规则(绊线/区域)吐告警
   采集          检测(第九部分)      跟踪(第62章)            事件(第十八部分)
```

难点不在任何单个环节——它们前面都讲过了——而在**怎么把它们“串”成一个健壮、可扩展、还能扛住实时压力的系统**。这一章我们就来搭这个骨架。

## 设计一：用 `trait Stage` 把管线做成可插拔积木

一个好管线的标志是**加规则不用改主干**。我们把每个事件环节抽象成一个 `Stage`：吃“带 id 的一帧”，吐若干 `Event`。有状态的规则（比如绊线要记住每个目标上一帧的脚点）自己 `&mut self` 持有状态。

```rust
/// 跟踪器输出的“带 id 的一帧”——事件规则的统一输入。
struct TrackedFrame { ts_ms: u64, obs: Vec<TrackObs> }

trait Stage {
    fn name(&self) -> &str;
    fn process(&mut self, tf: &TrackedFrame) -> Vec<Event>;
}
```

> 🕳️ **坑（接口对齐）**：[第 83 章](../p18-events/ch83-filtering-basics.md) 的 `Stage` 吃的是 `&Frame`（裸检测）。但到了完整管线里，**绊线要判方向、区域要判停留，都得按 `track_id` 分别追踪**——裸检测没有 id 根本做不到。所以这里让 `Stage` 吃 `TrackedFrame`（带 id 的一帧）。**这不是另起炉灶，而是同一心智模型的自然延伸**：管线的数据流从“帧”升级成了“带 id 的帧”，跟踪器就卡在检测与事件之间做这个升级。

管线本身只是**把跟踪器和一串 `Box<dyn Stage>` 串起来**，顺带统计吞吐：

```rust
fn feed(&mut self, frame: &Frame) -> Vec<TrackObs> {
    self.frames_processed += 1;
    self.dets_seen += frame.detections.len();
    let obs = self.tracker.update(frame);          // 检测 → 带 id 的轨迹观测
    let tf = TrackedFrame { ts_ms: frame.ts_ms, obs: obs.clone() };
    for st in self.stages.iter_mut() {             // 逐个可插拔阶段跑规则
        self.events.extend(st.process(&tf));
    }
    obs
}
```

想加“越界停留”“违停”规则？**写个新 `Stage`、`Box::new` 塞进 `stages` 就行，主干一行不动。**

## 设计二：跟踪器是管线的心脏

检测器每帧独立工作，它不知道“这一帧的人”和“上一帧的人”是不是同一个。**跟踪器负责缝合**：本项目用一个简易 SORT 式跟踪器（恒速 alpha-beta 预测 + 贪心 IoU 关联 + 生命周期管理，原理见 [第 62 章](../p13-tracking/ch62-mot.md)，此处直接复用），给每个目标一个**稳定的 `track_id`**。

`track_id` 稳不稳，直接决定上层业务对不对：**一次进出要正好数一次、一次入侵要正好报一次，全靠 id 不乱跳。**id 跳变（ID switch）就意味着一个人被当成两个。所以本项目专门造了个考验：**目标 1 在第 12、13 帧漏检**（模拟真实检测器的偶发丢框），看跟踪器能不能靠 `MAX_AGE=3` 的缓冲扛过去、不把它拆成两条轨迹。

## 动手：把三段串成一条管线

> ⚠️ **注意**：完整独立工程见 `code/projects/ch97_pipeline/`，**`cd` 进去 `cargo run --release`**，纯 `std` 无依赖。采集+检测用**合成 `Vec<Frame>`**（3 个目标匀速走位、检测框加高斯抖动模拟真检测器漂移，离散随机走 LCG 高位不用低位，见配套工程与 API_NOTES §18），确定性可复现。

场景 640×360：一条绊线 `y=200`、一块布防 ROI 矩形。挂两个 `Stage`（绊线 + 区域），全量跑完 45 帧：

```text
—— ① 管线全量运行（不丢帧）——
可插拔阶段：[Tracker -> tripwire -> roi]
处理帧数         = 45
累计检测框        = 120
生成轨迹数（确认）= 3
ID 切换数         = 0
触发事件数        = 3
  [roi] t= 400ms track#3 car 进入布防区
  [tripwire] t= 720ms track#2 person 出 OUT（门内→门外）
  [tripwire] t= 920ms track#1 person 进 IN（门外→门内）
```

一条 `[Tracker]->[Tripwire]->[ROI]` 的管线，把 **120 个孤立检测框**缝成 **3 条稳定轨迹**，再吐出 **3 条业务事件**：车驶入布防区、一个人出、一个人进。**关键是 `ID 切换数 = 0`**——尽管目标 1 中途漏检两帧，跟踪器靠生命周期缓冲扛住了，全程没把任何目标数成两个。这就是管线能正确计数/报警的地基。

## 实时性：处理慢于到帧时的“丢帧不变式”

真实系统里，**检测+跟踪常常比出帧慢**。摄像头 25fps（每 40ms 一帧），可管线单帧要 55ms（≈18fps），帧就会**堆积**。堆到内存爆掉之前，必须丢帧。工程共识是**丢最旧、保最新**（[第 75 章](../p16-video/ch75-rtsp-streaming.md) 的“看最新胜过看全部”）：有界队列满了就 `pop_front` 扔掉队首那帧。

这里用一个**确定性的离散事件模拟**（虚拟毫秒时钟，不读系统时钟，所以数字可复现）来演示，核心是一条可断言的**帧账目守恒**不变式：

```rust
if queue.len() >= cap { queue.pop_front(); dropped += 1; } // 满了丢最旧
queue.push_back(seq);
// ……处理器空闲就取队首处理……
assert_eq!(kept.len() + dropped, N_FRAMES, "帧账目必须守恒");
```

```text
—— ② 实时性：处理慢于到帧时的丢帧不变式（呼应第 75 章）——
到帧 40ms/帧(≈25fps)，单帧处理 55ms(≈18fps)，有界队列(容量3)丢最旧
产出 45 帧，处理 35 帧，丢弃 10 帧   （35 + 10 = 45 ✓ 帧账目守恒）
只喂“处理到的 35 帧”给管线：触发事件数 = 3（持续性事件在丢帧下仍保住）
  [roi] t= 400ms track#3 car 进入布防区
  [tripwire] t= 720ms track#2 person 出 OUT（门内→门外）
  [tripwire] t= 880ms track#1 person 进 IN（门外→门内）
```

两条结论：**（1）帧账目永远守恒**——处理 35 + 丢弃 10 = 产出 45，`assert` 保证一帧不多不少，这是最基本的可测试不变式。**（2）丢掉 10 帧后，3 条事件一条没少**——因为进出、入侵都是“跨越/停留”这类**在一段时间里持续存在**的事件，隔几帧采样一次照样抓得到。代价是**时间精度下降**：目标 1 的“进 IN”从全量时的 `920ms` 变成了 `880ms`（那一帧恰好被丢了，规则在更早处理到的一帧上触发）。

## 常见坑与提示

> ⚠️ **注意（丢帧改变事件时刻）**：丢帧会**平移事件的时间戳**（本章目标 1 的 IN 从 920ms 挪到 880ms）。对“进没进、报没报”这类布尔判定无伤大雅，但**对“测速”“精确计时”类应用是硬伤**——它们依赖帧间的准确时间差。这类场景要么别丢帧（上更强的算力/更小的模型），要么给每帧打上**采集时的真实时间戳**、用时间戳而非帧序号做计算。

> 💡 **提示（先定不变式，再谈性能）**：实时系统最怕“偶尔多算一帧、偶尔漏一帧”的玄学 bug。**先写下像“处理 + 丢弃 = 产出”这样的守恒不变式并 `assert` 死它**，比事后 debug 高效得多。丢帧策略、队列容量都可以调，但不变式不能破。

> 📖 **诚实边界**：这是**教学级骨架**，与生产管线的差距要讲清。（1）**检测是合成的**——真检测器（YOLO 类）有漏检、误检、类别混淆，跟踪难度陡增；（2）**关联是单类、无遮挡的**——真实密集场景要处理跨类误配、长时遮挡、目标重识别（ReID）；（3）**时钟是虚拟的**——真系统的处理耗时随负载抖动，还要考虑线程/背压/GPU 排队。但“**采集→检测→跟踪→事件 + 可插拔 Stage + 丢帧保最新**”这套骨架，正是所有生产管线的共同起点。

## 本章小结

- **实时管线 = 采集 → 检测 → 跟踪 → 事件**，本章把它们串成一个**可插拔骨架**：每个环节是一个 `Stage`，加规则不动主干。
- **数据流的关键升级在跟踪器**：它把裸检测（`Frame`）缝成带稳定 `track_id` 的轨迹（`TrackedFrame`），上层的绊线/区域规则才能按目标分别判定。`Stage` 吃 `TrackedFrame` 是 [第 83 章](../p18-events/ch83-filtering-basics.md) 模型的自然延伸。
- 实测：120 个检测框 → 3 条轨迹 → 3 条事件、**0 次 ID 切换**（目标 1 漏检两帧也没被拆断），这是上层计数/报警正确的地基。
- **实时性靠“丢最旧、保最新” + 帧账目守恒**（呼应 [第 75 章](../p16-video/ch75-rtsp-streaming.md)）：处理 35 + 丢弃 10 = 产出 45，`assert` 死这条不变式；丢帧后持续性事件不丢失，但时间戳会平移（IN 920ms→880ms）。
- **诚实边界**：真系统的检测/关联/时钟都远比合成场景复杂，但这套骨架是共同起点。

## 动手练习

1. **加一个 `Stage`**：仿照 `RoiStage` 写一个“越界停留 N 秒才报警”的 `DwellStage`（呼应 [第 88 章](../p18-events/ch88-intrusion-dwell.md)），`Box::new` 塞进管线，验证“加规则不动主干”。
2. **调丢帧参数**：把单帧处理耗时从 55ms 改成 45ms、80ms，或把队列容量从 3 改成 1、8，重跑看“处理/丢弃”怎么变——什么时候几乎不丢？什么时候丢一大半？帧账目守恒还成立吗？
3. **制造 ID 切换**：把目标 1 的漏检帧从 `[12,13]` 扩到 `[12,13,14,15]`（超过 `MAX_AGE=3`），观察它是否被拆成两条轨迹、ID 切换数变成几——体会 `MAX_AGE` 的作用。
