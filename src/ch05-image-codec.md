# 第 5 章 · 图像编解码：JPEG/PNG 是如何压缩的

> **本章导读**：上一章我们把一张图在内存里的排布（RGB / BGR / YUV / NV12）看透了。但图片存到硬盘、发到网上时，几乎从不用这种"原始像素"的形式——它太大了。本章拆开两大主力格式：**PNG（无损）** 和 **JPEG（有损）**，讲清它们到底怎么把一张图压小的、各自适合什么场景、低质量 JPEG 为什么会糊成一格一格。最后用 Rust 的 `image` crate 亲手解码、并调节 JPEG 质量看文件大小怎么变。视频编解码（帧、码流、RTSP）留到第 6 章，这里只管"一张图"。

**学习目标**：
- 算清原始图像的数据量，理解为什么必须压缩
- 分清无损压缩与有损压缩的取舍，知道各自该用什么格式
- 讲清 PNG 的"预测（滤波）+ DEFLATE"和 JPEG 的五步流水线，知道有损发生在哪一步
- 会用 `image` crate 解码 JPEG/PNG，并用 `JpegEncoder` 精确控制 JPEG 质量
- 认识 EXIF 方向、ICC、CMYK、渐进式 JPEG 这些"解码之后才冒出来"的工程坑

## 5.1 先算一笔账：为什么必须压缩

在讲任何原理之前，先用数字吓自己一跳。取一张 4K 照片（3840×2160）、RGB 三通道、每通道 8 位：

```text
3840 × 2160 × 3 字节 ≈ 2488 万字节 ≈ 24 MB
```

**一张** 4K 原始图就 24 MB。手机相册里存几千张，硬盘直接爆；发给朋友，流量心疼；网页首图这么大，用户还没看到图页面已经加载超时了。就算退回到 1080p（1920×1080×3 ≈ 6.2 MB）也依旧吃不消。

所谓编解码，就是在"存/传"这一段把它压小：

- **编码（encode / 压缩）**：把原始像素压成一个小得多的文件（`.jpg`、`.png`）。
- **解码（decode / 解压）**：把文件还原回"每个像素的颜色"，供显示或喂给模型。

同一张 24 MB 的 4K 图，存成高质量 JPEG 通常只要 1~3 MB，**压缩 10~20 倍**；这就是编解码的价值。核心指标叫**压缩比**（原始大小 ÷ 压缩后大小）。

## 5.2 无损 vs 有损：两条路线的取舍

压缩分两大流派，先建立直觉：

| | **无损压缩** | **有损压缩** |
| --- | --- | --- |
| 解码后 | 和原图**逐字节一致** | 和原图**很像，但不完全一样** |
| 类比 | 把论文用 zip 打包，一个标点不差 | 把论文缩写成摘要，大意还在细节没了 |
| 压缩比 | 一般（2~5 倍） | 很高（10~50 倍） |
| 代表格式 | **PNG**、BMP（不压）、GIF | **JPEG**、WebP（有损档） |
| 适合 | 截图、线条图、UI、要精确复原的资料 | 照片、大图、对细节不敏感的场景 |

有损为什么"敢"丢数据？因为图像里有大量**冗余**——相邻像素长得很像（空间冗余）、人眼分辨不出的细节（视觉冗余）。丢掉这些，肉眼几乎看不出差别，文件却小一个数量级。无损压缩只利用"重复"这一种冗余，所以压不了那么狠。

一句话记住选型：**截图/文字/需要透明 → PNG；照片/大图 → JPEG（或更省的 WebP/AVIF）。**

## 5.3 PNG：无损压缩是怎么做到的

PNG 的压缩靠两步接力：先"预测"，再"字典压缩"。

### 第一步：预测（滤波）

直接压像素值不好压，PNG 先做一个巧妙的变换——**对每一行，用邻居像素去预测当前像素，只存"预测的误差"**。这一步叫**滤波（filter）**，最常用的 `Sub` 滤波器就是"当前像素减左边像素"：

```text
原始一行像素：  50  52  53  55  90  91  ...
减去左邻居后：  50   2   1   2  35   1  ...   ← 存这一行
```

一片平缓的天空、一堵纯色墙，相邻像素几乎相同，相减后大片都是 `0` 或很小的数。数据的"花样"一下子变少了，为下一步铺好路。PNG 每行可以独立挑最省的滤波器（None/Sub/Up/Average/Paeth），编码器会自动选。

### 第二步：DEFLATE（字典 + 哈夫曼）

滤波后的数据交给 **DEFLATE** 算法（`.zip`、`gzip` 用的也是它），它干两件事：

1. **LZ77 字典压缩**：重复出现的片段不重复存，只记"往前回看 N 个字节、照抄 M 个"。一整行的 `0 0 0 0 …` 立刻被浓缩成一句"重复 0 若干次"。
2. **哈夫曼编码**：统计每个字节出现的频率，**出现越频繁的值用越短的二进制码**。滤波后 `0` 占了绝大多数，就给它分配最短的码，平均码长被压下来。

所以 PNG 特别适合**截图、图标、线条图、卡通、UI**——这类图有大片纯色和重复图案，滤波后几乎全是 0，压得又小又无损，还支持**透明通道（alpha）**。

### 为什么照片用 PNG 反而大

把一张照片存成 PNG，往往比同等观感的 JPEG 大 3~10 倍。原因正好戳中 PNG 的软肋：照片每个像素都因为光照、传感器噪声而略有不同，几乎**没有逐字节重复的片段**；滤波后的误差也不是清一色的 0，而是一堆杂乱小数。LZ77 找不到可复用的模板、哈夫曼也压不动高熵数据，于是 PNG 只能老老实实把这些"噪声细节"全存下来（它是无损的，连噪声都不许丢）。这时候就该换 JPEG 了。

## 5.4 JPEG：有损压缩的五步流水线

照片怎么压？JPEG 的答案是一条精妙的五步流水线，**有损的那一刀只砍在第 ④ 步**：

```text
原图(RGB)
  │  ① 转 YCbCr + 色度下采样   —— 借人眼"重亮度轻色彩"的弱点
  │  ② 切成一个个 8×8 小块
  │  ③ 每块做 DCT，变成"频率成分"
  │  ④ 量化：除以量化表取整    —— 有损、可调、不可逆，就在这！
  │  ⑤ Zigzag + 熵编码(哈夫曼) —— 无损收尾，把 0 打包
  ↓
.jpg 文件
```

### ① 转 YCbCr 并对色度下采样

先把 RGB 换成 **YCbCr**——把"亮度 Y"和"色彩 Cb/Cr"分开（这套色彩空间的细节见第 4 章，这里不重复展开）。为什么要分？因为人眼对**亮度**敏感、对**色彩**迟钝。于是 JPEG 做**色度下采样（chroma subsampling）**：亮度 Y 全保留，色彩 Cb/Cr 的分辨率砍掉一半（常见的 `4:2:0`）。光这一步，色彩数据就少了 3/4，而肉眼几乎无感——这是最"划算"的一刀。

### ② 分成 8×8 的小块

JPEG 不整张一起处理，而是把图切成一个个 **8×8 像素的小块**，每块单独走后面的流程。8×8 是压缩效率和计算量的折中。记住"独立处理"这四个字，它是块效应的根源（见后文）。

### ③ DCT：把小块变成"频率成分"

**DCT（离散余弦变换，Discrete Cosine Transform）** 是整件事的灵魂。打个比方：一段音乐可以拆成不同音高的音符叠加（低音、中音、高音各占多少）；同样，一个 8×8 图像块也能拆成一组"从粗到细的明暗波纹"的叠加：

```text
8×8 块 = a₁×(整体明暗) + a₂×(缓慢渐变) + … + a₆₄×(最细密的高频波纹)
         └─ 低频：大色块、缓慢变化 ─┘   └── 高频：细节、锐利边缘 ──┘
```

DCT 之后，这块图不再是 64 个像素值，而是 64 个**系数**：第 1 个叫 **DC**（直流，代表整块的平均亮度），其余 63 个叫 **AC**（交流，代表各种频率的波纹强度）。关键性质是——**真实图像的能量高度集中在低频**：大块明暗的系数很大，高频细节的系数很小、甚至是 0。这就给"丢掉高频"埋好了伏笔。注意：DCT 本身只是换个方式表示，**没丢任何信息**。

### ④ 量化：quality 参数在这里丢信息

**量化（quantization）** 才是真正"扔东西"的一步：把每个 DCT 系数**除以一张量化表里对应位置的数，再四舍五入取整**。量化表在高频位置放大数字，专门把小的高频系数碾成 0。用一行小数字手算一遍（取某块第一行，量化表用标准亮度表 quality≈50 的值）：

| 频率 | DCT 系数 | 量化表 | 系数 ÷ 表 | 取整结果 |
| --- | --- | --- | --- | --- |
| DC（最低频） | 316 | 16 | 19.75 | **20** |
| 低频 | −27 | 11 | −2.45 | **−2** |
| 中频 | 11 | 10 | 1.10 | **1** |
| 高频 | −6 | 16 | −0.38 | **0** |
| 更高频 | 3 | 24 | 0.13 | **0** |
| 最高频 | 1 | 40 | 0.03 | **0** |

结果 `20, −2, 1, 0, 0, 0`：低频保住了，高频**全归零**。解码时反量化是"系数 × 量化表"：`20×16=320`（原来 316，差了 4）、`−2×11=−22`（原来 −27）……**取整那一下的零头再也回不来了**——这就是"不可逆"和"有损"的由来。

而 **quality 参数（0~100）本质就是给量化表整体缩放**：

- **quality 高**（如 90）：量化表数字小（上表 16 可能缩到 3），除完取整后连高频都能留下 → 细节多、文件大。
- **quality 低**（如 20）：量化表数字大，除完大批系数变 0 → 细节被抹平、文件小、失真明显。

### ⑤ Zigzag + 熵编码

量化后每块的高频区（右下角）几乎全是 0。JPEG 用 **Zigzag（之字形）** 顺序扫描这 64 个系数——从左上低频斜着扫到右下高频，好处是**把所有的 0 排到一串连续的尾巴上**。接着做**熵编码**（游程 + **哈夫曼编码**）：一句"后面 30 个系数全是 0"只需几个比特就描述完。这一步和 PNG 的哈夫曼一样是**无损**的，只是把已经稀疏的数据打包得更紧。

### 为什么低质量 JPEG 会出现块状和振铃

现在两个经典瑕疵你都能解释了：

- **8×8 块效应（blocking）**：每个 8×8 块是**独立量化**的。低质量下每块只剩 DC 和极少低频，整块近似一个平板色；相邻块的平均值对不齐，就在 8 像素的网格线上"接缝"，于是满屏马赛克方格。
- **振铃 / 蚊状噪声（ringing）**：锐利的边缘（文字、线条）本来需要很多高频系数才能拼出直角；量化把高频砍光后，解码只能用几个平滑的余弦波去凑边缘，凑出来的曲线会在边缘旁**过冲、来回波动**（数学上叫吉布斯现象），看起来像文字周围镶了一圈鬼影/涟漪。

所以**截图、文字、线条一定别存 JPEG**（会糊会振铃），照片才是 JPEG 的主场。

## 5.5 解码就是逆着走一遍

解码（打开一张 JPEG/PNG）就是把上面的流水线**反过来跑**：熵解码 → 反量化 → 反 DCT（把频率成分拼回 8×8 像素块）→ 色度上采样 → YCbCr 转回 RGB。最终产物是**一个完整的像素数组**，每个像素都有确定的颜色值。

这正好接上第 1 章那条流水线的第 ① 步——

```text
1. 相机拍照，存成 JPG / 视频里的一帧
2. 【解码】← 本章：把压缩文件还原成"每个像素的颜色"（W×H×3）
3. 【预处理】缩放、色彩转换、归一化、排张量布局（第 10 章）
4. 【推理】喂给模型 …
```

**换句话说，本章讲的"解码"就是喂给模型之前的第一道工序。** 一旦解码完成，我们手里就是第 3 章那套 `image` / `ndarray` 能直接操作的原始像素了，和图片当初是 JPEG 还是 PNG 已经无关。

## 5.6 Rust 实操：解码与控制 JPEG 质量

理论讲完，上手。新建项目并加依赖：

```bash
cargo new ch05_codec && cd ch05_codec
cargo add image anyhow
```

下面这个程序做两件事：**①** 解码一张图并打印它的尺寸/通道；**②** 用不同 `quality` 重新编码成 JPEG，比较字节数。

```rust,ignore
use anyhow::Result;
use image::GenericImageView;            // 提供 .dimensions() 等方法
use image::codecs::jpeg::JpegEncoder;   // 可精确控制质量的 JPEG 编码器

fn main() -> Result<()> {
    // ---------- ① 解码并打印基本信息 ----------
    // image::open 会自动嗅探文件类型（JPEG / PNG / WebP …）选对解码器。
    // 它的产物就是"每个像素的颜色"——正对应第 1 章流水线的第 ① 步。
    let img = image::open("test.jpg")?;

    let (w, h) = img.dimensions();          // 宽、高（像素）
    let color = img.color();                // 颜色类型枚举：Rgb8 / Rgba8 / L8 …
    let channels = color.channel_count();   // 通道数：RGB=3、RGBA=4、灰度=1
    println!(
        "尺寸 = {w}×{h}, 颜色类型 = {color:?}, 通道数 = {channels}",
    );
    // 解码后"摊平"的原始像素有多大——这就是 5.1 节算的那个大数字
    let raw_bytes = w as usize * h as usize * channels as usize;
    println!("解码成原始像素后约占 {} 字节（{:.1} MB）\n", raw_bytes, raw_bytes as f64 / 1e6);

    // ---------- ② 用不同 quality 编码 JPEG，比较体积 ----------
    // JPEG 不支持透明通道，先统一转成 RGB8（丢掉可能存在的 alpha）。
    let rgb = img.to_rgb8();
    let raw_rgb = w as usize * h as usize * 3;

    println!("quality | 字节数  | 压缩比");
    println!("--------|---------|-------");
    for q in [95u8, 75, 50, 25, 10] {
        let mut buf: Vec<u8> = Vec::new();  // 编码到内存，方便直接量字节数
        // new_with_quality 的第二个参数就是 0~100 的质量：越低压得越狠、越糊。
        let mut encoder = JpegEncoder::new_with_quality(&mut buf, q);
        encoder.encode_image(&rgb)?;        // 把像素喂进去，跑完整条 JPEG 流水线

        let ratio = raw_rgb as f64 / buf.len() as f64;
        println!("   {q:>3}  | {:>7} | {ratio:.1}×", buf.len());

        // 想存盘对比画质就用这行；用看图软件放大能看到低 quality 的块效应
        std::fs::write(format!("out_q{q}.jpg"), &buf)?;
    }
    Ok(())
}
```

拿一张 1920×1080 的照片跑，输出大致是这样（具体数字取决于图片内容）：

```text
尺寸 = 1920×1080, 颜色类型 = Rgb8, 通道数 = 3
解码成原始像素后约占 6220800 字节（6.2 MB）

quality | 字节数  | 压缩比
--------|---------|-------
    95  |  742139 | 8.4×
    75  |  281044 | 22.1×
    50  |  186503 | 33.4×
    25  |  118742 | 52.4×
    10  |   61529 | 101.1×
```

三个要点：

1. **quality 越低文件越小、失真越大**：从 95 到 10，文件小了十几倍，但 `out_q10.jpg` 放大看，8×8 块和文字边的振铃一目了然。**工程上人像/一般照片常用 80~90，缩略图可以到 60~70**，再低就肉眼可见糊了。
2. **PNG 没有 quality 这个旋钮**：它是无损的，"质量"永远是 100%，只能调压缩耗时（`CompressionType`），压不动照片。想对比可把上面 `save("x.png")` 存一份，会发现比 quality 90 的 JPEG 大好几倍。
3. **为什么用 `JpegEncoder` 而不是 `img.save("x.jpg")`**：第 3 章说过 `save()` 只按扩展名选编码器、**质量不可控**（内部用默认质量）。要卡质量、卡体积，就得像上面这样直接用编码器底层 API。

## 5.7 新格式一览：WebP / AVIF / HEIF

JPEG/PNG 是"老将"，近十年冒出一批压缩比更高的新格式，一句话各表：

| 格式 | 出身 | 一句话 |
| --- | --- | --- |
| **WebP** | 谷歌 | 有损+无损+透明+动画全能，同画质比 JPEG 小 25~35%，网页常用 |
| **AVIF** | 开放联盟（基于 AV1 视频编码） | 目前压缩率最强，网页新宠，编码较慢 |
| **HEIF/HEIC** | MPEG（基于 HEVC 视频编码） | iPhone 默认照片格式，省空间但兼容性一般 |

它们的思路和 JPEG 一脉相承（变换 + 量化 + 熵编码），只是算法更先进。好消息是：用 Rust 的 `image` crate 打开它们，代码和打开 JPEG **一模一样**——`image::open("x.webp")` 即可（AVIF/WebP 解码需要在 `image` 的 features 里开启）。**解码后拿到的都是同样的像素**，上层算法完全不用关心源格式。

## 5.8 工程坑：解码之后才是麻烦的开始

`image::open` 能成功返回，不代表你拿到的像素就"能直接用"。真实项目里踩得最多的四个坑：

### 坑一：EXIF 方向（orientation）——手机照片会"躺着"

这是**最高频、最坑新手**的一个。手机横着、竖着、倒着拍，传感器出来的像素其实一直是同一个方向，手机只是在文件的 **EXIF** 信息里记一个"方向标记（Orientation，1~8）"，让看图软件显示时自己转。问题是：**`image::open` 只解码像素，默认不读、不应用这个方向标记**。于是你解码出来的图可能是**躺着或倒着**的——人眼看着别扭，模型更是直接把一张"歪脖子"的图学歪，检测框全错位。

处理办法：解码后读出 EXIF Orientation，再把图转正。用 `kamadak-exif` 读方向：

```rust,ignore
// cargo add kamadak-exif
use std::fs::File;
use std::io::BufReader;

/// 读出 JPEG 的 EXIF Orientation（1~8），读不到就当 1（正常）
fn read_orientation(path: &str) -> u32 {
    let file = match File::open(path) { Ok(f) => f, Err(_) => return 1 };
    let mut reader = BufReader::new(file);
    let exif = match exif::Reader::new().read_from_container(&mut reader) {
        Ok(e) => e,
        Err(_) => return 1, // 很多图根本没有 EXIF，属正常
    };
    exif.get_field(exif::Tag::Orientation, exif::In::PRIMARY)
        .and_then(|f| f.value.get_uint(0))
        .unwrap_or(1)
}
```

拿到值后按下表旋正（`DynamicImage` 自带 `rotate90/180/270`、`fliph/flipv`）：

```rust,ignore
use image::DynamicImage;

/// 按 EXIF Orientation 把图像"摆正"
fn apply_orientation(img: DynamicImage, orientation: u32) -> DynamicImage {
    match orientation {
        2 => img.fliph(),                 // 水平镜像
        3 => img.rotate180(),             // 倒置（最常见之一）
        4 => img.flipv(),                 // 垂直镜像
        5 => img.rotate90().fliph(),
        6 => img.rotate90(),              // 顺时针 90°（竖拍最常见）
        7 => img.rotate270().fliph(),
        8 => img.rotate270(),             // 逆时针 90°
        _ => img,                         // 1 或未知：原样
    }
}
```

> 提示：较新版本的 `image` 也提供了 `DynamicImage::apply_orientation` 配合解码器读到的方向来一步旋正，但很多老代码/老版本没有，理解上面这套"读标记 → 手动旋转"的逻辑最保险。**一句话记牢：处理手机来源的图，第一件事就是查 EXIF 方向。**

### 坑二：ICC 色彩配置文件

图片里可能内嵌一段 **ICC（色彩配置文件）**，用来精确描述"这些数值到底对应什么颜色"（比如广色域的 Display P3）。`image` 解码时通常**不做色彩管理**，直接把数值当 sRGB 给你。后果：广色域拍的照片，解码后颜色可能偏淡或偏移。绝大多数视觉工程可以忽略这一层（模型对轻微色偏不敏感），但做**颜色测量、色差检测**这类任务时要当心，必要时借助专门的色彩管理库转换。

### 坑三：CMYK 的 JPEG

JPEG 绝大多数是 RGB（YCbCr），但**印刷行业**的 JPEG 可能是 **CMYK（四通道，青品黄黑）**，甚至是反相的 YCCK。这类图用一些解码器打开会**颜色诡异**（发蓝发紫）或直接报错。工程上遇到"某张图打开颜色全乱"，先怀疑它是不是 CMYK，用 `img.color()` 打印通道数排查（四通道就很可疑）。

### 坑四：渐进式 JPEG（progressive）

普通 JPEG 是**基线（baseline）**——从上到下一行行解码；**渐进式（progressive）JPEG** 则是先出一张全图的模糊版，再一遍遍加细节（网页上"先糊后清"的那种）。它更省体积、观感更好，但**解码要把整张图多遍扫描完才能出最终像素**，内存和耗时略高，且少数简易解码器不支持。`image` 能正常解码渐进式 JPEG，但在极端受限的嵌入式解码库上要留个心眼。

## 5.9 小结

- 原始像素太大（一张 4K RGB ≈ 24 MB），存和传都扛不住，所以图片一律要编解码。
- **无损**（PNG）解码后逐字节还原，适合截图/线条/透明；**有损**（JPEG）用肉眼无感的失真换十几倍压缩比，适合照片。
- PNG = **预测（滤波）+ DEFLATE（LZ77 字典 + 哈夫曼）**；照片没有重复片段，所以用 PNG 反而更大。
- JPEG 五步：**YCbCr + 色度下采样 → 8×8 分块 → DCT 变频率 → 量化（quality 在这丢信息）→ Zigzag + 哈夫曼**；块状伪影和振铃都源于"逐块独立量化、砍掉高频"。
- **解码 = 逆过程**，最终产物是每个像素的颜色，正是第 1 章流水线的第 ① 步；Rust 里用 `image::open` 解码、`JpegEncoder::new_with_quality` 控制质量。
- 解码成功不等于万事大吉：**EXIF 方向**（手机照片会歪，务必旋正）、ICC 色彩、CMYK、渐进式 JPEG 都是真实项目里的坑。

## 5.10 练习

1. **量化手算**：把 5.4 节量化表整体除以 4（模拟 quality≈90），重新计算那 6 个系数的量化结果。对比 quality≈50 的版本，多保住了哪几个高频系数？由此说明"高 quality 文件更大"。
2. **质量与体积曲线**：改写 5.6 节的程序，让它从 quality 10 循环到 100（步长 10），把每个质量的字节数打印出来。观察文件大小在哪个区间"性价比"最高（再往上加质量、体积猛涨但肉眼没啥变化）。
3. **PNG vs JPEG 对照实验**：找一张**截图**（含文字）和一张**风景照**，分别存成 PNG 和 quality 85 的 JPEG，比较四个文件的大小，并放大看截图的 JPEG 版文字边缘有没有振铃。用本章结论解释你看到的现象。
4. **方向坑复现**：用手机竖拍一张照片传到电脑，直接用 5.6 节程序 `image::open` 打开并 `save` 成新图，看它是不是躺下了；再接上 5.8 节的 `read_orientation` + `apply_orientation` 把它旋正。
