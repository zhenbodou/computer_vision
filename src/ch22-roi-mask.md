# 第 22 章 · 空间过滤器：ROI、Mask 与静态过滤

> **本章导读**：第 16 章让模型"看见"了目标，第 21 章给每个目标发了跟踪 ID。可模型是老实人——它会把**整幅画面**里所有的车、所有的人都报给你，而业务往往只关心其中一小块。检测+跟踪拿到目标之后，业务规则的第一关就是"**空间**"这一维：只关心画面里我在意的区域，别的通通不算数。本章讲三件事——**ROI**（感兴趣区域，只要框内）、**Mask**（掩码，屏蔽掉某块）、**静态过滤**（赶走长期不动的目标）。读完你能把"模型输出的一堆目标"收拾成"落在正确位置、值得上报的目标"，为后面第 23 章的拌线、第 24 章的去重打好地基。

## 22.1 为什么需要空间过滤：模型看全局，业务只管一块

想象你在监考。考场里坐着五十个考生，走廊上还来来往往一堆送水的、路过的老师。你作为监考员，**只管考场里这五十个人**——走廊上谁在走动跟你没半毛钱关系。于是你在门口拉一条**警戒线**：线内的人我盯着，线外的我一律不看。

机器视觉里也是同一回事。摄像头对着一个路口，模型会把画面里**能看到的一切**都检测出来：马路上的车、旁边停车场里停着的车、远处天桥上的行人……但如果这个项目的需求是"统计**这条主路**上的车流量"，那停车场里的车、天桥上的人全是噪声。你必须替模型划一条"警戒线"，告诉它：**只有落在这块区域里的目标才算数。**

这就是**空间过滤（spatial filtering）**：在"图像空间"这一维上，用人为定义的规则，把模型输出的目标筛一遍。它是把冷冰冰的"**模型输出**"翻译成有意义的"**业务事件**"的第一层规则。

```text
     模型侧                          业务规则第一关：空间
┌──────────┐ Detection ┌──────────┐  Track   ┌───────────────────────────┐
│  检测      │────────→ │  跟踪      │────────→ │      空间过滤（本章）         │──→ 时间维规则
│ 第 16 章   │  一堆框    │ 第 21 章   │ 带ID目标  │  ROI · Mask · 静态过滤       │   拌线/去重
└──────────┘           └──────────┘          └───────────────────────────┘   第 23/24 章
   画面里所有物体                                只留下"该管的那些目标"
```

本章的三件工具，对应三种"该不该管"的判断：

| 工具 | 一句话 | 典型用途 |
| --- | --- | --- |
| **ROI** | 只要**落在这块区域里**的目标 | 只报主路上的车、只统计闸机口的人 |
| **Mask** | **屏蔽掉某块区域**，里面的目标一律不算 | 遮住电视屏幕、水面反光等易误报区 |
| **静态过滤** | 干掉**长期不动**的目标 | 停着的车、雕像、固定误检物 |

> 注意本章的"空间"是**当前帧内的位置**这一维。目标**跨过一条线**触发事件（拌线）是第 23 章，同一个目标**短时间内别重复报**（cooldown 去重）是第 24 章——那些属于"时间"和"事件"维度，本章不碰。

## 22.2 矩形 ROI：最简单的感兴趣区域

**ROI（Region of Interest，感兴趣区域）** 就是画面里那块"我在意的区域"。最简单的形状是**矩形**：给定左上、右下两个角，判断目标在不在这个矩形里就行。

先约定：本章所有坐标——ROI 的顶点、mask 的像素、Track 的框——**统统是原图像素坐标**（和第 16 章后处理还原出来的框同一套坐标系）。这一点是空间过滤的命根子，第 22.8 节会专门再敲一遍。

复用全书统一的 `BBox`（左上-右下像素坐标）。一个矩形 ROI 可以直接用四元组 `(x1, y1, x2, y2)` 表示，判定"点在不在矩形内"只是四个比较：

```rust
/// 矩形 ROI：(x_min, y_min, x_max, y_max)，原图像素坐标
type Rect = (f32, f32, f32, f32);

/// 点是否落在矩形内（含边界）
fn point_in_rect(p: (f32, f32), r: Rect) -> bool {
    let (px, py) = p;
    let (x1, y1, x2, y2) = r;
    px >= x1 && px <= x2 && py >= y1 && py <= y2
}
```

问题来了：一个目标是一个**框**，不是一个点。拿框的哪个点去和 ROI 比？常见三种：

- **框中心点** `center()`：`((x1+x2)/2, (y1+y2)/2)`。
- **框底边中点**：`((x1+x2)/2, y2)`——也就是目标"脚下"那个点。
- **整个框**：要求框和 ROI 有交集，或框完全被 ROI 包住。

用哪个大有讲究，我们放到第 22.4 节专门讨论。这里先记住：**多数落地场景（人、车站在地面上）用底边中点最贴合直觉**。矩形 ROI 好写好调，但真实世界里"我在意的区域"往往不是规规矩矩的矩形——一条斜着的马路、一个梯形的闸机口——这就要请出多边形 ROI。

## 22.3 多边形 ROI 与射线法（point-in-polygon）

真实场景的 ROI 几乎都是**不规则多边形**：你在监控画面上手点几个点，圈出"这条马路"或"这个院子"。核心问题变成一句话：**给定一个点，判断它在不在这个多边形里？** 这就是计算几何里的经典问题——**点在多边形内判定（point-in-polygon）**，最常用的解法叫**射线法（ray casting）**。

### 射线法的原理

原理一句话就能说清：**从待测点朝任意方向发一条射线（通常向右，即 +x 方向），数它穿过多边形边界的次数。奇数次 → 在里面；偶数次 → 在外面。**

为什么？想象你站在一个院子里，笔直朝一个方向走出去到无穷远。每穿过一道墙，你就"进/出"切换一次。如果你**起点在院内**，那么走出去必然是"出墙"→（可能再进再出）……最后一定停在院外，穿墙次数是**奇数**。如果起点就在院外，来回进出后还是回到院外，次数是**偶数**。

### 手算一遍

给一个具体多边形，五个顶点按顺序（A→B→C→D→E）：

```text
  y
  6│               D(3,6)
  5│             ╱        ╲
  4│      E(1,4)            C(5,4)
  3│      │      P●───────────────→   从 P 向 +x 方向发射线
  2│      │                  │
  1│      A(1,1)─────────────B(5,1)
   └────────────────────────────────→ x
          1     2    3    4    5
```

待测点 **P = (3, 3)**，向右发一条水平射线（y 恒等于 3，x 从 3 一直到 +∞）。逐条边看它跨不跨过这条射线、交点在不在 P 的右边：

| 边 | 端点 | 跨过 y=3？ | 交点 x | 在 P 右侧(x>3)？ | 计一次？ |
| --- | --- | --- | --- | --- | --- |
| A→B | (1,1)–(5,1) | 否（水平边，在 y=1） | — | — | 否 |
| B→C | (5,1)–(5,4) | 是（1≤3<4） | 5 | 是 | ✅ |
| C→D | (5,4)–(3,6) | 否（都在 y≥4） | — | — | 否 |
| D→E | (3,6)–(1,4) | 否（都在 y≥4） | — | — | 否 |
| E→A | (1,4)–(1,1) | 是（1≤3<4） | 1 | 否（在左边） | 否 |

右侧穿越次数 = **1**，奇数 → **P 在多边形内**。符合直觉：P(3,3) 确实在这个五边形肚子里。

再验一个外部点 **Q = (6, 3)**：向右发射线，B→C 边交点在 x=5，但 5 < 6，在 Q 的**左边**不算；E→A 边交点在 x=1 更在左边。右侧穿越次数 = **0**，偶数 → **Q 在外部**。也对：多边形最大 x 才到 5，Q 在它右边。

### 可编译的 Rust 实现

下面是射线法的标准实现（业界俗称 PNPOLY），签名严格按约定：

```rust
/// 射线法判定点是否在多边形内部。
/// p:   待测点（原图像素坐标）
/// poly: 多边形顶点，按顺序排列（顺时针或逆时针都行），首尾自动闭合
fn point_in_polygon(p: (f32, f32), poly: &[(f32, f32)]) -> bool {
    let (px, py) = p;
    let n = poly.len();
    if n < 3 {
        return false; // 不足三个点构不成多边形
    }
    let mut inside = false;
    let mut j = n - 1; // j 是 i 的前一个顶点，构成边 (j -> i)
    for i in 0..n {
        let (xi, yi) = poly[i];
        let (xj, yj) = poly[j];
        // 这条边是否一端在射线上方、一端在下方（用半开区间避免顶点重复计数）
        let straddles = (yi > py) != (yj > py);
        if straddles {
            // 求边与水平线 y=py 的交点 x
            let x_cross = xi + (py - yi) / (yj - yi) * (xj - xi);
            // 交点在 P 右侧才算一次穿越 → 翻转内外状态
            if px < x_cross {
                inside = !inside;
            }
        }
        j = i;
    }
    inside
}
```

几个要点：

- `straddles` 用 `(yi > py) != (yj > py)` 而不是 `>=`，是为了把每条边看成**半开区间** `[下端, 上端)`，这样射线**正好穿过某个顶点**时不会被相邻两条边各算一次（那是射线法最容易翻车的 corner case）。
- 循环里 `j` 从最后一个顶点起步，保证 E→A 这条**闭合边**也被检查到——不用手动把首点再 push 一遍。
- 全程只做加减乘除，没有开销大的操作，一个点判定就是 O(顶点数)，几十个顶点也是纳秒级。

拿它验证刚才的手算：`point_in_polygon((3.0,3.0), &[(1.,1.),(5.,1.),(5.,4.),(3.,6.),(1.,4.)])` 返回 `true`，`(6.0,3.0)` 返回 `false`，与手算一致。

## 22.4 拿目标的哪个点去判定？中心点 vs 底边中点

有了 `point_in_polygon`，还得决定**用目标框的哪个点**去喂它。这个选择直接决定漏报和误报，务必想清楚。

```text
        ┌─────────┐  ← 框顶
        │         │
        │    ●center( (x1+x2)/2, (y1+y2)/2 )
        │         │
        └────●────┘  ← 底边中点 ( (x1+x2)/2, y2 )   ← "脚下"、落地点
```

给 `BBox` 加一个"底边中点"方法（`center()` 第 21 章已在用，这里按同样风格扩展）：

```rust
impl BBox {
    /// 底边中点：目标"脚下"落地的位置
    pub fn bottom_center(&self) -> (f32, f32) {
        ((self.x1 + self.x2) / 2.0, self.y2)
    }
}
```

两种选择的利弊：

| 判定点 | 好处 | 坑 |
| --- | --- | --- |
| **中心点** center | 简单对称，框上下抖动影响小 | 一个高个子的人站在 ROI 边界外，脚已进区但中心还在区外 → **漏报** |
| **底边中点** | 贴合"人/车站在地面的位置"，落地场景最准 | 框被画面边缘截断时 `y2` 失真；俯拍/空中目标没有"地面"概念时不适用 |

**经验法则**：地面场景（行人、车辆的周界入侵、区域统计）几乎一律用**底边中点**——因为业务关心的是"这个人的脚踩没踩进禁区"，而不是"他的躯干中心在哪"。俯拍视角、传送带上的零件、天上的无人机这类没有明确"落地点"的场景，用中心点更稳。极端严格的场景（一点都不能进）可以要求"整个框都在 ROI 内"，但那样召回会明显下降，慎用。

## 22.5 Mask：把不想看的区域直接涂黑

ROI 是"**只要里面**"的白名单思路。有时候反过来更方便：画面大部分都要看，只有**某几块**是麻烦精——比如墙上挂的**电视屏幕**（里面播的人物会被当成真人检测）、地面的**水洼反光**、随风摇的树影。这些区域你想**直接排除**。这就是 **Mask（掩码）** 的活。

Mask 是一张和原图（大致）等大的**二值图**：白色（255）表示"这里允许检测"，黑色（0）表示"这块屏蔽掉，里面出啥都不算"。你在工具里把电视、水面涂成黑色，存成一张 PNG，运行时按像素查表即可：

```rust
use image::GrayImage;

/// 查 mask 判断某点是否位于「允许检测」区域。
/// 约定：白(>127)=允许，黑=屏蔽。
/// mask 若与原图不等大，先把坐标按比例映射过去。
fn point_allowed_by_mask(
    p: (f32, f32),
    mask: &GrayImage,
    frame_w: u32,
    frame_h: u32,
) -> bool {
    let (px, py) = p;
    // 原图坐标 → mask 坐标（mask 可能是按缩略图画的）
    let mx = (px * mask.width() as f32 / frame_w as f32).round() as i32;
    let my = (py * mask.height() as f32 / frame_h as f32).round() as i32;
    // 越界当作屏蔽（也可按业务反过来当允许，取决于边界怎么定义）
    if mx < 0 || my < 0 || mx >= mask.width() as i32 || my >= mask.height() as i32 {
        return false;
    }
    mask.get_pixel(mx as u32, my as u32)[0] > 127
}
```

### ROI 和 Mask，一个白名单一个黑名单

它们本质是一回事——都在问"**点在不在某区域内**"——只是取用方向相反，表示形式也不同：

| | ROI | Mask |
| --- | --- | --- |
| 语义 | **白名单**：只要区域**内** | **黑名单**：屏蔽区域**内**，保留区域外 |
| 表示 | 少量顶点的**多边形**（矢量） | 一张**二值图**（栅格，逐像素） |
| 适合 | 一块规整的目标区 | 形状零碎、边界不规则的排除区 |

理论上一个多边形 ROI 也能烤成一张 mask，反之 mask 里的白区也能近似成多边形，二者可以互转。工程上按手感选：**要圈一块地**用多边形 ROI 顺手；**要抠掉几处犄角旮旯**用 mask 省事。二者也常常**同时用**（见第 22.7 节）。

### 别和第 18 章的分割 mask 搞混

同样叫 mask，本章的和第 18 章的完全是两码事，务必分清：

| | 第 18 章 分割 mask | 本章 规则 mask |
| --- | --- | --- |
| 谁产生的 | **模型**推理输出 | **人工**画好的固定规则 |
| 变不变 | **每帧都变**，跟着物体走 | **一次画好，长期不变** |
| 表达什么 | "这个**像素**属于哪个物体/类别" | "这**块区域**要不要参与业务判定" |

一句话：第 18 章的 mask 是"模型看到了什么"，本章的 mask 是"我允许它在哪儿看"。

## 22.6 静态过滤：赶走"长期不动"的目标

最后一个空间过滤器，专治一类顽固噪声：**长期不动的目标**。停在路边的车、广场上的**雕像**、被误检成"人"的立柱和海报——它们稳稳待在 ROI 里，帧帧都被上报，却没有任何业务价值。**静态过滤（static filtering）** 的任务就是把它们摘出去。

判断"动没动"，靠单帧是做不到的——你得知道这个目标**过去几帧在哪**。这正是第 21 章跟踪给的东西：每个目标有稳定的 `id`。于是思路清晰了：**给每个 track.id 记一段最近位置的历史，统计它在 N 帧内的位移；位移小于阈值，就判为静止、过滤掉。**

统一的 `Track` 结构（第 21 章）本身只带当前帧的 `bbox`，不含历史。所以我们在过滤阶段**另起一个历史缓冲**，用 `track.id` 作键累积位置——不改动统一类型，也更符合工程分层：

```rust
use std::collections::{HashMap, VecDeque};

/// 每个 track 最近若干帧的落地点历史（原图像素，用底边中点）
pub struct MotionHistory {
    window: usize,                              // 观察窗口帧数 N
    positions: HashMap<u64, VecDeque<(f32, f32)>>,
}

impl MotionHistory {
    pub fn new(window: usize) -> Self {
        Self { window, positions: HashMap::new() }
    }

    /// 每帧调用：把当前这批 track 的落地点追加进历史
    pub fn update(&mut self, tracks: &[Track]) {
        for t in tracks {
            let buf = self.positions.entry(t.id).or_default();
            buf.push_back(t.bbox.bottom_center());
            while buf.len() > self.window {
                buf.pop_front(); // 只留最近 N 帧
            }
        }
        // ⚠️ 工程上还要清理「已经消失的 track」，否则 HashMap 只涨不消（见 22.8 坑）
    }

    /// 判断某 track 是否「静止」：窗口内所有位置的散布范围小于阈值
    pub fn is_static(&self, id: u64, thresh_px: f32) -> bool {
        let Some(buf) = self.positions.get(&id) else { return false; };
        if buf.len() < self.window {
            return false; // 历史还不够长，刚出现的目标先放行，别急着判静止
        }
        // 取窗口内所有落地点的外接框，用它的对角线长度衡量「晃动范围」
        let (mut min_x, mut min_y) = (f32::MAX, f32::MAX);
        let (mut max_x, mut max_y) = (f32::MIN, f32::MIN);
        for &(x, y) in buf {
            min_x = min_x.min(x); min_y = min_y.min(y);
            max_x = max_x.max(x); max_y = max_y.max(y);
        }
        let spread = ((max_x - min_x).powi(2) + (max_y - min_y).powi(2)).sqrt();
        spread < thresh_px
    }
}
```

**为什么用"外接框对角线"而不是"首帧到末帧的直线位移"？** 因为检测框天生有抖动，一个真静止的目标，落地点也会在几像素内哆嗦。如果只比首末两点，目标"绕一圈回原地"会被误判成静止；而外接框衡量的是"这 N 帧里它到底晃出了多大范围"，对抖动和往返都更稳。手算一下：某 track 最近 5 帧落地点为 `(100,200) (101,199) (100,201) (102,200) (101,200)`，外接框 `x∈[100,102]、y∈[199,201]`，对角线 `√(2²+2²)=√8≈2.83` 像素。阈值取 12 像素，则 `2.83 < 12` → 判为**静止**，过滤掉。

### "静止多久算静止？""刚停"和"一直停"

这几个问题决定阈值和窗口怎么配：

- **窗口 N 定多大**：N 太小，抖一下就误判成运动/静止来回横跳；N 太大，反应迟钝，车停了半天才被过滤。按**帧率折算成秒**最直观：25fps 下 `N=75` 约等于"连续静止 3 秒才算数"。
- **刚停 vs 一直停**：目标从运动变静止时，窗口要慢慢被静止位置填满，才会翻成 `is_static`——中间有个"缓冲期"仍会上报。反过来，一个**从视频一开始就杵在那**的雕像，前 N 帧因为历史不足（我们设计成先放行）还会被报几下，之后才安静。要更快摁住这种"天生静止背景"，可以配合第 19 章的背景建模预先标出静止区。
- **别把"抓静止"的需求也过滤了**：有些业务恰恰要**抓刚停下的车**（违停检测）——这时静态过滤不能无脑开，甚至要**反过来用**（专挑静止的报）。工具是中性的，方向由业务定。
- **阈值最好按目标大小归一化**：远处的车在画面上本来就只挪几个像素。固定像素阈值会让远处目标全被当成静止。工程上常改成"位移 / 框对角线 < 某比例"，让远近一视同仁。

## 22.7 串成一个空间过滤阶段

三件工具单独看都简单，真正上线时把它们串成**一个空间过滤阶段**：一批带 ID 的 `Track` 进去，一批"该管的" `Track` 出来。

```rust
use image::GrayImage;

/// 空间过滤：ROI（多边形）+ Mask（可选）+ 静态过滤，串成一关。
/// 所有坐标均为原图像素。判定点统一用底边中点。
pub fn spatial_filter(
    tracks: &[Track],
    roi: &[(f32, f32)],        // 多边形 ROI 顶点，按顺序
    mask: Option<&GrayImage>,  // 可选屏蔽掩码
    frame_w: u32,
    frame_h: u32,
    motion: &MotionHistory,    // 运动历史（由外部按帧维护）
    static_thresh_px: f32,
) -> Vec<Track> {
    tracks
        .iter()
        .filter(|t| {
            let p = t.bbox.bottom_center(); // 用"脚下"落地点判定

            // 1) ROI：必须落在感兴趣多边形内
            if !point_in_polygon(p, roi) {
                return false;
            }
            // 2) Mask：落在屏蔽区（黑）就丢掉
            if let Some(m) = mask {
                if !point_allowed_by_mask(p, m, frame_w, frame_h) {
                    return false;
                }
            }
            // 3) 静态过滤：长期不动的目标丢掉
            if motion.is_static(t.id, static_thresh_px) {
                return false;
            }
            true // 三关都过，才是"该管"的目标
        })
        .cloned()
        .collect()
}
```

在每帧的主循环里，**先更新历史，再过滤**（否则当前帧就没被计入位移统计）：

```rust
// 假设 tracks 来自第 21 章的跟踪器输出
motion.update(&tracks);
let kept = spatial_filter(
    &tracks, &road_roi, Some(&exclude_mask),
    frame_w, frame_h, &motion, 12.0,
);
// kept 里就是「在马路 ROI 内、没被屏蔽、且正在移动」的目标，
// 交给下一关（第 23 章拌线、第 24 章去重）。
```

组织上有几点顺手的约定：ROI 和 mask 是廉价的**点判定**，放前面先把大部分目标筛掉；静态过滤要查历史、稍重，放最后。三者是"**与**"的关系——任意一关不过，目标就出局。真实项目里这一整段常包成一个 `SpatialFilter` 结构体，把 `roi`、`mask`、`motion`、各种阈值都存成字段，从配置文件加载，一处配置、多路复用。

## 22.8 工程坑位清单

- **坐标系必须全程一致**。ROI 顶点、mask、Track 的框，都得是**原图像素坐标**。最常见的翻车：ROI 是在**缩放后的预览画面**上点的，却拿去和原图坐标的框比——整块区域偏移错位。凡是"在某个尺寸的画面上标注的坐标"，用之前都要按比例还原回原图（和第 16 章的 letterbox 逆变换、第 18 章 mask 缩放是同一类问题）。
- **ROI 顶点顺序不能乱**。射线法不在乎顺时针还是逆时针，但**在乎顶点是按边相邻排列的**。如果从配置里读点时顺序被打乱，多边形会自交成"蝴蝶结"，判定结果全错。存 ROI 时务必保持点的顺序，画出来目检一眼是不是想要的形状。
- **判定点选错 = 系统性漏报/误报**。中心点还是底边中点，一旦选错，是**整批目标**一起错，而不是偶尔错一个。地面场景默认底边中点；框被画面边缘截断时 `y2` 不可靠，要留意。详见第 22.4 节。
- **mask 分辨率要和原图对齐**。mask 常按缩略图画，运行时坐标要按 `mask尺寸/原图尺寸` 映射（代码里已处理）。还要注意**二值化阈值**（画的时候是不是纯黑纯白、有没有抗锯齿的灰边）和**边界越界**怎么算。二值 mask 若需要缩放，用**最近邻**，别用双线性插出 0.5 这种不黑不白的值。
- **静态历史的 HashMap 会内存泄漏**。`MotionHistory` 只加不删的话，跑久了 `positions` 里塞满早已消失的 track。要么在 `update` 里对"本帧没出现过的 id"计数、超过若干帧就删掉，要么定期清理。
- **跟踪掉了 ID，静态判定就重置**。如果跟踪器把一个静止目标跟丢又重新分配了新 ID，它的历史清零、又被当成"刚出现、先放行"，于是静止的东西又冒出来报一下。静态过滤的效果，**天花板就是跟踪的稳定性**（第 21 章）。

## 22.9 小结

- 检测+跟踪之后，业务规则的第一关是**空间维**：模型看全局，业务只管画面里在意的那一块，像监考只管警戒线内的人。
- **ROI**（感兴趣区域）是白名单。矩形 ROI 用四个比较即可；真实场景的不规则多边形靠**射线法**做点在多边形内判定——向右发射线数穿越次数，奇数在内、偶数在外，实现是纯加减乘除的 `point_in_polygon`。
- 判定点选**底边中点**（脚下落地点）最贴合地面场景，选中心点会在 ROI 边界处系统性漏报；选错是整批错。
- **Mask** 是黑名单，用一张二值图屏蔽电视、反光等易误报区；它和 ROI 是同一问题的两个方向，也要和第 18 章模型输出的分割 mask 严格区分。
- **静态过滤**借第 21 章的 track.id 累积历史，用窗口内落地点的散布范围判断"长期不动"，赶走停着的车、雕像和固定误检；窗口大小、阈值归一化、"刚停 vs 一直停"都要按业务权衡。
- 三者"与"起来组成 `spatial_filter` 一个阶段；全程坐标系一致是命根子。

## 22.10 练习

1. **补全矩形与整框判定**。基于第 22.2 节，写一个 `bbox_in_roi(b: &BBox, roi: &[(f32,f32)], mode: JudgeMode) -> bool`，`JudgeMode` 是枚举 `{ Center, BottomCenter, WholeBox }`。`WholeBox` 要求框的四个角都落在多边形内。用第 22.3 节那个五边形，构造一个"框大部分在内、只有一角探出去"的 `BBox`，观察三种模式各判成什么，体会召回差异。

2. **验证射线法的顶点 corner case**。构造一个点，让它向右的射线**正好穿过多边形的某个顶点**（比如上面五边形里对准 D(3,6) 那一横排）。分别用 `>` 版和把条件改成 `>=` 的版本跑一遍，看看后者为什么会把这个点判错。想清楚半开区间 `(yi>py)!=(yj>py)` 是怎么救场的。

3. **给静态过滤加上"大小归一化"**。把 `is_static` 的固定像素阈值改成"散布范围 / 框对角线 < 比例"（比例如 0.1）。造两个 track：一个近处的大框、一个远处的小框，且两者实际都只抖动几个像素。对比归一化前后，远处小目标是否还被误判成运动。

4. **让 `MotionHistory` 不再泄漏内存**。给它加一个"过期清理"：记录每个 id **最后出现的帧号**，在 `update` 里把连续 M 帧没再出现的 id 从 `positions` 里删掉。想一想 M 取多大合适——太小会把"暂时被遮挡、马上回来"的目标历史误删，太大又留垃圾。
