# 第 31 章 · 测试与性能剖析：单测、golden 回归、基准与火焰图

> **本章导读**：第 29 章教你把系统设计得又快又稳，第 30 章教你量化模型准不准。但还有两个资深工程师每天在做、初学者却常常跳过的动作：**怎么证明代码改了之后没改坏？怎么找到程序真正的性能瓶颈？** 视觉系统的 bug 特别阴险——它不崩溃，只是让坐标偏几个像素、让某个分支悄悄算错，画面看着"差不多"，谁都没发现，直到线上出事。这一章讲一整套"给自己上保险"的工程手段：**单元测试**给纯函数上锁、**golden 测试**给整条流水线拍快照、**属性/模糊测试**用机器生成刁钻输入、**criterion 基准**把快慢变成可比较的数字、**火焰图**精准定位瓶颈（而不是靠猜），再到**长稳/压力测试**逼出内存泄漏，最后把这一切挂进 **CI 自动门禁**。读完你写的就不再是"能跑一次的 demo"，而是"改一百次也不怕的工程代码"。

## 31.1 视觉系统的 bug 为什么特别"安静"

普通程序出 bug 往往会崩溃、抛异常、报错——响亮，容易发现。视觉系统不一样，它的输出是**图像和一堆数字**，错了也常常"看起来还行"：

- 后处理里逆 letterbox 的公式改了一版，坐标系统性偏移 5 像素——画面上框还在人身上，肉眼根本看不出，直到下游抠脸抠歪了才暴露。
- NMS 的 IoU 阈值不小心从 0.45 写成 0.045——重叠框被过度抑制，漏检悄悄增多，但单看某几张图"还是有框的"。
- 某次重构把 RGB 当成了 BGR（第 4 章的经典坑）——颜色反了，模型精度掉一截，但程序照跑不误。

这些都是**沉默的错误（silent failures）**：不崩、不报、不留痕，只是结果慢慢变差。**肉眼和"跑一次看看"根本兜不住**——这正是必须写自动化测试的理由。测试就是你事先埋好的、会替你尖叫的哨兵：**只要坐标偏了、阈值错了、颜色反了，测试立刻变红，而不是等线上事故。**

一个实用的心智模型——**测试金字塔**，从下到上、从多到少、从快到慢：

```text
        ╱ 端到端 ╲          少量：整条流水线 golden 测试（31.3）
      ╱───────────╲
    ╱   集成测试    ╲        适量：几个模块拼起来跑（如"预处理+推理"）
  ╱───────────────────╲
╱      单元测试         ╲    大量：纯函数逐个上锁（31.2）——又快又多，主力
```

底座是海量又快又准的单元测试，越往上越少越慢。下面从底座讲起。

## 31.2 单元测试：给纯函数上锁

视觉流水线里有一大批**纯函数**：输入定了、输出就定了，不依赖外部状态——IoU 计算、NMS、letterbox、坐标逆变换、射线法判点在多边形内、叉积判方向……**这些是单元测试的黄金目标**，因为它们的正确答案可以手算出来。

Rust 的单元测试是语言内置的，`#[test]` 标注函数、`cargo test` 运行，天然零门槛。给第 16 章的 `BBox::iou` 上锁：

```rust,ignore
#[cfg(test)]
mod tests {
    use super::*;

    // 浮点不能用 == 比较，要容差（第30章/附录A 反复强调）
    fn approx(a: f32, b: f32) -> bool { (a - b).abs() < 1e-5 }

    #[test]
    fn iou_完全重合是1() {
        let b = BBox { x1: 0.0, y1: 0.0, x2: 10.0, y2: 10.0 };
        assert!(approx(b.iou(&b), 1.0));
    }

    #[test]
    fn iou_完全不相交是0() {
        let a = BBox { x1: 0.0, y1: 0.0, x2: 10.0, y2: 10.0 };
        let c = BBox { x1: 20.0, y1: 20.0, x2: 30.0, y2: 30.0 };
        assert!(approx(a.iou(&c), 0.0));
    }

    #[test]
    fn iou_半重叠手算验证() {
        // 两个 10×10 框，x 方向错开 5：交集 5×10=50，并集 100+100-50=150
        let a = BBox { x1: 0.0, y1: 0.0, x2: 10.0, y2: 10.0 };
        let b = BBox { x1: 5.0, y1: 0.0, x2: 15.0, y2: 10.0 };
        assert!(approx(a.iou(&b), 50.0 / 150.0)); // = 0.3333...
    }
}
```

三个测试卡住了 IoU 的三种典型情形，其中"半重叠"用**手算的确定答案**（50/150）验证——这就是单元测试的精髓：**用一个你能笔算的例子，锁死函数的行为**。以后任何人重构 `iou`，只要算错，`cargo test` 立刻红给你看。

**最该上锁的是"可逆"的一对操作**——letterbox 预处理（第 10 章）和它的坐标逆变换（第 16 章）。它们必须严格互逆，否则框会系统性偏移：

```rust,ignore
#[test]
fn letterbox往返应还原坐标() {
    let (orig_w, orig_h) = (1280u32, 720u32);
    // 原图上的一个点，经 letterbox 映射到 640 输入、再逆映射回来，应≈原值
    let (px, py) = (800.0f32, 300.0f32);
    let info = letterbox_info(orig_w, orig_h, 640);      // 第10章：缩放比+padding
    let (mapped_x, mapped_y) = to_input_space(px, py, &info);
    let (back_x, back_y) = to_orig_space(mapped_x, mapped_y, &info); // 第16章逆变换
    assert!((back_x - px).abs() < 0.5 && (back_y - py).abs() < 0.5);
}
```

这个"往返测试（round-trip test）"是防坐标 bug 最省力的一招：**不用知道中间值是多少，只要求转过去再转回来能对上**。第 27 章反复强调的"坐标必须全程在原图像素系"，用这一个测试就能守住。

## 31.3 Golden 测试：给整条流水线拍快照

单元测试锁的是单个函数，但"检测器 + 后处理"整条链路串起来对不对，得靠 **golden 测试（也叫快照测试）**：**拿一张固定的输入图，跑完整流水线，把输出结果和事先存好的"标准答案（golden file）"逐一比对**。

思路像"对答案"：第一次人工确认结果正确后，把它存成文件（golden）；以后每次跑，新结果和 golden 一比，不一致就报警。

```rust,ignore
#[derive(serde::Deserialize)]
struct GoldenBBox { x1: f32, y1: f32, x2: f32, y2: f32 }

#[derive(serde::Deserialize)]
struct GoldenDetection { bbox: GoldenBBox, score: f32, class_id: usize }

/// golden 测试：固定输入图 → 检测 → 和存档结果比对
#[test]
fn 检测结果不应偏离golden() -> anyhow::Result<()> {
    let mut detector = Detector::load("tests/fixtures/yolov8n.onnx")?;
    let img = image::open("tests/fixtures/street.jpg")?.to_rgb8();
    let dets = detector.detect(&img)?;

    // 读取由独立更新脚本或显式更新模式生成并经人工确认的 golden
    let golden: Vec<GoldenDetection> =
        serde_json::from_reader(std::fs::File::open("tests/golden/street.json")?)?;

    // 数量必须一致
    assert_eq!(dets.len(), golden.len(), "检测框数量变了");
    // 逐个比对：类别严格相等，分数和坐标允许极小容差（推理有浮点抖动）
    for (a, b) in dets.iter().zip(golden.iter()) {
        assert_eq!(a.class_id, b.class_id, "类别变了");
        assert!((a.score - b.score).abs() < 1e-3, "分数漂移过大");
        let golden_box = BBox {
            x1: b.bbox.x1, y1: b.bbox.y1,
            x2: b.bbox.x2, y2: b.bbox.y2,
        };
        assert!(a.bbox.iou(&golden_box) > 0.999, "框位置漂移过大");
    }
    Ok(())
}
```

几个关键工程决定：

- **为什么要容差**：不同硬件、不同 ORT 版本、FP16 与否，推理结果会有微小浮点差异（第 13、14 章）。golden 测试**不能用 `==` 死磕**，要给分数和坐标留一点容差，否则换台机器就全红。这也呼应了第 13 章要讲的"ort 一致性"——同一模型跨平台输出应在容差内一致。
- **golden 什么时候更新**：模型换了、后处理逻辑**有意**改了，旧 golden 就该作废。常规做法是留一个开关（如环境变量 `UPDATE_GOLDEN=1`）**重新生成** golden，但**更新前必须人工核对新结果确实正确**——否则你把 bug 也一起存成了"标准答案"。
- **golden 要进版本管理**：`tests/golden/*.json` 跟代码一起提交，这样每次改动都能在 diff 里看到"结果变了多少"。

Golden 测试是"防止手滑改坏整条链路"的性价比之王：**一张图、一个 JSON，就守住了从预处理到后处理的全流程行为**。

## 31.4 属性测试与模糊测试：让机器生成刁钻输入

人写测试用例总会漏掉边界。**属性测试（property-based testing）**换个思路：不写具体例子，而是声明一条**永远该成立的性质**，让框架（Rust 生态用 `proptest`）自动生成成百上千组随机输入去砸它，一旦找到反例还会自动"缩小"成最小的复现用例。

视觉里有一堆天然的"性质"：

```rust,ignore
use proptest::prelude::*;

fn any_detection() -> impl Strategy<Value = Detection> {
    (
        0.0f32..1000.0, 0.0f32..1000.0,
        0.1f32..500.0, 0.1f32..500.0,
        0.0f32..1.0, 0usize..80,
    ).prop_map(|(x, y, w, h, score, class_id)| Detection {
        bbox: BBox { x1: x, y1: y, x2: x + w, y2: y + h },
        score,
        class_id,
    })
}

proptest! {
    // 性质①：IoU 永远落在 [0,1]，无论两个框多离谱
    #[test]
    fn iou永远在0到1之间(
        x1 in 0.0f32..1000.0, y1 in 0.0f32..1000.0,
        w1 in 0.1f32..1000.0, h1 in 0.1f32..1000.0,
        x2 in 0.0f32..1000.0, y2 in 0.0f32..1000.0,
        w2 in 0.1f32..1000.0, h2 in 0.1f32..1000.0,
    ) {
        let a = BBox { x1, y1, x2: x1 + w1, y2: y1 + h1 };
        let b = BBox { x1: x2, y1: y2, x2: x2 + w2, y2: y2 + h2 };
        let iou = a.iou(&b);
        prop_assert!((0.0..=1.0).contains(&iou), "IoU 越界: {}", iou);
    }

    // 性质②：NMS 不会凭空创造框，输出来自输入且数量不增
    #[test]
    fn nms输出是输入子集(dets in prop::collection::vec(any_detection(), 0..50)) {
        let kept = nms_per_class(dets.clone(), 0.45);
        prop_assert!(kept.len() <= dets.len());
        for k in &kept {
            prop_assert!(dets.iter().any(|d|
                d.class_id == k.class_id
                    && d.score.to_bits() == k.score.to_bits()
                    && d.bbox == k.bbox
            ));
        }
    }
}
```

属性测试特别擅长挖出**你没想到的边界**：零面积的框、完全重合的框、超大坐标——这些手写用例常漏，却正是线上"偶发崩溃"的来源。

**模糊测试（fuzzing）**是它的近亲，专门喂**畸形/恶意输入**看程序会不会 panic 或越界：损坏的 JPEG、`0×0` 的图、宽高巨大的图、坐标是 `NaN`/`Inf` 的框。视觉程序天天处理外部来的图像和网络流，**一张坏图不能让整个服务崩**（呼应第 29 章"坏帧跳过不 panic"）。最起码要保证：

```rust,ignore
fn validate_image(img: &image::RgbImage) -> anyhow::Result<()> {
    anyhow::ensure!(img.width() > 0 && img.height() > 0, "图像尺寸不能为 0");
    Ok(())
}

fn valid_bbox(b: &BBox) -> bool {
    [b.x1, b.y1, b.x2, b.y2].iter().all(|v| v.is_finite())
        && b.x2 >= b.x1
        && b.y2 >= b.y1
}

#[test]
fn 空图和畸形框应被拒绝() {
    // 第 10 章的 preprocess 假定输入已经过校验；边界层应先拒绝 0 尺寸图。
    let empty = image::RgbImage::new(0, 0);
    assert!(validate_image(&empty).is_err());

    let weird = BBox { x1: f32::NAN, y1: 0.0, x2: 10.0, y2: 10.0 };
    assert!(!valid_bbox(&weird));
}
```

## 31.5 基准测试：把"快慢"变成可比较的数字

第 29 章讲了一堆性能优化，但"到底快了多少"不能靠感觉。**基准测试（benchmark）用统计方法测出一段代码的耗时分布**，让优化前后可对比。Rust 生态标准工具是 **`criterion`**——它自动预热、多次采样、算均值和方差、还能和上次结果对比给出"快了 X%"。

```rust,ignore
use criterion::{criterion_group, criterion_main, Criterion};

fn bench_postprocess(c: &mut Criterion) {
    // 准备一份固定的模型输出张量（真实形状 [1,84,8400]）
    let raw = load_fixture_output();
    c.bench_function("postprocess_8400", |b| {
        // 只测后处理这一环：criterion 会自动跑很多轮取稳定统计量
        b.iter(|| postprocess(&raw, 1.0, (0.0, 0.0), 0.25, 0.45));
    });
}

criterion_group!(benches, bench_postprocess);
criterion_main!(benches);
```

基准测试的三条铁律（踩过才知道有多重要）：

1. **必须 `--release`**：debug 版慢 10~50 倍（第 29 章），拿 debug 测性能得出的结论全是错的。criterion 默认在 `cargo bench` 下用 release profile。
2. **单独测每一环**：把解码、预处理、推理、后处理分开各测一个 benchmark，才知道时间花在哪。测整体只能得到一个总数，定位不了瓶颈。
3. **微基准与线上尾延迟分开测**：criterion 会给出均值、中位数、置信区间和离群值，适合比较单个函数。服务的 **p99（99 分位延迟）**还包含排队、线程调度和 I/O，应在压力测试或运行时指标中按请求/帧记录，不能直接拿 criterion 的统计量代替。

## 31.6 性能剖析：用火焰图找瓶颈，别靠猜

基准测试告诉你"后处理花了 5ms"，但**5ms 花在后处理内部的哪一行**？新手最爱犯的错是**凭直觉猜瓶颈然后埋头优化**，结果优化了半天的地方只占总耗时的 2%。资深工程师的铁律是：**先测量，再优化（Measure, don't guess）**。

**性能剖析（profiling）**工具会在程序运行时高频采样"此刻正在执行哪个函数"，统计出每个函数占的时间比例，最直观的呈现就是**火焰图（flame graph）**：

```text
每一层是调用栈，宽度 = 占总时间的比例。越宽 = 越该优化。

┌─────────────────────────────────────────────────────────┐ process_frame 100%
│┌──────────────┐┌───────────────────────┐┌──────────────┐│
││ preprocess18%││    session.run  63%    ││postprocess19%││
││┌────┐┌──────┐│└───────────────────────┘│┌───┐┌────────┐││
│││cvt ││resize│└─ 推理是大头，但已是模型极限 ││nms││decode  │││
│││ 4% ││ 13% ←── 缩放最宽！先优化它       ││8% ││boxes11%│││
└┴┴────┴┴──────┴─────────────────────────────┴───┴────────┴┘
```

一眼看出：`resize` 占了 13%——这时换 `fast_image_resize`（第 29 章的 SIMD 缩放）就是**有的放矢**，而不是盲目优化。推理占 63% 是大头但那是模型本身的成本，除非量化/换模型否则动不了。

Rust 里生成火焰图很方便，常用 **`cargo-flamegraph`**（底层用 Linux `perf` 或 macOS `dtrace`）：

```bash
cargo install flamegraph
# 直接对 release 构建采样，跑完生成 flamegraph.svg，浏览器打开可交互
cargo flamegraph --release --bin my_detector -- --input test.mp4
```

剖析的思维方式，就一句话——**80/20 法则**：程序 80% 的时间通常花在 20% 的代码上。火焰图帮你精准找到那 20%，把优化的力气**全押在最宽的那根柱子上**，性价比最高。

> **一个反直觉的常见发现**：很多"慢"最后查出来根本不是算法慢，而是**每帧都在重新分配大 buffer、或者在热路径里悄悄 `clone` 了大图**（第 29 章零拷贝那节）。火焰图里这些会显示成 `malloc`/`memcpy` 占了异常宽——这类"分配型瓶颈"光看代码逻辑根本猜不到，非剖析不可。

## 31.7 压力测试与长稳测试：逼出并发与泄漏问题

单帧跑得对、跑得快，不代表**扛得住高压、跑得了长久**。上线前还有两类测试专治这两件事。

**压力测试（load/stress test）**：模拟真实甚至超额的负载，看系统在极限下的表现。视觉服务的典型问题是**多路并发**——同时接 16 路、32 路 RTSP 会怎样？

```text
路数    吞吐(总FPS)   平均延迟   p99延迟   丢帧率    内存
 4        95         12ms      28ms      0%       1.2G
 8       178         14ms      45ms      0%       2.1G
16       210         38ms     180ms    2.3%       3.8G   ← 开始丢帧，延迟飙升
32       215        220ms     950ms   31.0%       5.1G   ← 过载，p99 已不可用
```

这张表告诉你**系统的实际容量上限**：这台机器稳定跑 8 路没问题，16 路开始降级，32 路就过载了。**知道拐点在哪，才能做容量规划**（第 32 章）——而不是上线后被"怎么加到第 20 路就雪崩了"打个措手不及。压测还会暴露背压和丢帧策略（第 29 章）是否真的生效。

**长稳测试（soak test）**：让系统**连续跑几十小时甚至几天**，专抓那些"跑一会儿没事、跑一夜就崩"的隐藏问题——最典型的就是**内存泄漏**。第 27 章那三个只增不减的 `HashMap`、第 22 章的 `MotionHistory`，正是这类坑：单帧测试永远发现不了，跑一夜内存涨到 OOM 才暴露。

长稳测试的核心是**盯住随时间变化的资源曲线**：

```text
内存(RSS)
  5G ┤                                    ╱╱  ← 泄漏！内存单调上涨，迟早 OOM
     │                              ╱╱╱╱╱
  3G ┤                    ╱╱╱╱╱╱╱╱╱
     │          ╱╱╱╱╱╱╱╱╱
  1G ┤━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ← 健康：涨到稳态就走平
     └────────────────────────────────────▶ 运行时长
     0h        6h        12h       18h      24h
```

**健康的系统内存会涨到一个稳态就走平**（缓冲区、通道都到了容量上限）；**如果曲线持续单调上涨，就是泄漏**，必须回去查是不是有哪个 `HashMap`/`Vec` 只加不删。除了内存，还要盯**文件句柄数**（抓拍存图忘了关文件）、**线程数**（RTSP 重连是不是每次都新起线程没回收）。用 `tracing`（第 29 章）定期打一行资源快照，或接入监控（第 32 章），跑一夜看曲线，是上线前的必经一关。

## 31.8 把测试挂进 CI：让机器替你守门

上面所有测试，手动跑一次没意义——**必须自动化**，每次改代码都自动全跑一遍，红了就拦住合并。这就是 **CI（持续集成）**。把第 30 章的评估门禁、本章的各类测试串成一道流水线：

```text
每次提交代码 →
  ① cargo fmt --check     格式规范（团队代码风格一致）
  ② cargo clippy          静态检查（揪出可疑写法、常见错误）
  ③ cargo test            单元测试 + golden 测试 + 属性测试（本章 31.2~31.4）
  ④ cargo bench + 基线对比 基准回归：保存/比较报告，慢超过 X% 就报警（31.5）
  ⑤ 模型评估门禁          跑固定测试集算 mAP + regression_gate（第30章）
  ↓ 全绿才准合并 / 发布
```

关键理念是**门禁（gate）**：任何一步红了，就**自动拦住**这次改动进主干。这样"手滑改坏坐标""换了个更差的模型""重构后慢了一倍"这些事故，在合并前就被机器拦下，而不是流到线上。对视觉项目，尤其要把这三样做成硬门禁：

- **golden 测试**：守住流水线行为不被悄悄改坏。
- **模型评估门禁**（第 30 章 `regression_gate`）：守住模型质量不回退。
- **基准回归**：守住性能不悄悄劣化。

> 一个 CI 配置文件（GitHub Actions、GitLab CI 等）就能把这套跑起来，细节因平台而异，这里不铺开。要记住的是**理念**：测试的价值不在"写出来"，而在"每次改动自动全跑、红了就拦"。**没接 CI 的测试，迟早没人跑，等于没写。**

## 31.9 小结

- 视觉系统的 bug 常是**沉默的错误**（坐标偏、阈值错、颜色反），不崩不报只是结果变差，**肉眼和"跑一次"兜不住**，必须靠自动化测试当哨兵。
- **测试金字塔**：底座是大量又快又准的**单元测试**（给 IoU/NMS/letterbox 逆变换等纯函数上锁，用手算答案和"往返测试"守住坐标系）；中间是集成测试；顶端是少量**golden 测试**（固定图跑全流程、和存档结果带容差比对，防整条链路被改坏）。
- **属性测试**（proptest 声明"IoU∈[0,1]""NMS 输出是子集"等性质，机器生成海量输入去砸）和**模糊测试**（畸形图/NaN 框不许 panic）能挖出人写不出的边界用例。
- **基准测试**（criterion）把单个函数的快慢变成可比较的数字；必须使用 release 并分环节测。线上 p99 要在压力测试或运行时另行统计；**性能剖析**（cargo-flamegraph 火焰图）遵循"先测量再优化"和 80/20 法则，把力气押在最宽的柱子上——分配型瓶颈尤其只能靠剖析发现。
- **压力测试**摸清系统容量拐点（几路开始降级）、**长稳测试**盯资源曲线抓内存/句柄/线程泄漏（健康系统涨到稳态走平，单调上涨就是漏）。
- 一切测试都要挂进 **CI 门禁**：golden、模型评估回归、基准回归三道硬门，红了自动拦；**没接 CI 的测试等于没写**。

## 31.10 练习

1. **给几何原语上锁**：为第 23 章的 `side`（叉积符号）和 `segments_intersect`（线段相交）各写至少 3 个单元测试，包括共线、端点相接、完全不交等边界，用手算答案验证。想想哪些退化情形最容易写错。

2. **写一个 letterbox 往返测试并故意改坏它**：实现 31.2 的往返测试，跑通后，故意把逆变换里的 `padding` 减法改成加法，确认测试立刻变红——体会"往返测试"是怎么一秒抓住坐标 bug 的。

3. **给检测器建 golden**：选 3 张固定图跑 `Detector::detect`，把结果存成 golden JSON，写好带容差的比对测试。然后把 NMS 的 IoU 阈值从 0.45 改成 0.05，看 golden 测试报出"框数量变了"——这就是流水线级保险。
