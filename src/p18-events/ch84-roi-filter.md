# 第 84 章 ROI 区域过滤与多边形内外判断

> **本章导读**
> - 学会用 **ROI（感兴趣区域）** 做空间过滤：只关心画面里某块多边形区域（一条车道、一个门口），区域外的检测一律无视——这是降误报最狠、最省事的一招。
> - 亲手写出十几行的**射线法（point-in-polygon）**，判断一个点在不在任意多边形内部，配 ASCII 图讲清"奇偶穿越"的道理，且**凹多边形照样适用**。
> - 想清楚一个工业里反复踩的细节：判定时该用目标的**脚点 `bottom_center()`** 还是中心？为什么？
> - 顺带搞定：矩形 ROI 只是多边形的特例、多个 ROI 取并集、点恰好落在边上的边界情形、以及 y 向下别搞反。

## 场景：我只想看这一条车道

接着上一章的门口摄像头。经过[第 83 章](ch83-filtering-basics.md)的清洗，检测框已经干净多了——分数够高、类别是人、尺寸形状也正常。可运维还是嫌吵：**画面里其实拍到了三条车道加一片停车场，而业主只关心最左边那一条应急车道有没有人闯入。** 右边两条车道上正常走动的行人，全被当成了报警。

这时候你需要的不是"更准的检测器"，而是**在空间上划一块地**：告诉系统"只盯着这块多边形区域，区域外的检测再准也不关我事"。这块被圈出来的区域，就叫 **ROI**。

> 📖 **术语**：**ROI（region of interest，感兴趣区域）**。在画面上人为划定的一块区域（通常是个多边形），系统只对落在其中的目标做后续处理/报警。它是工业监控里**性价比最高的降误报手段**之一：不用改模型、不用加算力，画个多边形就能把一大半"我不关心的地方"的误报直接干掉。周界入侵、车道占用、区域客流，全靠它打底。

ROI 一画，问题就变成一道纯几何题：**给定一个多边形和一个点，怎么判断这个点在多边形里面还是外面？** 这就是本章的技术核心。

## 原理：射线法判断点在多边形内

判断"点在多边形内"，有个又简单又通用的办法叫**射线法（ray casting）**，也叫**奇偶规则（even-odd rule）**。直觉一句话就能说明白：

**从待测点朝任意一个方向射出一条射线（我们统一朝右），数它穿过多边形边界多少次。穿过奇数次，点在内部；穿过偶数次（含 0 次），点在外部。**

为什么？想象你站在一间不规则形状的房间里，朝一个方向直直走出去：你只会穿过墙壁**奇数次**（至少 1 次才能出去）。而你本来就在房子外面，朝房子方向走再走出来，穿墙就是**偶数次**（进去几次就得出来几次）。看图：

```text
              ┌───────────────────┐
              │                   │
   内点 P     │  ●────────✕───────┼────────▶   穿边界 1 次(奇) → 在内 ✔
              │                   │
 外点 Q ●─────┼─────✕─────────────✕────────▶   穿边界 2 次(偶) → 在外 ✘
              │                   │
              └───────────────────┘
```

`P` 在框内，射线向右只穿过右边那条边 1 次；`Q` 在框外（左侧），射线先穿左边、再穿右边，共 2 次。妙的是这个规则**对凹多边形、甚至奇形怪状的多边形一样成立**——不管边界多曲折，"进去必须再出来"的配对关系永远保证内部是奇数、外部是偶数。

具体到代码，我们逐条边检查：设待测点为 \\( (px, py) \\)，一条边的两个端点为 \\( (x_i, y_i) \\) 和 \\( (x_j, y_j) \\)。这条边是否与"从点出发向右的水平射线"相交，分两步：

1. 这条边是否在纵向"跨过"了 \\( py \\)？也就是两个端点**一个在射线上方、一个在下方**。用 `(yi > py) != (yj > py)` 判断——这是个**半开区间**约定（上端点算、下端点不算），能自动避开"射线正好扫到某个顶点被数两次"的经典麻烦。
2. 若跨过，算出这条边与水平线 \\( y = py \\) 的交点横坐标 \\( x_{at} \\)，只有当交点在点的**右边**（`px < x_at`）时，才算被这条向右的射线穿到，翻转一次"内/外"标记。

交点横坐标由线性插值给出（就是在这条边上按 y 的比例求 x）：

\\[ x_{at} = x_i + \frac{py - y_i}{y_j - y_i}\,(x_j - x_i) \\]

### 为什么用"脚点"而不是中心

多边形内外判断需要一个**代表目标位置的点**。检测框是一整个矩形，该拿哪个点去判定？新手直觉会用**中心点**，但工业里几乎都用**底边中点**，也就是 `BBox::bottom_center()`——我们管它叫**脚点**。

道理很实在：**人是站在地面上的，一个人"在哪个区域"，取决于他的脚踩在哪块地上，而不是他的躯干飘在哪。** 想象一个高个子站在车道**外侧**，但身子微微前倾探进了车道上方——他的**脚**明明在线外，可框的**中心**却落进了区域里。用中心判定会误报，用脚点才对。同理，判断"过没过一条线"（[第 87 章](ch87-tripwire.md)绊线），看的也是脚点越没越线。记住这条约定，后面几章都用它。

## 动手写代码：给车道画个 ROI

老规矩，**只用 std**，合成几个检测跑一遍。运行：

```bash
cargo run --example ch84_roi_filter
```

先是那十几行的射线法——**本章最该吃透的一段**：

```rust
/// 射线法判断点 (px, py) 是否在多边形 poly 内。
/// poly 是按顺序给出的顶点（顺/逆时针都行），首尾自动相连成闭合多边形。
fn point_in_polygon(px: f32, py: f32, poly: &[(f32, f32)]) -> bool {
    let n = poly.len();
    if n < 3 {
        return false; // 少于 3 个点构不成多边形
    }
    let mut inside = false;
    let mut j = n - 1; // 上一个顶点：先指向最后一个，和第 0 个连成收尾那条边
    for i in 0..n {
        let (xi, yi) = poly[i];
        let (xj, yj) = poly[j];
        // 这条边 (j -> i) 的两端，是否一个在射线上方、一个在下方？
        let crosses = (yi > py) != (yj > py);
        if crosses {
            // 边与水平线 y = py 的交点横坐标；交点在点右侧才算被向右的射线穿过
            let x_at = xi + (py - yi) / (yj - yi) * (xj - xi);
            if px < x_at {
                inside = !inside;
            }
        }
        j = i;
    }
    inside
}
```

短短十几行，凹多边形、复杂多边形通吃，不需要任何库。`BBox` / `Detection` 就是[第 83 章](ch83-filtering-basics.md)的共享模型（示例文件里为独立运行再抄了一份）。

接着定义一个梯形 ROI。因为透视，画面里的车道**近处宽、远处窄**；又因为图像 y 向下，"远处"在画面上方（y 小）、"近处"在下方（y 大），所以这个梯形**上窄下宽**：

```rust
let roi: Vec<(f32, f32)> = vec![
    (200.0, 100.0), // 左上
    (440.0, 100.0), // 右上
    (520.0, 320.0), // 右下
    (120.0, 320.0), // 左下
];
```

然后合成 6 个目标，用**脚点**判定，同时也算一遍**中心点**做对比：

```rust
let dets = make_dets();
let mut hit = 0;
for d in &dets {
    let (fx, fy) = d.bbox.bottom_center(); // 脚点
    let (cx, cy) = d.bbox.center();        // 中心（仅用于对比）
    let in_foot = point_in_polygon(fx, fy, &roi);
    let in_center = point_in_polygon(cx, cy, &roi);
    if in_foot { hit += 1; }
    // ……打印每个目标的保留/剔除……
}
```

其中有一个目标是精心设计的"探身进来"的家伙——脚点在车道外、但框中心在车道内（合成时脚点设在 `(300, 340)`，恰好在梯形下边 `y=320` 之下）。运行结果（数字真实可复现）：

```text
== 逐个判定（脚点 bottom_center 是否落在 ROI 内）==
[保留] person 脚点=(300,300) 在内(脚点)=是 在内(中心)=是
[剔除] person 脚点=( 60,300) 在内(脚点)=否 在内(中心)=否
[剔除] person 脚点=(320, 60) 在内(脚点)=否 在内(中心)=否
[剔除] person 脚点=(300,340) 在内(脚点)=否 在内(中心)=是
[保留] person 脚点=(250,200) 在内(脚点)=是 在内(中心)=是
[保留] car    脚点=(470,310) 在内(脚点)=是 在内(中心)=是

ROI 内命中（按脚点）：3 / 6 个检测
```

看第 4 行那个 `脚点=(300,340)` 的家伙：**按脚点判定"否"（剔除），按中心判定却是"是"**——这正是"探身进车道"的情形。如果你图省事用了中心点，就会平白多一条误报。6 个目标里，按脚点最终命中 3 个，干净利落地把车道外的行人挡在了报警之外。

代码后半段还演示了三件小事：

```rust
// 矩形 ROI 是多边形的特例：同一个 point_in_polygon 就能用
let rect = rect_roi(300.0, 150.0, 120.0, 120.0);
// 多个 ROI 取并集：落在任意一块里就算命中
let in_any = rois.iter().any(|poly| point_in_polygon(q.0, q.1, poly));
// 边界情形：点正好落在边上
```

对应输出：

```text
矩形 ROI 特例：点 (350,200) 在矩形内 = 是
多 ROI 并集：点 (580,110) 命中任一区域 = 是

边界点 (300,320) 落在下边上，在内 = 否
边界点 (300,100) 落在上边上，在内 = 是
```

三点结论：**①** 矩形不用单独写判断——把它当成 4 个顶点的多边形，复用 `point_in_polygon` 即可（`rect_roi` 就是个把 `(x,y,w,h)` 转成 4 个顶点的小助手）。**②** 想同时盯好几块区域，对每块跑一遍、取 `any`（并集）就行。**③** 注意最后两行：同样落在边上，落在**上边**算"在内"、落在**下边**算"在外"——这是前面半开区间约定 `(yi > py) != (yj > py)` 的必然结果，下面细说。

## 常见坑与提示

> 🕳️ **坑**：**图像的 y 是向下的，别把 ROI 画反了。** 这是新手在 ROI 上栽的头号跟头。屏幕/数学课上习惯 y 向上，但图像坐标（[第 8 章](../p02-image-basics/ch08-pixels.md)）原点在左上、**y 向下增大**。所以画面**上方**的点 y **更小**，"远处"的车道口 y 小、"近处"y 大。我们那个梯形之所以"上窄下宽"，正是这个缘故。射线法本身不在乎 y 朝哪，但你**填顶点坐标**时必须按图像坐标来，否则 ROI 会上下颠倒，判定全错。

> ⚠️ **注意**：**点恰好落在边上，是"内"是"外"取决于约定，别依赖它。** 浮点世界里"正好在边上"极少发生，但一旦发生，结果由算法的半开区间约定决定：我们的写法让**上边界算内、下边界算外**（见上面 `(300,100)` 与 `(300,320)` 的对比）。这个不对称**恰恰是好事**——当两块 ROI 共享一条边时，它保证边上的点只被算进其中一块，不会两块都命中、导致重复报警。真要求"边上也算内"，可以把 ROI 顶点稍微外扩一两像素，别去改这套久经考验的判定逻辑。

> 💡 **提示**：**射线法对凹多边形一样好使，别被"凹"吓退。** 无论是"L 形"通道还是挖了个缺口的怪异区域，只要顶点按边界顺序给出，`point_in_polygon` 都对。它不要求凸、不要求顺时针还是逆时针。所以你可以放心地沿着真实场景的边缘（马路牙子、门框、栅栏）一路点过去，画出任意形状的 ROI。

> 🕳️ **坑**：**脚点也不是万能的，被遮挡时会失真。** 用脚点判定的前提是"框的底边大致就是目标着地处"。可当一个人下半身被栏杆、车辆挡住时，检测框的底边其实是"腰"而不是"脚"，脚点会偏高、判定可能出错。工程上的缓解办法：结合跟踪（[第 88 章](ch88-intrusion-dwell.md)）看轨迹连续性，或把"脚点"稍微下压一点作补偿。先知道有这个局限，别以为脚点就一劳永逸。

> 💡 **提示**：**ROI 顶点从哪来？** demo 里是硬编码的。真实系统里，通常在配置界面上让用户**在画面截图上鼠标点几下**画出多边形，把顶点坐标存进配置（第 93 章的规则引擎就吃这种配置）。注意存的是**归一化坐标还是像素坐标**：如果摄像头分辨率会变，存 `[0,1]` 的归一化坐标更稳妥，判定前再乘以当前宽高还原成像素。

## 本章小结

- **ROI（感兴趣区域）** 是在画面上划定的多边形，只处理落在其中的目标——降误报性价比最高的一招，不改模型、不加算力。
- **射线法（奇偶规则）**：从点向右射线，数穿过多边形边界的次数，奇数在内、偶数在外。十几行搞定，**凹多边形也适用**，无需任何库。关键是 `(yi > py) != (yj > py)` 的半开区间判断加上交点横坐标插值。
- 判定用目标的**脚点 `bottom_center()`** 而非中心：人站在地上，脚踩哪块地才决定它在哪个区域；"探身进来"的目标用中心会误报。
- **矩形是多边形的特例**（4 个顶点复用同一函数）；**多个 ROI 取并集**用 `any`；点在边上的内外由半开约定决定，正好避免相邻区域共享边被重复命中；**图像 y 向下**，填顶点坐标别搞反。

## 动手练习

1. **画你自己的 ROI**：把 `roi` 换成一个"L 形"的**凹**多边形（比如把梯形右下角挖掉一块），构造几个目标验证凹处内外判定依然正确。
2. **脚点 vs 中心，眼见为实**：把判定从 `bottom_center()` 换成 `center()` 重跑，数一数命中数从 3 变成了几，找出是哪个目标的去留翻了盘。
3. **区域外才报警**：本章保留的是"区域内"的目标。改成相反语义——实现一个"离岗检测"，即目标**离开** ROI 时才算命中（提示：`!point_in_polygon(...)`），想想值守岗、安全区这类应用。
4. **进阶·归一化坐标**：把 ROI 顶点改成 `[0,1]` 的归一化坐标，在判定前根据画面宽高（比如 `640×360`）还原成像素。验证换一个分辨率时同一个归一化 ROI 依然圈住同一块相对区域。

我们已经有了两道空间/属性上的过滤关。但它们都是**逐帧独立**的——检测器偶尔某一帧抽风，冒出一个又高分、又在 ROI 内、形状还正常的"假人"，照样能骗过前两关。怎么办？答案是**看时间**：真目标会连续好几帧都在，偶发误检往往只闪一帧。下一章我们就用**时间窗口投票**把这种"一闪而过"的抖动摁下去。👉 [第 85 章 时间窗口过滤与状态机（N/M 投票、去抖）](ch85-temporal-window.md)
