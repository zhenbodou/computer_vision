# 第 83 章 检测结果清洗：置信度/类别/尺寸/长宽比过滤

> **本章导读**
> - 想清楚一件在工业项目里价值千金、学术书却几乎不提的事：检测器吐出来的框，**为什么不能直接拿去报警**。
> - 认识贯穿整个第十八部分的**共享数据模型**——`BBox`、`Detection`、`Frame`、`Track`、`Event`，以及"流水线一环"的 `Stage` 心智模型。后面十章全部建立在这套类型上。
> - 动手写出事件层的"第一道岗"：**置信度、类别、尺寸、长宽比**四种最基础的清洗过滤，并统计"谁被剔了、为什么被剔"。
> - 全程只用 std，输入是我们自己合成的一批"脏"检测，自包含、可复现。

## 场景：一个报警 100 次的门口

你把一个训练得不错的行人检测器（第九部分会教你怎么做）接到门口的摄像头上，满心欢喜地写了行代码："只要检测到 `person`，就发一条报警。"上线第一天，运维就来找你了——**一个下午收到了 3000 条报警**，其中真正有人经过的不到 50 次。

翻一翻这些误报，你会发现检测器的原始输出有多"毛糙"：

- 墙角的阴影被打了个 `person` 框，**置信度只有 0.18**，但你没设阈值，它也报了；
- 画面里飘过一只猫，被识别成 `dog`——**类别根本不是你关心的**；
- 树叶抖动产生一个 `8×6` 像素的**碎框**，小得根本不可能是人；
- 检测器偶尔抽风，把大半个画面框成一个 `600×360` 的**巨框**；
- 一个真的行人站在门口 8 秒，检测器每秒跑 25 帧，于是**同一个人被报了 200 次**。

这就是本章（以及整个第十八部分）要解决的问题：**检测器负责"看见"，但"看见"离"可用的业务告警"还差着一整层。** 这一层就叫**事件规则层**，它是工业视觉项目里最不起眼、却最决定成败的部分。

> 📖 **术语**：**后处理 / 事件规则层（event layer）**。检测/跟踪给出的是"这一帧有哪些框"，而业务要的是"有人翻墙了""进店 37 人"这样的**事件**。把前者变成后者的所有规则——阈值过滤、ROI、时间窗投票、去重冷却、绊线、停留……统称事件规则层。它**只消费**检测结果，不关心检测器内部怎么实现，所以本部分所有示例都不依赖深度学习，用合成数据就能跑。

## 事件层在流水线的什么位置

回顾[第 1 章](../p01-start/ch01-what-is-cv.md)那条五步流水线，事件层就是第 ④ 步"后处理/业务规则"。把它放大看：

```text
                             ┌──────────────── 事件规则层（本部分 ch83–93）────────────────┐
摄像头 → 解码成帧 → 检测器 →  │ 清洗过滤 → ROI → 时间窗投票 → 去重冷却 → 绊线/入侵/停留 → 联动 │ → 业务告警
        (第16部分)  (第9部分) │  ch83     ch84    ch85         ch86        ch87–89       ch91 │
                  Detection  └──────────────────────────────────────────────────────────────┘   Event
                              [可选：跟踪器(第13部分)给每个目标一个稳定 id → Track]
```

事件层是**一条可插拔的流水线**：检测结果从左边流进来，穿过一串"规则/过滤器"，每一环要么**筛掉一些检测**（像本章的阈值、下一章的 ROI），要么**在满足条件时吐出一条 `Event`**（像绊线、停留）。本章负责最前面那道**清洗**岗——把明显不该报警的框先扫地出门，后面的规则才不会被垃圾数据淹没。

## 共享数据模型：后面十章的地基

在动手过滤之前，我们得先把"检测结果长什么样"用 Rust 类型钉死。**第十八部分所有章节都用同一套类型**，这样各章的代码才能无缝拼接、交叉引用。本章负责把它完整介绍给你，后面的章节直接沿用。

坐标与时间有两条全局约定，务必记牢：

- **图像坐标**：原点在**左上角**，x 向右、y 向下（和 `image` 库、和[第 8 章](../p02-image-basics/ch08-pixels.md)完全一致）。注意 y 是向下增大的，这一点在下一章判断"上边/下边"时会反复用到。
- **时间戳**：统一用 **`u64` 毫秒**，字段名 `ts_ms`。合成数据时我们自己造**递增**的时间戳（如 1000、1040、1080……），**不读系统时钟**——这样示例才可复现。真要用真实时钟时（第九十一章联动）再用 `std::time`。

下面是这套 canonical（标准）类型的完整定义，逐个字段都有注释：

```rust
/// 轴对齐包围盒：左上角 (x, y) + 宽高 (w, h)，单位像素。
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct BBox {
    pub x: f32,
    pub y: f32,
    pub w: f32,
    pub h: f32,
}

impl BBox {
    pub fn new(x: f32, y: f32, w: f32, h: f32) -> Self { BBox { x, y, w, h } }

    /// 中心点
    pub fn center(&self) -> (f32, f32) { (self.x + self.w / 2.0, self.y + self.h / 2.0) }

    /// 底边中点（脚点）——过线 / 入区域判定常用它而非中心（见第 84 章）。
    pub fn bottom_center(&self) -> (f32, f32) { (self.x + self.w / 2.0, self.y + self.h) }

    /// 面积（像素^2）
    pub fn area(&self) -> f32 { (self.w * self.h).max(0.0) }

    /// 交并比 IoU ∈ [0,1]，用于同帧去重 / 跨帧关联（见第 86 章）。
    pub fn iou(&self, o: &BBox) -> f32 {
        let x1 = self.x.max(o.x);
        let y1 = self.y.max(o.y);
        let x2 = (self.x + self.w).min(o.x + o.w);
        let y2 = (self.y + self.h).min(o.y + o.h);
        let iw = (x2 - x1).max(0.0);
        let ih = (y2 - y1).max(0.0);
        let inter = iw * ih;
        let uni = self.area() + o.area() - inter;
        if uni <= 0.0 { 0.0 } else { inter / uni }
    }
}

/// 一个检测框：来自检测器（第九部分）。事件层只消费它。
#[derive(Clone, Debug)]
pub struct Detection {
    pub bbox: BBox,
    pub class_id: u32,
    pub label: String, // 类别名，如 "person" / "car"
    pub score: f32,    // 置信度 [0,1]
}

/// 一帧的检测结果（带时间戳）。事件层的输入通常是 Vec<Frame> 或帧流。
#[derive(Clone, Debug)]
pub struct Frame {
    pub ts_ms: u64,
    pub detections: Vec<Detection>,
}

/// 跟踪后的目标：跟踪器（第十三部分）给每个目标分配**稳定 id**。
/// 停留时长、绊线方向、轨迹这些跨帧规则，都要靠 id 把同一个目标连起来。
#[derive(Clone, Debug)]
pub struct Track {
    pub id: u64,
    pub label: String,
    pub history: Vec<(u64, BBox)>, // (ts_ms, bbox) 按时间递增
}

/// 事件层的输出：一条业务事件 / 告警。
#[derive(Clone, Debug)]
pub struct Event {
    pub kind: String,          // "roi" | "tripwire" | "intrusion" | "dwell" | ...
    pub ts_ms: u64,
    pub track_id: Option<u64>,
    pub message: String,
}
```

几点说明：

- **`BBox`** 用"左上角 + 宽高"表示框（不是"左上角 + 右下角"），单位是 `f32` 像素。它自带几个好用的方法：`center()` 中心点、`bottom_center()` 脚点（下一章的主角）、`area()` 面积（本章要用）、`iou()` 交并比（第 86 章去重要用）。
- **`Detection`** = 一个框 + 类别 + 置信度。`label` 是人类可读的类别名，`score` 是检测器给的把握程度，落在 `[0, 1]`。**本章的四种过滤全都盯着 `Detection` 的这几个字段做文章。**
- **`Frame`** = 一个时间戳 + 这一帧的所有检测。事件层的输入通常就是一串 `Frame`（`Vec<Frame>` 或帧流）。
- **`Track`** 和 **`Event`** 本章还用不到（分别是第十三部分和后面规则章的主角），先混个脸熟：`Track` 有一个**跨帧稳定的 `id`** 和一段历史轨迹；`Event` 就是这一整层最终要吐出去的东西。

最后是把整层串起来的**心智模型**——一个规则/过滤"环"就是一个 `Stage`：

```rust
/// 事件层的一环：吃一帧，产出若干事件（可能为空）。
/// 有状态的规则（时间窗、cooldown、绊线方向）把状态放进 &mut self。
pub trait Stage {
    fn process(&mut self, frame: &Frame) -> Vec<Event>;
}
```

绊线、停留这类规则会**实现** `Stage`（满足条件时 `process` 返回 `Event`）；而本章的清洗过滤属于另一类"环"——它不产出事件，只是**把 `Frame` 里的脏检测筛掉、返回一个更干净的 `Frame`**。两类环最终会在[第 93 章](ch93-rule-engine.md)被同一个 `Pipeline` 串起来。心智模型统一，实现可以各自简化——不必强迫每个环都实现这个 trait。

## 动手写代码：四道清洗关卡

这一层的输入不需要真跑检测器。我们**手工合成一批检测**，故意混进各种"脏货"，再让它们过一遍清洗链。**只用 std，无需任何依赖。**

运行方式：

```bash
cargo run --example ch83_filtering_basics
```

四道关卡的逻辑非常朴素，但顺序有讲究——**先做便宜的判断（比大小、比字符串），再做几何计算**：

```rust
/// 一条检测被剔除的原因——用来统计"到底为什么被清掉"。
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum Reject {
    LowScore,  // 置信度太低
    BadClass,  // 类别不在白名单
    TooSmall,  // 框面积过小（多半是噪点 / 碎块）
    TooLarge,  // 框面积过大（多半是误检 / 整屏框）
    BadAspect, // 长宽比不合理（形状不像目标）
}

/// 清洗过滤器的配置。真实项目里这些阈值通常从配置文件读，且可按类别分别设定。
struct DetectionCleaner {
    score_thresh: f32,  // 置信度阈值：低于它直接丢
    allow: Vec<String>, // 类别白名单：只保留这些 label
    min_area: f32,      // 最小框面积（像素^2）
    max_area: f32,      // 最大框面积
    min_aspect: f32,    // 最小长宽比 w/h
    max_aspect: f32,    // 最大长宽比 w/h
}

impl DetectionCleaner {
    /// 判断单个检测：Ok(()) 保留，Err(原因) 剔除。返回第一条不通过的原因。
    fn check(&self, d: &Detection) -> Result<(), Reject> {
        if d.score < self.score_thresh {
            return Err(Reject::LowScore);
        }
        if !self.allow.iter().any(|c| c == &d.label) {
            return Err(Reject::BadClass);
        }
        let area = d.bbox.area();
        if area < self.min_area {
            return Err(Reject::TooSmall);
        }
        if area > self.max_area {
            return Err(Reject::TooLarge);
        }
        // 长宽比 r = w / h；高为 0 视为无穷大（必然出局）。
        let aspect = if d.bbox.h > 0.0 { d.bbox.w / d.bbox.h } else { f32::INFINITY };
        if aspect < self.min_aspect || aspect > self.max_aspect {
            return Err(Reject::BadAspect);
        }
        Ok(())
    }

    /// 清洗一帧：返回只留下"干净"检测的新 Frame（下游拿到的就是它）。
    fn clean_frame(&self, f: &Frame) -> Frame {
        let kept = f.detections.iter().filter(|d| self.check(d).is_ok()).cloned().collect();
        Frame { ts_ms: f.ts_ms, detections: kept }
    }
}
```

四道关卡各自的道理：

1. **置信度阈值**：`score` 低于阈值的直接丢。这是最立竿见影的一刀——上面那个 0.18 分的墙角阴影就死在这里。
2. **类别白名单**：只放行你关心的类别。看门只关心 `person`，那 `dog`、`bird` 一律不要。
3. **尺寸过滤**：太小的框（`min_area`）多半是噪点或误检碎块；太大的框（`max_area`）多半是检测器抽风框住了大半个画面。用面积卡两头。
4. **长宽比过滤**：一个站立的人，框应该是"竖高"的（宽/高约 `0.3~0.6`）；如果出来一个又扁又长（`4.0`）或又细又高（`0.08`）的框，形状根本不像人，滤掉。

接着合成输入。注意时间戳是我们**手造的递增值**：

```rust

            det(0.0, 0.0, 600.0, 360.0, "person", 0.91),   // 几乎整屏的巨框：剔

```

## 常见坑与提示

> ⚠️ **注意**：**阈值是一场"漏检 vs 误报"的拉锯，没有免费的午餐。** 置信度阈值调高，误报少了，但**真目标也可能被误杀**（漏检）；调低则反过来。这条取舍贯穿整个事件层。工程上的做法不是纠结一个"完美阈值"，而是**先设一个偏宽松的阈值放行**，再靠后面几章的时间窗投票（[第 85 章](ch85-temporal-window.md)）、去重冷却（[第 86 章](ch86-cooldown-dedup.md)）把偶发误报压下去——多道防线合力，好过第一道关就卡死。

> 💡 **提示**：**不同类别该用不同阈值。** 我们的 demo 用了一个全局 `score_thresh`，但真实系统里，`person` 可能 0.5 就够、`car` 也许要 0.6、而容易误检的 `bag` 得提到 0.8。把 `score_thresh` 从一个 `f32` 换成一张 `HashMap<String, f32>`（按 `label` 查阈值），是最常见、最值钱的一个小改动。尺寸、长宽比同理——不同类别的合理形状天差地别。

> 🕳️ **坑**：**尺寸阈值不能全画面用一个数。** 因为透视，**近处的人又大、远处的人又小**：门口一个人可能 `120` 像素高，画面尽头同一个人只有 `20` 像素高。全画面卡死一个 `min_area`，要么放走远处的碎噪点，要么误杀远处的真人。讲究的做法是让尺寸阈值随目标在画面里的位置（近大远小）变化——这属于场景标定/鲁棒性的范畴，我们留到[第 90 章](ch90-arming-tamper.md)再谈。本章先掌握"有这道关"。

> 🕳️ **坑**：**别在这一步做"去重"。** 你可能想："同一个人连续几帧都被检出来，是不是该在这里合并成一个？"——**不要**。同帧里的重叠框去重（NMS 式）、跨帧同一目标只报一次（cooldown），是[第 86 章](ch86-cooldown-dedup.md)的活，需要用到 `IoU` 甚至 `track_id`。本章的清洗是**每帧独立、无状态**的：只看单个检测自身的分数/类别/形状，不看它和别的框、别的帧的关系。把职责分清楚，流水线才好维护。

> 💡 **提示**：**用 `Result<(), Reject>` 记录"为什么被剔"，而不是简单的 `bool`。** 一个返回 `true/false` 的过滤器上线后，你完全不知道那些框死在哪一关。带上原因，就能打印出上面那份统计，排障时事半功倍。这是把玩具代码变成生产代码的一个小习惯。

## 本章小结

- 检测器只负责"看见"，它的原始输出充满**低分框、无关类别、尺寸/形状离谱的框**，直接拿去报警会淹没在假警里。把检测结果变成可用业务事件的这一层，叫**事件规则层**，是工业落地的胜负手。
- 第十八部分共用一套数据模型：**`BBox`（左上角+宽高）、`Detection`（框+类别+置信度）、`Frame`（时间戳+检测）、`Track`（带稳定 id 的轨迹）、`Event`（最终告警）**，外加 `Stage` 心智模型（流水线的一环）。坐标原点左上、y 向下；时间戳用 `u64` 毫秒且自造递增值。
- 最基础的清洗有四道关：**置信度阈值、类别白名单、面积上下限、长宽比区间**。顺序上先做便宜的比较，再做几何计算；用 `Result<(), Reject>` 记下剔除原因便于统计与排障。
- 阈值是"漏检 vs 误报"的取舍，别指望一刀切；不同类别用不同阈值；尺寸阈值要考虑透视；**去重不在这一步做**。

## 动手练习

1. **按类别设阈值**：把 `score_thresh: f32` 改成 `HashMap<String, f32>`，给 `person` 设 0.5、`car` 设 0.7，重跑并观察哪些框的去留发生了变化。
2. **加一条"黑名单"**：现在用的是白名单（只留 `allow` 里的）。反过来实现一个黑名单版本（`deny: Vec<String>`，命中就剔），想想在类别很多时白名单和黑名单各自更省事的场景。
3. **补全统计**：让 `Stats` 额外记录每一帧各剔了几个（而不只是总数），打印成一张"帧 × 原因"的小表格。
4. **进阶·长宽比方向**：本章的长宽比过滤对"太扁"和"太细"用了同一组阈值。试着为 `person`（应偏竖）和 `car`（应偏横）分别设不同的长宽比区间，验证一辆 `130×66` 的车不会被"太扁"误杀。
