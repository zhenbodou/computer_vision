# 第 92 章 多路流并发调度与工程架构：线程、汇聚、背压与抽帧

> **本章导读**
> - 前面所有章都在跟**一路**视频较劲。可真实项目里，一台服务器往往要同时接**十几到几十路**摄像头。这一章讲清支撑起整套系统的**工程骨架**：每路怎么跑、结果怎么汇、机器扛不住了怎么办。
> - 用 `std::thread` + `std::sync::mpsc` 搭出「**每路视频一条线程、各路结果汇到一个通道、主线程统一分发**」的经典架构，并给出一张贯穿全书的**整体架构图**。
> - 把工程里最要命的**背压（backpressure）与丢帧策略**讲透：通道满了，是让上游**阻塞等待**（`Condvar`），还是**丢最新**（`sync_channel` + `try_send`），还是**丢最旧**（环形缓冲）？给可运行对照，报真实数字。
> - 全程只用 std，不硬引 `tokio`/`rayon` 这类重运行时——它们作为进阶选项，末尾一句带过。

## 场景：一台机器，三十二路摄像头

你的事件规则层（第 83–91 章）单路跑得漂亮。项目验收时甲方说："我们这栋楼有 32 个摄像头，都接到这一台服务器上。" 你心里一紧——**32 路同时来，怎么组织？**

几个天真的想法很快撞墙：

- **一个大循环轮流处理 32 路？** 第 1 路检测耗时 30ms，轮完一圈就是近 1 秒，每路实际帧率被压到 1fps 出头，全糊了。而且第 1 路要是卡住（比如网络抖动读不到帧），后面 31 路**跟着一起卡**。
- **32 路各写各的、各发各的告警？** 那 32 套重复代码谁维护？告警从 32 个地方冒出来，运维根本理不清。

正确的骨架其实很朴素，也是工业界的标准答案：**每路一条线程，各自独立地"解码→检测→跟踪→事件规则"，跑出的结果全汇到同一个通道，由一个汇聚点统一聚合、统一分发。** 一路卡住只卡它自己；32 路的结果在一处收口，干净可控。

## 原理：生产者—消费者与那条汇聚通道

这套架构的学名叫**生产者—消费者模型（producer–consumer）**：N 个生产者（每路视频一个线程）不停产出结果，一个（或少数几个）消费者在汇聚端处理。它们之间靠一条**通道（channel）**解耦——生产者只管往通道里塞，消费者只管从通道里取，互不知道对方是谁、有多少个。

整套系统的骨架长这样（本部分从第 83 章一路搭到这里，就是为了这张图）：

```text
  摄像头1 ─┐    ┌───────────── 每路一条线程（生产者）─────────────┐
  摄像头2 ─┤    │  解码 → 检测(第9部分) → 跟踪(第13部分) → 事件规则(ch83–90)  │──┐
   ...    ─┤    └──────────────────────────────────────────────────┘  │
  摄像头N ─┘         （各路各跑各的，一路卡住不连累别人）                   │
                                                                        ▼
                                                            ┌────────────────────┐
                                                            │   汇聚通道（mpsc）   │ ← 背压/丢帧在这决断
                                                            └────────────────────┘
                                                                        │
                                                                        ▼
                                            主线程：聚合统计 → 统一分发（第 91 章的 Sink：打印/存库/webhook…）
```

Rust 的所有权模型天生适合写这个：通道的发送端 `Sender` 可以 `clone` 给每路线程，接收端 `Receiver` 留在汇聚线程；数据 `send` 进去就把所有权**移交**给通道，编译期就杜绝了"多个线程同时改一份数据"的数据竞争。这就是 Rust 引以为傲的 **"无畏并发（fearless concurrency）"**。

> 📖 **术语**：**mpsc = multi-producer, single-consumer**（多生产者、单消费者）。`std::sync::mpsc` 正是为这个架构量身定做的：多个 `Sender`（每路一个 clone）→ 一个 `Receiver`（汇聚线程）。

## 动手写代码：每路一线程，mpsc 汇聚

完整代码见 `code/examples/ch92_concurrency.rs`，**只用 std**：

```bash
cargo run --example ch92_concurrency
```

先把"一路视频处理完一帧"抽象成一条消息 `Msg`（真实系统里它背后是解码+检测+跟踪+规则跑完的结果，这里只留调度需要的字段）：

```rust
#[derive(Clone, Debug)]
struct Msg {
    stream_id: usize,   // 哪一路
    frame_no: u64,      // 第几帧
    ts_ms: u64,         // 时间戳
    event: Option<Event>, // 本帧是否命中了事件（复用第 83 章的 Event）
}
```

然后就是骨架本身——起 N 个线程，每个 clone 一份 `Sender`，主线程用一个 `Receiver` 收：

```rust
let (tx, rx) = mpsc::channel::<Msg>();
let mut handles = Vec::new();
for sid in 0..n_streams {
    let tx = tx.clone();                 // 每路自己的发送端
    handles.push(thread::spawn(move || {
        for fno in 0..frames_per {
            if tx.send(process_one_frame(sid, fno)).is_err() { break; }
        }
    }));
}
drop(tx);                                // 关键！见下方的坑

let mut per_stream = vec![0u32; n_streams];
let mut events = Vec::new();
for msg in rx {                          // 迭代到所有 Sender 都 drop 才结束
    per_stream[msg.stream_id] += 1;
    if let Some(e) = msg.event { events.push(e); }
}
```

跑起来（4 路，每路 100 帧，数字真实可复现）：

```text
== Part 1：每路一线程，mpsc 单通道汇聚 ==
  4 路，每路 100 帧：
    流#0 汇入 100 帧
    流#1 汇入 100 帧
    流#2 汇入 100 帧
    流#3 汇入 100 帧
  汇聚总帧数：400（= 4×100，不丢帧）
  汇聚到的事件数：16（每路每 25 帧 1 次 → 每路 4 次）
  => 这些事件接下来交给第 91 章的 Sink 统一分发（打印 / 存库 / webhook…）
```

4 路并发跑出的 400 帧，全部干净汇到一处；16 条事件收口后，正好接上[第 91 章](ch91-actions-push.md)的 `Sink` 去分发。骨架就这么简单。

> 🕳️ **坑**：**`drop(tx)` 那一行删了，程序会永远卡死。** `for msg in rx` 是"等到**所有** `Sender` 都被 drop 了才结束"。每路线程结束时会 drop 它自己那份 clone，但**主线程手里还攥着最初那把 `tx`**——只要它没 drop，`rx` 就以为"还可能有人发"，于是永远等下去。所以起完所有线程后，必须 `drop(tx)` 把主线程这份也放掉。这是 mpsc 新手第一名的坑。

## 通道满了怎么办：背压 vs 丢帧

上面用的是**无界通道**（`mpsc::channel`），它永不阻塞、永不丢。但天下没有免费的午餐：如果检测比进帧慢，通道里的帧会**越堆越多，直到内存爆掉**。真实系统必须给缓冲**设上限**，于是就要回答那个经典问题：**缓冲满了，怎么办？** 三种答案，各有各的适用场景。

### 答案一：背压——让上游等一等（不丢帧）

用一个**有界阻塞队列**：满了，`push` 就阻塞，逼生产者停下来等消费者腾地方。这叫**背压（backpressure）**——下游的压力"顶"回上游。实现它要用 `Condvar`（条件变量），让线程"睡着等条件成立"而不是忙等空转 CPU：

```rust
struct BoundedBlockingQueue<T> {
    inner: Mutex<VecDeque<T>>,
    not_full: Condvar,   // 「队列不满了」的通知
    not_empty: Condvar,  // 「队列非空了」的通知
    cap: usize,
}
impl<T> BoundedBlockingQueue<T> {
    fn push(&self, item: T) {
        let mut q = self.inner.lock().unwrap();
        while q.len() >= self.cap {          // 满了：睡着等「不满」的通知（背压！）
            q = self.not_full.wait(q).unwrap();
        }
        q.push_back(item);
        self.not_empty.notify_one();          // 叫醒可能在等数据的消费者
    }
    fn pop(&self) -> T {
        let mut q = self.inner.lock().unwrap();
        while q.is_empty() {                  // 空了：睡着等「非空」的通知
            q = self.not_empty.wait(q).unwrap();
        }
        let item = q.pop_front().unwrap();
        self.not_full.notify_one();
        item
    }
}
```

跑起来（4 路各 50 帧，缓冲 cap=16）：

```text
== Part 2A：有界阻塞队列（cap=16）——满则背压，不丢帧 ==
  汇聚总数：200（应等于 4×50=200），丢弃：0
  队列历史峰值长度：16 ≤ cap 16（内存有界，从不无限堆积）
  => 代价：队满时生产者被阻塞等待（背压会「顶」到摄像头端）。适合能减速的源。
```

一帧不丢，且缓冲长度**始终没超过 16**——内存有界。代价是队满时生产者被"背压"住得干等。**背压适合"源可以被减速"的场合**（比如读本地文件、离线批处理）。但摄像头的实时帧流**不等人**——你阻塞在这儿，网络缓冲里的帧照样在丢，还丢得更没章法。这时就得主动丢。

### 答案二 / 三：丢最新 vs 丢最旧

既然要丢，就有两种丢法，区别不在"丢多少"，而在"**留下的是哪些帧**"：

- **丢最新**：缓冲满了，新来的帧发不进去就**丢掉它**。用 `sync_channel(cap)`（有界通道）+ `try_send`（发不进不阻塞、直接返回 `Full`）：

```rust
let (tx, rx) = sync_channel::<u64>(cap);
for i in 0..n_frames {
    match tx.try_send(i) {
        Ok(()) => {}
        Err(TrySendError::Full(_)) => dropped_new += 1, // 满了 → 丢「最新」这帧
        Err(TrySendError::Disconnected(_)) => break,
    }
}
```

- **丢最旧**：缓冲满了，**弹掉最旧那帧**给新帧腾位。用一个环形缓冲（`VecDeque`，满了 `pop_front` 再 `push_back`）：

```rust
if q.len() == cap { q.pop_front(); dropped_old += 1; } // 丢「最旧」
q.push_back(i);
```

同一场景（猛推 50 帧，缓冲 8）下对照：

```text
== Part 2B：队满就丢——丢最新 vs 丢最旧（生产者猛推 50 帧，缓冲 cap=8）==
  丢最新：处理 8 帧，丢弃 42 帧；活下来的是 帧#0..#7（ts 1000..1280ms）
  丢最旧：处理 8 帧，丢弃 42 帧；活下来的是 帧#42..#49（ts 2680..2960ms）
  => 丢弃条数相同，但「丢最新」留下的是陈旧帧，「丢最旧」永远处理最新帧（延迟低）。
     安防/实时场景通常选「丢最旧」：宁可跳过旧画面，也要盯住此刻发生了什么。
```

看清楚这个关键区别：两种策略都丢了 42 帧、都只处理 8 帧，但**丢最新留下的是帧 #0\~#7（最早、最陈旧的画面）**，而**丢最旧留下的是帧 #42\~#49（此刻最新的画面）**。对安防、实时监控这种"我要知道**现在**发生了什么"的场景，**丢最旧几乎总是对的**——你宁可跳过几秒前的旧画面，也不能让检测永远滞后在一分钟前。这就是为什么实时视频系统的缓冲大多是"留最新"的环形缓冲。

> 💡 **提示**：**"抽帧"就是丢帧的主动版。** 与其等缓冲满了被动丢，不如一开始就**按固定间隔主动降采样**——每 3 帧只处理 1 帧（`if frame_no % 3 != 0 { continue; }`）。25fps 抽成 8fps，检测负载直接降到三分之一，对"有没有人闯入"这类慢事件毫无影响。抽帧是多路系统最立竿见影的减负手段，本章标题里的"抽帧"正是这个。

## 常见坑与提示

> ⚠️ **注意**：**线程数不必等于路数，更不该"每帧一线程"。** 32 路开 32 个解码线程没问题，但如果检测很重（占满 CPU），可以让**少数几个 worker 线程**从汇聚通道里抢活干（消费者也能是多个）。切忌"每来一帧 `spawn` 一个线程"——创建/销毁线程的开销比检测还大。需要"一批帧并行跑"时，用**线程池**或纯 Rust 的 `rayon`（`par_iter`，见第 108 章）把一帧内的多个 ROI 并行化，别自己造线程。

> 🕳️ **坑**：**别在汇聚/检测线程里同步等 webhook。** 承接[第 91 章](ch91-actions-push.md)：分发（尤其发 HTTP）可能阻塞好几秒。如果你在消费者线程里直接 `send_json`，对方一慢，整个汇聚就堵死、所有路一起丢帧。正确做法是**再加一级通道**：消费者只管把事件丢进"分发通道"，另起专门的分发线程去慢慢发。各司其职，一环慢不拖垮全局。

> 💡 **提示**：**框平滑、隐私打码这些"每路要做的活"，放进各自的线程里。** 框平滑（对跟踪框做时间域滑动平均，去抖动）、隐私打码（把人脸/车牌区域打马赛克再存证）都是**单路内的处理环节**，天然属于"每路那条线程"的流水线（解码→检测→跟踪→**打码/平滑**→规则），跑完再把结果汇聚。它们不涉及跨路协调，所以并发架构完全不用改。

> 📖 **术语**：**跨相机去重**。楼道拐角两个摄像头拍到同一个人，会各报一次。想合并成"一个人"，需要跨路做**再识别（ReID）**或用标定把两个视野映射到同一平面——这属于多相机融合的进阶话题（涉及第 14 部分的几何标定）。本章的汇聚通道只是把结果收到一处，去重逻辑可以加在消费者端，但别指望"汇聚"本身能去重。

> 💡 **提示**：**`tokio` 是另一条路，但不是这里的必需品。** 如果你的瓶颈是"同时等几千个网络连接"（海量 IO 并发），异步运行时 `tokio` 更合适。但视频分析的瓶颈通常是**CPU（解码/检测）**，"每路一线程 + mpsc" 这套同步模型足够好、也更好懂好调。**别为了赶时髦硬上重运行时**——先把 std 这套跑通、压测出瓶颈，再决定要不要换。

## 本章小结

- 多路视频的工程骨架是**生产者—消费者**：**每路一条线程**独立跑完"解码→检测→跟踪→规则"，结果全汇到**一条 mpsc 通道**，主线程统一聚合、统一分发。一路卡住不连累别人。
- Rust 的所有权让这套架构**天生无数据竞争**：`Sender` clone 给各路，数据 `send` 即移交所有权。**记得 `drop` 掉主线程多余的 `Sender`**，否则 `rx` 永不结束。
- 缓冲必须有界，满了有三种应对：**背压**（`Condvar` 阻塞上游，不丢帧，适合可减速的源）、**丢最新**（`sync_channel`+`try_send`，留下陈旧帧）、**丢最旧**（环形 `VecDeque`，永远处理最新帧，实时场景首选）。demo 里两种丢法都丢 42 留 8，但留的是"最旧 8 帧"还是"最新 8 帧"，天差地别。
- **抽帧**是最省事的主动减负；框平滑/隐私打码是**单路内**的处理环节；`rayon`/`tokio` 是进阶选项，别过早引入。

## 动手练习

1. **加一级分发线程**：在 Part 1 的基础上，把汇聚到的事件不直接处理，而是再 `send` 进第二条通道，另起一个线程用[第 91 章](ch91-actions-push.md)的 `Sink` 分发。验证"检测"和"分发"彻底解耦。
2. **抽帧减负**：给 `process_one_frame` 前面加一道"每 3 帧处理 1 帧"的抽帧，重跑 Part 1，观察汇聚总帧数从 400 变成多少，事件是否还抓得到。
3. **多消费者**：把 Part 2A 的消费者从 1 个改成 2 个 worker 线程（都从同一把 `Arc<BoundedBlockingQueue>` 里 `pop`），验证总数仍是 200、且两个 worker 分摊了活。
4. **进阶·真并发丢帧**：把 Part 2B 改成真的两个线程（快生产者 + 慢消费者，消费者每帧 `sleep` 一小会），观察丢弃条数——你会发现它每次运行**略有浮动**（这正是正文说"并发下具体条数随调度波动"的原因），但"处理数+丢弃数=生产数"这条守恒恒成立。
