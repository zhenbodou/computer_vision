# 第 85 章 时间窗口过滤与状态机（N/M 投票、去抖）

> **本章导读**
> - 搞懂检测器为什么会「闪」——单帧偶发的误检（凭空多一个框）与漏检（真目标那一帧没框）。
> - 学会用**时间维度确认**把「一帧就报」的毛糙输出，变成稳定可信的告警：连续 N 帧、更鲁棒的 **N/M 投票**。
> - 亲手写一个**四态状态机**（空闲→候选→确认→疑失）管理目标的出现与消失，并容忍短暂遮挡。
> - 实测对比「不去抖 vs 去抖」：同一段抖动序列，告警从一堆噪声收敛成 **1 次确认 + 1 次消失**。

## 场景：一帧就报，警报响个不停

接着 [第 83 章](ch83-filtering-basics.md) 的清洗和 [第 84 章](ch84-roi-filter.md) 的 ROI 过滤往下走。现在画面里的检测框已经「干净」了：置信度够、类别对、落在布防区内。是不是可以直接报警了？

别急。把摄像头对着门口连着看几百帧，你会发现检测器有个恼人的毛病——它会**闪**：

- **偶发误检（false positive）**：明明没人，某一帧突然在门口冒出一个「person」框（一片晃动的树影、一道反光就够了），下一帧又没了。
- **偶发漏检（false negative）**：明明有人稳稳站着，某一帧却偏偏没框出来（姿态一变、被栏杆挡了半边）。

如果你「一帧命中就报警」，这些单帧抖动会让告警**响个不停**：真目标站 10 秒你能收到几十条，外加时不时一条凭空的误报。运维同事的手机会被你炸崩。

问题的本质是：**单帧的判断不可靠，但时间会说真话。** 真目标会「持续」出现，而抖动是「零星」的。于是解法顺理成章——**在时间维度上做确认**：别信某一帧，看最近一小段时间的「投票」结果。

## 原理一：从「连续 N 帧」到「N/M 投票」

最朴素的去抖是**连续 N 帧命中才确认**：要求目标连着出现 N 帧（比如 3 帧），才认定它是真的。一次单帧误检只有 1 帧，凑不够 N，直接被滤掉。

但「连续」太脆了。想象真目标站在那儿，中间被路过的人挡了**一帧**——连续计数瞬间清零，前功尽弃，得从头再连 N 帧。现实里漏检很常见，「连续」会让确认反复推迟。

更鲁棒的是 **N/M 投票（N-out-of-M voting）**：只看**最近 M 帧**这个滑动窗口，里面只要有 **N 帧命中**就算真目标。用记号写出来，设 \\( \text{hit}_k \in \lbrace 0,1 \rbrace \\) 表示第 k 帧是否命中，则在第 t 帧确认的条件是：

\\[ \text{votes}_t = \sum_{k=t-M+1}^{t} \text{hit}_k \ge N \\]

「连续 N 帧」其实是它 **M = N** 的特例。放宽到 M > N（比如 N/M = 3/5），就能**容忍窗口里偶发的漏检**：5 帧里漏 1、2 帧无所谓，只要够 3 帧命中就确认。这一个小改动，让去抖既能压住误检，又不怕零星漏检。

> 📖 **术语**：**去抖（debounce）**。这个词借自电子工程——按键的金属触点接通瞬间会「弹跳」出一串抖动信号，电路要等信号稳定一小段时间才认这次按下。检测框的闪烁和按键弹跳是一回事，时间窗口投票就是我们的「去抖电路」。

## 原理二：用状态机管理「出现与消失」

光有「确认」还不够。一个目标的完整生命周期是：**没出现 → 冒头了 → 确认是真的 → 待了一会儿 → 走了**。用一个**状态机（state machine）** 来管理它最清晰。我们设四个状态：

- **Idle（空闲）**：什么都没有。
- **Candidate（候选）**：见到零星命中，还没凑够票数，先盯着。
- **Confirmed（确认）**：窗口投票达标，认定真目标——**在这里吐出「确认」事件**。
- **Lost（疑失）**：确认之后开始漏检，但还在容忍范围内（可能只是短暂遮挡），先别急着报「走了」。

状态转移图（箭头上是触发条件）：

```text
              第一次命中
   ┌──────┐ ───────────────▶ ┌───────────┐
   │ Idle │                   │ Candidate │
   │ 空闲 │ ◀─────────────── │   候选    │
   └──────┘  候选期连续漏检    └───────────┘
     ▲  ▲     超过耐心             │ 最近 M 帧命中 ≥ N
     │  │                         ▼
     │  │  连续漏检 > gap    ┌───────────┐
     │  └─────────────────  │ Confirmed │ ★吐出「确认」事件
     │      ★吐出「消失」    │   确认    │
     │                      └───────────┘
     │   连续漏检 > gap        ▲       │ 漏检 1 帧
     │  ┌──────┐              │       ▼
     └─ │ Lost │  又出现(不重报)└──── ┌──────┐
        │ 疑失 │ ◀──────────────────│ Lost │
        └──────┘                    └──────┘
```

关键设计有两处：

1. **Confirmed → Lost 而不是直接 → Idle。** 确认后哪怕漏检一帧，也先进「疑失」缓冲。只要在 `gap` 帧之内目标**又出现**，就悄悄回到 Confirmed，**不重复报**「又来了一个目标」。只有连续漏检超过 `gap`，才判定真的消失。这就是**容忍短暂遮挡**。
2. **回到 Idle 时清空窗口。** 一旦放弃（候选没凑够、或确认后彻底消失），就把投票窗口清零，别让上一个目标的旧票污染下一个目标的判断。

## 动手写代码：给抖动序列去抖

我们合成一段带抖动的检测流，用 N/M = 3/5 投票 + 四态状态机跑一遍，逐帧打印状态，并和几种「不去抖 / 弱去抖」的基线对比误报次数。**只用 std**，输入是合成的 `Vec<Frame>`（时间戳自己造递增值，不读系统时钟），完全可复现。

数据模型 `BBox` / `Detection` / `Frame` / `Event` 沿用 [第 83 章](ch83-filtering-basics.md)，此处省略（完整文件见 `code/examples/ch85_temporal_window.rs`）。本章有个前置小问题：**凭什么说「这一帧的框」和「上一帧的框」是同一个目标？** 这里我们还没有跟踪器给的稳定 id，就用最朴素的办法——看这一帧有没有框和门口「锚框」的 IoU 够大（关联靠 IoU / 位置）。等到 [第 86 章](ch86-cooldown-dedup.md) 有了 `track_id`，跨帧关联会更省事。

运行：

```bash
cargo run --example ch85_temporal_window
```

核心代码（省略共享模型部分）：

```rust
use std::collections::VecDeque;

/// 门口的「锚框」：真实目标大致站这儿。没有 track_id 时靠它与本帧框的 IoU 判断命中。
fn anchor() -> BBox { BBox::new(280.0, 120.0, 60.0, 180.0) }

/// 本帧是否命中：有 person 检测且与锚框 IoU ≥ 阈值即算命中（最朴素的跨帧关联）。
fn hits_anchor(frame: &Frame, anchor: &BBox, iou_thr: f32) -> bool {
    frame.detections.iter()
        .any(|d| d.label == "person" && d.bbox.iou(anchor) >= iou_thr)
}

/// 四态状态机
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum State { Idle, Candidate, Confirmed, Lost }

/// N/M 滑动窗口投票 + 状态机去抖器
struct Debouncer {
    window_m: usize,    // 窗口长度 M
    need_n: usize,      // 确认阈值 N
    gap_tolerance: u32, // 确认后容忍的连续漏检数（短暂遮挡不算消失）
    cand_patience: u32, // 候选态最多容忍几帧连续漏检
    window: VecDeque<bool>,
    consec_miss: u32,
    state: State,
}

impl Debouncer {
    fn votes(&self) -> usize { self.window.iter().filter(|&&h| h).count() }

    fn reset(&mut self) { self.window.clear(); self.consec_miss = 0; } // 回空闲就清窗口

    /// 喂进本帧命中与时间戳，返回可能产生的事件（确认 / 消失）。
    fn update(&mut self, hit: bool, ts_ms: u64) -> Option<Event> {
        self.window.push_back(hit);                       // 维护最近 M 帧
        if self.window.len() > self.window_m { self.window.pop_front(); }
        let votes = self.votes();
        if hit { self.consec_miss = 0; } else { self.consec_miss += 1; }

        let mut event = None;
        match self.state {
            State::Idle => {
                if hit { self.state = State::Candidate; }  // 见到第一次命中
            }
            State::Candidate => {
                if votes >= self.need_n {                  // 票数够 → 确认
                    self.state = State::Confirmed;
                    event = Some(Event {
                        kind: "confirm".to_string(), ts_ms, track_id: None,
                        message: format!("目标确认（最近{}帧命中{}次）", self.window.len(), votes),
                    });
                } else if self.consec_miss >= self.cand_patience {
                    self.state = State::Idle; self.reset();  // 零星误检，放弃
                }
            }
            State::Confirmed => {
                if self.consec_miss >= 1 { self.state = State::Lost; } // 先进疑失，不急着报消失
            }
            State::Lost => {
                if hit {
                    self.state = State::Confirmed;          // 又出现：短暂遮挡而已，不重报
                } else if self.consec_miss > self.gap_tolerance {
                    self.state = State::Idle;               // 超过容忍 → 真的走了
                    event = Some(Event {
                        kind: "gone".to_string(), ts_ms, track_id: None,
                        message: format!("目标消失（连续漏检{}帧）", self.consec_miss),
                    });
                    self.reset();
                }
            }
        }
        event
    }
}
```

`make_frames` 按一段命中序列合成帧流（剧情：单帧误检#1 → 真目标出现且中途几次漏检 → 真目标离开 → 单帧误检#2），`main` 里逐帧喂给 `Debouncer` 并打印过程，最后用三种基线对比。运行输出（数字真实可复现）：


盯着这段输出看几眼，几件事一目了然：

1. **第 1 帧、第 21 帧的单帧误检**都停在 Candidate，连续漏检攒到 2 帧就放弃回 Idle，**从没进过 Confirmed**——误检被干净滤掉。
2. **第 6 帧**窗口投票凑够 3/5，确认真目标（ts=1240ms）。中途第 8、11、12、16、17 帧的漏检只让状态在 Confirmed↔Lost 之间轻轻跳动，**目标没有被误判为消失**——这就是 gap 容忍的价值。
3. **误报次数的收敛**极其直观：不去抖是 **11** 条，退化的「连续 3 帧」方案因为一次遮挡就把同一个人**重复确认 2 次**，而 N/M 投票 + 状态机把整段序列干净地表达成 **1 次确认 + 1 次消失**。这正是真目标该有的样子。

## 常见坑与提示

> ⚠️ **注意**：**窗口越长越稳，但越迟钝——这是延迟与稳健的权衡。** M、N 调大，抗抖动能力更强，可确认也更晚：M/N = 3/5 在 25fps 下最快也要约 5 帧≈0.2 秒才确认。安防场景（宁慢勿误报）可以放大；而闯入报警、碰撞预警这类**要求低延迟**的场景就得压小窗口、甚至接受偶发误报。没有万能值，按「你更怕误报还是更怕漏报/延迟」来定。

> 🕳️ **坑**：**目标短暂被遮挡，不该立刻判「消失」。** 新手常把 Confirmed 直接接到「一漏检就报消失」，结果一根晃动的栏杆、一个路人穿过，就让系统反复报「目标走了→又来了」。一定要留 `gap` 容忍：连续漏检超过阈值才算真的走。`gap` 怎么定？看你的帧率和目标典型遮挡时长——25fps 下容忍 0.3 秒遮挡，就设 gap ≈ 7~8 帧。

> 🕳️ **坑**：**状态机的边界条件最容易埋雷。** 回到 Idle 时忘了清空投票窗口，上一个目标的残留命中会「帮」下一个目标提前确认；Lost 态恢复到 Confirmed 时误发了一次「确认」事件，就变成同一目标重复报警。写完一定要像上面那样**逐帧打印状态和事件**核对，边界帧（刚确认、刚消失、误检临界）都要盯一遍。

> 💡 **提示**：**跨帧到底按什么 key 关联？** 本章没有跟踪器，只能用 IoU / 位置把「这一帧的框」和门口锚框关联起来判断命中——简单够用，但目标一多、互相交叉就会张冠李戴。真正稳的做法是让**跟踪器（[第 62 章](../p13-tracking/ch62-mot.md)）给每个目标一个稳定的 `track_id`**，去抖状态机就**按 track_id 分别维护**（一个人一套状态机）。下一章的 cooldown 去重正是建立在 `track_id` 之上。

## 本章小结

- 检测器会「闪」：单帧偶发的**误检**与**漏检**，直接「一帧就报」会导致告警风暴 + 零星误报。
- **时间维度确认**是解药：**连续 N 帧**最朴素但脆；**N/M 投票**（最近 M 帧里 N 帧命中）能容忍偶发漏检，「连续 N 帧」是它 M = N 的特例。
- 用**四态状态机**（Idle→Candidate→Confirmed→Lost）管理目标出现/消失；Confirmed→Lost 的缓冲 + `gap` 容忍，让短暂遮挡不误判消失；回 Idle 要清空窗口。
- 实测：同一段抖动序列，不去抖 11 条告警、脆弱的连续方案重复确认，N/M + 状态机收敛成 **1 次确认 + 1 次消失**。
- 跨帧关联的 key：有跟踪器就用 `track_id`，没有就退而用 IoU / 位置——这把钥匙引出下一章。

## 动手练习

1. **调窗口感受权衡**：把 `Debouncer::new` 的 N/M 从 3/5 改成 2/3 和 5/7，重跑，观察确认时刻提前/推后了几帧，体会「延迟 vs 稳健」。
2. **加大遮挡**：在 `make_frames` 的命中序列里，把真目标中段改成连续漏检 3 帧（超过 gap=2），看状态机是否会「误判消失又重新确认」；再把 `gap_tolerance` 提到 3，验证它又能容忍了。
3. **按 track_id 多目标去抖**：假设每个 `Detection` 带一个 `track_id`，把 `Debouncer` 改成 `HashMap<u64, Debouncer>`，给每个 id 维护独立状态机，让两个目标互不干扰地各自确认。
4. **进阶——迟滞阈值**：给「确认」和「消失」用不同的投票阈值（如命中 ≥3/5 才确认、命中 ≤1/5 才消失），实现**迟滞（hysteresis）**，让状态在临界点不来回抖。
