# 第 86 章 冷却（cooldown）、跨帧去重、告警聚合与节流

> **本章导读**
> - 解决「告警风暴」：一个人在门口站 10 秒、每帧都命中，怎么让系统只报一条而不是一百条。
> - 掌握四把「去重」利器：**cooldown 冷却**、**跨帧去重**（按 `track_id` / IoU）、**同帧去重**（NMS，复用 `BBox::iou`）、**告警聚合 / 节流**。
> - 想清楚一个关键抉择：cooldown 该**按目标**还是**按区域**——两种口径会漏报/误合并完全不同的东西。
> - 实测把一条持续命中的检测流层层收敛：**364 个原始框 → 3 条告警 → 1 条摘要**。

## 场景：站了 10 秒，报了 100 条

上一章（[第 85 章](ch85-temporal-window.md)）我们用时间窗口投票 + 状态机，把「闪」的检测流确认成了稳定目标。可确认之后，新的麻烦来了。

设想门口站着一个人，纹丝不动待了 10 秒。检测器很称职，**每一帧都稳稳命中**——25fps 下这就是 250 次命中。如果你「确认一次就报一条」，运维会在 10 秒内收到 250 条「有人闯入」。第二天他就把你的报警静音了。

这不是检测错了，恰恰是检测**太对了**。同一个物理事件（一个人在这儿）被**反复报告**。我们要的是：**同一件事，只报一次（或每隔一段时间提醒一次）。** 这一章就讲怎么把「一堆重复命中」收敛成「恰到好处的几条告警」。

去重要分三个层次看，外加最后一层聚合：

```text
一帧的原始框
   │  ① 同帧去重 NMS(IoU)      去掉「一个人身上多个重叠框」
   ▼
每个目标一个框
   │  ② 跨帧关联(track_id)      认出「还是刚才那个人」
   ▼
带稳定 id 的命中流
   │  ③ cooldown(按 id + 时间)  冷却期内同一目标不重复报
   ▼
少量告警
   │  ④ 聚合 / 节流(时间窗)     同类多条 → 一条摘要
   ▼
一条摘要
```

## 原理一：同帧去重——一个目标，多个框

先看**同一帧内**的重复。检测器有时会在一个人身上吐出好几个高度重叠的框（尤其是自带的 NMS 阈值没调好时）。这一步的去重就是我们在 [第 45 章](../p09-detection/ch45-detection-principles.md) 见过的 **NMS（非极大值抑制）**：按分数从高到低，保留一个框就压掉与它 **IoU 过高**的其余框。

判断「两个框是不是同一个东西」的度量，正是 [第 83 章](ch83-filtering-basics.md) `BBox` 上的 `iou`——交并比越接近 1，越可能是同一物体的重复框。这里直接复用它，一行搞定。

## 原理二：跨帧去重与 cooldown——还是刚才那个人

同帧去重之后，每个目标一帧一个框。可**跨帧**看，同一个人连续 250 帧都在，这 250 个框还是「同一个人」。怎么认出「还是刚才那个」？

- **有跟踪器**：[第 62 章](../p13-tracking/ch62-mot.md) 的跟踪器会给每个目标一个**稳定的 `track_id`**，同一个人跨帧都是同一个 id——这是最省事、最可靠的去重钥匙。
- **没跟踪器**：退而用 **IoU / 位置关联**——这一帧的框和上一帧哪个框 IoU 最大，就认为是同一个（上一章我们就用 IoU 和锚框关联过）。

认出「是同一个」之后，用 **cooldown（冷却）** 控制报警频率：**同一个目标一旦报过一次，冷却期 T 内不再重复报**。实现就是记一张「上次报警时间表」，来了新命中先查表——距上次报警还没到 T 就压掉，超过 T 才放行并刷新时间：

\\[ \text{放行} \iff t_{\text{now}} - t_{\text{last}}[\text{key}] \ge T \\]

这里的 `key` 用什么，是本章最需要想清楚的一件事，下面代码里我们会把「按 `track_id`」和「按区域」两种口径都跑一遍对比。

> 📖 **术语**：**cooldown（冷却 / 冷静期）**。和游戏技能的冷却时间一个意思：放一次技能后要等 CD 转好才能再放。告警的 cooldown 就是「报一次后，这个目标（或这个区域）要冷静 T 秒才准再报」。

## 原理三：告警聚合与节流

最后一层是**聚合（aggregation）/ 节流（throttling）**：把一个时间窗内的**同类**事件，攒成一条摘要。比如「5 分钟内 3 次闯入」比 3 条孤立告警更有信息量、也更不打扰。cooldown 是「同一目标少报」，聚合是「同类事件合并报」，两者互补。

## 动手写代码：把持续命中收敛成几条告警

我们合成一段 300 帧（10fps，30 秒）的帧流：3 个目标先后出现（其中 1 号和 2 号有一段并存），每个都持续命中，检测器还时不时多吐一个重复框。然后依次做同帧 NMS → 按 `track_id` 的 cooldown → 聚合。**只用 std**，时间戳自造递增值，可复现。

数据模型 `BBox` / `Detection` / `Track` / `Event` 沿用 [第 83 章](ch83-filtering-basics.md)，此处省略（完整见 `code/examples/ch86_cooldown_dedup.rs`）。跟踪器已给每个框配好 `track_id`，我们用一个薄壳 `TrackedDet` 把 `(track_id, Detection)` 配对着用。

运行：

```bash
cargo run --example ch86_cooldown_dedup
```

核心代码（省略共享模型部分）：

```rust
use std::collections::HashMap;

/// 跟踪器给框配好 track_id 后的「带 id 检测」（id 官方记在 Track 上，逐帧处理时配对更顺手）。
#[derive(Clone, Debug)]
struct TrackedDet { track_id: u64, det: Detection }

/// ① 同帧去重：贪心 NMS。按分数降序，保留一个就丢掉与它 IoU 过高的其余框。复用 BBox::iou。
fn nms_same_frame(mut dets: Vec<TrackedDet>, iou_thr: f32) -> Vec<TrackedDet> {
    dets.sort_by(|a, b| b.det.score.partial_cmp(&a.det.score).unwrap());
    let mut keep: Vec<TrackedDet> = Vec::new();
    'outer: for d in dets {
        for k in &keep {
            if d.det.bbox.iou(&k.det.bbox) > iou_thr {
                continue 'outer; // 与已保留的高分框重叠过多 → 判为重复，丢弃
            }
        }
        keep.push(d);
    }
    keep
}

/// ② cooldown 冷却闸门：同一个 key 一旦放行，冷却期 cd_ms 内不再放行。
/// key 用 track_id → 按目标冷却；key 用区域 id → 按区域冷却。
struct CooldownGate { cd_ms: u64, last_fire: HashMap<u64, u64> }

impl CooldownGate {
    fn new(cd_ms: u64) -> Self { CooldownGate { cd_ms, last_fire: HashMap::new() } }
    fn allow(&mut self, key: u64, ts_ms: u64) -> bool {
        match self.last_fire.get(&key) {
            Some(&t) if ts_ms.saturating_sub(t) < self.cd_ms => false, // 冷却期内，压制
            _ => { self.last_fire.insert(key, ts_ms); true }           // 放行并刷新计时
        }
    }
}
```

`main` 里的流水线（节选）：

```rust
// ① 同帧 NMS 去重
let deduped: Vec<TrackedFrame> = stream.iter()
    .map(|f| TrackedFrame { ts_ms: f.ts_ms, dets: nms_same_frame(f.dets.clone(), 0.5) })
    .collect();

// ② 按 track_id 的 cooldown：同一个人 60s 内只报一次
let mut gate = CooldownGate::new(60_000);
let mut alarms: Vec<Event> = Vec::new();
for f in &deduped {
    for td in &f.dets {
        if gate.allow(td.track_id, f.ts_ms) {          // 冷却闸门放行才发告警
            alarms.push(Event {
                kind: "intrusion".to_string(), ts_ms: f.ts_ms,
                track_id: Some(td.track_id), message: "有人进入布防区".to_string(),
            });
        }
    }
}
```

运行输出（数字真实可复现）：

```text
== 原始检测流（10 fps，共 300 帧 = 30 秒）==
原始检测框（含同帧重复框）：364

== ① 同帧去重：NMS（IoU>0.5）==
去重前：364 框
去重后：302 框（合并掉 62 个重复框）

== ② 跨帧去重 + cooldown（按 track_id，冷却 60s）==
若不做 cooldown：每个「目标在区域内」的帧都报 → 302 条告警
实际发出的告警（每个目标进入后 60s 内只报一次）：
  [告警] t= 1.0s  track#1  intrusion  有人进入布防区
  [告警] t= 7.0s  track#2  intrusion  有人进入布防区
  [告警] t=22.0s  track#3  intrusion  有人进入布防区
命中帧（去重后仍是「某目标在区域内」）：302  →  实际告警：3

== cooldown 按目标 vs 按区域 ==
按 track_id 冷却：3 条告警（每个不同的人各报一次，能抓住并存/后到的人）
按 区域   冷却：1 条告警（冷却期内 track#2、track#3 进入被一并压掉，会漏报不同目标）

== ③ 告警聚合 / 节流（把同类事件聚成一条）==
30s 窗口内 intrusion 类事件：3 次 → 聚合 1 条摘要
  摘要：30秒内共发生 3 次闯入（首次 t=1.0s，末次 t=22.0s）

== 总览：告警是怎样被一层层收敛的 ==
原始框 364 → 同帧NMS 302 → cooldown后告警 3 → 聚合摘要 1 条
```

这条「收敛链」把去重的层次感讲得很清楚：

1. **同帧 NMS** 把 62 个重复框合并掉（364 → 302），保证一个人这一帧只剩一个框。
2. **cooldown 按 track_id** 把 302 次持续命中收敛成 **3 条告警**——三个人各报一次。注意 1 号（站了 18 秒）和 2 号（第 7 秒路过）**时间上并存**，但因为 `track_id` 不同、cooldown 按目标各记各的，**两个人都报到了**。
3. **对比按区域冷却**：整块布防区共用一个 key，1 号在第 1 秒触发后进入冷却，结果 2 号、3 号进来时全被压掉，只剩 **1 条**——不同的人被漏报了。
4. **聚合**再把 3 条同类事件收成 1 条摘要。

## 常见坑与提示

> ⚠️ **注意**：**cooldown 时长要按业务定，不是越长越好。** 太短压不住风暴（站 10 秒还是报好几条），太长会漏掉「短暂离开又回来」这种真该再报的情况。安防常见 30s~几分钟；本例用 60s 是为了让每个目标在其停留期内恰好只报一次。记住 cooldown 换来的代价是**时间分辨率**：冷却期内发生的同类事件你就看不到细节了。

> 🕳️ **坑**：**cooldown 按目标还是按区域，会漏报完全不同的东西——这是本章最关键的抉择。** 按 `track_id`（本例 3 条）：每个不同的人各报一次，适合「必须抓住每一个闯入者」；但一群人涌入会各报一条，可能又成风暴。按**区域**（本例 1 条）：整片区域冷却期内只报一次，适合压制「一根晃动的树枝反复触发同一个点」；但**会把冷却期内进来的另一个人也一起压掉**（上面 2 号、3 号就被漏报了）。选哪个取决于你更怕「重复报同一处」还是「漏报不同目标」。

> 🕳️ **坑**：**去重 key 选错，要么漏报要么误合并。** 同帧 NMS 的 IoU 阈值调太高，两个真的挨得近的人会被当成重复框合并成一个（漏报）；调太低，同一个人的两个框合并不掉（重复）。跨帧若没有 `track_id`、纯用 IoU 关联，两个目标交叉走位时极易「串号」，把 A 的告警记到 B 头上。能上跟踪器给稳定 id 就别硬扛 IoU。

> 💡 **提示**：**别把不同目标误合并。** 本例三个目标锚框位置分得很开（IoU=0），所以同帧 NMS 绝不会错并。真实场景里两个人贴身而过、框大面积重叠时，光靠 IoU 会误合并——这时候 `track_id` 或外观特征（[第 62 章](../p13-tracking/ch62-mot.md) DeepSORT 的 re-ID）才能把他们分开。去重的前提永远是「先正确关联，再合并」。

> 💡 **提示**：**聚合窗口按事件频率和通知渠道定。** 本例窗口取整段 30 秒只为演示；生产里「5 分钟内 N 次闯入聚一条」很常见——既保留了「发生了几次」的信息，又不会让推送（[第 91 章](ch91-actions-push.md)）把人淹没。高频事件（如客流计数）甚至会用「每分钟一条汇总」的固定节流。

## 本章小结

- 检测器「太对了」也会出问题：同一物理事件被反复命中 → **告警风暴**。去重分三层 + 一层聚合。
- **同帧去重**用 NMS（复用 `BBox::iou`）合并「一个目标多个重叠框」；**跨帧去重**靠 `track_id`（首选）或 IoU 关联认出「还是刚才那个」。
- **cooldown**：同一 key 报过一次，冷却期 T 内不再报。`key = track_id` 是**按目标**冷却，`key = 区域` 是**按区域**冷却，两者会漏报/合并完全不同的东西，按业务选。
- **聚合 / 节流**把时间窗内的同类事件收成一条摘要（如「5 分钟内 3 次闯入」）。
- 实测收敛链：**原始框 364 → 同帧 NMS 302 → cooldown 后 3 条告警 → 聚合 1 条摘要**；且按目标冷却能抓住并存/后到的人，按区域冷却会漏掉他们。

## 动手练习

1. **调 cooldown**：把 60s 改成 5s，重跑，看每个长时间停留的目标会被拆成几条告警；再改成 300s，观察是否每人恰好 1 条。理解「时长 ↔ 时间分辨率」的取舍。
2. **切换冷却口径**：把发告警的 `gate.allow(td.track_id, ...)` 改成按区域 key，复现「不同目标被漏报」；再想想门禁 vs 周界两种场景各该用哪种。
3. **IoU 跨帧去重**：假装拿不到 `track_id`，写一个「本帧框与上一帧框 IoU>0.5 就算同一个」的关联，给它编稳定 id 后再做 cooldown，对比和用真 `track_id` 的差别。
4. **进阶——真·聚合器**：实现一个滑动时间窗（如 5000ms）的聚合器，输入连续告警流，每当窗口内同类事件数达到阈值就吐一条「N 分钟内 M 次」摘要，其余压制。
