# 第 62 章 多目标跟踪（SORT / DeepSORT）

> **本章导读**
> - 学完你能：给视频里的**每个目标一个稳定 id**，并把它跨帧连成一条轨迹；亲手写出一个能跑的简化版 **SORT** 跟踪器。
> - 搞懂 tracking-by-detection 范式，以及 SORT 的"三件套"：卡尔曼预测、IoU 关联、轨迹生命周期。
> - 理解 **id-switch（换标）**是怎么发生的，以及 **DeepSORT** 为什么要加"外观特征"来救场。
> - 明白匈牙利算法与贪心分配的取舍，知道纯 Rust 里该怎么落地。

## 场景引入：商场里怎么"数清"有几个人经过

监控画面里，五六个人来来往往。你的检测器（第九部分）每一帧都能框出"这里有个人、那里有个人"——但它是**健忘**的：第 10 帧框出的 3 个人，和第 11 帧框出的 3 个人，谁是谁？它一无所知。

可业务想要的偏偏是"谁是谁"：**同一个人从进门到出门，自始至终是同一个编号**。只有这样，你才能数客流（每个 id 算一个人，而非每帧重复数）、判断"这人在货架前停留了多久"、触发"有人逆行"的告警。给每个目标一个**稳定 id**、把它**跨帧连起来**——这就是**多目标跟踪（Multiple Object Tracking，MOT）**要干的事。

> 📖 **术语**：**tracking-by-detection（检测后跟踪）**。现代 MOT 的主流范式：把"发现目标"交给检测器（第九部分的 YOLO 之类），跟踪器**只负责关联**——把这一帧的检测框，正确地接到上一帧的某条轨迹上。检测器管"有什么、在哪"，跟踪器管"这个和上一帧那个是不是同一个"。本章的跟踪器完全不看图像像素，只吃检测框，所以我们能用**合成的检测框序列**把它讲透、跑通。

## 原理：SORT 的三件套

**SORT**（Simple Online and Realtime Tracking）是 2016 年提出的一个"简单到不可思议却很好用"的跟踪器。它只靠三样东西：**卡尔曼预测、IoU 关联、生命周期管理**。先看整条数据流：

```text
每一帧（检测器给出这一帧的一批检测框）：

   上一帧留下的若干条轨迹
            │
            ▼
 ┌────────────────────────────────────────────────┐
 │ ① 预测：每条轨迹用卡尔曼把自己的位置「推进一帧」  │  ← 复用第 60 章思想
 └────────────────────────────────────────────────┘
            ▼
 ┌────────────────────────────────────────────────┐
 │ ② 关联：预测框 × 本帧检测框 → 算 IoU 代价矩阵      │
 │        用匈牙利算法（或贪心）求「谁配谁」          │
 └────────────────────────────────────────────────┘
        ├── 匹配上 ──▶ ③ 用检测框「校正」这条轨迹（update）
        ├── 没配上的检测 ──▶ 新建一条轨迹（试用期）
        └── 没配上的轨迹 ──▶ 失配计数 +1；太久没配上就删除
```

### ① 卡尔曼预测：让轨迹"猜"自己下一帧在哪

如果一个人上一帧在 (100, 80)、再上一帧在 (92, 80)，那他这一帧**大概率**在 (108, 80) 附近——因为他在**匀速向右走**。卡尔曼滤波（第 [60 章](ch60-kalman.md)详细讲过）干的就是这件事：维护一个**运动状态**（位置 + 速度），每帧先按运动模型**预测**，再用观测**校正**。

本章我们用它最精简的形态：**恒速模型（constant velocity）+ alpha-beta 滤波**（也叫稳态卡尔曼滤波）。状态是中心位置 \(p=(c_x, c_y)\) 和速度 \(v=(v_x, v_y)\)。预测一步：

\\[ \hat{p}_t = p_{t-1} + v_{t-1}, \qquad \hat{v}_t = v_{t-1} \\]

拿到匹配上的检测（观测中心 \(z_t\)）后，用**残差** \(r = z_t - \hat{p}_t\) 同时修正位置和速度：

\\[ p_t = \hat{p}_t + \alpha\, r, \qquad v_t = \hat{v}_t + \beta\, r \\]

其中 \(\alpha, \beta \in (0,1)\) 是两个固定增益（本章取 \(\alpha=0.6, \beta=0.25\)）。这就是一个"简化到没有协方差矩阵"的卡尔曼——但**核心价值一模一样**：即使这一帧目标被遮挡、没有检测框，轨迹也能靠 \(\hat{p}_t = p_{t-1}+v_{t-1}\) **凭空续一步**，等目标重新出现时接得上。

### ② IoU 关联：谁配谁？

预测完，手上有 \(m\) 条轨迹的预测框、\(n\) 个本帧检测框。"谁是谁"本质是一个**二部图最优分配**问题。用什么衡量"像不像"？最简单的就是 **IoU（交并比）**——两个框重叠得越多越像：

\\[ \text{IoU}(A, B) = \frac{|A \cap B|}{|A \cup B|} \in [0, 1] \\]

把"代价"定义为 \(1 - \text{IoU}\)（越小越该配），就得到一个代价矩阵：

```text
            检测A    检测B    检测C
  轨迹1 [  0.02     0.71     0.95 ]   ← 值=1−IoU，越小越像
  轨迹2 [  0.88     0.05     0.90 ]
  轨迹3 [  0.93     0.92     0.10 ]
```

一眼能看出最优分配是"轨迹1-A、轨迹2-B、轨迹3-C"（对角线代价最小）。**匈牙利算法（Hungarian / Kuhn-Munkres）**能在多项式时间里求出**全局总代价最小**的分配，是标准做法。

但匈牙利算法要写几十行、还得处理矩形（\(m \neq n\)）的情形。本章先用**贪心近似**把思路讲通：把所有 IoU ≥ 阈值的候选对**按 IoU 从大到小排序**，从最像的一对开始，依次占用（一条轨迹、一个检测各只能被用一次）。这和特征匹配里的"互为最近邻"思想（第 [25 章](../p04-features/ch25-matching-ransac.md)）是一个味道。

> ⚠️ **注意**：贪心不保证全局最优。在拥挤场景里，贪心"先占最大"可能逼得后面的配对只能选次优解，而匈牙利会通盘权衡。好在只要各目标分得开，两者结果一致——所以贪心是极好的入门近似，工程上要上强度再换匈牙利（纯 Rust 可用 `pathfinding` crate 里的 Kuhn-Munkres，用前自行 `cargo add` 验证版本）。

### ③ 轨迹生命周期：新建、确认、老化、删除

关联之后总有"剩下的"：

- **没配上的检测** → 可能是新进画面的目标，给它**新建**一条轨迹，先设为"试用（tentative）"。
- **没配上的轨迹** → 目标可能被遮挡或漏检了，**失配计数 +1**，先别删（靠卡尔曼继续预测）。

用两个阈值管住生死：

```text
  新检测 ──▶ [Tentative 试用] ──连续命中≥min_hits──▶ [Confirmed 确认]
                  │                                       │
              还没站稳就丢                            失配累计上升
                  ▼                                       ▼
               直接丢弃                       失配 > max_age ──▶ [Deleted 删除]
```

- `min_hits`（本章 3）：新轨迹要**连续命中 3 次**才"转正"、才对外输出 id，以滤掉检测器"闪一下就没"的偶发误检。
- `max_age`（本章 3）：一条轨迹**连续失配超过 3 帧**才删除，给短暂遮挡留出"缓冲期"——遮挡几帧能靠预测续上，太久才判定离开。

## 动手写代码：一个能跑的简化 SORT

配套示例 `code/examples/ch62_mot.rs`，只用标准库。我们**合成** 30 帧、3 个目标的检测框序列：目标 1 在中间车道左→右、目标 2 在下方车道右→左（两者中途**交叉而过**），目标 3 在顶部车道左→右；并**故意让目标 1 在第 8、9 帧漏检**（模拟短暂遮挡）、目标 3 在第 20 帧漏检。跟踪相关的类型在本部分**局部最小自定义**（框用 `(x, y, w, h)` 的 `f32`，IoU 自己写十来行），不依赖后面第十八部分的数据模型。

先是最小包围盒与 IoU（这十几行就是关联的全部数值基础）：

```rust
#[derive(Clone, Copy, Debug)]
struct BBox { x: f32, y: f32, w: f32, h: f32 }

impl BBox {
    fn center(&self) -> (f32, f32) { (self.x + self.w / 2.0, self.y + self.h / 2.0) }
    /// 交并比 IoU = 交集面积 / 并集面积
    fn iou(&self, o: &BBox) -> f32 {
        let x1 = self.x.max(o.x);            let y1 = self.y.max(o.y);
        let x2 = (self.x + self.w).min(o.x + o.w);
        let y2 = (self.y + self.h).min(o.y + o.h);
        let inter = (x2 - x1).max(0.0) * (y2 - y1).max(0.0);
        let uni = self.w * self.h + o.w * o.h - inter;
        if uni <= 0.0 { 0.0 } else { inter / uni }
    }
}
```

一条轨迹就是"恒速状态 + 生命周期计数"，`predict`/`update` 直接对应上面的两条公式：

```rust
struct Track {
    id: u64,
    cx: f32, cy: f32, vx: f32, vy: f32, w: f32, h: f32, // 状态：位置+速度+尺寸
    hits: u32,              // 累计命中次数
    time_since_update: u32, // 距上次匹配上的帧数
    confirmed: bool,
    // ... first_frame / last_frame 用于统计
}

impl Track {
    fn predict(&mut self) {           // 恒速推进一帧
        self.cx += self.vx;  self.cy += self.vy;
        self.time_since_update += 1;  // 先假设「这帧没配上」
    }
    fn update(&mut self, b: &BBox) {  // 用检测框做 alpha-beta 校正
        let (mx, my) = b.center();
        let (rx, ry) = (mx - self.cx, my - self.cy);  // 残差 = 观测 − 预测
        self.cx += 0.6 * rx;  self.cy += 0.6 * ry;    // 修正位置（α=0.6）
        self.vx += 0.25 * rx; self.vy += 0.25 * ry;   // 修正速度（β=0.25）
        self.hits += 1;  self.time_since_update = 0;
        if self.hits >= 3 { self.confirmed = true; }  // min_hits=3
    }
}
```

关联用贪心：把所有 IoU ≥ 0.3 的候选对按 IoU 降序，依次占用未被用过的轨迹与检测：

```rust
fn associate(tracks: &[Track], dets: &[Det]) -> (Vec<(usize, usize)>, Vec<usize>, Vec<usize>) {
    let mut cand: Vec<(f32, usize, usize)> = Vec::new();
    for (ti, t) in tracks.iter().enumerate() {
        for (di, d) in dets.iter().enumerate() {
            let iou = t.bbox().iou(&d.bbox);
            if iou >= 0.3 { cand.push((iou, ti, di)); }   // IOU_THRESH=0.3
        }
    }
    cand.sort_by(|a, b| b.0.partial_cmp(&a.0).unwrap());  // IoU 从大到小
    // ... 依次占用，收集 matched / 未匹配轨迹 / 未匹配检测
}
```

主循环严格照"预测 → 关联 → 更新/新建 → 老化"走，同时用一个隐藏的真值 id（`gt`，跟踪器看不到）在事后统计 **id-switch**：每个真值目标"上一次"挂在哪个 track id 上，一旦变了就计一次换标。运行：

```bash
cargo run --example ch62_mot
```

关键输出（逐字实测）：

```text
帧14 | 检测3: gt1->id1 gt2->id2 gt3->id3 | 确认轨迹: id1@(155,76) id2@(164,100) id3@(157,30)
帧15 | 检测3: gt1->id1 gt2->id2 gt3->id3 | 确认轨迹: id1@(164,75) id2@(155,100) id3@(165,30)
...
目标 gt1: 最终 id=1，被成功跟踪 28 帧
目标 gt2: 最终 id=2，被成功跟踪 30 帧
目标 gt3: 最终 id=3，被成功跟踪 29 帧
id-switch 次数 = 0（理想为 0）
```

三件事值得盯着看：

- **交叉不换标**：第 14→15 帧，目标 1 与目标 2 擦肩而过（`id1` 的 x 从 155→164、`id2` 从 164→155，**x 坐标互换**），但 id 纹丝不动。功臣有二：车道错开 24px（y=76 vs 100）让 IoU 天然分得清；卡尔曼预测让 `id1` 一直"知道自己往右走"，不会去认那个往左走的框。
- **漏检靠预测续命**：目标 1 在第 8、9 帧漏检，`id1` 靠 `predict()` 凭空往前走两帧（输出标 `*`），第 10 帧检测框一回来立刻无缝接上——`max_age=3` 给的正是这个缓冲。
- **零换标**：全程 `id-switch = 0`，3 个目标各被稳定跟踪 28 / 30 / 29 帧（目标 1 少 2 帧是那两次漏检没计命中）——这正是我们要的"稳定 id"。

> 💡 **提示**：这套跟踪器的输出（每个 id 的历史轨迹）就是第十八部分业务规则的输入——**轨迹将在第十八部分被"绊线计数、区域停留、逆行判断"等规则消费**（见第 [89 章](../p18-events/ch89-trajectory.md)）。跟踪器负责"连成线"，业务层负责"读懂这条线的含义"。

## DeepSORT：当 IoU 不够用时，请出"外观"

SORT 只看**几何**（框在哪、怎么动）。可现实里有个致命场景：**两个人在画面中重叠遮挡**，一个把另一个挡住几帧，再分开时——纯靠位置和运动，跟踪器很可能把两个 id 接反了（一次 id-switch）。因为遮挡期间谁都在"预测"，等重新出现时，两条预测轨迹和两个检测框的 IoU 可能难分伯仲。

**DeepSORT** 的对策是加一路信息：**外观（appearance）**。它在 SORT 之上，为每个检测框额外抽取一个**外观特征向量（re-id embedding）**——一段能代表"这个人长什么样（衣服颜色、体态……）"的数字向量。关联时不再只看 IoU，而是**运动距离 + 外观距离加权**：

\\[ c_{i,j} = \lambda\, d_{\text{motion}}(i, j) + (1 - \lambda)\, d_{\text{appear}}(i, j) \\]

其中 \(d_{\text{appear}}\) 常用轨迹历史外观向量与检测外观向量的**余弦距离**，\(\lambda\) 是权重。这样即便遮挡后位置对不上，只要"长得像"，就能把 id 正确接回去——遮挡场景的 id-switch 大幅下降。

> ⚠️ **注意（诚实交代纯 Rust 现状）**：那个"外观特征"从哪来？它来自一个**深度 re-id 模型**（在行人重识别数据集上训练的 CNN，输入人体小图、输出 128/256 维向量）。**本章不提供能跑的深度 re-id**——那需要一个训练好的模型权重，超出本章合成数据的范围，硬编一个假的只会误导你。诚实的落地路径是：
>
> - 用 candle 或 tract **加载一个 re-id ONNX/safetensors 模型**做前向推理（纯 Rust 的推理链路见第 [94 章](../p19-deploy/ch94-onnx.md)）；抽 embedding 的做法，和第 [57 章人脸识别](../p12-face/ch57-face-recognition.md)里"把人脸编码成向量再比余弦相似度"如出一辙——re-id 就是"把行人编码成向量"。
> - 把每个检测框抠出小图 → 喂 re-id 模型得向量 → 在上面的加权公式里加入外观距离。**运动 + 外观的加权关联框架，本章的贪心/匈牙利完全能直接套用**，缺的只是那个模型。

也就是说：**SORT 的骨架你今天已经会写了；DeepSORT 只是把关联代价从"纯 IoU"换成"IoU + 外观"，多接一个推理模型而已。** 这是"会用"到"精通"之间很实在的一步。

## 常见坑与提示

> 🕳️ **坑：IoU 关联在快速运动 / 低帧率下会"断片"**。IoU 要求预测框和检测框**有重叠**才配得上。如果目标动得太快、或视频帧率太低，相邻两帧的框根本不相交（IoU=0），关联直接失败、轨迹断成两截、id 从此改变。对策：靠卡尔曼预测把框"推"到该在的位置再算 IoU（本章已经这么做）；或改用**中心点距离 / 马氏距离**做代价，别死磕 IoU。

> 🕳️ **坑：拥挤 + 遮挡是 id-switch 的重灾区**。多个同类目标挤在一起、互相遮挡时，纯几何信息不足以区分，贪心更容易接错。这正是 DeepSORT 加外观特征的动机。评估跟踪器时，**id-switch 次数**和 MOTA / IDF1 等指标一样关键——一个"框都框对了但 id 乱跳"的跟踪器，对客流计数这类业务是灾难。

> ⚠️ **注意：匈牙利 vs 贪心**。目标稀疏、分得开时两者结果几乎一样，贪心又快又好懂；一旦拥挤、代价矩阵里有大量"势均力敌"的竞争，就该上匈牙利求全局最优。别为了炫技在简单场景硬套匈牙利，也别在硬场景里迷信贪心。

> 💡 **提示：卡尔曼与关联是"耦合"的**。预测越准，关联越容易；关联越准，卡尔曼拿到的观测越干净、预测越准。反过来，一次错误关联会把"脏观测"喂给卡尔曼，污染速度估计、引发连环错配。所以 `α/β`（卡尔曼增益）、IoU 阈值、`max_age` 要**一起**调，别孤立看某一个。

## 本章小结

- **MOT = 给每个目标稳定 id + 跨帧连成轨迹**；主流范式是 tracking-by-detection：检测器给框，跟踪器只管关联。
- **SORT 三件套**：① 卡尔曼（本章用恒速 alpha-beta 稳态卡尔曼）预测每条轨迹的位置；② IoU 代价矩阵 + 匈牙利/贪心做关联；③ 生命周期用 `min_hits`（转正）和 `max_age`（老化删除）管住轨迹的生死。
- 我们实测跑通了一个 30 帧、3 目标、含交叉与漏检的场景：**id-switch = 0**，三目标分别被稳定跟踪 28 / 30 / 29 帧，交叉擦肩与短暂遮挡都没换标。
- **DeepSORT** 在 SORT 上加"外观 re-id 特征"，用"运动 + 外观"加权关联，专治遮挡后的 id-switch；纯 Rust 里 re-id 模型可用 candle/tract 加载 ONNX 推理（本章不伪造能跑的深度 re-id，只给出关联框架与落地路径）。
- 常见坑：IoU 在快速运动/低帧率下失效、拥挤遮挡引发换标、匈牙利与贪心的取舍、卡尔曼与关联的相互耦合。

## 动手练习

1. **调 max_age**：把 `MAX_AGE` 从 3 改成 1，再把目标 1 的漏检扩到"第 8、9、10 帧"。观察轨迹是否被提前删除、随后新建出一个不同 id（一次 id-switch），体会它如何权衡"抗遮挡"与"及时清理离场目标"。
2. **制造一次换标**：把目标 1、2 的车道 y 都设成 88，让它们**正面重叠**交叉。重新运行，看 id-switch 是否从 0 变成正数——这就是"纯 IoU 打不过遮挡"的现场，也是 DeepSORT 存在的理由。
3. **换个代价函数**：把关联代价从 `1 - IoU` 改成"预测中心与检测中心的欧氏距离"（超阈值视为不可配）。在快速运动（每帧位移从 8px 调到 40px）下，对比它和 IoU 谁更不易断轨。
4. **（进阶）上匈牙利**：`cargo add pathfinding`，用 `kuhn_munkres` 求最小代价分配替换贪心；构造一个多目标 IoU 都在 0.3~0.5 的拥挤帧，对比两者的分配差异。
