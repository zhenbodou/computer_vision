# 第 4 章 · 编解码：图片和视频是如何被压缩的

> **本章导读**：一张 1920×1080 的原始照片要 6.2 MB，而你的手机里存了几千张照片。这中间 20 倍的"缩水"就是编解码的功劳——本章拆开看图片（JPEG/PNG）和视频（H.264）两大压缩体系是怎么做到的。理解了冗余、色度抽样、I/P/B 帧这些核心概念，你以后面对任何新格式都能举一反三。最后我们用 Rust 实战从视频里抽出帧。

**学习目标**：
- 算清原始图像/视频的数据量，理解压缩的必要性
- 区分无损压缩与有损压缩，知道三类"冗余"分别是什么
- 讲清 JPEG 编码的五步流水线，知道有损发生在哪一步
- 掌握 I 帧 / P 帧 / B 帧 / GOP 的概念，理解它们对视频体积和延迟的影响
- 分清"容器"与"编码"，能用 Rust 从视频中抽出帧

## 4.1 为什么需要编解码：先算账

在讲任何原理之前，先用数字震撼一下自己。

**一张图**：1920×1080、RGB、8 位：

```text
1920 × 1080 × 3 字节 = 6.2 MB
```

**一段视频**：同样的分辨率，30 帧/秒：

```text
6.2 MB × 30 = 186 MB/秒
一分钟 = 11 GB
一小时 = 660 GB
一天（24 小时不间断监控）= 15.8 TB
```

就算是一家只有 16 个摄像头的小超市，一天也要产生 250 TB 数据——没有任何硬盘阵列存得起，更没有网络传得动。

**编码（encode/compress）** 就是把原始像素压得足够小再存/传；**解码（decode）** 就是把压过的数据还原回像素（还原程度取决于有损/无损）。压缩比（原始大小 ÷ 压缩后大小）就是这场游戏的核心指标。

## 4.2 压缩的两条路线

**无损压缩**：解压缩后和原始数据**逐字节一致**。类比：把 1 万字论文用 zip 打包——内容一个标点都不变，只是打包方式更紧凑。

**有损压缩**：允许丢掉一些"不重要的信息"，换取大得多的压缩比。类比：把 1 万字总结成 1 千字——大意还在，细节没了。

有损压缩敢丢数据，是因为图像里存在三种"冗余"：

| 冗余 | 含义 | 例子 |
| --- | --- | --- |
| **空间冗余** | 相邻像素长得很像 | 蓝天、白墙，一大片都是一个颜色 |
| **视觉冗余** | 人眼看不出的信息 | 色度细节（2.3.4 节）、极高频的微小变化 |
| **时间冗余** | 视频前后帧几乎一样 | 监控画面里，背景一分钟都不动 |

图片压缩主要吃**空间冗余 + 视觉冗余**；视频压缩额外吃**时间冗余**。记住这三张牌，接下来所有编码器你都能看懂。

## 4.3 图像编码逐个讲

### BMP / RAW：不压缩的"原始人"

像素直接按字节排排坐存进文件（BMP 只是加个很小的文件头）。优点：读写简单、无失真；缺点：体积爆炸。现在只用于相机 RAW 底片、算法中间结果。

### PNG：无损压缩的典范

PNG 的压缩基于 **DEFLATE** 算法，核心是两个思想：

1. **LZ77 字典压缩**：重复的图案不重复存，只记"向前回看 N 个字节、重复 M 次"。一张图里有 1000 个相同的"白天空像素块"，只存一份模板加 999 个"同上"。
2. **哈夫曼编码**：统计每个字节出现的频率，**出现越多的字节用越短的二进制码**。比如像素值 255 出现了 10 万次，就给它分配 2 位的码；出现 3 次的值分配 16 位的码。平均码长就被压下来了。

PNG 完全无损，还能存透明通道，所以**截图、文字、UI、线条图**一律存 PNG——这类图有大量的纯色重复，PNG 能压得很好。但它对**照片**无能为力：照片每个像素都略有不同，几乎没有"重复块"可挖，最终文件比 JPG 大好几倍。

### JPEG：有损压缩的王者

照片怎么压？JPEG 的回答是一条精妙的五步流水线，**有损的那一刀就在第 ④ 步**：

```
① 色彩空间转换      RGB → YCbCr（2.3.3 节）
② 色度抽样          UV 分辨率砍半（4:2:0，2.3.4 节）
③ 分块 + DCT        切成 8×8 小块，每块做离散余弦变换
④ 量化              除以量化表取整 —— 有损就发生在这里！
⑤ 熵编码            哈夫曼编码收尾（无损）
```

逐步说清：

**① ② 两步**把 RGB 换成"亮度 + 色度"并对色度抽样，因为人眼对颜色不敏感（视觉冗余）。这一步本身不丢数据（4:2:0 抽样算轻度有损）。

**③ DCT（离散余弦变换）** 是整件事的灵魂。类比音乐：任何一段旋律都能拆成不同音高的音符叠加（傅里叶的思想），任何一块 8×8 的图像也能拆成一组"从粗到细的波纹图案"的叠加：

```text
8×8 图像块 = a₁×(平坦图案) + a₂×(横向渐变) + a₃×(纵向渐变)
           + a₄×(斜向波纹) + ... + a₆₄×(最细密高频波纹)
```

DCT 之后，这块图不再存 64 个像素值，而是存 64 个**系数**。关键性质：真实图像的系数能量高度集中——平坦项和低频项（大块明暗、缓慢变化）系数很大，高频项（细节纹理）系数很小甚至为零。

**④ 量化**就是"取整扔掉小数字"：每个系数除以一个量化表中对应位置的数再四舍五入。量化表的数值不是固定的——**JPEG 的"质量参数"（0~100）本质就是选哪张量化表**：质量 90 用温和的表，只丢一点点高频；质量 30 用凶狠的表，大量系数被量化成 0。**有损、可调、不可逆，全在这一步。**

**⑤ 熵编码**：量化后的系数里出现大片连续的 0（高频区被砍光了），用"行程编码 + 哈夫曼"描述"第 5 到第 40 个系数全是 0"只需几个字节。

JPEG 的三大后遗症，现在你都能解释了：

- **块效应**：8×8 块边界处量化程度不同，高压缩率下可见方块马赛克（第 ④ 步的锅）
- **对文字/线条糊**：锐利的边缘富含高频，被第 ④ 步砍了（所以截图要用 PNG）
- **不支持透明**：设计时就没考虑 Alpha 通道

### GIF：老将发挥余热

只支持 256 种颜色（色深只有 8 位的索引色），但支持多帧动画。现在的动图早被 WebP/MP4 抢走大半江山，只剩表情包领域发挥余热。256 色对照片是灾难，所以它从来就不是干照片活儿的。

### WebP / HEIC / AVIF：新王者们

| 格式 | 出身 | 特点 |
| --- | --- | --- |
| WebP | 谷歌 | 有损+无损+透明+动画全能，同质量比 JPG 小 25~35% |
| HEIC | MPEG | iPhone 默认照片格式，基于 HEVC（视频编码）技术 |
| AVIF | 开放联盟 | 基于 AV1 视频编码，压缩率最强，网页新宠 |

**怎么选格式**：截图/文字 → PNG；照片 → JPG（兼容性无敌）或 WebP/HEIC（更省）；需要透明 → PNG/WebP；做网页 → WebP/AVIF。

## 4.4 视频编码基础：帧与它们的朋友

图片压缩只解决了 1/30 的问题——视频还有 30 帧/秒的时间维度。先立三个基本概念：

- **帧率（fps）**：每秒多少帧。翻页动画就是帧率的直觉：12 页/秒已经很流畅，30 页/秒行云流水。
- **分辨率**：每帧的像素网格（同 2.1 节）。
- **码率（bitrate）**：每秒多少比特。这是视频的"饭量"总开关：**码率 = 质量 × 体积**，三者只能权衡。同样内容，码率给得高画质好文件大；平台限制流量就必须压码率牺牲质量。

### I 帧、P 帧、B 帧：分工合作

如果对视频的每一帧都按 JPEG 处理，体积还是太大。视频编码的杀手洞察是**时间冗余**：监控画面里背景一分钟都不动，为什么要重复存？

```text
I 帧（关键帧）：完整的自包含图像，类似一张 JPEG，谁都能独立解码
P 帧（预测帧）：只存"和前面某帧的差异"——像'找不同'游戏的答案
B 帧（双向帧）：参考前后两帧，存的信息最少
```

类比翻一本画册：I 帧是完整的一页画，P 帧是便利贴写着"这页和上一页比，只把小狗的位置往右挪了三厘米"，B 帧是"我这页介于第 5 页和第 7 页之间，插值即可"。

解码 P 帧时必须已经解出它引用的前面的帧——这带来一个后果：**视频必须从头（或某个 I 帧）顺序解码**，不能像图片那样随便"读"某一帧。

### GOP：关键帧之间的距离

**GOP（Group of Pictures）** = 两个 I 帧之间的帧序列。GOP 长度的权衡非常工程：

- **GOP 长**（如 250 帧才一个 I 帧）：I 帧少，整体体积小；但 seek（拖动进度条）时必须一路解码到目标位置才能显示，反应慢；直播延迟也高。
- **GOP 短**（如 25 帧一个 I 帧）：seek 快、直播延迟低；但 I 帧占比高，体积大。

所以你会看到：视频网站点播用长 GOP 省流量，直播平台用短 GOP 换低延迟。

## 4.5 视频编码标准家族

编码标准是"压缩算法的公开规范"，标准是死的，实现是活的：

| 标准 | 别名 | 压缩效率 | 专利费 | 现状 |
| --- | --- | --- | --- | --- |
| H.264 | AVC | 基准 | 收 | **兼容性之王**，至今最主流 |
| H.265 | HEVC | 比 264 省 ~50% 码率 | 收且贵 | 4K/8K、监控领域普及中 |
| VP9 | — | 与 265 接近 | 免版税 | YouTube 全站使用 |
| AV1 | — | 比 265 再省 ~20% | 免版税 | 网页视频新趋势（B 站等在推） |

"实现"这边你会听到的名字：**x264 / x265 / openh264** 是开源的编码器软件（把标准写成能跑的程序）；同时手机、显卡、芯片里还有**硬编硬解**——专用电路直接烧在芯片上，又快又省电，软解（CPU 跑软件）完全不是对手。这就是为什么 4K 视频在手机上能播但电脑风扇狂转。

## 4.6 容器 vs 编码：盒子与水

这是初学者 100% 会混淆的点，一次说清：

> **容器（Container）= 装东西的盒子；编码（Codec）= 盒子里装的内容。**

| 容器 | 说明 |
| --- | --- |
| MP4 | 最通用的盒子，几乎什么编码都能装（H.264/H.265/AV1），所有设备都认 |
| MKV | 开源界的"什么都能装"，多音轨多字幕支持最好 |
| MOV | 苹果的盒子，本质是 MP4 的近亲 |
| AVI | 上古格式，老设备存量多 |
| TS | 直播场景的"切片"格式，小文件独立可解码，CDN 分发用它 |

常见误区答疑：

- ❓"MOV 是不是比 MP4 画质好？" → 盒子不影响画质，看里面装的什么编码。
- ❓"摄像头厂商说支持 RTSP 播放" → RTSP 不是容器也不是编码，是**取流协议**（4.8 节）。
- 经验之谈：**`.mp4` 文件里装的通常是 H.264/H.265**，但拿到陌生的视频文件，最稳妥的判断方式是用 `ffprobe` 看（下一节）。

## 4.7 Rust 实战：从视频里抽帧

在 Rust 生态里，视频解码有三条路线。

### 路线一：ffmpeg 命令行（工业界最常见的姿势）

**ffmpeg 是音视频界的瑞士军刀**，几乎一切"转换"需求都能用一行命令解决。比如从视频里每秒抽 1 帧存成图片：

```bash
# -i 输入；-vf fps=1 每秒抽一帧；%03d 序号补零
ffmpeg -i video.mp4 -vf fps=1 frame_%03d.png
```

用 Rust 的 `std::process::Command` 包装它，你就能在程序里调用：

```rust
use std::process::Command;

fn extract_frames(video: &str, out_pattern: &str) -> anyhow::Result<()> {
    let status = Command::new("ffmpeg")
        .args(["-i", video, "-vf", "fps=1", out_pattern])
        .status()?;
    anyhow::ensure!(status.success(), "ffmpeg 执行失败");
    Ok(())
}
```

先装 ffmpeg：`brew install ffmpeg`（macOS）或 `sudo apt install ffmpeg`（Linux）。

它的兄弟 `ffprobe` 负责"体检"——拿到任何视频文件第一步：

```bash
ffprobe video.mp4
# 输出会告诉你：视频流是 h264 编码、1920×1080、30fps、装在 mp4 容器里
```

### 路线二：opencv crate（逐帧读取，做算法用这个）

```bash
cargo add opencv   # 编译较重；macOS 需要 brew install opencv
```

```rust
use opencv::{videoio::{VideoCapture, CAP_PROP_FPS, CAP_PROP_FRAME_COUNT}, prelude::*};

fn main() -> anyhow::Result<()> {
    let mut cap = VideoCapture::from_file("video.mp4", opencv::videoio::CAP_ANY)?;
    let fps = cap.get(CAP_PROP_FPS)?;
    let total = cap.get(CAP_PROP_FRAME_COUNT)?;
    println!("共 {} 帧, {:.1} fps, 时长约 {:.1} 秒", total, fps, total / fps);

    let mut frame = Mat::default();
    let mut n = 0;
    while VideoCapture::read(&mut cap, &mut frame)? {
        // Mat 是 OpenCV 的图像类型。注意：它默认是 BGR 顺序！
        // 想保存或喂模型，先转 RGB。这里演示：每 30 帧存一张
        if n % 30 == 0 {
            let img = opencv::imgcodecs::imatencode(".png", &frame)?;
            std::fs::write(format!("frame_{:04}.png", n), img)?;
        }
        n += 1;
    }
    Ok(())
}
```

要点：`VideoCapture` 统一处理 mp4 文件和摄像头（`VideoCapture::new(0, ...)` 就是本机摄像头）。`Mat` 转 `image` 类型需要手工做字节搬运 + BGR→RGB 交换——这正是第 5.4 节要标准化的操作。

### 路线三：ffmpeg 原生绑定（知道即可）

`ffmpeg-next`、`rsmpeg` 两个 crate 直接绑定 C 的 ffmpeg 库，灵活度最高（能解任意流、抽裸数据、自定义 filter），但 API 繁琐、unsafe 多、部署要带动态库。初学者先记住：**命令行走不通/性能不够时再上绑定**。

## 4.8 网络视频流一口鲜

工业摄像头几乎不"存文件再给你读"，而是**持续往外推流**。最常见的是 **RTSP**（Real Time Streaming Protocol）：摄像头常驻一个 `rtsp://192.168.1.100:554/stream` 这样的地址，谁连上谁就能取流——类比"用 URL 调频看电视频道"。OpenCV 同样能读：

```rust
let mut cap = VideoCapture::from_file(
    "rtsp://admin:password@192.168.1.100:554/cam/realmonitor?channel=1&subtype=0",
    opencv::videoio::CAP_FFMPEG,   // 指定 ffmpeg 后端
)?;
```

国内安防行业还有国标 **GB28181**（基于 SIP 协议的摄像头接入标准）， you'll 在对接海康、大华这类厂商设备时经常听到——它是"协议层"的约定，底层传输的还是 H.264/H.265 码流。

## 4.9 小结

- 原始数据量大到存不下传不动，所以一切都要编解码：图像吃空间+视觉冗余，视频额外吃时间冗余。
- 无损（PNG：字典+哈夫曼）vs 有损（JPEG：YUV→抽样→DCT→**量化**→熵编码，质量参数就是量化表的选择）。
- 视频靠 I/P/B 帧消灭时间冗余；GOP 长度在体积、seek 速度、直播延迟之间权衡。
- 容器（MP4/MKV）是盒子，编码（H.264/H.265）是内容，协议（RTSP）是取水方式——三者别混。
- Rust 取帧三条路：ffmpeg 命令行（万能）、opencv crate（做算法）、ffmpeg 绑定（极限场景）。

## 4.10 练习

1. 用 4.1 的公式算一算：你的手机摄像头拍一段 10 秒 4K 60fps 视频，原始数据是多少 GB？
2. 装 ffmpeg，对同一张 test.jpg 分别以质量 90、50、10 重新编码（`ffmpeg -i test.jpg -q:v 10 out.jpg`），对比文件大小，并放大看块效应。
3. 用 ffprobe 检查任意一个你电脑里的视频文件：容器是什么？视频编码是什么？音频编码是什么？
4. 用 ffmpeg 把一段视频的前 5 帧存成 PNG，然后用第 3 章的知识把其中一帧转灰度。
